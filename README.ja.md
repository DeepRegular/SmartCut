## SmartCut とは

SmartCut は、日本のテレビ録画から CM を切り取るためのデスクトップアプリです。
一晩分の `.ts` ファイルをまとめてドロップすると、CM の切れ目を自動で探します。
あとは境界を目で確かめてカットし、書き出すだけです。

ポイントは書き出し方にあります。ふつうの動画編集ソフトは、ファイル全体を
いったんデコードしてから、一から作り直します。時間がかかるうえに、すべての
フレームの画質が少しずつ落ちます。

SmartCut はこの方法を採りません。映像は、それ 1 枚で画像を復元できるキーフレームと、
前のフレームからの差分だけを記録したフレームで構成されています。キーフレームの
位置で切れば、残りはバイト単位でそのままコピーできます。作り直すのは、カット点が
キーフレームの間に落ちたときの数フレームだけです。

実際の放送録画なら、**出力の 99% 以上が入力と同一のコピー**になります。
CM の切れ目のようにカット位置がキーフレームに一致する場合は、1 フレームも
再エンコードしません。

この方式をスマートレンダリングと呼びます。SmartCut は映像だけでなく、音声や、
日本の放送に含まれる字幕・番組情報のストリームも同じ考え方で扱います。

## SmartCut を使う理由

**画質を無駄に落としません。** 2 時間の録画を再エンコードすれば、全フレームが
少しずつ劣化します。SmartCut が作り直すのは多くても数十フレーム、多くの場合は
0 フレームです。

**書き出しが速く終わります。** やっていることはバイトのコピーなので、速度を
決めるのは CPU ではなくディスクです。30 分の録画なら 1 分もかかりません。

**放送録画の中身がそのまま残ります。** 字幕、番組情報、放送局名、d ボタンで見られる
データ放送、二か国語放送の両音声、インターレース、2:3 プルダウンをすべて引き継ぎ
ます。出力も録画ファイルと同じ形式なので、普段使っている録画向けのツールで
そのまま開けます。

**一晩分をディスクとして出せます。** ファイルに書き出すだけでなく、レコーダーが
BD-RE に書くのと同じ BDAV フォルダーとしても書き出せます。各番組には放送時の
番組名・チャンネル・録画日時・番組内容が付き、CM を抜いた位置ごとにチャプターが
入ります。指定すれば、そのまま焼ける `.iso` イメージにまとめます。詳しくは
[ディスクを書く](docs/technical/bdav.ja.md)にあります。

**1 枚に入りきらない録画も、ディスクに収められます。** ディスクの使用量がグラフで
表示され、入りきらないときは映像だけを書き直して縮めます。このときデコードは
行いません。量子化を粗くし、画質への寄与に対して符号量が大きすぎる係数を捨てる
だけなので、GOP もタイムスタンプも動きベクトルも、音声・字幕・番組情報もそのまま
です。対象は MPEG-2 の録画です。詳しくは
[ディスク容量に合わせる](docs/technical/transrate.ja.md)にあります。

**切る場所を字幕で確かめられます。** 継ぎ目が台詞の途中に来ていないかは、映像だけを
見ても分かりません。そのため、編集画面のプレビューに字幕を表示できます（既定では
表示しません）。放送の ARIB 字幕は、放送局が指定した位置と色のまま文字で出します。
ディスクの字幕（PGS・DVD のサブピクチャ）は、収録されている画像のまま重ねます。
放送局が文字ではなくドットで送ってくる記号、たとえば行の続きを示す矢印も、その
ビットマップのまま描きます。

**音と画素でも確かめられます。** プレビューの横には音声レベルメーターが立ちます。
再生中は鳴っている音を、止めているときは再生位置のフレームの音を示すので、CM の
切れ目にある無音がどこから始まるかを 1 フレームずつたどれます。`Z` で開く
拡大表示は、プレビューの一部を録画そのもののピクセルで拡大します。画面幅に
縮めた映像では消えてしまうインターレースの縞も、そのまま確かめられます。

**CM の切れ目を自動で探します。** 手がかりは、放送局が字幕ストリームに入れる
切り替えの印、無音区間の並び、局ロゴの有無の 3 つです。SmartCut が行うのは候補に
印を置くところまでで、実際にどこを切るかは利用者が決めます。

**黒・白の区間と無音の区間も探せます。** こちらは CM 検出とは別の機能で、順位も
付けず、候補も絞りません。見つけた区間をタイムラインにそのまま並べ、両端に
キーフレームを置きます。CM の切れ目には真っ黒なフレームが数枚と 1 秒ほどの無音が
入ることが多いので、検出が取りこぼした場所を自分で見つける手がかりになります。

**一晩分をまとめて処理できます。** 20 本の録画を追加して `Ctrl+A` → `Ctrl+D`
を押したら、あとは放っておけます。読み込み・検出・編集は並行して動くので、
まとめて処理している最中でも操作を続けられます。

**誰もいないあいだに書き出せます。** 保存したプロジェクトをキューに並べておくと、
バッチ出力ツールが順に書き出します。このツールは別ウィンドウ・別プロセスで動くので、
本体を閉じてもキューは止まりません。1 件失敗しても次へ進みます。すべて終わった
あとのスリープやシャットダウンも任せられます。詳しくは
[まとめて処理する](docs/user-guide/batch.ja.md#一晩かけてプロジェクトを順に処理する)に
あります。

## ダウンロード

ビルド済みのファイルは
[Releases ページ](https://github.com/DeepRegular/SmartCut/releases)にあります。
deb 以外はすべて FFmpeg を同梱しているので、ほかに用意するものはありません。

| プラットフォーム | ファイル | 備考 |
|---|---|---|
| **Linux** | `SmartCut_0.8.0_amd64.AppImage` | 実行権限を付けて起動します |
| **Linux** | `SmartCut-0.8.0-linux-x86_64.tar.gz` | 展開して `./smartcut` を実行します。FUSE を使いたくない場合はこちらです |
| **Linux (Debian/Ubuntu)** | `smartcut_0.8.0_amd64.deb` | `sudo apt install ./smartcut_0.8.0_amd64.deb`。システムに入っている FFmpeg を使うので 4.5 MB で済みます |
| **Windows** | `SmartCut_0.8.0_x64-setup.exe` | インストーラ |
| **Windows** | `smartcut-portable-x64-0.8.0.zip` | 展開して `smartcut.exe` を実行します |

**動作条件。** AppImage と tar.gz には glibc 2.39 以降が必要です（Ubuntu 24.04、
Debian 13、Fedora 40 以降）。deb は FFmpeg 7.1 を使うので、Debian 13 または
Ubuntu 25.04 以降が必要です。deb では GUI が `smartcut`、コマンドライン版が
`smartcut-cli` としてインストールされます。Windows 版は x64 のみで、WebView2
ランタイムが必要です（Windows 11 には標準で入っており、Windows 10 でもほとんどの
環境に入っています）。

ソースからビルドする場合は[ビルド](docs/technical/building.ja.md)を参照して
ください。

## クイックスタート

### GUI を使う

1. **録画を追加する。** ウィンドウにドラッグ＆ドロップするか、
   **＋ ファイルを追加**から選びます。ドロップした瞬間に一覧に行が追加され、
   読み込みなどの準備は裏で進みます。読み込みが終わる前でも、その録画を開けます。
2. **CM を検出する。** `Ctrl+A` で全選択して `Ctrl+D` を押します。SmartCut が
   順に処理して、各 CM ブロックの開始位置と本編に戻る位置に印を置きます。
3. **カットする。** 行をダブルクリックするとカット編集画面が開きます。印はすでに
   置かれているので、CM の先頭の印をクリックして `I`、本編に戻る位置の印を
   クリックして `←` を 1 回押してから `O`、最後に **✂ カット** を押します。
   その録画が終わったら **OK** で一覧に戻ります。
4. **出力設定を確認する。** 出力設定タブの内容は一覧全体に適用されます。保存先、
   ファイルの形式、音声の扱いをここで決めます。
5. **書き出す。** 出力タブで、一覧を上から順に書き出します。

作業の途中でも `Ctrl+S` で一覧を保存できます。カットの内容も含めて保存され、
次回そのまま復元されます。スクリーンショット付きの詳しい手順は
[GUI の使い方](docs/user-guide/gui.ja.md)にあります。

### ディスクを開く

ディスクもそのまま開けます。フォルダーでも、マウントしていない `.iso` でも
かまいません。Blu-ray はレコーダーが書く BDAV と市販ディスクの BDMV の両方に
対応し、DVD-Video も読めます。タイトルと再生時間、チャプター、収録されている
音声・字幕トラックを読み取ります。

ウィンドウにドロップすると、ディスクの中のどれを読み、その録画のどのトラックを
取り込むかを選ぶ画面が出ます。この確認を省けないのは、市販の 1 期分のボックスには
ロゴ・警告・メニューのループが 50 本ほど入っていて、本編 12 話がその中に紛れて
いるためです。しかもディスク上では、62 本すべてが `000NN` という名前です。
本編らしいものには、あらかじめチェックが入っています。

**開くのは一瞬です。** ディスクには再生を始められる位置の一覧が記録されているので、
SmartCut はそれを読むだけで、録画全体を走査しません。81 GB・2 時間 34 分の UHD
タイトルでは、8 分 45 秒かかっていた読み込みが 1 秒未満になりました。音声の言語も
同じ索引から引き継ぐので、2 か国語収録のディスクを切っても、どちらが日本語かは
出力に残ります。

書き出し先はディスクと同じ場所で、ファイル名には番組名を使います。日本の録画では
チャプター位置がそのまま CM の境目であることが多いので、ディスクのチャプターは
最初から印としてタイムラインに並びます。

```bash
smartcut Anime.iso                      # 何が入っているか
smartcut Anime.iso --title 2 --cut 8.0-20.0 -o out.ts
```

暗号化されたディスクは対象外です。読み取りの仕組みと、できないことは
[ディスクを読む](docs/technical/disc.ja.md)にあります。

### コマンドラインを使う

```bash
smartcut input.ts --keep 5.3-12.7 -o out.ts   # この区間を残す
smartcut input.ts --cut 8.0-20.0  -o out.ts   # この区間を削除する
smartcut input.ts --analyze                   # 計画だけ表示し、書き出さない

smartcut input.ts --analyze --detect-cm --logo  # CM 候補を一覧する
smartcut input.ts --analyze --scenes            # シーンの変わり目を一覧する

smartcut input.ts --cut 8.0-20.0 --bdav ~/disc  # ファイルではなくディスクに書く
```

`--keep` と `--cut` は複数回指定できます。秒数のほか `1:23:45.6` の形式も
使えます。オプションの全一覧は
[コマンドラインで使う](docs/user-guide/cli.ja.md)にあります。

## 読めるもの・書けるもの

**開けるファイル:** `.ts` `.m2ts` `.mts` `.m2t` `.mp4` `.mkv` `.webm` `.mov`
`.m4v` `.vob` `.mpg` `.mpeg` `.m2p`、およびディスク（Blu-ray の BDAV / BDMV、
DVD-Video。フォルダーでも、暗号化されていない `.iso` でも、そのまま読めます）

DVD は規格上、1 本のつながった映像を 1 GB 前後のファイルに分けて収めています。
SmartCut は展開もコピーもせずにこれらをつないで読み、必要な範囲だけを取り出します。
DVD の形式に戻すには SmartCut が書かないテーブルがいくつも必要になるので、
書き出しは MPEG-TS です。

**書けるファイル:** MPEG-TS / M2TS / MP4 / Matroska / WebM / QuickTime、または
BDAV ディスク（プレーヤーが番組の一覧として読む索引の付いた録画フォルダー。
`.iso` にもまとめられます）。既定では、入力と同じ形式・同じフォルダーに
書き出します。

**複数の録画を 1 つのファイルにまとめられます。** 出力設定でチェックを 1 つ
入れると、リストが 1 行ずつではなく 1 本のファイルとして書き出されます。
前編と後編、12 話ぶんの録画、同じ放送を 2 回録ったもの。仕様の一致する録画は
単体で切るときとまったく同じようにスマートレンダリングされるので、20 本を
まとめる手間は 20 本を切る手間と変わりません。

仕様の合わない録画は、**基準クリップ**として選んだ 1 本の形に合わせて書き直し
ます。解像度、フレームレート、コーデック、音声のいずれが違っていても結合でき
るのはこのためです。書き直すのはその録画だけで、どれをなぜ書き直すのかは
1 バイトも書く前に知らせます。

継ぎ目には**トランジション**を入れられます。黒または白へのフェード、
ディゾルブ、上下左右からのワイプとスライド。長さは 30 秒まで自由に決められ、
12 種類のイージング曲線で加減速を付けられます。静止画を重ねることもできます。
トランジションはここで唯一スマートレンダリングできない機能です。どちらの録画
にも無いフレームを作るので、その秒数ぶんだけ書き直します。継ぎ目にだけ用意
してあるのは、まさにそのためです。

**映像:** H.264 / HEVC / MPEG-2 / MPEG-4 Part 2 / VC-1 / VP9 / AV1。
インターレース素材はインターレースのまま保たれ、2:3 プルダウンも潰さずに
扱います。

**可変フレームレートにも対応しています。** フレームは、ヘッダが宣言する長さでは
なく、次のフレームが来るまで画面に出ています。1 分間止まっている画面録画はその 1 分を
保ちますし、保持の途中で終わる範囲も指定どおりの長さになります。保持の内側に丸ごと
収まる範囲は、そこに出ていた 1 枚をその長さぶん表示します。

逆向きの変動にも対応しています。23.976 の本編に、エンディングだけ 59.94 が 1 秒
混じるような作りで、配信で手に入るものの多くがこれです。この場合、出力の
タイムラインは 2 つのレートの平均ではなく、素材が作られたレートを基準に組み、
速い部分も収まる細かさで刻みます。この形の 24 分番組で測ったところ、3 区間の
カットはフレーム 6294 枚すべてが揃い、間隔の誤差も最大 0.6ms でした。以前は
11 枚が欠落していました。

固定フレームレートの録画の扱いは何も変わりません。

4K HDR10 も切れます。継ぎ目で書き直すフレームにも録画と同じ HDR の設定を付ける
ので、途中で見え方が変わることはありません。4K 放送が HLG を後方互換の形で伝える
書き方、つまりストリームの 2 か所にわざと違う値を入れる書き方も、そのまま再現
します。Dolby Vision はコピーする範囲では丸ごと残りますが、書き直すフレームには
付けられないので、書き直しが発生するカットではその旨を表示します。

**VP9 と AV1 も同じ仕組みで切れます。** この 2 つには H.264 のような
パラメータセットがありません。VP9 のキーフレームには解像度と色がそのまま
書かれていますし、AV1 のエンコーダはどれもキーフレームの直前にシーケンス
ヘッダを置きます。書き直した冒頭のうしろに録画のフレームを並べれば、間を
繕わなくてもつながります。1080p の VP9 録画（音声 Opus）で、前後とも GOP の
途中から始まる範囲を切ったところ、フレームの 83% が録画そのもののバイト列
のまま出てきました。

明示が必要だったのは、継ぎ目を書く AV1 エンコーダの選び方だけです。
libavcodec に任せると libaom の最も遅い設定になり、1080p の 2 秒に 348 秒
かかります。SmartCut は SVT-AV1 を指定するので 4 秒で済みます。SVT-AV1 が
無い環境では rav1e、次に libaom の順に切り替えます。画質の差は 0.002 dB
です。

VC-1 だけは事情が違います。2010 年頃までにプレスされた Blu-ray の多くが
このコーデックですが、VC-1 のエンコーダは FFmpeg にもグラフィックスカードにも
ありません。そこで SmartCut は、区間の両端だけを書くためのエンコーダを自前で
実装しています。出力するのは 1 枚で完結するフレームだけです。継ぎ足す断片には
それで足り、実装もフォーマットのごく一部で済みます。元のフレームより符号量は
増えますが、断片は 1 秒に満たないので、増えるぶんはわずかです。残りはほかの
コーデックと同じく、バイト単位のコピーです。

**音声:** AAC・AC-3・E-AC-3・MP2・Blu-ray のリニア PCM はスマートレンダリングの
対象です。ファイル内の全トラックを個別にカットするので、二か国語放送は両方の
言語が残ります。5.1ch のステレオへのダウンミックスと、出力する音声コーデック
（AAC・AC-3・DTS・リニア PCM）の指定にも対応します。ただしこの 2 つと
サンプリング周波数の変更では、コピーできるフレームが無くなるので、トラック全体を
作り直します。

出力設定の画面に出るのは、実際に書ける組み合わせだけです。コーデックが対応
しないサンプリング周波数や、1 フレームに必要な下限を割るビットレートは、そもそも
選べません。そのため、書き出しの最後になって失敗することはありません。
ディスクのロスレス音声（DTS-HD と TrueHD）は再エンコードせず、バイト単位で
そのままコピーします。

**放送の付随データ（`.ts` で出力する場合）:** 字幕はバイト単位でそのまま引き
継ぎます。地震速報や開票速報のように放送中の画面に重ねて出る文字スーパーも
同じです。文字スーパーは専用のストリームで届き、出力でも専用のストリームの
ままです。4K 放送の字幕は ARIB の文字コードではなく XML 文書で、これも引き継ぎ
ます。時刻が文書の中に書かれているので、その部分を書き換えます。
番組情報・放送局名・放送時刻は書き出しのあとに書き戻し、各ストリームは元の
位置に置き直します。データ放送（d ボタンで見られるページ）も引き継ぎます。
多重化の処理を通せないので、パケットを録画から取り出し、書き出したファイルへ
バイトのまま並べ直します。受信機側では元と同じページが組み立てられます。
不要なら `--no-data-broadcast` で削除できます。データ放送のカルーセルは多重化
全体の 1/100 から 1/5 を占めるので、ファイルサイズを優先する場合はこちらを
選んでください。

**ディスクの字幕（`.ts` / `.m2ts` で出力する場合）:** Blu-ray の字幕は文字では
なく画像です。1 枚の画像が切り離せない複数のパケットに分かれて記録されているので、
これをまとまりごと引き継ぎ、残す範囲の両端を整えます。範囲の先頭ですでに表示
されていた字幕は最初のフレームで出し直し、範囲の終わりで表示中の字幕は消します。
次の場面まで出しっぱなしになることはありません。
[ディスクが描く字幕](docs/technical/disc.ja.md#ディスクが描く字幕)を参照してください。

**カットに焼き込むか、別ファイルにするか。** DVD の字幕も同じく画像ですが、TS には
それを収める場所がありません。そこで既定では、Blu-ray と同じ字幕の形式に変換
します。同じ画素・同じ色のまま書き直すので、カットは字幕入りの 1 ファイルに
なります。残る 2 つの方法はどちらのディスクにも使え、字幕を別ファイルに書き出し
ます。プレーヤーでも字幕ツールでもそのまま読める `.idx` と `.sub`（VobSub）か、
ディスプレイセットをそのまま収めた `.sup` です。Blu-ray の字幕を `.sup` に出す
場合は、バイト単位でそのままです。どの方法でも、残す範囲の両端は整えます。
`.mp4` に切ってディスクの字幕を残すには、別ファイルに書き出すこの方法を使います。
[ディスクの字幕を焼き込むか、別ファイルにするか](docs/technical/disc.ja.md#ディスクの字幕を焼き込むか別ファイルにするか)
を参照してください。

映像トラックは 1 ファイルにつき 1 本のみです。制限の一覧は
[既知の制限](docs/technical/validation.ja.md#既知の制限)を参照してください。

## 「GOP 単位で切って繋ぐ」では済まない理由

「キーフレームを探して、そこで切って、つなぐ」という方法は誰でも思いつきますが、
実際には動きません。以下はいずれも試作の途中で実際に遭遇した問題で、それぞれ
再現するテストを用意してあります。

- **パラメータセットが一致しない。** 再エンコードした断片の SPS は元のエンコーダの
  ものとビット単位では一致せず、MP4 の `avcC` ボックスには 1 組しか入りません。
  素朴につなぐと、出力の半分が違う SPS で復号されます。
- **キーフレームは復号では見つからない。** デコーダは参照先のない I ピクチャを
  出力できないため、`ffprobe -skip_frame nokey` はオープン GOP のアクセスポイントを
  取りこぼします。最初の試験素材では 10 個中 3 個しか見つかりませんでした。
- **leading picture。** デコード順では I ピクチャの後、表示順では前に来る
  ピクチャで、直前の GOP を参照しています。捨てられるかどうかは、そのコーデックが
  leading picture を参照ピクチャにしてよいと定めているかで変わり、
  MPEG-2・H.264・VC-1 でそれぞれ違います。
- **秒を単位にしてはいけない。** `-c copy` の区間長は DTS で測られますが、DTS は
  並べ替えのぶんだけ表示時刻より先に進んでいます。180 フレームのはずが 182 フレーム
  出てきました。
- **音声には GOP 構造がありません。** フレーム境界が映像のカット位置にそろうことも
  まずありません。
- **継ぎ目の両側で、ピクチャオーダーカウントは互いに通用しません。**
  デコーダはこの番号の順にピクチャを返しますが、継ぎ目の両側の番号は別々の
  エンコーダが振ったものです。番号が重なる箇所では、前の区間の最後の 1 フレームが、
  次の区間の最初のフレームより *後* に返ってきます。

こうした難所は全部で 11 個あり、
[実装上の難所](docs/technical/algorithm.ja.md#実装上の難所)に遭遇した順に
並べてあります。ドキュメントを 1 ページだけ読むなら、このページをおすすめします。

## どのくらい安全か

**元のファイルは変更しません。** SmartCut は読み込むだけです。出力は新しい
ファイルに書き、既定では入力と同じフォルダーに `cut_` を頭に付けた名前で
作ります。

**出力の大部分は、入力と同一であることが保証されます。** コピーした区間は文字
どおり同じバイト列です。推定値ではなく、コピーである以上そうなります。

**作り直した部分は実測しています。** テストスイートが出力をデコードし、ソースと
1 フレームずつ突き合わせます。実際の放送録画での結果は次のとおりです。

| 素材 | 結果 |
|---|---|
| 地上波 NHK E テレ（MPEG-2 1440x1080i） | 899/899 フレーム、98.2% 無劣化、インターレース保持 |
| BS11（MPEG-2 1920x1080i） | 899/899 フレーム、98.2% 無劣化 |
| AT-X（MPEG-2 1440x1080、2:3 プルダウン） | 719/719 フレーム、99.9% 無劣化、プルダウンパターン保持 |
| 22 分・5 区間の CM カット | 40589/40589 フレーム、**100% ビット単位で一致** |
| VC-1 の Blu-ray（1920x1080i アニメ）、キーフレームの間から間まで 10 秒 | 308/308 フレーム、映像の 90% がバイト一致、残りは 48 dB で書き直し |
| VC-1 の Blu-ray（1920x1080p 実写・強いグレイン）、同じく 10 秒 | 246/246 フレーム、90% がバイト一致、残りは 45 dB でグレインも残存 |

**GUI では書き出す前に結果が分かります。** タイムライン下のステータス行には、
エンジンが実際に実行する計画がそのまま表示されます。どの区間をコピーし、どこを
何フレーム作り直すかが分かります。「映像は完全に無劣化」と出ていれば、1 フレームも
再エンコードしません。

**四捨五入で「100%」にすることはありません。** 40000 フレーム中 2 フレームを
作り直した場合、四捨五入すれば 100.0% になります。しかしスマートレンダラーが
その数字を表示してはいけません。SmartCut はフレーム数を表示し、本当に 100% でない
限り 100% とは書きません。

途中で見つかった不具合や、この方式そのものの限界も含めた完全な結果は
[検証](docs/technical/validation.ja.md)にあります。

## 中身の構成

エンジンは 1 つの Rust クレートです。GUI とコマンドラインはその上に載る 2 つの
フロントエンドで、どちらもカットの中身には関与しません。

```
             gui/                          rust/crates/cli/
  ┌──────────────────────────┐   ┌──────────────────────────┐
  │  Tauri v2・バニラ JS     │   │  smartcut-cli            │
  └────────────┬─────────────┘   └────────────┬─────────────┘
               └───────────────┬──────────────┘
                               ▼
  ┌─────────────────────────────────────────────────────────┐
  │  rust/crates/core — smartcut-core                       │
  ├─────────────────────────────────────────────────────────┤
  │  ソースを開く        input  netpath  index  seek_index  │
  │                      proxy  thumbs                      │
  │  カットそのもの      plan  bitstream  cut  audio  adts  │
  │  放送そのもの        si  arib  caption  series  text    │
  │  切れ目を探す        cm  logo                           │
  │  ディスク、両方向    disc  dvd  udf  bdav  udfw restamp │
  │  容量に合わせる      fit                                │
  │  字幕                pgs  vobsub  subs                  │
  │  編集画面に見せる    preview  playback_audio            │
  └────────────┬───────────────────────────┬────────────────┘
               ▼                           ▼
  ┌──────────────────────────┐   ┌──────────────────────────┐
  │  FFmpeg  libav*          │   │  rust/crates/vc1         │
  │  分離・復号・符号化      │   │  イントラ専用 VC-1       │
  │                          │   │  エンコーダ              │
  │                          │   ├──────────────────────────┤
  │                          │   │  rust/crates/mpeg2       │
  │                          │   │  デコードせずに映像を    │
  │                          │   │  小さく書き直す          │
  └──────────────────────────┘   └──────────────────────────┘
```

### なぜこの実装を信用できるか

同じものを二度書いてあるからです。

`smartcut/` には、同じアルゴリズムの Python 実装があります。放置された試作では
なく、アルゴリズムと落とし穴を最初に固めた実装で、**リファレンス実装兼テスト
オラクル**として残してあります。両方を同じフレームハッシュ照合にかけ、同じ入力に
対して同じ無劣化率を返さなければテストは通りません。

```
                        アルゴリズム
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
   smartcut/        (Python)        rust/crates/core   (Rust)
   リファレンス実装                 配布されるほう
   planner · renderer ·             plan · cut · audio ·
   bitstream · probe · verify       bitstream · ...
              │                               │
              ▼                               ▼
     tests/run_tests.sh              tests/run_rust_tests.sh
              │                               │
              └───────────────┬───────────────┘
                              ▼
         同じ実録画に対する同じフレームハッシュ照合
                              │
                              ▼
                      一致する無劣化率
```

オラクルと結果が食い違う変更は、エンジン側が正しいとは見なしません。
Python 実装を今も残しているのは、この照合のためです。

両方に通している E2E テスト 25 スイート・485 チェックは `tests/` にあります。
どのモジュールに何が入っているかは [Rust コア](docs/technical/rust-core.ja.md)、
なぜこの分け方なのかは[設計ノート](docs/technical/design.ja.md)にあります。
