# BDAV ディスクを読む

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](bdav.md)

**録画した Blu-ray を、フォルダーのままでも `.iso` のままでも開ける。**
一覧に並ぶのは `00001.m2ts` ではなく番組名である。

```
$ smartcut Anime_Test.iso
disc  : Anime_Test.iso
        3 recording(s)

  1  00:08:30.010  2026年08月17日01時00分-BS11イレブン-アズールレーン びそくぜんしんっ!にっ!! #07「神様的休息日の過ごし方。」  2 mark(s)
  2  00:08:30.010  2026年08月24日01時00分-BS11イレブン-アズールレーン びそくぜんしんっ!にっ!! #08「私の罪をお赦しください・・・」  2 mark(s)
  3  00:08:29.976  2026年08月31日01時00分-BS11イレブン-アズールレーン びそくぜんしんっ!にっ!! #09「わたしのラッキーアイテム?」  2 mark(s)

name one with --title N to open it
```

GUI では、ISO かディスクのフォルダーを窓に落とすと、その中の録画が 1 件ずつ行になる。
ISO 内の `.iso` を含むフォルダーを落としても同じで、一晩ぶんのディスクがそのまま
一覧になる。

## BDAV とは

BDMV ではない。BDMV は市販の映像ソフトの形式で、メニューがあり `BDMV/` があり
`index.bdmv` がある。BDAV は**録画の形式**で、レコーダーが書くのも、オーサリング
ツールに「録画のディスク」を作らせたときに出てくるのもこちらである。

```
BDAV/
  info.bdav              プレイリストの一覧と順序
  PLAYLIST/00001.rpls    録画 1 件: どのクリップを、どこからどこまで
  CLIPINF/00001.clpi     そのクリップの索引
  STREAM/00001.m2ts      トランスポートストリームそのもの
```

ストリームは MPEG-2 TS を 192 バイトパケットで包んだもの——188 バイトのパケットの前に
到着時刻 4 バイトが付く——で、libavformat は何も言わなくても読む。**したがって
ストリームは最初から問題ではなかった。** 足りなかったのは索引である。`00001.m2ts`
`00002.m2ts` `00003.m2ts` という並びは、どれがどの番組かを何も言わない。一晩ぶんの
録画が入ったディスクは、まさにそれが問題になる場合である。

## ISO をマウントせずに読む

`.iso` は UDF ファイルシステムである。Linux ならマウントできるが、マウントには root と
ループデバイスが要り、編集のあいだじゅうカット編集ツールにマウントを握らせるのは、
落ちたときに宙ぶらりんのマウントを残すということである。Windows なら `.iso` は
ダブルクリックでマウントできるが、それは「プログラムを使う前にユーザーが済ませて
おかなければならない手順」がひとつ増えるということである。

だからマウントしない。イメージはそのままの場所で読む
（[`udf.rs`](../../rust/crates/core/src/udf.rs)）。答えるべき問いはひとつだけ:

> **各ファイルはイメージの何バイト目から始まり、何バイトあるのか。**

焼かれた `.m2ts` はひと続きのバイト列なので、答えは**バイト範囲**になる。そして
バイト範囲は、libavformat に `subfile` プロトコルでそのまま渡せる:

```
subfile,,start,747520,end,1232594944,,:file:/rec/Anime_Test.iso
```

デマルチプレクサはこれをただのストリームとして読み、まわりにファイルシステムが
あることを最後まで知らない。だからその先——パケット走査、アクセスポイントへのシーク、
コピー——は普通のファイルのときと 1 行も変わらない。

> 内側のパスを `file:` で始めているのは、オプションの並びが**最初のコロンで終わる**
> ためである。そうしないと Windows の `C:\…` が「プロトコル `c`」と読まれる。

### 1 ギガバイトの壁

UDF の割り当て記述子は長さフィールドが 30 ビットしかないので、記述子 1 個で
1 GiB より長い範囲は表せない。つまり 1.2 GB のクリップは記述子 2 個になる。

```
len=1073739776  lbn=77      -> byte 747520
len=158107648   lbn=524364  -> byte 1074487296
```

747520 + 1073739776 = 1074487296。**隙間なく続いている。** 焼き込みは連続した領域に
書くので、断片化しているのは記述子であってファイルではない。
[`Entry::contiguous`](../../rust/crates/core/src/udf.rs) は続いているものを繋いで
ひとつの範囲にし、本当に飛んでいる場合は——ディスクに書かれたものではまず無いが——
`None` を返す。そこで嘘の範囲を読むより、読めないと言うほうがよい。

### メタデータパーティション

UDF 2.50 以降のイメージには**メタデータパーティション**がある。ファイルエントリを
まとめて置くための仕組みで、ファイル本体は隣の物理パーティションに残る。つまり
論理ブロック番号を「メタデータファイルの中の位置」として解き、そのファイル自身の
エクステントを辿って初めて実際のセクタになる。ImgBurn が書く UDF 2.60 はこれを使い、
genisoimage が書く UDF 1.02 は使わない。両方読める。

**暗号化されたディスクは対象外である。** AACS は復号の問題であり、このプログラムは
その一切を持たない。

## 番組名は ARIB のテキストである

`.rpls` は番組名を UTF-8 では持っていない。ARIB STD-B24 の 8 単位符号——ISO 2022 の
子孫で、漢字・英数・ひらがな・カタカナの 4 つの図形集合を同時に保持し、シフトと
エスケープで切り替える——で書かれている。文字の大きさや色の制御符号も同じバイト列に
混ざっている。

[`arib.rs`](../../rust/crates/core/src/arib.rs) はこれを**読む**。描画はしない。
大きさも色も落として、文字の並びだけを取り出す。JIS X 0208 から Unicode への表は
自前で持たず、EUC-JP 経由で引いている（EUC-JP は JIS X 0208 の両バイトに最上位ビットを
立てたものなので、同じ表である）。依存は `encoding_rs` ひとつ。

2 つだけ気を付けている点がある。

- **JIS の 85 区以降は ARIB 自身の記号である。** JIS では未定義のこの領域に、ARIB は
  `[新]` `[字]` `[終]` といった記号を置いている。それらを埋めている**別の**符号化の
  変換表に通すと、まったく違う文字が出てくる。だからそこへ来た文字は変換せず、
  受像機が出すのと同じ `〓` にする。
- **かなの集合の末尾 8 セルは、かなではなく約物である。** JIS の 4 区・5 区は最後まで
  埋まっておらず、ARIB は余ったセルに `ー` `。` `「` `」` `、` `・` を入れている。
  ここを取りこぼすと、番組名が `#07〓神様的休息日の過ごし方。」` になる。

## 一覧に並ぶもの

**プレイリスト 1 件が 1 行**である。`info.bdav` が並べた順で、レコーダーの録画一覧と
同じ見え方になる。名前・録画日時・IN/OUT 時刻・チャプターマークは、すべて `.rpls` から
読める。

プレイリストが 2 つ以上のクリップを再生している場合——番組が、レコーダーがストリームを
分割する長さを超えたとき——は、クリップごとに 1 行にして `(1/3)` `(2/3)` `(3/3)` と
付ける。ひとつのタイムラインに繋ぐのは別の仕事である（クリップごとに時計が違うので、
2 本を継ぐのは 1 本を切るのと同じ操作ではない）。それができるまでは、分かれていることを
そのまま見せるほうが正直である: 録画のどの秒にも手が届き、分かれていることは一覧が
言っている。

チャプターマークは**信用できるときだけ**読む。マークの並びは節の長さから分かるが、
その中で時刻がどこに座っているかはディスクによって違う（BDMV のマークは 14 バイトで
時刻が 4 バイト目、レコーダーの BDAV のマークはもっと長く、名前とサムネイル参照を
伴う）。そこで候補の位置をそれぞれ試し、**全部のマークがタイトルの中に落ちる**ものを
採る。どれも落ちなければマークは出さない。見当違いの場所にあるチャプターは、
チャプターが無いことより悪い。

### マークはキーフレームになる

ディスクから開いた録画は、そのチャプターが最初からカット編集画面に並んでいる。
日本のレコーダーのチャプターは CM の境目そのものであることが多く、それは
[CM 検出](../user-guide/cm-detection.ja.md)が数分かけて探しているものを、録画した
機械が正確に書き残したものである。

ひとつだけ間があるのは**時計が違う**ことである。プレイリストはストリーム自身の
45 kHz で数え、編集画面が描くものはコンテナの開始時刻で原点を取り直してある。
だからマークの置き場所はこうなる。

```
entry.start + mark - src.start_time
```

`entry.start` はプレイリストの IN 点で、まさにこのためにマークと一緒に持ち回る。
ディスクを読む側は `start_time` を知らない——それはストリームを開いて初めて分かる
——ので、マークは読んだ場所で時刻に直さず、行と一緒に編集画面まで運ばれる。

置くのは**初めて開いたときだけ**で、録画の隣に `.keyframe` があればそちらが勝つ。
あのファイルは誰かの答えであり、ディスクのものは誰も答えていないときの答えである。
素材の外に落ちるマークは、丸め込まずに捨てる（理由は上と同じ）。窓を開かずに
時刻を見たいときは `smartcut <ディスク> --title N` がそのまま印字する。

## 出力先と名前

ディスクの中には書けない。イメージの中にはそもそもフォルダーが無いし、コピーした
ディスクの中はディスクのものである。だから既定の出力は**ディスクの隣**、名前は
**番組名**になる。

```
/rec/Anime_Test.iso
/rec/cut_2026年08月17日01時00分-BS11イレブン-アズールレーン ….ts
```

ファイル名にできない文字（`\ / : * ? " < > |`）は全角に置き換える。日本のレコーダーが
同じ問題に対してしていることと同じで、名前は読めるまま残る。

**コンテナは `.ts` になる。** `.m2ts` を求められた libavformat は Blu-ray 自身の姿で
書く——192 バイトのフレーミングと、Blu-ray 自身の PID 番号——が、どちらもマルチプレクサが
決めることであり、[このプログラムが書き戻す放送のテーブル](../technical/broadcast-ts.ja.md)が
語っている配置ではない。だから「入力と同じ」は、ディスクから来た録画については `.ts` を
意味する。中身は同じストリームである。出力設定画面で M2TS を選べば、これまでどおり
M2TS が出る（そのときテーブルはマルチプレクサに任される、とその場で言う）。

## 名前が 1 本であること

このプログラムは**ひとつの文字列**にすべてを掛けている。一覧が持つのも、シーク用
インデックスとプロキシのキャッシュキーも、出力を隣に置く基準も、デマルチプレクサに
渡すのも、その 1 本である。ディスクの中の録画が入ってもそれは変えたくない。

そこで、イメージの中の録画は**イメージをフォルダーのように綴った名前**を持つ:

```
/rec/Anime_Test.iso/BDAV/STREAM/00001.m2ts
```

でっち上げた記法ではない。イメージには本当にその名前のファイルが入っている。普通と
違うのは `/rec/Anime_Test.iso` がフォルダーではなくファイルであることだけで、
[`input.rs`](../../rust/crates/core/src/input.rs) が見ているのはまさにそこである。
パスを遡って**ファイルであるところ**で切ると、3 つの答えが同時に出る。

| | |
|---|---|
| **URL** | `subfile,,start,…,end,…,,:file:/rec/Anime_Test.iso` — libavformat に渡すもの |
| **ファイル** | `/rec/Anime_Test.iso` — OS に問い合わせるもの。キャッシュが大きさと更新時刻で判断できる |
| **範囲** | そのバイト範囲。libavformat を通さず自分で TS を読む処理のため |

3 つ目が要るのは [`si.rs`](../../rust/crates/core/src/si.rs) である。放送自身の
テーブル（PAT・PMT・SDT・EIT・SIT）を読む処理はファイルを直接舐めるので、**イメージの
中の範囲**として開き、なおかつ **192 バイト間隔**でパケットを拾えなければならない。
どちらも入ったので、ディスクから切った出力にも放送のテーブルがそのまま乗る。

## 何をしていないか

| | |
|---|---|
| **暗号化ディスク** | 対象外。AACS の復号は一切扱わない |
| **BDAV として書き出す** | 未対応。オーサリングであり、別の問題である |
| **複数クリップの結合** | 未対応。クリップごとに 1 行として見せている（上記） |
| **CLPI の EP マップ** | 未使用。索引は今のところパケット走査で作る。[`index.rs`](../../rust/crates/core/src/index.rs) の `IndexSource` に足せば、走査 1 回ぶんが浮く |
| **BDMV（市販ソフト）** | 未対応。この ffmpeg は `--enable-libbluray` 付きでビルドされているので `bluray:` プロトコルには手が届くが、`.rpls` は libbluray の管轄外である |
| **BD 固有のストリーム** | LPCM（`pcm_bluray`）は MP4 でも MKV でも通らず、TS では `bin_data` に落ちる。PGS 字幕・TrueHD・DTS-HD・VC-1 も未検証 |

## 検証

実素材と合成素材の両方で確認している。

**実素材** — TMSR6 が書いた BDAV を ImgBurn が UDF 2.60 の ISO にしたもの
（3.4 GB、3 クリップ、1920x1080 MPEG-2 + AAC + ARIB 字幕、部分 TS）。3 件の番組名が
すべて正しく読め、バイト範囲は独立に書いた Python の UDF リーダーと一致し、切り出した
60 秒は 99.2% 無劣化で、放送自身のテーブル（PID 0x1100 / 0x1101 / 0x1102、SIT 0x1F）が
そのまま乗った。**同じクリップをフォルダーに取り出して同じ範囲を切ると、出力は
md5 まで一致した。**

**合成素材** — [`tests/run_bdav_tests.sh`](../../tests/run_bdav_tests.sh) が、既存の
テスト素材から小さなディスクを組み立てる。TS を 192 バイトパケットに詰め直し、
[`tests/bdav_disc.py`](../../tests/bdav_disc.py) が索引ファイルを書き、genisoimage が
UDF 1.02 のイメージに包む。そのうえで、フォルダーとイメージが同じ答えを返すこと、
両方から切った出力が**バイト単位で同一**であること、テーブルが書き戻されることを
確かめる。11 件すべて通っている。
