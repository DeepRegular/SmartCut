## 継ぎ目

カットは GOP を丸ごとコピーし、両端だけを再エンコードする。だから境界の数
フレームはこのプログラムのエンコーダが書き、残りは録画そのもののバイト列に
なる。**その数フレームを書くレートは、録画が入ってきたレートの 1.2 倍だ。**
置き換えられるピクチャは、ディスクや放送を作った何かが好きなだけ時間をかけて
符号化したもので、こちらは 1 回、素早く書く。同じレートでは、隣に並ぶコピー
されたピクチャに対して目に見えて甘くなる。

数えるのは索引のパスだ。どうせ全パケットを持っているので、`walk` が映像
パケットのバイト数を足し上げ、尺で割る。他に言えるものがない。トランスポート
ストリームはストリームごとのビットレートを宣言しないし、コンテナ全体の数字は
音もテーブルもピクチャに混ぜて数えている。

以前は `width × height × fps × 0.08` で、録画のことを何も知らなかった。
この素材では 5〜6 分の 1 という外れ方をしていた。

| | 元 | 書いていた値 | 現在 |
|---|---|---|---|
| ブルーレイ 1080p | 27.2 Mbit/s | 4.5 Mbit/s | 32.6 Mbit/s |
| UHD 2160p | 73.5 Mbit/s | 15.9 Mbit/s | 88.2 Mbit/s |
| ブルーレイ 1080i の継ぎ目 | コピー部 75 kB/フレーム | 26 kB/フレーム | 96 kB/フレーム |

元との PSNR で測ると、上の 1080p のクリップは **29.7 dB から 35.1 dB** に
なった。ピクチャを読まなかった索引——[ディスク自身のマップ][discindex]、
コンテナのシークテーブル——の場合は、ファイル自身のレートから音の分を引いた
値が代わりに立ち、その後ろの最後の手段がフレームの大きさになる。

[discindex]: disc.ja.md#ディスク自身の索引

### 入れ物の違い

MP4 は NAL ごとに長さを前置し、パラメータセットは `hvcC` に置く。トランス
ポートストリームは NAL をスタートコードで区切り、セットはストリームの中で
出会うことを期待する。再エンコードされたピクチャはどちらの場合もスタート
コード付きでエンコーダから出てくるので、**詰め替えが要るのはコピーされた
ピクチャだけ**だ。MP4 へ入るときが `Reframe`、MP4 から出るときが `Unframe`。

後者が無かった。MP4 のカットを `.ts` で書くと、コピーしたピクチャがそのまま
——デコーダがスタートコードを探している場所に 4 バイトの長さが——渡っていた。
4K クリップの 10 秒のカットで、**635 枚のうち届いたのは 36 枚**。その 36 枚は
再エンコードされた両端だった。`tests/run_rust_tests.sh` は、MP4 で書いた
カットと同じカットをトランスポートストリームで書いたものの枚数を数え、
一致することを確かめる。

### HDR もピクチャの中にある

HDR10 は 2 つの SEI メッセージ——マスタリングディスプレイの原色と輝度範囲、
そして録画中で最も明るいもの——で、ここで計ったファイルではビットストリームに
だけ入っていてコンテナには無い。コピーされたピクチャは自分のぶんを持って
いくが、再エンコードされたピクチャには何も無かった。だからプレイヤーはカットの
途中でトーンマッピングを切り替える。`mastering_of` がピクチャを 1 枚デコード
してそれを読み、`decoded_side_data` としてエンコーダに渡す。libx265 はそこを
見る。カット 1 回につき 1 度だけ、しかも再エンコードするものがあるときだけ
行う。読みに行くかどうかは伝達関数で決める。PQ と HLG はこれを持ち、
`bt2020-10`——ブルーレイの広色域 SDR——は持たない。

## タイムスタンプ問題の解消

Python 版は生のエレメンタリストリームを ffmpeg に渡すしかなく、その結果最初の
フレームが 13 ミリ秒早くなっていた（`irregular=[(0, 0.046667)]`）。

Rust 版は各ピクチャの表示インデックスから、**PTS と DTS を整数ティックで直接
割り当てる**。出力のタイムベースは `1/fps の分子` なので、1 フレームがちょうど
`fps の分母` ティックになり、丸めが一切発生しない。

```
h264 keyframe-exact   lossless 180/180   first=0.00000 step=0.033333 jitter=0
mpeg2 ts open-GOP     lossless 283/283   first=0.00000 step=0.033367 jitter=0
```

`tests/run_rust_tests.sh` で検証している。全ケースがちょうど 0.000 秒から始まり、
ジッタは 0 である。

## SPS/PPS 混在の解決

MP4 の `avcC` はパラメータセットを 1 組しか持てないが、再エンコード部分の SPS は
必ず元ストリームのものと異なる。さらに MP4 は NAL を長さ前置で格納するのに対し、
エンコーダが吐くのは Annex-B である。どちらかを放置すると、映像は
`sps_id 32 out of range` や `Invalid NAL unit size` で崩壊する。

必要なことは 3 つある。

- サンプルエントリを **`avc3` / `hev1`** にして、ストリーム内のパラメータセットを
  許可する。
- エンコーダ出力を Annex-B から長さ前置へ組み直す。
- **コピー部分のキーフレームの前に、元の SPS/PPS を再挿入する。** 再エンコード部分の
  SPS が有効なままだと、コピー部分が誤った SPS で復号される。そのため継ぎ目ごとに
  元のパラメータセットを復元する。

背景は[難所 1](../technical/algorithm.ja.md#1-パラメータセットspsppsが一致しない)に
ある。

## 参照判定が Python より正確になった点

Python はビットストリームを読むために ffmpeg をもう一度起動する必要があり、
**ファイル内の 1 か所を標本にして全体に適用**していた。

Rust ではパケットを走査しているその場で `nal_ref_idc` を読めるので、判定を
**アクセスポイントごとに厳密に**行える。追加のパスも追加のコストも不要である。

## エンコーダのないコーデック: VC-1

このプログラムが扱うコーデックには、1 つを除いてすべて libavcodec にエンコーダが
ある。VC-1 のエンコーダだけはどこにも存在しない。libavcodec にも、グラフィックス
カードにも、フリーな実装のどれにもない。`ff::encoder::find(AV_CODEC_ID_VC1)` は空で
返り、これを書くまで VC-1 素材のカットはそこで止まっていた。

これが問題になるのは、VC-1 で書かれているものが何かによる。2010 年頃までにプレス
された Blu-ray の多くがそれである。読むことは[ディスク](disc.ja.md)でできていたが、
カットはできていなかった。

そこで用意したのが `rust/crates/vc1` で、このフォーマットのイントラピクチャだけを
書くエンコーダである。これが研究課題ではなく現実的な作業になるのは、スマートカットが
実際に必要とするものが限られているからである。範囲の両端に必要なのは GOP の断片
——数十枚——であり、それを素材そのもののバイト列のコピーに繋ぐ。断片の外を参照しては
ならないのだから、断片内のピクチャはすべてイントラにできる。そしてイントラ専用の
エンコーダなら、実装するのはフォーマットのごく一部で済む。

| 不要なもの | 理由 |
|---|---|
| 動き推定と動きベクトル | イントラピクチャは何も予測しない |
| 5 種のビットプレーン符号化 | raw モードはマクロブロック層に 1 ビットずつ書くだけで、どこでも合法 |
| 可変ブロック変換 | 対象のディスクは `VSTRANSFORM=0` を宣言しており、全ブロックが 8x8 |
| オーバーラップ平滑化、AC 予測 | どちらも任意で、ピクチャヘッダで断れる |
| 自前のシーケンスヘッダ | 素材自身のものを毎ピクチャの前に置き直す。ディスク自身がそうしているので、継ぎ目の向こうのコピーされたピクチャは、まさに符号化されたときのパラメータで復号される |

必要なのはブロック層である。DC 差分の符号、2 つの符号化セットの AC 係数符号、
coded block pattern とその予測、DC 予測、インタレース用の走査、そして 8x8 変換で
ある。テーブルはフォーマットのものであり、手写しではなく FFmpeg のデコーダのものから
機械的に生成している。数千個のうち 1 つ間違うだけで、途中からノイズに復号される
ストリームができあがるからである。

変換については一言必要である。フォーマットが定義しているのは逆変換だけで、順変換は
エンコーダを書く側に委ねられている。`transform::inverse` はデコーダのものを移植した
もので、テストで両者を突き合わせるためにある。`transform::forward` はその代数的な
逆である。行列は直交だが行ごとにノルムが違うので、係数ごとに別々の値で正規化する。

### 正しいと分かる理由

比較できる別の VC-1 エンコーダが無いので、テストは往復で行う。ピクチャを符号化し、
一般的なプレイヤーが使っているデコーダに渡し、返ってきたものを測る
（`tests/run_vc1_tests.sh`）。この 2 つが両方とも必要である。わずかに壊れた
ビットストリームでも復号自体はできてしまう（ノイズになったり、マクロブロック 1 行
だけ壊れた絵になったりする）ので、「復号できた」だけでは何も証明しない。そして変換の
正規化を間違えると、明るさだけが違う完全に合法なストリームができ、これはエラー無く
復号できてしまうので、復号の成否からは決して分からない。

検証にはディスクを 2 枚使っており、この 2 枚で Advanced Profile の違いはほぼ覆える。
1 枚は 1920x1080i 29.97、インタレースフレーム符号化、non-uniform 量子化、全 GOP が
クローズド。もう 1 枚は 1920x1080 プログレッシブ 23.976、uniform 量子化、全 GOP が
オープン、プルダウンはフレーム単位の形式、skipped ピクチャあり、そして強いフィルム
グレインである。グレインは量子化を通すと最も平滑化されやすいものである。それぞれ、
与えたピクチャに対して測った値は次のとおり。

| 量子化ステップ | 1080i アニメ | 1080p 実写グレイン |
|---|---|---|
| 4（既定） | 48.0 dB、1 枚 109 KB | 44.8 dB、1 枚 205 KB |
| 8 | 45.2 dB、76 KB | 41.0 dB、129 KB |
| 16 | 42.4 dB、50 KB | 37.3 dB、74 KB |

グレインは 2 倍のビットを食って 3dB 落ちるが、それはどのエンコーダでも同じである。
文脈で見るほうが意味がある。**グレインの側のディスク自身の I ピクチャは平均 327KB**
で、ここで書く 205KB より 6 割大きい。アニメの側もディスクが平均 166KB に対して
109KB である。つまり、このエンコーダのイントラピクチャは、ディスクが同じ場所に
置いているものより小さい。プレイヤーに新しい負担をかけてはいない。

どちらのディスクでも、GOP 途中から GOP 途中まで 10 秒の実カットを行い、映像の 90%
が元とバイト単位で一致した。グレインの側は、置き換えたピクチャと等倍で見比べても
粒子が残っている。

### 断るもの

パンスキャンのウィンドウと、ピクチャ端で量子化を変える指定（`DQUANT=2`）である。
どちらもピクチャヘッダの途中にあり、正確に真似る必要があるが、実際のディスクで
見かけたことがない。これらを持つ素材は、間違って書くのではなく名指しで断る。

フィールドピクチャ（`FCM=11`）は読めるが書かない。インタレース素材なら、周囲の
ピクチャがどちらで符号化されていようとインタレースフレームとして書く。VC-1 はこれを
ピクチャごとに宣言するので、両者が 1 つのストリームに混在できる。

### 今後の検討事項

どれもカットを止めるものではない。書き残しておくのは、いずれもエンコーダを動かす
ために下した判断であり、次にこのファイルを開いた人が「なぜこうなのか」を考える場所
だからである。

| | |
|---|---|
| **ウィンドウにステップの設定が無い** | `--vc1-quant` はコマンドラインにしかない。ウィンドウには映像の設定が 1 つも無く、出力画面の項目はすべて音声の話なので、これが最初の 1 つになる。どこに置くかはエンコーダの問題ではなく、あの画面の問題である。それまで、ウィンドウからのカットは既定値を使う |
| **フィールドピクチャを書かない** | インタレース素材ならインタレースフレームとして書く。フィールドの対と並んでいても合法だが、前後がフィールド対で符号化されたストリームをデコーダに読ませたことはない。手元の 2 枚はどちらもフレームで符号化されている。フィールドで符号化された素材が手に入れば、両方の書き方で並べて確かめたい |
| **必要以上にビットを使っている** | 任意だという理由で 3 つ省いた。AC 予測、係数をテーブルの項目との差として書く 2 種のエスケープ形式、そして AC テーブルの選択（量子化ステップから 1 組を選んで通している）である。それぞれ数パーセント削れるが、断片が短いのでまだ問題になっていない |
| **断片が全部イントラである** | ビットレートを最も削れるのは上のどれでもなく P ピクチャである。ただし動き推定と、動きベクトルを運ぶ構文の全体が必要になる。それは別の仕事であり、そもそもこの実装に着手できたのは、それをやらずに済むと分かったからである |
