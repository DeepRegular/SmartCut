## タイムスタンプ問題の解消

Python 版は生のエレメンタリストリームを ffmpeg に渡すしかなく、その結果最初の
フレームが 13 ミリ秒早くなっていた（`irregular=[(0, 0.046667)]`）。

Rust 版は各ピクチャの表示インデックスから、**PTS と DTS を整数ティックで直接
割り当てる**。出力のタイムベースは `1/fps の分子` なので、1 フレームがちょうど
`fps の分母` ティックになり、丸めが一切発生しない。

```
h264 keyframe-exact   lossless 180/180   first=0.00000 step=0.033333 jitter=0
mpeg2 ts open-GOP     lossless 283/283   first=0.00000 step=0.033367 jitter=0
```

`tests/run_rust_tests.sh` で検証している。全ケースがちょうど 0.000 秒から始まり、
ジッタは 0 である。

## SPS/PPS 混在の解決

MP4 の `avcC` はパラメータセットを 1 組しか持てないが、再エンコード部分の SPS は
必ず元ストリームのものと異なる。さらに MP4 は NAL を長さ前置で格納するのに対し、
エンコーダが吐くのは Annex-B である。どちらかを放置すると、映像は
`sps_id 32 out of range` や `Invalid NAL unit size` で崩壊する。

必要なことは 3 つある。

- サンプルエントリを **`avc3` / `hev1`** にして、ストリーム内のパラメータセットを
  許可する。
- エンコーダ出力を Annex-B から長さ前置へ組み直す。
- **コピー部分のキーフレームの前に、元の SPS/PPS を再挿入する。** 再エンコード部分の
  SPS が有効なままだと、コピー部分が誤った SPS で復号される。そのため継ぎ目ごとに
  元のパラメータセットを復元する。

背景は[難所 1](../technical/algorithm.ja.md#1-パラメータセットspsppsが一致しない)に
ある。

## 参照判定が Python より正確になった点

Python はビットストリームを読むために ffmpeg をもう一度起動する必要があり、
**ファイル内の 1 か所を標本にして全体に適用**していた。

Rust ではパケットを走査しているその場で `nal_ref_idc` を読めるので、判定を
**アクセスポイントごとに厳密に**行える。追加のパスも追加のコストも不要である。

## エンコーダのないコーデック: VC-1

このプログラムが扱うコーデックには一つを除いてすべて libavcodec にエンコーダが
あります。VC-1 のエンコーダはどこにも存在しません——libavcodec にも、
グラフィックスカードにも、フリーな実装のどれにもです。
`ff::encoder::find(AV_CODEC_ID_VC1)` は空で返り、これを書くまで VC-1 素材の
カットはそこで止まっていました。

これが問題になるのは、VC-1 で書かれているものが何かによります。2010 年頃までに
プレスされた Blu-ray の多くがそれです。読むことは[ディスク](disc.ja.md)で
できていましたが、カットはできていませんでした。

そこで `rust/crates/vc1` はこのフォーマットのイントラピクチャだけを書く
エンコーダです。これが研究課題ではなく現実的な作業になるのは、スマートカットが
実際に必要とするものによります。範囲の両端に必要なのは GOP の断片——数十枚——で、
それを素材そのもののバイト列のコピーに繋ぎます。断片の外を参照してはならない
のだから、断片内のピクチャはすべてイントラにできます。そしてイントラ専用の
エンコーダはフォーマットのごく一部です。

| 不要なもの | 理由 |
|---|---|
| 動き推定と動きベクトル | イントラピクチャは何も予測しない |
| 5 種のビットプレーン符号化 | raw モードはマクロブロック層に 1 ビットずつ書くだけで、どこでも合法 |
| 可変ブロック変換 | 対象のディスクは `VSTRANSFORM=0` を宣言しており、全ブロックが 8x8 |
| オーバーラップ平滑化、AC 予測 | どちらも任意で、ピクチャヘッダで断れる |
| 自前のシーケンスヘッダ | 素材自身のものを毎ピクチャの前に置き直す。ディスク自身がそうしているので、継ぎ目の向こうのコピーされたピクチャは、まさに符号化されたときのパラメータで復号される |

必要なのはブロック層です。DC 差分の符号、2 つの符号化セットの AC 係数符号、
coded block pattern とその予測、DC 予測、インタレース用の走査、そして 8x8 変換。
テーブルはフォーマットのものであり、手写しではなく FFmpeg のデコーダのものから
機械的に生成しています——数千個のうち一つ間違うだけで、途中からノイズに復号される
ストリームができあがるからです。

変換には一言必要です。フォーマットが定義しているのは逆変換だけで、順変換は
エンコーダを書く側に委ねられています。`transform::inverse` はデコーダのものを
移植したもので、テストで両者を突き合わせるためにあります。`transform::forward`
はその代数的な逆です——行列は直交ですが行ごとにノルムが違うので、係数ごとに
別々の係数で正規化します。

### 正しいと分かる理由

比較できる別の VC-1 エンコーダが無いので、テストは往復です。ピクチャを符号化し、
どのプレイヤーも使っているデコーダに渡し、返ってきたものを測る
（`tests/run_vc1_tests.sh`）。両方が要ります。わずかに壊れたビットストリームでも
復号自体はできてしまう——ノイズに、あるいはマクロブロック 1 行だけ壊れた絵に——ので、
「復号できた」だけでは何も証明しません。そして変換の正規化を間違えると、
明るさだけが違う完全に合法なストリームができ、エラー無く復号できることでは
決して露見しません。

2 枚のディスクで検証しており、この 2 枚で Advanced Profile の違いはほぼ
覆えます。1 枚は 1920x1080i 29.97、インタレースフレーム符号化、non-uniform
量子化、全 GOP がクローズド。もう 1 枚は 1920x1080 プログレッシブ 23.976、
uniform 量子化、全 GOP がオープン、プルダウンはフレーム単位の形式、skipped
ピクチャあり——そして強いフィルムグレイン。グレインは量子化を通すと最も
平滑化されやすいものです。それぞれ与えたピクチャに対して測った値:

| 量子化ステップ | 1080i アニメ | 1080p 実写グレイン |
|---|---|---|
| 4（既定） | 48.0 dB、1 枚 109 KB | 44.8 dB、1 枚 205 KB |
| 8 | 45.2 dB、76 KB | 41.0 dB、129 KB |
| 16 | 42.4 dB、50 KB | 37.3 dB、74 KB |

グレインは 2 倍のビットを食って 3dB 落ちますが、それはどのエンコーダでも同じ
です。文脈で見る方が意味があります——**グレインの側のディスク自身の I ピクチャは
平均 327KB** で、ここで書く 205KB より 6 割大きい。アニメの側も平均 166KB に対して
109KB です。このエンコーダのイントラピクチャは、ディスクが同じ場所に置いている
ものより小さいということです。プレイヤーに新しい負担をかけてはいません。

両方とも GOP 途中から GOP 途中まで 10 秒の実カットを行い、映像の 90% が元と
バイト単位で一致しました。グレインの側は、置き換えたピクチャと等倍で見比べても
粒子が残っています。

### 断るもの

パンスキャンのウィンドウと、ピクチャ端で量子化を変える指定（`DQUANT=2`）。
どちらもピクチャヘッダの途中にあり、正確に真似る必要がありますが、ディスクで
見かけたことがありません。これらを持つ素材は、間違って書くのではなく名指しで
断ります。

フィールドピクチャ（`FCM=11`）は読めますが書きません。インタレース素材なら、
周囲のピクチャがどちらで符号化されていようとインタレースフレームとして書きます。
VC-1 はこれをピクチャごとに宣言するので、両者が一つのストリームに混在できます。

### 今後の検討事項

どれもカットを止めるものではありません。書き残しておくのは、いずれもエンコーダを
動かすために下した判断であり、次にこのファイルを開いた人が「なぜこうなのか」を
考える場所だからです。

| | |
|---|---|
| **ウィンドウにステップの設定が無い** | `--vc1-quant` はコマンドラインにしかありません。ウィンドウには映像の設定が一つも無く、出力画面の項目はすべて音声の話なので、これが最初の一つになります。どこに置くかはエンコーダの問題ではなく、あの画面の問題です。それまでウィンドウからのカットは既定値を使います |
| **フィールドピクチャを書かない** | インタレース素材ならインタレースフレームとして書きます。フィールドの対と並んでいても合法ですが、前後がフィールド対で符号化されたストリームをデコーダに読ませたことはありません。手元の 2 枚はどちらもフレームで符号化されています。フィールドで符号化された素材があれば、両方の書き方で並べて確かめたいところです |
| **必要以上にビットを使っている** | 任意だという理由で三つ省きました。AC 予測、係数をテーブルの項目との差として書く 2 種のエスケープ形式、そして AC テーブルの選択（量子化ステップから 1 組を選んで通します）。それぞれ数パーセント削れますが、断片が短いのでまだ問題になっていません |
| **断片が全部イントラである** | ビットレートを最も削れるのは上のどれでもなく P ピクチャです。ただし動き推定と、動きベクトルを運ぶ構文の全体が要ります。それは別の企てであり、この企てに手をつける価値があったのは、それをやらずに済むからでした |
