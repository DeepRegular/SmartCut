# バッチ処理

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](batch.md)

SmartCut は、一晩ぶんの録画をまとめて片付けることを前提に作られています。20 本を
放り込み、`Ctrl+A` → `Ctrl+D` を押し、編集画面で 1 本ずつ切って、最後にまとめて
書き出す、という流れです。

このページでは、その間に裏で何が動いているのか、そしてなぜそれが作業の邪魔に
ならないのかを説明します。

## 作業の流れ

```
ファイル追加  →  裏で索引とサムネイル  →  Ctrl+D で CM 検出
              →  編集画面で 1 本ずつ切る  →  一覧をまとめて書き出す
```

カットは編集ウィンドウではなくクリップ側に残ります。そのため一覧を上から順に
切っていき、そのあとでまとめて書き出す、という進め方ができます。

## 3 つの処理が並行して走る

裏で動く処理は 3 つあります。**1 つ目はパケットを走査してシーク用インデックスを
作り、2 つ目はキーピクチャを復号してサムネイルとシーンの変わり目を作り、3 つ目が
CM を検出します。** 同じ種類の処理は同時に 1 つずつ、種類が違えば 3 つ同時に
走ります。

分けているのは、3 つの負荷の性質が違うからです。走査はディスク律速です。1 コアが
1 GB を 1 秒ほどで読み、デコーダには一切触れません。サムネイル作成は CPU 律速
です。キーピクチャをすべて libavcodec に通すので、1 GB あたり約 4 秒かかります。
CM 検出は 1 コアと大量のディスク待ちです（字幕を読むのも、音声とロゴを見るのも、
libavcodec のスレッド化が効きません）。裏の処理どうしが分け合って失うものより、
`Ctrl+D` が得るもののほうがずっと大きく、これが「夜に押して朝までに終わる」と
いう結果につながっています。

**走査とサムネイル作成を直列にせず並走させているのが、一覧が速い理由です。**
直列だと、ただの足し算でした。走査が録画を丸ごと読み、そのあとサムネイル作成が
同じ録画をもう一度丸ごと読む。どちらも相手を待つ理由が無いのに、順番待ちを
していたわけです。並走させると、走査が一覧を先へ進み、サムネイル作成が 1 本ずつ
後ろを追う形になります。その結果、**どの行もディスクの速度で埋まり**、復号は
ディスク待ちの裏で済みます。

サムネイル作成が走査のすぐ後ろを追うのは、走査が通したばかりの録画を読めば、
2 回目の読みがディスクではなくページキャッシュから返るからです。共有フォルダー上の
録画でも同じで、キャッシュに当たった読みはネットワークにも届きません。

4 つ目の処理は用意していません。追加すれば同じコアを使う 2 つ目のデコーダに
なりますし、それ以前にディスクが上限になります。

## 編集画面は裏の処理を待ちません

走査・サムネイル作成・CM 検出・カット編集は同時に動きます。互いに何も共有して
いません。裏の処理も書き出しも、ディスク上のシーク用インデックスから録画を開き
直すので、12 本目に長い処理が走っていても、いま編集しているクリップには何の影響も
ありません。

編集ウィンドウが開いているあいだ、裏の 3 つの処理はマシンの**半分**だけを分け
合います。人が待っているのはポインタの下にある絵なので、裏の処理が数秒遅く終わる
のは妥当な代償です。

**まだ読み込みが終わっていないクリップも開けます。** 編集画面は自分でその処理を
行い、読めたところから使えるようになります（[GUI の使い方](gui.ja.md#開いた瞬間から使えます)）。
順番を待っても得るものはありません。

**編集画面を開いても、裏の処理は止まりません。** そのクリップで既に走っている処理は
最後まで走りきります。読んだところは読んだままで、行の進捗も、絵も、シーンの印も、
ウィンドウを開いたせいで「解析待ち」に戻ることはありません。編集画面が同じファイルを
読む分は、裏の処理が埋めていくページキャッシュに乗るので、ディスクまで取りに戻る
わけではありません。裏の処理が飛ばすのは、編集画面が開いているクリップで新しい処理を
**始める**ことだけです。それは編集画面がいま自分でやっていることの繰り返しにしか
なりません。編集画面が書いたインデックスはディスクに残るので、編集画面を閉じて裏の
処理がその行を取り上げるときには、読み込み 1 回ぶんで済みます。

## 一覧全体に CM 検出をかける

`Ctrl+A` → `Ctrl+D` で、選択したすべてのクリップの検出がキューに積まれます。
18 本を選んで `Ctrl+D` を 1 回押せば、一晩ぶんの作業がキー操作 1 回で始まります。
これがこの機能の目的です。その間、まだ索引の無いクリップの読み込みも並行して
進みます。

進み具合は各行に出ます（`CM 検出中 84% — ロゴを探しています`）。まだ順番の来て
いない行は `CM 検出 待機中` と表示されます。

**解析を中止**を押すと 3 つの処理がすべて止まり、もう一度押すと再開します。走査と
サムネイル作成はファイルの途中でも止まれますが、CM 検出を構成する 3 つのパスは
途中で止まれないので、停止はクリップとクリップの**間**で起こります。

停止の対象は「いま動いているもの」だけで、そのあとに続くものには影響しません。
そのため、バッチを止めてすぐ別のバッチを始められます。

## クリップの複製

**⧉ クリップを複製**は、同じ録画をもう 1 行足します。2 時間の録画に番組が 2 本
入っている場合のための機能です。同じファイルを 2 行に置き、それぞれ違う範囲で
書き出します。

**複製はカットも印も引き継ぎます。** 2 本目のカットは、ゼロから作るものではなく
1 本目をずらしたものであることがほとんどです。編集内容を捨てるコピーでは、複製の
目的を果たせません。インデックス・尺・CM 検出の結果も引き継がれます。どれも同じ
ファイルについての答えなので、複製してもディスクの読み直しは発生しません。

**同じファイル名になる行には、一覧順に `_1` `_2` が付きます。** 複製がその代表例
ですが、それだけではありません。別のフォルダーにある同名の番組も、ディスクから
読んだ録画（どれも `00001`）も、同じ出力先に書けば同じ名前になります。番号が
無ければ 2 本目が 1 本目を消してしまい、「2 本出力しました」と言いながら 1 本
消えていることになります。片方を消すと、残ったほうは番号の無い名前に戻ります。
番号は複製時に刻み込むのではなく、そのつど一覧から数えているためです。

## 一覧を書き出す

出力タブは一覧を上から順に、1 本ずつ書き出します。各行に進み具合と結果が出て、
その上に全体の状況・経過時間・残り時間が出ます。

`出力中止` は、いま書き出しているクリップを最後まで書き終えてから止まります。
途中まで書かれたファイルが残ることはありません。**ディスクに書いている途中で
止めた場合は、書いたぶんもディスクから引き上げます**——止めた実行では索引を作る
行程が走らず、索引の無いストリームはディスクの誰からも指されないからです。詳しくは
[GUI ガイド](gui.ja.md#4-書き出す)にあります。

書き出しの順序は一覧の順序なので、「これを最初に書き出したい」というときは
その行を上へドラッグします。

## ネットワーク共有上の録画を扱う

SMB 共有上の録画は、コマンドラインの引数としても、ファイルマネージャーからの
ドロップとしても、出力先フォルダーとしても扱えます。SmartCut は共有パスを
「このマシンで実際にマウントされている場所」に読み替えます。それ以降は普通の
パスなので、パケット走査もシーク用インデックスも書き出しも、ネットワークが
関わっていることを知らないまま進みます。

**SmartCut 自身はマウントを行いません。** マウントにはパスワードが伴いますが、
それはカット編集ソフトではなくデスクトップのキーリングが持つべきものだからです。
つながっていない共有を渡された場合は、どこで接続すればよいかを示して断ります。

```
\\nas\rec につながっていません。ファイルマネージャーで smb://nas/rec を
開いてから、もう一度追加してください。（現在つながっている共有: \\nas\録画）
```

## バッチを保存する

一覧全体（録画・カット・トラックの選択・出力設定）は `Ctrl+S` でプロジェクトとして
保存でき、次回そのまま戻ってきます。[プロジェクト](projects.ja.md)を参照して
ください。
