# ディスクを読む

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](disc.md)

*逆方向、つまり一晩分のカットをディスクとして書き出すほうは
[ディスクを書く](bdav.ja.md)にある。*

**ディスクは、フォルダーのままでも `.iso` のままでも開ける。** Blu-ray は規格の
両方、つまり録画形式の BDAV と市販ソフトの形式である BDMV のどちらも読む。DVD-Video
も読む（[後述](#dvd-video)）。一覧に並ぶのは `00001.m2ts` ではなく番組名である。

```
$ smartcut Anime_Test.iso
disc  : Anime_Test.iso
        bdav -- Anime_Test
        3 recording(s)

  1  00:08:30.010  2026年08月17日01時00分-衛星第一-サンプル番組 てすとばんぐみ!にっ!! #07「架空の休息日の過ごし方。」  2 mark(s)
       0x1101  AAC stereo 48kHz
       0x1102  stream type 0x06
  2  00:08:30.010  …
```

市販ディスクには番組名が入っていないので、行の名前はディスク名とクリップ番号になる。
また、入っているものの大半は本編ではないので、本編らしいものには印が付く。

```
$ smartcut AnimeBox_Season1.iso
disc  : AnimeBox_Season1.iso
        bdmv -- Anime Box Season 1
        62 recording(s)

   1  00:00:43.543  Anime Box Season 1 00008  1 mark(s)
       0x1100  AC-3 stereo 48kHz eng
       0x1200  PGS eng
   2  00:00:11.511  Anime Box Season 1 00002  1 mark(s)
   …
*  8  00:11:52.003  Anime Box Season 1 00014  4 mark(s)
       0x1100  TrueHD multi 48kHz eng
       0x1101  TrueHD stereo 48kHz jpn
       0x1200  PGS eng
       0x1201  PGS eng
```

市販ディスクは丸ごと取り込むのではなく、まず訊く。
後述の[選択ダイアログ](#選択ダイアログ)を参照。

GUI では、ISO かディスクのフォルダーをウィンドウにドロップすると、その中のどれを
読むのかを確認する画面が出る。ディスクを何枚か入れたフォルダーを落としても同じで、
一晩分のディスクがそのまま 1 つの一覧になる。

## ふたつの方言

**BDAV** は**録画の形式**で、レコーダーが書くのも、オーサリングツールに
「録画のディスク」を作らせたときに出てくるのもこちらである。

```
BDAV/
  info.bdav              プレイリストの一覧と順序
  PLAYLIST/00001.rpls    録画 1 件: どのクリップを、どこからどこまで
  CLIPINF/00001.clpi     そのクリップの索引
  STREAM/00001.m2ts      トランスポートストリームそのもの
```

**BDMV** は市販の映像ソフトの形式である。プレスされたディスクか、その複製がこれに
あたる。構造は同じだが名前が違い、そして分量がまるで違う。メニュー、Java アプリケー
ション、索引一式の予備が `BACKUP/` にもう 1 組。そのどれも録画ではない。

```
BDMV/
  index.bdmv             プレーヤーのメニュー用のタイトル一覧
  PLAYLIST/00009.mpls    ディスクの通し方 1 通り: どのクリップを、どの順で
  CLIPINF/00014.clpi     そのクリップの索引
  STREAM/00014.m2ts      トランスポートストリームそのもの
  META/DL/bdmt_eng.xml   ディスクの名前
  BACKUP/                上のすべての予備
```

違うのは 4 か所だけである。ディレクトリ名、プレイリストの拡張子とマジック、
プレイリスト一覧の出どころ、そしてプレイリストが番組名を持つかどうか。残りはすべて
同じである。
**PlayItem のバイト配置も、チャプターマークのそれも同じ**である。だから
[`disc.rs`](../../rust/crates/core/src/disc.rs) は「どちらの方言を見ているか」を
渡された 1 つのリーダーであって、同じものを 2 回書いた 2 つのリーダーではない。

BDMV にひとつだけ、ここでは読めないものがある。`index.bdmv` が並べているのは
**タイトル**である。そしてタイトルは、プレイリストではなくナビゲーションや Java の
プログラムだ。「T05 Extra 01」がどのプレイリストを再生するかを知るには、ディスク自身の
メニューコードを走らせるしかない。それは Blu-ray プレーヤーであって、これではない。
したがってプレイリストは、ディレクトリから名前順に取っている。これはオーサリング
ツールが番号を振った順で、実際に見たどのディスクでも、人が選ぶとすれば同じ順になる。

ストリームは MPEG-2 TS を 192 バイトパケットで包んだもの（188 バイトのパケットの前に
到着時刻 4 バイトが付く）で、libavformat は何も指定しなくても読める。**したがって
ストリームは最初から問題ではなかった。** 足りなかったのは索引である。`00014.m2ts`
`00015.m2ts` `00016.m2ts` という並びは、どれが本編で、どれがメニュー前に流れる 8 秒の
ロゴなのかを何も語らない。

## ISO をマウントせずに読む

`.iso` は UDF ファイルシステムである。Linux ならマウントできるが、マウントには root と
ループデバイスが要り、編集のあいだじゅうカット編集ツールにマウントを握らせるのは、
落ちたときに宙ぶらりんのマウントを残すということである。Windows なら `.iso` は
ダブルクリックでマウントできるが、それは「プログラムを使う前にユーザーが済ませて
おかなければならない手順」がひとつ増えるということである。

そこでマウントはしない。イメージはその場で読む
（[`udf.rs`](../../rust/crates/core/src/udf.rs)）。答えを出すべき問いは 1 つだけで
ある。

> **各ファイルはイメージの何バイト目から始まり、何バイトあるのか。**

焼かれた `.m2ts` はひと続きのバイト列なので、答えは**バイト範囲**になる。そして
バイト範囲は、libavformat に `subfile` プロトコルでそのまま渡せる:

```
subfile,,start,747520,end,1232594944,,:file:/rec/Anime_Test.iso
```

デマルチプレクサはこれをただのストリームとして読み、まわりにファイルシステムが
あることを最後まで知らない。だからその先、つまりパケット走査・アクセスポイントへの
シーク・コピーは、普通のファイルのときと 1 行も変わらない。

> 内側のパスを `file:` で始めているのは、オプションの並びが**最初のコロンで終わる**
> ためである。そうしないと Windows の `C:\…` が「プロトコル `c`」と読まれる。

### 1 ギガバイトの壁

UDF の割り当て記述子は長さフィールドが 30 ビットしかないので、記述子 1 個で
1 GiB より長い範囲は表せない。つまり 1.2 GB のクリップは記述子 2 個になる。

```
len=1073739776  lbn=77      -> byte 747520
len=158107648   lbn=524364  -> byte 1074487296
```

747520 + 1073739776 = 1074487296。**隙間なく続いている。** 焼き込みは連続した領域に
書くので、断片化しているのは記述子であってファイルではない。
[`Entry::contiguous`](../../rust/crates/core/src/udf.rs) は続いているものを繋いで
1 つの範囲にし、本当に飛んでいる場合は `None` を返す（焼かれたディスクではまず
起きない）。誤った範囲を読むくらいなら、読めないと答えるほうがよい。

### メタデータパーティション

UDF 2.50 以降のイメージには**メタデータパーティション**がある。ファイルエントリを
まとめて置くための仕組みで、ファイル本体は隣の物理パーティションに残る。つまり
論理ブロック番号を「メタデータファイルの中の位置」として解き、そのファイル自身の
エクステントを辿って初めて実際のセクタになる。ImgBurn が書く UDF 2.60 はこれを使い、
genisoimage が書く UDF 1.02 は使わない。両方読める。

**暗号化されたディスクは対象外である。** AACS は復号の問題であり、SmartCut は
その一切を持たない。

ただし、そうだと言うことはする。レコーダーはストリームを暗号化して索引は平文のまま
残すので、この種のディスクは一覧だけは完璧に出て、どれも開かない。libavformat が
返すのは `Invalid data found when processing input` で、バイト列については正しいが
理由は何も言わない。`BDAV` の隣にある `AACS` ディレクトリが理由である。選択画面は
チェックを付ける前にそれを言い、開くのに失敗したときはデマルチプレクサの一文の
代わりにそれを表示する。読むのは失敗した後か、説明するときだけで、拒否には使わない。
ストリームをその場で復号したイメージはディレクトリを残したまま開けるし、
ストリームを別の場所へ移すツールはディレクトリも自分の場所へ移す。

## プレイリストは録画について何を言っているか

**BDAV では、人が読むものはプレイリストに入っている。** 番組名だけではない。
レコーダーは、録ったチャンネルとその 3 桁の番号、録画を始めた瞬間、そして放送局が
書いた番組内容を数百バイト書く。番組表に載る 1 文と、その下の出演者やスタッフである。
どれもプレイリスト先頭の自己記述の中の決まった位置にあり、ここではその全部を読む。
その録画のカットを自分のディスクに書くとき、同じことを言えないといけないからだ。
位置と、どのツールがどれを書くのかは[ディスクを書く](bdav.ja.md#プレイリストに書かれていること)にある。

`smartcut <disc> --title N` は読めたものを表示する。

```
title : アニメ 第03話「はじめての遠出」ほか
        衛星第一 (161)  2010-02-14 00:30:00
        美術科に入学した主人公が、学校の前のアパートでひとり暮らしを始める。…
```

## 番組名は ARIB のテキストである

**これは BDAV の話である。** `.rpls` は番組名を UTF-8 では持っていない。ARIB
STD-B24 の 8 単位符号で書かれている。これは ISO 2022 の子孫で、漢字・英数・ひらがな・
カタカナの 4 つの図形集合を同時に保持し、シフトとエスケープで切り替える方式である。
文字の大きさや色の制御符号も、同じバイト列に混ざっている。

[`arib.rs`](../../rust/crates/core/src/arib.rs) はこれを**読む**。描画はしない。
大きさも色も落として、文字の並びだけを取り出す。JIS X 0208 から Unicode への表は
自前で持たず、EUC-JP 経由で引いている（EUC-JP は JIS X 0208 の両バイトに最上位ビットを
立てたものなので、同じ表である）。依存は `encoding_rs` ひとつと、自前の表がひとつ。
自前のほうは JIS が最後まで割り当てなかった区で、UTF-8 の世界のどの符号化も ARIB と
同じようには埋めていない領域である。

2 つだけ気を付けている点がある。

- **JIS の 85 区以降は ARIB 自身の記号であり、名前を与えなければならない。** JIS では
  未定義のこの領域に、ARIB は自前の記号を置いている。それらを埋めている**別の**符号化の
  変換表に通すと、まったく違う文字が出てくる。だから自前で名前を与えないのなら、
  受像機が出すのと同じ `〓` を返すほかない。

  最初は 85 区以降をまるごと `〓` にしていた。番組名が天気記号を持つことはない、という
  理由である。**しかしシーズン番号は持つ。** 第 3 期のシリーズは `Ⅲ` で、これは
  94 区 3 点である。JIS でもなければ ASCII の `III` でもない。番組名は真ん中に `〓` を
  抱えて戻ってきて、同じ文字列がそのままディスクに書かれるものだから、`〓` がディスクに
  焼かれて残った。同じ領域には JIS X 0208 が落とした漢字、`髙` や `﨑` も入っており、
  日本語の名前はこれを普通に使う。そこで今はすべてに名前を与えている。出典は
  ARIB STD-B62 の対応表で、85・86 区が漢字、90 区が交通の記号、91 区が地図の記号、
  92 区が単位と数字、93 区が天気と分数、94 区が数字記号である。何も割り当てられて
  いないセルは今も `〓` で、DRCS のダウンロード外字も**ここでは** `〓` である。名前は
  文字列であって、放送局がドットで送ってきた字は文字列ではない。そのドットを受け取って
  描くのは字幕側で、[放送局が「画像で送ってくる文字」](broadcast-ts.ja.md#放送局が画像で送ってくる文字)にある。

  **90 区の 48〜84 セルは、描くのではなく書き下す。** 番組表の角括弧付きの記号、
  `[新]` `[字]` `[終]` `[再]` である。テレビでは 1 つの囲み文字、それ以外の場所では
  囲みの中の語になる。Unicode にはこれらの文字もあるが、環境にあるフォントの半分は
  それを描けない。そして番組表に入っているのは `[新]` である。

  **書き出すときは、語を元のセルへ戻す。** 録画が 1 セルで持っていたものを 3 文字で
  書くのは、放送が送った名前ではなく番組表が刷る名前を書くことになる。セルなら 2 バイト
  で済むところが 10 バイトになり、テレビは囲み文字を描くはずのところに `[` `新` `]` を
  描く。そこで書き出すときに綴りを照合する。ただし角括弧で語を綴るものだけである。
  37 個のうち 3 個は普通の文字で綴られており（`■` `●` `ほか`）、番組名はそれらを
  それ自体として持ちうる。`…遠出」ほか` で終わる題名は、そうしないと末尾のかな 2 文字を
  記号に飲み込まれてしまう。

  **この罠には反対側の端もある。** `Ⅲ` `①` `㈱` `℡` `㎏` はいずれも 13 区にあり、
  ここも JIS X 0208 は未定義のまま残していて、UTF-8 の世界が手を伸ばす符号化はそこを
  ベンダーの追加文字で埋めている。つまり EUC-JP を通して名前を書き**出す**と、数字記号は
  ARIB が何も置いていない区へ入り、受像機はそこに描くものを持たない。入口で 85 区以降を
  弾くのと同じ理由で、出口では 13 区を弾き、代わりに ARIB 自身のセルへ書く。エスケープ
  で G0 に指示し、書いたら指示を戻す。これはこの問題が見つかった放送自身がしている
  ことでもある。
- **かなの集合の末尾 8 セルは、かなではなく約物である。** JIS の 4 区・5 区は最後まで
  埋まっておらず、ARIB は余ったセルに `ー` `。` `「` `」` `、` `・` を入れている。
  ここを取りこぼすと、番組名が `#07〓架空の休息日の過ごし方。」` になる。

### ただし 4K レコーダーは UTF-8 で書く

**4K レコーダーは番組名を UTF-8 で書く。** 放送が独自の文字として送っている記号
（`🆞`・`🈔`）も、Unicode の文字に直したうえで入っている。ARIB として読むと
`ＮＨＫ　ＢＳ` が `わぜぎわぜえわぜかゃわぜあわぜこ` になり、そのディスクの行が
全部でたらめな名前になる。

どちらかを言っているのはファイルのバージョンである。4K 録画のプレイリストとクリップ
索引はバージョン 2.00 で、`PLST0200`・`M2TS0200` と名乗る。オーサリングツールは
`0100`、HD のレコーダーは `0110` である。ただし `info.bdav` は 2.00 のディスクでも
`BDAV0100` のままなので、バージョンだけでは決まらない。バイト列にも訊く。

バイト列に訊けるのはここまでだ。ARIB のテキストは `0E`・`0F`・`1B` で文字集合を
切り替える。UTF-8 のテキストがこれらを含むことはない。`89`・`8A` の単一シフトも同様で、
これで始まる正しい UTF-8 の並びは無い。**ところが漢字だけで書かれた名前はシフトを
一度も使わない。** 復号はそこから始まるからである。その名前は `0x80` 未満のバイトの
並びで、UTF-8 としても妥当であり、UTF-8 として読めば 2 バイトずつが綴るラテン文字の
でたらめになる。そこで、2.00 と名乗るファイルは UTF-8 として読む。名乗らないファイル
は、ARIB では書けない文字がバイト列に入っているときだけ UTF-8 として読む。これが
`disc::recorded_text` である。

`.mpls` のほうは名前をまったく持っていない。映画のタイトルはメニュー、つまり Java
アプリケーションの中にあるからである。そこで市販ディスクの行は、`Anime Box Season 1
00014` のように、ディスク名とクリップ番号で名付ける。ディスクが自分を何と呼んでいるか
は `META/DL/bdmt_*.xml` から取る。ただし XML として解析するのではなく、必要な部分を
拾い読みしている。あのファイルは名前空間が十数個宣言された文書だが、必要な要素は
1 つだけである。`<di:name>` を読むためだけに XML パーサを抱え込めば、SmartCut
最大の依存関係になってしまう。

## 文字スーパーと、もう一つの字幕

放送が送っているテキストは字幕だけではない。その隣を**文字スーパー**が走る。地震、
開票速報、迷子の知らせ。放送局が、そのとき画面に出ているものの上に書く行である。
専用のストリームに、字幕と同じ ARIB の文字で載っている。そして **4K** 放送の字幕は
まったく別の形式で書かれている。TTML、つまり字幕 1 枚につき XML 文書 1 つで、言葉と、
それを置く領域がピクセルで入っている。

**libav はこの 3 つのうち 1 つだけに名前を付け、残り 2 つをひとまとめにする。** HD
放送の字幕は `arib_caption` として返ってくる。文字スーパーと 4K の字幕はどちらも
`bin_data`、つまり素性の無いバイト列として返ってくる。そのまま読んだ結果、4K
ディスクの字幕は「文字スーパー」と名乗って捨てられていた。1 行に間違いが 2 つである。

見分けるのは録画自身の map である。ARIB はストリームを 1 バイトの component tag で
指す。0x30〜0x37 が字幕、0x38〜0x3F が文字スーパーだ。その隣にデータ符号化方式記述子が
あり、テキストが ARIB STD-B24 であることを示す。4K 録画はこの記述子もこのテキストも
持たない。そこで map は開くたびに読み（`si::stream_tags`）、tag と記述子の両方で 3 つを
見分ける。規則の全体は `lib::text_stream` にある。map が読めなかったときは libav
自身の名前が代わりに答える。

3 つとも `.ts` へ運ぶ。3 つともプレビューに出せる。それ以外に読むのは最初の 1 つだけ
である。切れ目を探すのも（[`caption::resets`]）、ディスクの字幕を描き換えるのも、番組の
字幕であって放送局の文字スーパーではない。

### 4K の字幕は、時刻が文書の中にある

TTML のストリームには、ほかのどのストリームとも違うところが 2 つある。

**パケットには時計ではなくカウンタが載っている。** レコーダーは 1・2・3 と打つ。最初の
文書の presentation time が `1`、次が `2` である。言葉を出す時刻は文書の中に文字列で
入っている。`begin="00:02:21.667"` のように。

**その時刻は、クリップが提示を始める場所から数えてある。** ファイルの先頭ではない。
どこから始まるかはディスクの管理情報に書かれている。プレイリストの `IN_time` と同じ数字で、
`disc::clip_presentation_start` がそれを読む。提示開始が 0.5 秒違う 2 本のクリップで
測ったところ、どちらも最初の字幕がちょうどその 5 秒後、タイトルバックに切り替わる
フレームに乗った。ファイルの先頭から数えたとすれば、2 本はそれぞれ 1.2 秒と 1.7 秒
ずれる。

だからカットは、このパケットをほかのストリームのようには動かせない。代わりにするのは、
文書の中の時刻を動かして書き戻すことである（`cut::take_ttml`）。どの区間にも入らない
字幕は運ばない。区間の頭をまたぐ字幕は区間の頭から出る。区間の尻を越える字幕は区間の
尻で消える。文書の長さは変わらない。`HH:MM:SS.mmm` は幅が固定だからで、これは
レコーダーが文書の前に書く 12 バイトが文書の長さを数えているので重要である。

出てくる時刻は、カットの最初のピクチャから数えたものになる。プレイリストの無いファイルは
そこから始まるからである。

## 一覧に並ぶもの

**クリップ 1 本が 1 行**である。プレイリスト 1 件が 1 行、ではない。

BDAV ではこの 2 つは同じことである。プレイリストが 2 つ以上のクリップを再生している
場合だけが違う。それは番組が、レコーダーがストリームを分割する長さを超えたときに起きる。
その場合はクリップごとに 1 行にして `(1/3)` `(2/3)` `(3/3)` と付ける。

BDMV ではまるで同じことではない。市販ディスクは同じクリップを複数のプレイリストから
指す。そのクリップ専用のプレイリストで 1 回、「全話連続再生」の中で 1 回、メニューの
チャプター一覧が指すもので 1 回。これを書くにあたって使ったディスクでは、
**45 本のプレイリストが合わせて 328 個の PlayItem を指しており、
実体は 62 クリップだった。**PlayItem ごとに 1 行にすれば、
同じ話数を 3 回並べることになる。

そこで行の鍵は「プレイリストがそのクリップのどの部分を再生するか」、つまりクリップ
番号と IN/OUT のティックにし、最初にそれを指したプレイリストが行を作る。クリップ
だけを鍵にしないのは、レコーダーが 2 番組を 1 本のストリームに書き、半分ずつの
プレイリストを 2 本書くことがあるからで、それは 2 件の録画である。

複数クリップのプレイリストを 1 つのタイムラインに繋ぐのは、別の仕事である（クリップ
ごとに時計が違うので、2 本を繋ぐのは 1 本を切るのとは別の操作になる）。それが
できるようになるまでは、分かれていることをそのまま見せるほうが正直である。ディスクの
どの秒にも手は届くし、分かれていることは一覧が示している。なお、市販ディスクの
「全話連続再生」は*分かれた録画ではない*ので、その行に `(1/15)` は付けない。ディスク
自身がそんな関係を主張していない以上、付ければこちらが関係を捏造したことになる。

### 選択ダイアログ

録画ファイルは 1 件で、訊くことは何もない。市販ディスクはそうではない。あの 62 行は
ロゴ・警告・メニューのループ・8 秒の繋ぎが 50 本と、その中に紛れた 12 話であり、
ディスクはそのすべてを `000NN` と呼んでいる。

そこで索引を並べ、何も開かないうちに一度だけ確認する。ダイアログに出る情報が、長さ・
サイズ・PID で示したトラックという、索引だけで答えられるものばかりなのはそのため
である。

**5 分**を超えるクリップは最初からチェックが入る。あのディスクではそれがちょうど 12 話で、
残りはチェックボックスひとつの裏に畳まれる。この閾値は、ディスクを取っておく理由に
なるいちばん短いものよりずっと短く、メニューを構成するいちばん長いものよりずっと長い。
どれも 5 分に届かないディスクは「何も入っていないディスク」ではないので、その場合は
いちばん長いものにチェックを入れる。BDAV は全部にチェックが入る。録画のディスクは、
誰かが録ると決めたものが入っているディスクだからである。

### クリップが持っているもの

各行の下に出るトラックは、そのクリップの `.clpi` から読む。十分に安く済むのはこれ
だけだからである。自分を描画するために 30 ギガバイトを demux するダイアログなど、
誰も待ってくれない。実際にカットするときに最終的な根拠になるのは demuxer が読み取った
内容で、ここに出しているのは「ディスクがそう書いている」という情報である。

```
映像  / H.264 1080p 23.976fps / PID 0x1011 / 映像は外せません
音声  / TrueHD multi 48kHz    / eng / PID 0x1100
音声  / TrueHD stereo 48kHz   / jpn / PID 0x1101
字幕  / PGS                   / eng / PID 0x1200
メニュー / IGS                / eng / PID 0x1400 / カットでは持ち出せません
```

方言によって `.clpi` の署名が違い、その後ろは同じである。市販ディスクは `HDMV`、
レコーダーは `M2TS` で始まる。またレコーダーは言語欄を切り詰めるので、BDAV の行は
言語なしの `AAC stereo 48kHz` になる。続いていた 3 バイトを言語として出すよりましである。
放送の私的ストリーム（字幕もそのひとつ）は番号で呼ぶ。私的ストリームの中身はディスクの
索引に書かれていることではなく、索引ではなく録画そのものを読む編集画面のトラックメニューが
きちんと名前を付ける。

4 種類が並ぶが、外せないものが 1 つ、持ち出せないものが 1 つある。映像はカットの
対象そのものなので外せない。メニュー（IGS）はボタンの状態と飛び先を持っていて、
その飛び先はカットが今ばらしたばかりのタイムラインを指している。一覧に出しているのは
選ばせるためではなく、持ち出せないことを伝えるためである。字幕（PGS）は同じ種類の
ストリームだが仕事が違い、こちらは[運ぶ](#ディスクが描く字幕)。

ディスクに入っている話数はどれも同じトラック構成なので、1 行の答えを同じ構成の全行に
写すボタンを用意してある。同じ問いに 12 回答えさせるのと、1 回で済ませるのとは
別物だからである。

**言語もカットについていく。** Blu-ray の番組マップに言語記述子は無い。言語は
`CLIPINF` にしか書かれていないので、`.m2ts` だけを渡されたデマルチプレクサには
手がかりがない。その結果、一覧では `eng` と `jpn` と出ているディスクを切ると、
区別のつかない音声トラックが 2 本並ぶ出力になっていた。書き出したトランスポート
ストリームにも無く、そこから作ったディスクのクリップ索引にも無い。索引はストリームを
読み直して作るからだ。そこで、ディスク上の録画を開いたときに
`disc::carry_disc_languages` が PID で突き合わせて埋め、カットが書くマップには
各トラックの ISO 639 記述子が入る。
ストリーム自身が言語を宣言していた場合はそちらが優先される。放送がそう宣言して
いるなら、それはどの索引よりも音に近いところで宣言している。

### トラックは PID で示す

選択ダイアログは**何も開かないうちに**答えを出す。一方、ストリーム番号は libavformat
が録画を読んで初めて作られるものである。そこで、答えは PID の並びとして持ち回り、
実際にストリームを開く側、つまりその行を開いたときの編集画面と、書き出すときの
バックエンドで解決する。

PID は 2 本以上のストリームを指すことがある。Blu-ray のロスレス音声は、AC-3 を内側に
畳み込んだ TrueHD として**ひとつの PID に**乗ってきて、libavformat はそれを別々に渡す。

```
stream|index=1|codec_name=truehd|channels=6|id=0x1100
stream|index=2|codec_name=ac3   |channels=6|id=0x1100
```

そのトラックを外すというのは、両方を外すということである。PID で指定していれば
そうなるが、ストリーム番号で指定していたら片方だけを外すことになっていた。

**1 つの PID から書き出すのは 1 本目だけ**なのも同じ理由である。カットは各ストリームを
到着した PID へ書き戻すので、2 本のストリームが 1 つの PID を共有することはできない。
マルチプレクサにそれを指示すれば、次のように表示して止まる。

```
[mpegts] Duplicate stream id 4352
Error: Invalid argument
```

PID の 1 本目は番組マップが挙げたストリームで、その後ろに来るものは demuxer が
そこから切り出した断片である。だから TrueHD を書き出し、内側に畳み込まれていた AC-3 は
落とす。TrueHD の素ストリーム単体は、プレーヤーがデコードできるトラックである。
落としたことはトラックメニューとコマンドラインの出力で言う。

```
        not carried: a compatibility stream folded into the track written on pid 0x1100
```

選択ダイアログの答えが効くのは、編集画面が答えを出すまでである。あちらのトラックメニューは
ストリーム番号を編集内容に書き、その瞬間から編集内容がその行を代表する。そうしないと、
編集画面で戻したトラックが、誰も録画を見ないうちに出された答えによって出口でまた
外されてしまう。

### ディスクが持っている音声

放送の録画が持っているのは AAC だけである。ただしフレーミングは 2 種類ある。HD 録画は
ADTS の MPEG-2 AAC で、ストリーム種別は `0x0F`。4K 録画は LATM の MPEG-4 AAC で、
種別は `0x11` である。一覧の行はそのどちらかを名乗る。どちらであるかは、カットの
境界のフレームをどう書くかを決める。
[もう一つのフレーミング](audio.ja.md#もう一つのフレーミング-latm4k-録画)に詳しい。
4K レコーダーは標本周波数の欄に `15` を書く。索引が名乗れるレートのどれでもないので、
行はレートを言わない。何ヘルツで走るかはフレームが持っており、録画を開けば
トラックの行が 48 kHz と言う。

ディスクはそれ以外に 5 種類を持ってきて、そのどれもが書き出しでは別々の問題になる。

| ディスク上 | カットがすること |
|---|---|
| **LPCM**（`pcm_bluray`） | TS へはそのままコピーし、**スマートレンダリングもする**。LPCM にはエンコーダ遅延も窓の重なりも無いので、境界が落ちたフレームは向こう側を無音にして書き直すだけで済み、ほかは何も動かない。MP4・MKV へはビッグエンディアンの PCM として書く（`ipcm`、QuickTime なら `twos` / `in24`）。素材と同じビット幅である。どちらのコンテナにも Blu-ray のフレーミングを入れる箱が無いからである |
| **DTS**・**DTS-HD**・**DTS-HD MA** | どのコンテナへもバイト単位でそのままコピーする |
| **TrueHD** | バイト単位でそのままコピーする。同じ PID に畳み込まれた AC-3 コアは抜く（上記）。MP4 では 2 つの妥協が要り、そう表示する。`mlpa` の箱は規格外であり、トラックはストリーム自身の同期点から始めなければならない（測った素材では頭が 13 ミリ秒ほど遅れる） |
| **E-AC-3** | そのままコピーする |

**ロスレス音声を再エンコードすることはない。** libavformat が持っている DTS と
TrueHD のエンコーダはロッシーなコアだけを書き、ロスレスたらしめている部分を落とす。
境界フレームを「差し替え」たら、それは切り詰めではなくトラックに開いた穴になる。
だから全再エンコードを指定されても、ダウンミックスを指定されても、実行も失敗もせず、
受け付けないうえでその旨を表示する。ダウンミックスは名前を変えただけの再エンコードである。

**LPCM を MP4 に入れても何も失われない。** サンプルは 32 ビット浮動小数点を通るが、
その 24 ビットの仮数は Blu-ray LPCM が運べる値をすべて表せる。そして Blu-ray の
LPCM は 24 ビットより深くならない。MP4 から出てくるのは入れたものと 1 サンプルも
違わない。変わったのは周りの箱だけである。

ストリーム種別はディスク自身のものである。libavformat の TS マルチプレクサは、この
3 つを知らない。LPCM を書けと言われれば「private data」と宣言し、E-AC-3 を書けと
言われれば Blu-ray の `0x84` ではなく ATSC の `0x87` を持ち出す。ただし `.ts` として
書いたカットは[録画自身のテーブル](broadcast-ts.ja.md)を保つので、番号はそちらから
来る。

### ディスクが描く字幕

放送は字幕を**書く**。ARIB の字幕文は 1 パケットに 1 つの時刻で収まっていて、
カットを越えて運ぶとは 1 パケットを運ぶことである。ディスクは**描く**。運ばれるのは
**ディスプレイセット**である。どこに何を置くかという composition、window、パレット、
そしてランレングス圧縮された画像そのもので、その一つひとつが自分の時刻を持った
PES パケットである。

```
PCS  WDS  PDS  ODS  END      字幕が出る
PCS  WDS  END                そしてしばらく後、面が消される
```

つまりパケットは字幕と同じように時刻を持ち、同じように運べる。違うのは時刻が
**まとまり単位**に付いていて、まとまりは半分では意味を持たないことである。違いは
それだけで、規則にすると 3 つになる（[`pgs.rs`](../../rust/crates/core/src/pgs.rs)）。

1. **ディスプレイセットは丸ごと運ぶか、まったく運ばないか。** 範囲の終わりを
   またぐものは置いていく。意味を与える composition のないまま断片だけが届いても
   仕方がない。
2. **範囲が開く瞬間に出ている字幕は、もう一度出し直す。** それを描いたセットは
   カットの手前の素材と一緒に置いていかれている。そこでカットは各範囲の手前 8 秒を
   読み、単独で成立する最後のディスプレイセットを覚えておいて、範囲の最初のフレーム
   でもう一度送る。エポックの先頭だと書き換えて送る。この出力にとっては、実際そう
   だからである。
3. **範囲が終わる瞬間に出ている字幕は、下ろす。** 消しに来るはずのセットはカットの
   向こう側の素材にある。消去は、出ている composition から object を取り除いて番号を
   1 つ進めたものであり、ディスクが面を空けるときに送っているものと同じである。

手前 8 秒を読むのは 2 と 3 のためで、どれだけ読めば足りるかはディスクの振る舞いが
決める。あるディスクの本編 30 分を測ると、ディスプレイセットは 1334 個。うち 386 個が
エポックの先頭、561 個が**アクイジションポイント**、387 個が面の消去である。
アクイジションポイントは、途中から再生を始めたプレーヤーのために同じ字幕を丸ごと
送り直したものだ。1 つの字幕が出ている時間は中央値 2.3 秒、最長は 116 秒。
それでも単独で成立するセットの間隔は 2.8 秒を超えない。どれだけ長く出ていようと、
このディスクは送り直し続けている。8 秒はそれを何度も含み、
送り直しをまったくしないディスクでも、いちばん長く出ている
字幕以外は拾える。読む費用は 1 範囲あたり 1 秒ほどで、図形ストリームを持つ録画で
しか発生しない。

**どこへ出せるか。** Blu-ray 自身の枠組み（`.m2ts`）へは出せる。libavformat が
プレーヤーの期待する種別を書く。素の `.ts` へも出せる。ただしマルチプレクサは
種別不明の private data として書き、それを読み戻すと何もかもが `bin_data` になる。
運ばれ、宣言され、そして見えない。そこでマルチプレクサの地図の上に書き直す地図が
`0x90` と言い、番組を HDMV として登録する。[ディスクの LPCM](#ディスクが持っている音声)
に必要な訂正と同じもので、同じパスで行う。MP4 へはそもそも出せず、そう言われる。
そのうえで、もう一つの答え、つまり中ではなく
[別ファイルに書く](#ディスクの字幕を焼き込むか別ファイルにするか)ことを提示する。

メニュー（IGS）は同じ種類のストリームで仕事が違う。ボタンには状態と飛び先があり、
どちらもカットが今ばらしたばかりのタイムラインを指している。こちらは置いていくことを
伝えるためだけに一覧に出す。

**編集画面のプレビューにも出せる。** 運ぶのとは別の問いで、いま画面に何が出ている
のかを知りたいときのものである（`subs.rs`）。ここは libavcodec が復号できる。
PGS も DVD のサブピクチャも、返ってくるのは 1 ピクセル 1 バイトの索引と色の表で、
[`vobsub::drawn_from`](../../rust/crates/core/src/vobsub.rs) が両方をひとつの形に
まとめている。それを字幕自身の矩形に切り詰めた PNG にして、ウィンドウが画面の
同じ場所に重ねる。DVD のパレットはストリームに無いので、ここでもディスクの管理情報から
読む（[下記](#ディスクの字幕を焼き込むか別ファイルにするか)）。放送の文字字幕を読む仕組みは
[放送 TS](broadcast-ts.ja.md#字幕を読んでプレビューの上に出す) にある。

### メニューはストリームではなく、それを知っているのは索引だけである

Blu-ray が積んでいるもののうち 2 つは、ディスク自身の索引だけが名前を知っていて、
どちらも置いていく（[`disc.rs`](../../rust/crates/core/src/disc.rs)）。

| | |
|---|---|
| **メニュー**（`0x91`、IGS） | インタラクティブグラフィックス。画像と、状態と遷移コマンドを持つボタンである。コマンドはカットには存在しないプレイリストやタイトルを指しており、composition はカットが今ばらしたばかりのプレイリストの時計で時刻を持っている |
| **テキスト字幕**（`0x92`、TextST） | 書式付きのテキスト。その書体はストリームの中ではなくディスクの `AUXDATA` にあるファイルである。カットに持ち込んでも、描けるものが何も無いテキストになる。そして描こうとするものも無い。libavcodec は `hdmv_text_subtitle` というコーデック ID を持っているだけで、その後ろにデコーダは無い |

**この PID に何が乗っているかを demuxer に訊けば答えは返ってくる。ただしそれは
当て推量である。** ここで測ったディスクでは、`0x1400` のメニューが **MP3 音声**
として返ってきた。映像も本物の音声も持っているクリップで、である。それを信じた
カットは、メニューを音声と宣言して出力に書き込んでいたことになる。助かったのは、
同じプローブがその推量に添えるサンプリング周波数を見つけられず、周波数の無い
トラックは数行後に外されるからで、しかもそのときの注記は「pid 0x1400 の音声」と
呼んでいた。

そこで索引に答えさせる。索引がこの 2 つのどちらかだと言う PID は、プローブが
入れようとしたどの一覧からも外し、実際に何であるかで名前を付ける。

```text
audio  : pcm_bluray 48000Hz 2ch  jpn  main   [stream 1 pid 0x1100]
        not carried: a menu on pid 0x1400
```

**メニューだけ**のクリップは、何かが欠けた録画として失敗するのではなく、そうと言う。
ディスクのメニュークリップは実際そうで、グラフィックスだけで映像が 1 枚も無い。

### マーク

チャプターマークは**信用できるときだけ**読む。マークの並びは節の長さから分かるが、
その中で何がどこに座っているかは方言によって違う。BDMV のマークは 14 バイトで、予約
1 バイト・種別・属する PlayItem・時刻が入る。レコーダーの BDAV のマークはもっと長く、
名前とサムネイル参照を時刻とともに持つ。そこで配置は決め打ちにしない。候補をそれぞれ
試し、**全部のマークが、自分が属すると言っているクリップの中に落ちる**ものを採る。
どれも落ちなければマークは出さない。見当違いの場所にあるチャプターは、チャプターが
無いことより悪い。

**マークがどの PlayItem のものか**を読むことが、「全話連続再生」を使えるものにしている。
それが無ければ、どのマークも下に時計のない数字でしかない。5 話目のチャプターは 5 話目
自身のタイムライン上にあり、1 話目のそれとは「どちらも 11 秒あたりから始まる」以上の
共通点がない。どのクリップのことか言えない配置は、クリップを 1 本しか再生しない
プレイリストでだけ信用する。そうしなければ全話のチャプターが 1 話目に積み上がるが、
それなら 1 個も置かないほうがましである。

行のマークをいちばん**短い**プレイリストから取るのも同じ理由である。ディスクは
1 つの話数を、専用のプレイリストでも「全話連続再生」の中でも指していて、
どの話数のことか知らずに読めるのは前者だけである。

### マークはキーフレームになる

ディスクから開いた録画は、そのチャプターが最初からカット編集画面に並んでいる。
日本のレコーダーのチャプターは CM の境目そのものであることが多く、それは
[CM 検出](../user-guide/cm-detection.ja.md)が数分かけて探しているものを、録画した
機器が正確に書き残したものである。

1 つだけ食い違うのが**時計**である。プレイリストはストリーム自身の 45 kHz で数えて
いるのに対し、編集画面が描くタイムラインはコンテナの開始時刻を原点に取り直してある。
そのため、マークの置き場所は次の式で求める。

```
entry.start + mark - src.start_time
```

`entry.start` はプレイリストの IN 点で、まさにこのためにマークと一緒に持ち回る。
ディスクを読む側は `start_time` を知らない。それはストリームを開いて初めて分かる。
だからマークは読んだ場所で時刻に直さず、行と一緒に編集画面まで運ばれる。

マークを置くのは**初めて開いたときだけ**で、録画と同じ名前の `.keyframe` があれば
そちらが優先される。`.keyframe` は人が出した答えであり、ディスクのマークは誰も答えていない
ときの初期値だからである。素材の範囲外に落ちるマークは、丸め込まずに捨てる（理由は
上と同じ）。GUI を開かずに時刻を確認したいときは、`smartcut <ディスク> --title N` が
そのまま印字する。

## ディスク自身の索引

**Blu-ray はもうそのパスを済ませている。** すべてのストリームの隣、
`CLIPINF/000NN.clpi` に、プレーヤーが再生を始められるピクチャの位置が、表示時刻と
ファイル中のパケット番号として書かれている。それは
[パケットを走査するパス][packetscan]が録画を丸ごと 1 回読んで作る一覧と同じものだ。

だから読む。`disc::entry_points` がマップを解釈し、`index::DiscIndex` が
[`IndexSource`] として差し出す。そのための継ぎ目は初めから用意してあった。
ここで計った UHD ディスク、1 クリップ 81 GB・2 時間 34 分では、タイトルを開くのに
**8 分 45 秒かかっていたものが 1 秒未満**になり、出てきた計画はセグメント単位で
走査版と一致した。

マップは 2 枚の表でできている。**粗い**エントリが時刻の上位とパケット番号の
上位を持ち、残りを埋める**細かい**エントリの先頭を指す。だから 1 点の時刻は
両者を組み合わせて得る。配置は `libbluray` が読んでいるものと同じで、規格の
記述に出てこない点がひとつある。ストリームごとのマップは、自分の細かい表への
4 バイトのオフセットで始まり、粗い表はその後ろから始まる。

**そして粗いエントリは、正しい上位を持っているとは限らない。** 細かいエントリが
持つパケット番号は 17 ビットで、131,072 パケットごとに一周する。録画にすると
20 秒ほどで、一周するたびに粗いエントリが 1 つ書かれる。ここで測ったレコーダーの
ディスクのうち 1 クリップで、そのうち 9 つが一周分古い上位を書いていた。細かい
エントリと組むと、マップが 25 MB 引き返したように読める。後ろの区間の時刻を持つ
9 点が、前の区間の中に入り込む。同じ 4 枚の残り 19 クリップは正常で、測ったプレス
ディスクも全部正常である。エントリーポイントはファイルの中の場所であり、ファイルは
一方向にしか進まない。だから位置が戻るときは、戻らなくなるまで 17 ビットの周を
足す。20 クリップのうち 19 はこれまでと 1 バイトも変わらない。

**古い上位を持つ粗いエントリは、両方のフィールドで古い。** だから時刻も同じよう
に繰り上げる。細かいエントリが持つ時刻は 11 ビットで、2^20 チックごとに一周する。
11.65 秒であり、粗いエントリの刻みの 2 つ分である。粗いエントリが進んでいないと、
時刻はまるまる一周分早く読める。直し方は位置と同じだが、1 つだけ違う。**時刻が
増えるのは 1 つの区間の中だけである。** 何度かに分けて書かれたクリップは区間ごとに
時計を持ち、それが振り出しに戻るのはマップのずれではない。ここのディスクには、
前の区間が終わる 7 秒前から始まる区間がある。だから基準は継ぎ目ごとに捨てる。
時計が戻るマップは読んだままにする。ピクチャと突き合わせて確認した。測った 4 クリップ
のうち 3 つは、3,592 点から 3,615 点の全部が、書いてある時刻にそこにあるピクチャを
指している。直す前も後も同じである。

**4 つ目のクリップは、別の何かを説明しているマップだった。** 1 つの区間、クリップ
の 1 割にあたる 357 点が、指しているピクチャより 6 秒ほど早い時刻を書いていて、位置も
どのピクチャにも当たらない。同じクリップの残り 5 区間は正確である。ここまでの直しは
どれも効かない。ビットのずれが 1 つも無いからである。レコーダーは、そのあと書か
なかった区間のマップを書いた。カットができるのは、その旨を表示することだけである。
エントリーポイントの時刻に届いてピクチャが無かったとき、代わりに始められる最初の
ピクチャがどれだけ先かを表示する。8 秒ずれた読みが、シークの余裕不足と取り違えられないように。

**マップが言えないこと**は、GOP が開いているかどうか、そこにぶら下がる先行
ピクチャを捨ててよいかどうかだ。それはビットストリームの中にあり、どんな索引
にもない。だから点は `leading_known: false` で届き、`index::refine_leading` が
境界の落ちうる点だけを測る。各範囲の両端の前後 20 数点ずつ、1 点につきシーク 1 回と
短い読み 1 回である。範囲の中の全点を測ると（走査版は自分で答えられるので
この関数が走らず、長らく見えていなかった）、あの 1 万 6 千点で 10 分かかった。
つまりディスクの管理情報が何ももたらさない。

ピクチャの重さも言えない。継ぎ足す分は[録画が入ってきたときのレート][splice]
で書くので、誰も数えなかった場合はファイル自身のレートから音の分を引いた値が
代わりに立つ。Blu-ray ではそれで大半が説明できる。非圧縮の音は、ピクチャの次に
重いものだからだ。

[`IndexSource`]: ../../rust/crates/core/src/index.rs
[packetscan]: ../../rust/crates/core/src/index.rs
[splice]: rust-core.ja.md#継ぎ目

## 出力先と名前

ディスクの中には書けない。イメージの中にはそもそもフォルダーが無いし、コピーした
ディスクの中はディスクのものである。だから既定の出力は**ディスクと同じ場所**、名前は
**番組名**になる。

```
/rec/Anime_Test.iso
/rec/cut_2026年08月17日01時00分-衛星第一-サンプル番組 ….ts
```

ファイル名にできない文字（`\ / : * ? " < > |`）は全角に置き換える。日本のレコーダーが
同じ問題に対してしていることと同じで、名前は読めるまま残る。

**コンテナは `.ts` になる。** `.m2ts` を求められた libavformat は、Blu-ray 自身の形、
つまり 192 バイトのフレーミングと Blu-ray 自身の PID 番号で書く。しかしどちらも
マルチプレクサが決めることであり、
[SmartCut が書き戻す放送のテーブル](broadcast-ts.ja.md)
が示している配置とは違う。そこで、ディスクから来た録画について「入力と同じ」は `.ts`
を意味することにしている。中身は同じストリームである。出力設定画面で M2TS を選べば、
これまでどおり M2TS で出力される（そのときテーブルはマルチプレクサに任されることを、
その場で表示する）。

## 名前が 1 本であること

SmartCut は、録画 1 本を**1 つの文字列**で表すことに統一している。一覧が
持つのも、シーク用インデックスとプロキシのキャッシュキーも、出力を同じ場所へ置くときの
基準も、デマルチプレクサに渡すのも、すべてその 1 本である。ディスクの中の録画を
扱えるようにしても、この前提は変えたくなかった。

そこで、イメージの中の録画には**イメージをフォルダーのように綴った名前**を与えて
いる。

```
/rec/Anime_Test.iso/BDAV/STREAM/00001.m2ts
```

これは勝手に作った記法ではない。イメージには本当にその名前のファイルが入っている。
普通と違うのは `/rec/Anime_Test.iso` がフォルダーではなくファイルである点だけで、
[`input.rs`](../../rust/crates/core/src/input.rs) が見ているのはまさにそこである。
パスを遡って**ファイルであるところ**で切ると、3 つの答えが同時に出る。

| | |
|---|---|
| **URL** | `subfile,,start,…,end,…,,:file:/rec/Anime_Test.iso`。libavformat に渡すもの |
| **ファイル** | `/rec/Anime_Test.iso`。OS に問い合わせるもの。キャッシュが大きさと更新時刻で判断できる |
| **範囲** | そのバイト範囲。libavformat を通さず自分で TS を読む処理のため |

3 つ目が必要なのは [`si.rs`](../../rust/crates/core/src/si.rs) である。放送自身の
テーブル（PAT・PMT・SDT・EIT・SIT）を読む処理はファイルを直接舐めるので、**イメージの
中の範囲**として開き、なおかつ **192 バイト間隔**でパケットを拾えなければならない。
どちらも入ったので、ディスクから切った出力にも放送のテーブルがそのまま乗る。

### 時計が途中で戻るクリップ

レコーダーは録画を止めては再開する。止めるたびに、次に書く区間は**新しい
シーケンス**として自分の時計を持つ。それが 1 本の `.m2ts` に全部入る。ここで
測った BD-RE は 1 クリップに 5 本、6 本、7 本を持っていた。プレイリストははっきり
そう書いている。シーケンス 1 本につきプレイアイテム 1 つで、IN と OUT が
どのシーケンスの時計の上にあるかも書いてある。

丸ごと読むと、このファイルは誰も知らせないまま読めなかった。エントリーポイント
マップは 3,598 点あり、バイト位置は最後まで増え続けるのに、**時刻は 2 回戻る**。
4 点目で 7.1 秒から 1.1 秒へ、最終点でもう一度。時刻が場所を指さなくなる。
libavformat はこのファイルの長さを測ることを諦めるので、`--keep` は
「長さ 0 の録画より後ろから始まっている」と全部断られていた。ストリームが
壊れているわけではない。先頭から読めば最後までデコードできる。

**そこで、読みながら時計をつなぎ直す。**
[`restamp.rs`](../../rust/crates/core/src/restamp.rs) がそれで、つなぎ方の全部が
ここにある。各区間をファイルが持っている順に 1 本の時間軸へ並べ、その差分を
区間の中の全タイムスタンプに足す。提示時刻は PES ヘッダの決まった 5 バイト、
プログラムクロック参照はアダプテーションフィールドの決まった 6 バイトなので、
**何も動かないし長さも変わらない**。クリップ自身のエントリーポイントマップは
元の場所を指したままだし、シークインデックスも同じバイトを指す。
デマルチプレクサが読むのは、端から端まで 1 本の時計で走るストリームになる。

状態も持たない。あるバイトがどの区間に属するかは位置だけで決まるので、
補正値はパケットの位置から求まる。これがシークを成立させている。libavformat は
どこへ飛んでもよく、着いたパケットは先頭から読んだときと同じだけ補正される。

区間をどこへ置くかは 2 つの手がかりを突き合わせて決める。どちらも単独では足りない
からである。
**シーケンス表**はその区間が提示する範囲を書くが、それはプレイアイテムが
再生する範囲であってファイルが持っている範囲ではない。測ったクリップでは
892.94 秒と書いてあり、ピクチャは 894.5 秒まで続いていた。レコーダーはグループの
末尾まで書いて、その内側で編集する。**エントリーポイントマップ**はピクチャの位置を
知っているが、プレーヤーが再生を始められる場所しか知らない。両端でグループ 1 つ分
足りない。ただしマップからは速度が出る。この区間の 1 秒が何バイトかである。
最後のエントリーポイントから区間の終わりまでのバイト数をその速度で読めば、
どれだけ続くかが出る。どちらの証言も却下しない。区間を広く言った方を採る。
そうすればプレイアイテムが再生する範囲が外に出ることはない。先頭の区間は
動かさない。先頭から読んだクリップはこれまでと同じ時刻で読める。

**どちらの手がかりも、再生される範囲の外側までは届かない。** プレイアイテムの
IN はピクチャである。その瞬間の音は 1、2 フレーム手前から始まっていて、ファイルは
それを持っている。ピクチャを起点に置き場所を決めると、その音は前の区間の終わりより
後ろに落ちる。そこはもう出力の時間軸に書き終えた場所なので、カットはそれを
落とす。その瞬間自体は前の区間が埋めているので、落ちるのは 2 度目の
記述であって穴ではない。カットの最後に出る注記はいまそう表示する。以前は録画が
壊れていると言っていた。

**そしてどちらの読みも上限でも下限でもない。** 2 つとも区間を狭く言うので、
置いた結果として区間どうしが重なることがある。ここで測ったクリップでは、
ある区間が 1 つ前の区間の末尾 0.46 秒に食い込んで始まる。そのバイト範囲では、
1 つの時刻が 2 つの区間を指す。だから**あるパケットがどちらの区間のものかは
位置で決める。時計では決めない。** `restamp::Seam` が両方を持つのはそのためで
ある。時刻は計画が切る場所である。範囲は時刻の範囲だからである。バイトは
レコーダーが実際に書いた境目である。

行はクリップ全体になり、名前はもとのままである。

```
/rec/Recording.iso/BDAV/STREAM/00001.m2ts
```

SmartCut のデマルチプレクサは文字列 1 本からしか開かないので、実際に
渡すのはこの名前を `restamp:` の URL で包んで補正表を持たせたものである。
[`input.rs`](../../rust/crates/core/src/input.rs) は自前の libavformat i/o
コンテキストを通して読み、ソースパケット単位で通り道に補正をかける。
`subfile` と `concat` がそのまま効くのはそのためである。

**継ぎ目はカットとして計画する。** 区間の先頭のピクチャは、レコーダーが止まる前の
ピクチャを参照している。それは書かれていない。そのままコピーすると、デコーダは
次に画面を作り直すピクチャまで壊れたものを出す。レコーダーのストリームではそれが
1 分後ということもある。そこで `plan::plan_on` は計画の前に、残す範囲を
継ぎ目で切る。出力の時間軸は詰まる。セグメントが占めるのは書いたフィールド数
であって、元の時刻ではないからである。測った録画では、全体のカットが 5 範囲で
**コピー 99.7%** だった。

そのカットが狙った場所に落ちるには 4 つ必要で、この録画を通しで切るまで
どれも合っていなかった。

- **継ぎ目はカットを指示する側の時計に乗せる。** `input::joins` が答えるのは
  デマルチプレクサ自身の時計で、トランスポートストリームはゼロから始まらない。
  直さないと継ぎ目は毎回その秒数だけ後ろの区間の**中**に置かれる。あるクリップで
  1.1 秒、別のクリップで 5.0 秒だった。手前の範囲は次の録画のピクチャを要求し、
  コピーは本物の継ぎ目をまたいで走った。
- **デコーダには区間を 1 つしか見せない。** 向こう側も渡すと、libavcodec は
  手前の分を捨てる。継ぎ目の後の区間は IDR で始まり、その IDR が「並べ替え待ちの
  ピクチャは出すな」と言う。手前の区間の最後の 1 秒は、完成して順番を待って
  いただけのピクチャごと消える。そこで `cut::reencode_segment` は継ぎ目のバイトで
  供給を止め、そこでデコーダを空にする。待たされていたピクチャはそれで返ってくる。
- **向こう側は継ぎ目ではなく最初のエントリーポイントから始める。** 間にあるのは
  その区間の先行ピクチャで、ファイルの中にそれを解く材料はない。普通の頭として
  計画すると、存在しないピクチャの再エンコードを指示することになってカットが止まる
  （`segment …: no pictures decoded`）。`plan::past_the_seam` が範囲の頭を
  エントリーポイントへ動かす。プレーヤーが再生を始める場所も同じである。
  一緒に録れていた音もそこで捨てる。0.3 秒ほどである。ピクチャより先まで音を残すと、
  範囲の残り全部がずれるからである。
- **読み出しは正しい区間の中から始める。** 継ぎ目の向こうの時刻へは、時刻として
  シークできない。libavformat はバイト位置で時刻を読みながら探すが、継ぎ目を
  またぐと時刻がバイトと一緒に増えなくなる。継ぎ目の直後から始まるコピーは、
  1 つ前の区間の最後のエントリーポイントを先に拾う。ファイルでは手前にあって
  時刻では後ろにある点である。それをシークの行き過ぎと読んで止まっていた。
  着地が継ぎ目より手前になるときは、`cut::seek_into` が継ぎ目のバイトへ
  シークする。

つなぐのは、プレイリストがクリップ全体を説明しているときだけである。クリップが
持つシーケンスの全部を、ファイルが持っている順に、プレイアイテム 1 つずつで
指していること。それ以外はこれまでどおりで、プレイアイテムごとに 1 行、
再生するパケットで指す。DVD のタイトルをセクタで指すのと同じである。

```
/rec/Recording.iso/BDAV/STREAM/00001.m2ts@8960-4605951
```

シーケンスが 1 本のクリップは丸ごと指す。これまでのディスクは全部それだし、
SmartCut が書くディスクもそうである。シーケンス表が表として読めない
クリップも丸ごと指す。シーケンスはクリップの先頭から始まり、前のものより
後ろに並び、全部がファイルの中に収まっていなければならない。

**実測**。レコーダーが焼いた BD-RE 4 枚で、106 行に並んでいた 20 番組が 20 行に
なった。長さは索引のとおり 44:19 から 47:57 で、放送尺の 44:41 と 45:10 に
合う。参照ディスク 4 枚、プレス Blu-ray、DVD は以前とまったく同じに並ぶ。

**カットも 20 本すべて通した。** 書き出せたのは 17 本から 19 本になった。20 本目は[次の節](#区間のマップが別の何かを指している)である。
どちらでも書き出せたタイトルで比べると、出力の映像の最大の穴は 0.751 秒から
0.083 秒に縮む。継ぎ目 1 つの代償はピクチャ 3 枚であって、1 秒分ではない。
出力の時間軸に置けなかったピクチャ 68 枚も 0 枚になる。音の穴は残る。同じタイトルで
0.38 秒と 0.84 秒で、これは新旧どちらも同じである。録画そのものにある穴だから
である。トランスポートストリームはある瞬間の音をピクチャの 1 秒ほど後ろに載せるので、
レコーダーが書き終えた時点でその 1 秒は書かれていない。

**継ぎ目の代償がピクチャ 3 枚で済まないこともある。ここで測った 1 か所は 22 枚である。**
コピーをどこから始められるかは、その入口にぶら下がる先行ピクチャで決まる。そして
それを測る（`index::refine_leading`）のは、**呼び出し側が指定した範囲の境目のまわり
だけ**である。継ぎ目は計画の側があとから作る境目なので、そこで範囲が始まる点は
一度も測られない。ピクチャを読んでいない索引は、どの点も安全だと答える。レコーダーの
ストリームではそうでないことが多い。このクリップを走査すると、5,444 点のうち
**5,440 点が「参照されている先行ピクチャを持つ開いた GOP」**である。
そこからコピーを始めると、デコーダは復帰するまで何も出さない。1 本丸ごとで測ると、
4 つの継ぎ目のうち 2 つは 0 枚、3 つ目が 0.067 秒、**4 つ目が 0.734 秒**だった。
パケットは書かれている。映像が画面に出ないだけである。

継ぎ目でも測った結果に従うのが素直な答えだが、採っていない。この素材では安くない
からである。コピーを再開できるのは**約 18 秒先**で、継ぎ目 4 つなら 72 秒の
再エンコードになる。ほかは 99.7% がコピーのタイトルで、である。`--clean-joins` が
既定オフで提供されているのと同じ取引なので、ここに書き留めておく。

### 区間のマップが別の何かを指している

20 本目はここで止まっていた。上の 4 つとは別の不具合である。継ぎ目は
レコーダーの言うとおりの場所にあり、**エントリーの側**が間違っている。
1 本のクリップの 6 区間のうち 4 番目だけが、指している位置のピクチャより 6 秒早い
時刻を書き、しかも先頭 2 点はさらに 11.65 秒早い。これは細かいエントリが持つ
11 ビットの一周分である。区間の長さも同じだけ狂っていて、ピクチャ 289 秒分に対して
316 秒と書いてある。同じクリップの他の区間も、同じディスクの他の 7 クリップの
3,592〜3,615 点も、すべてストリームと 1/1000 秒で合っている。

どの区間が信用できるかはマップのどこにも書いていないので、**全部に 1 つずつ確認
する**。シーク 1 回と短い読み取り 1 回で済む問いである。**その区間の先頭バイトに
ある最初のピクチャは、先頭のエントリが指しているピクチャか。** 違えばその区間の
エントリは捨て、
ストリームを読んで作り直す。読むのはその区間だけで、クリップ全体ではない
（数百 MB）。そして手前の継ぎ目を、その区間が実際に持っている最後のピクチャまで
引き戻す。
`index::mend_stretches`。

**確認するのは継ぎ目を持つクリップだけ**、つまりレコーダーが焼いたクリップだけであり、
**ストリームから作っていない索引に対してだけ**である。走査した索引は自分が読んだ
ものと食い違えない。20 本のうち発動するのは 1 本の 1 区間で、残り 19 本は
コピー秒数まで以前と同じ計画になる。直った 1 本はコピー 99.8% で書き出せる。
隣のタイトルと同じ値である。

普通の録画には何も起きない。それも測った。放送 TS 3 本、参照 Blu-ray 2 枚、
DVD 2 タイトルのカットは、**バイト単位で以前と同一**である。

## DVD-Video

DVD は Blu-ray と同じ入口から来るが、共通点はそれだけである。だから
[`disc.rs`](../../rust/crates/core/src/disc.rs) ではなく
[`dvd.rs`](../../rust/crates/core/src/dvd.rs) が読む。`disc::read` は両方に訊き、
ディスクを認識したほうが答える。下流に渡るのはこれまでと同じ `Disc`・`Entry`・
`Track` である。

```
$ smartcut documentary-01.iso
disc  : documentary-01.iso
        dvd -- documentary-01
        2 recording(s)

  1  00:59:51.400  documentary-01 1 (1/2)  18 mark(s)
       0x01e0  MPEG-2 720x480 NTSC 4:3
       0x0080  AC-3 2ch 48kHz  ja
  2  00:00:08.342  documentary-01 1 (2/2)  1 mark(s)
```

DVD の性質のうち 3 つが、この読み取りの形を決めている。

### ストリームは 9 本ではなく 1 本である

`VTS_01_1.VOB` から `VTS_01_9.VOB` までは**1 本の** MPEG プログラムストリームで、
ISO 9660 が 1 GB より大きいファイルを扱えなかったために分割されているにすぎない。
ディスクはこれを 0 から数える 1 続きのセクタとして指す。つまりセクタ 536,000 から
始まるセルは、**3 本目**のファイルの 400 MB 目にある。

断片は隙間なく並んでいる。今回対象にしたディスクではぴったり並んでいた。

| | オフセット | 終端 |
|---|---|---|
| `VTS_01_1.VOB` | 24,727,552 | 1,098,182,656 |
| `VTS_01_2.VOB` | 1,098,182,656 | 2,171,582,464 |
| `VTS_01_3.VOB` | 2,171,582,464 | 3,244,935,168 |
| `VTS_01_4.VOB` | 3,244,935,168 | 4,289,400,832 |

だからイメージの中ならタイトルセット全体が**ひと続きのバイト範囲**であり、
タイトルは Blu-ray のクリップと同じく `subfile` 1 本で開く。フォルダーなら断片は
9 個のファイルなので、libavformat の `concat` プロトコルでつなぎ、その外側に
`subfile` を被せてタイトルの範囲だけを取り出す。どちらの場合も、展開もコピーも
しない。

プロトコルを入れ子にするには一言必要になる。最上位で何が許されていようと、
その**内側**のプロトコルは `file` だけを含むホワイトリストで検査される。
`input::demux` は、SmartCut 自身が書いた URL に対してだけ
`protocol_whitelist` を設定し、ただのパスには設定しない。

### タイトルはセルの連なりである

Blu-ray が 1 話に 1 本のストリームを与えるのに対し、DVD が与えるのは 1 本の
ストリームの一区間であり、その位置を語るのは `.IFO` のテーブルだけである。

| テーブル | そこから取るもの |
|---|---|
| `VIDEO_TS.IFO` の `TT_SRPT` | プレーヤーが番号を振る順のタイトル一覧と、それぞれがどのタイトルセットにあるか |
| `VTS_NN_0.IFO` の `VTS_PTT_SRPT` | セット内の各タイトルについて、チャプターである `(チェーン, プログラム)` の組 |
| `VTS_NN_0.IFO` の `VTS_PGCIT` | 各プログラムチェーン。そのセル、長さ、再生するセクタ、各プログラムが始まるセル |
| `VTS_NN_0.IFO` の `VTSI_MAT` | 映像と、セットが宣言している音声・サブピクチャのトラック |

チャプターの位置は、その手前のセルの長さの合計で決まる。つまり、セルが端から端まで
連なっていなければこの計算は意味を持たない。連なっていないチェーンはアングルブロック
か、複数タイトルの断片から組まれたものなので、これらは読まない。セルがたまたま収まって
いる範囲はタイトルではないので、それをタイトルとして差し出すくらいなら、何も出さない
ほうがよい。

タイトルがファイルではなく区間である以上、名前がどの区間かを示す必要がある。

```
/rec/documentary-01.iso/VIDEO_TS/VTS_01_1.VOB@0-2081904
```

このセクタ番号はディスク自身のもので、タイトルセットのストリームの先頭から
数えている。`VTS_01_1.VOB` とだけ書いた名前は、ディスクが持つ 4 GB 全部を指して
しまい、どの 1 話も指さない。

### 時計はストリームの側にあり、索引の側にはない

セルの時間は、タイトルの先頭から数えた長さである。プログラムストリームの
タイムスタンプは、オーサリング時のマルチプレクサが始めた場所から始まる。今回のディスク
なら 0.281 秒である。「12 分のところ」というチャプターは、両者を
つなぐものがなければその時計の上の時刻にはならない。

つなぐのはナビゲーションパックである。VOBU は必ずこれで始まる。プレーヤーが
読んで表示しない 2048 バイトで、`VOBU_S_PTM`（後続のピクチャを提示する時刻）と
`VOBU_E_PTM`（それが終わる時刻）を持っている。タイトルの先頭セクタのそれを
読むのは 2048 バイトの読み取り 1 回で、エディタがまさに必要とする数値が
そのまま得られる。DVD の `Entry::start` が索引の推測ではなく実測なのはそのため
である。

**そしてこれが、タイトルが複数の時計をまたいでいることを教えてくれる。** DVD は
別々に多重化された断片からタイトルを組んでよく、その継ぎ目でタイムスタンプは
振り出しに戻る。今回のディスクがまさにそれだった。

```
セル 18 の終わり  323,571,480  (3595.24 秒)
セル 19 の始まり       36,010  (   0.40 秒)
```

2 つの時計を繋ぐのは、1 つを切るのとは別の操作である。Blu-ray で複数クリップの
プレイリストがクリップごとに 1 行になるのと同じ理由である。そこで DVD のタイトルも
継ぎ目で分ける。上のディスクは、18 チャプターの 1 時間と、その隣の 8 秒として出る。
1 行のなかで後半が前半に重なることはない。2 つのセルが同じ連なりに属するのは、後の
セルが前のセルの終わったところから始まるときである。前のセルがどこで終わったかは、
索引が指し示すそのセルの最終 VOBU から読み取る。

このディスクの 2 つのタイトルは、19 セルと、その最後を除いた 19 セルである。
合わせて 3 つではなく 2 つなので、行は指しているストリームの区間で重複を除く。

### プログラムストリームはタイムスタンプを省く

プログラムストリームは、すべてのピクチャに提示時刻を載せるわけではない。前後の
ピクチャから
表示順が割り出せる場合、マルチプレクサはそれを省く。今回のディスクでは 4 枚に 1 枚が
そうだった。

```
pts=31263  dts=22254  K     pts=N/A    dts=31263
pts=25257  dts=25257        pts=34266  dts=34266
pts=28260  dts=28260        pts=N/A    dts=40272
```

ここの処理はすべて提示時刻を鍵にしているので、時刻のないピクチャは捨てられていた。
無劣化コピーの出力からフレームが 4 分の 1 も減る、ということが起きる。
libavformat 自身は時刻を割り出せる（`fflags +genpts` がデコード時刻から並べ直す。
これは正確である）が、ファイルを開く前に指定しなければ動かない。そこで
`input::demux` は、プログラムストリームに対してだけこのフラグを指定する。トランス
ポートストリームはすべてのピクチャに時刻を打っているので、このフラグを付けても何も変わら
ないが、それでも、すべての録画が通る経路に余計なフラグを置くことになるからである。
（開き直す理由はもう 1 つあり、それも同じ考え方による。
[下記](#フレームレートを名乗らないディスク)。）

プログラムストリームがもう 1 つ持っていないのが、**自分の長さ**である。libavformat
はファイルの両端のタイムスタンプから長さを割り出すが、末尾に不連続を含む 4 GB の DVD
では、1 時間のタイトルに対して 8.3 秒と答えてきた。全パケットを読む走査のほうが正しい
答えを持っているので、そちらを `index::Index::end` として報告するようにした。ただし
コンテナ自身の答えのほうが長ければ、そちらを採る。長さを正しく知っているコンテナは、
その答えをそのまま保てる。

### コンテナのシークテーブルは、末尾まで届くだけでなく録画全体を覆っていなければならない

`--index auto` はパケット走査の前にコンテナのシークテーブルを尋ねる。テーブルを
読むのはただで、4 GB を歩くのはただではないからだ。ところがプログラムストリームには
そんなテーブルが無い。libavformat がプログラムストリームに対して返すのは、最初の
数フレームへ辿り着くまでの probe がたまたま索引した分だけである。12 分半のタイトルで
**8 エントリ、先頭 4 秒分**だった。

これを額面どおり受け取ると、索引が無いより悪い。4 秒より後のどこで切ってもコピー元に
できるエントリーポイントが見つからず、タイトルを丸ごと再エンコードすることになる。
`--scenes` は録画中の境界をすべて同じフレームに引き寄せる。

そこで、ただで済む問いをテーブルに投げる。**そのテーブルは録画を覆っているか**。
probe が止まったところで止まっているテーブルは採用せず、代わりに走査が答える。同じカット
が 98.2% をコピーするようになり、シーン一覧は 1 つの繰り返しではなく 249 件になった。

**末尾まで届いているか**だけを問うのでは足りない。1999 年の DVD がそれを見せた。
libavformat はプログラムストリームの長さを、ファイルの末尾へシークしてそこにあるもの
を読んで測る。そしてその 1 パケットも他と同じように索引する。1 時間半のタイトルに対して
残されたテーブルは、**先頭 5 秒に 10 エントリ、そして 5110.9 秒のうち 5110.6 秒に
1 エントリ**だった。末尾には届いている。その間には何も無く、それで通ってしまった。
結果として壊れたのはカットではなく編集画面である。フィルムストリップはエントリー
ポイントの上にセルを描くので、その 1 時間半のどこを開いても描く材料は 2 つしかなく、
キーフレーム送りには送る先が無かった。

そこで穴についても問う。ただし測る相手はテーブル自身の間隔ではなく録画の長さである。
本物のテーブルの間隔は 3 倍どころではなく散らばる。エンコーダが映像の変わったところに
エントリを置くからだ。ここで捕まえたいのは、間隔が不揃いなテーブルではなく空の
テーブルである。**録画の 10 分の 1 より広い穴**が空いているものは、コンテナが
保っていたテーブルではない。

代わりに答えた走査は、4 GB のタイトル全体を **3.2 秒**で読み切った。これがこの順序が
正しいもう半分の理由である。DVD ではテーブルは元々たいして節約しておらず、そのくせ
すべてを台無しにしていた。

`examples/indexdiag.rs` は 3 つの供給元それぞれに別々に尋ね、各々が何と答えるかを
表示する。弾くべきテーブルが通ってしまっていることは、こうして見つかる。早い段階の
供給元が誤った答えを返しても、どこも派手には壊れないからだ。録画は開くし、編集画面は
渡されたエントリーポイントで描かれる。

### DVD の音声は、DVD 以外が名乗らないストリームに入った LPCM である

DVD のリニア PCM は、その枠組みを DVD だけが説明するプライベートストリームに乗って
いる。マルチプレクサが手を伸ばすストリーム種別は「何かのプライベートデータ」で、これで
書き出すと、どの読み取り側もそのトラックを `bin_data` と呼び、無音を再生した。

そこで **Blu-ray の LPCM** として出すようにした。トランスポートストリームがまさに
これらのサンプルのために持っている形である。マルチプレクサが正しく名乗る `.m2ts` と
ディスクは、それだけで直る。素の `.ts` には
[PMT の書き直し](broadcast-ts.ja.md#録画自身の表を書き戻す)が必要で、
そもそも放送でなかった録画には PMT のパスが無かった。今はそれも通る。マルチプレクサ自身が
書いたものを土台に、この 1 点だけ直して、他には何も足さずに組み直す。

### ディスクの字幕を焼き込むか、別ファイルにするか

DVD も Blu-ray と同じように字幕を描く。表示コマンドの付いた、ランレングス圧縮された
画像である。似ているのはそこまでだ。Blu-ray のグラフィックスには TS の
ストリーム種別 `0x90` があり、[カットの中を運べる](#ディスクが描く字幕)。**DVD の
ものには無い。** `.ts` に書き込むと種別不明の private data になり、読み戻すと
どれも `bin_data` になる。運ばれ、宣言され、そして見えない。訂正に使える番号が
存在しない。

そこで行き先は 2 つあり、`--subtitles` が選ぶ。ディスクを切るときに出力設定が
1 行で訊く質問も同じものである:

| | |
|---|---|
| `pgs`（既定） | **カットの中**へ、TS が運べる種類として。Blu-ray のものは無加工で通し、DVD のものは[変換する](#dvd-の字幕を-blu-ray-のものに変換する) |
| `beside` | **カットとは別のファイル**へ、`.idx` と `.sub` の 2 ファイルとして。DVD のものは無加工で置き、Blu-ray のものは[ディスプレイセットから読み戻す](#blu-ray-の字幕を-dvd-のものとして書く) |
| `sup` | **カットとは別のファイル**へ、`.sup` として。コンテナの外に出したディスプレイセットそのもの。Blu-ray のものはバイト単位でそのまま、DVD のものはカットに入れるときと同じ変換を通す（[下記](#sup-ディスプレイセットに何も被せない形)） |

既定が「中」なのは、1 ファイルは 1 ファイルだからである。字幕が中に入ったカットは、
どこで開いても字幕が付いてくる。別ファイルが必要になるのは字幕ツール、古いセット
トップボックス、そして MP4 である。MP4 は何を指定されても別ファイルにしか置けない。

2 ファイルは世の中がすでに読める **VobSub** の形である
（[`vobsub.rs`](../../rust/crates/core/src/vobsub.rs)）:

```text
cut_title.ts     カット
cut_title.idx    字幕が何で、どれがいつ出るか
cut_title.sub    字幕の画像そのもの、無加工
```

再エンコードは一切しない。`.sub` にはディスク自身のユニットが、届いたときの
プログラムストリームの枠組みのまま、1 セクターに 1 つずつ入る。`.idx` は時刻と
ファイル位置のテキストである。プレーヤーはカットを開けば名前でこの 2 つを見つける。

**パレットはストリームの中に無い。** ユニットは「色 4」としか言わず、色 4 が何色かは
言わない。DVD は 16 色を索引の側、それが属するセルの連なりとともに置いている。
そこでカットはディスクに戻ってタイトルが切り出されたチェーンのパレットを読み、
DVD が書いている studio range の輝度と 2 つの色差から変換して、`.idx` の先頭に
書く。これが無いと字幕は偶然にしか読めない。

**残す範囲の両端は整える。** Blu-ray のグラフィックスと同じで、しかももっと単純である。
ユニットが自分の時間割を持っているからだ。範囲が開く瞬間に出ていたものは最初の
フレームでもう一度書き、終わる瞬間に出ているものは「止めろ」とだけ言う 10 バイトの
ユニットで下ろす。ディスク自身が面を空けるときに送っているものと同じである。後半は
省けない。ここで測ったディスクのユニットは、**1 つとして自分では止まらない**。
どの字幕も次のユニットが来るまで出続けるので、途中で終わったカットは出しっぱなしの
まま、下ろしに来るものが無い状態になる。

#### DVD の字幕を Blu-ray のものに変換する

**既定。カットは 1 ファイルであるべきだからである。** DVD のユニットから画像を取り
出して、TS が運べる種類の字幕、つまり Blu-ray のものとして書き直す。そうすれば字幕は
カットの中にあり、開いた読み取り側はどれもそれを見つける。運べるのは TS だけなので、
MP4 を指定された場合はその旨を表示して、代わりに 2 ファイルを別途書き出す。

再サンプルはせず、画素は 1 つも失わない。**2 つの形式は字幕を同じ形で持っている。**
画素ごとのインデックス、そのランレングス符号、そして色の表である。変わるのは
ランの綴り方（一方に 4 通り、他方にも別の 4 通りある）と、色の書き方だけである。
DVD は赤・緑・青とどれだけ不透明かを言い、Blu-ray は輝度・2 つの色差と
どれだけ不透明かを示す。画像を取り出すのは libavcodec 自身のデコーダで（ディスクの
索引から取ったパレットを渡す。これだけはデコーダに分かりようがない）、書き直すのは
[`pgs.rs`](../../rust/crates/core/src/pgs.rs) である。

画素の他に必要なのは時間割で、そこが 2 つの形式の食い違うところである。DVD の
ユニットは、いつ出るかを自分で持ち、いつ消えるかも持っていることがある。Blu-ray の
ディスプレイセットは、どちらも外から指示されないと分からない。そこでここでは 1 つずつ
持つ。新しいものが出れば前のものを置き換え、消える時刻を持っていたものはその時刻に
下ろし、範囲が終わる時点で出ているものはそこで下ろす。[上記](#ディスクが描く字幕)で
範囲の両端を整えたのと同じことを、反対側からやっている。

#### Blu-ray の字幕を DVD のものとして書く

同じ道のりを逆向きに行く。理由も逆で、字幕ツールや、ディスプレイセットなど聞いた
ことのないプレーヤーや、MP4 が読めるのは別ファイルの 2 つだからである。Blu-ray に
`--subtitles beside` を指定すると、ディスプレイセットを 1 つずつデコードし
（[`pgs::read`](../../rust/crates/core/src/pgs.rs)）、その画像を DVD のユニットとして
書き直す（[`vobsub::unit`](../../rust/crates/core/src/vobsub.rs)）。

途中で 3 つを作り出さなければならない。DVD の形式が持っていて、Blu-ray の形式が
2 ファイルで必要になる場所に持っていないものである。

**16 色のパレット。** DVD のものはディスクの管理情報にある。Blu-ray のものは
ディスプレイセットごとに入っていて、毎回違い、多いときは 256 色ある。そこで字幕が
通り過ぎるたびに 16 色を組み立てる。各字幕の色を `.idx` が呼ぶ番号の下に書き留め、
**すでに書いた色に十分近い色はその色にする**。字幕の 4 色はそれが描かれた色の平均で
あり、同じ白い文字でも 1 行ごとに平均は一段ずれる。来たとおりに書き留めていたら、
1 本の映画の白だけでパレットを使い切る。16 が埋まったあとは、いちばん近い色が
17 色目の代わりになる。

**字幕あたり 4 色。** DVD のユニットは 1 画素 2 ビットで、16 色のうち 4 つ、背景・
パターン・エンファシス 2 つを挙げる。これはまさに字幕を成すもの、すなわち
「何も無い」と文字と縁とその間のぼかしである。Blu-ray のアンチエイリアスされた文字は
それが 30 段階で届くので、実際に描かれている色を、各色が画像のどれだけを占めるかで
重み付けして 3 つにまとめる。**使用量の多い順に 3 つ、ではない。** 文字の内側の
階調は縁より多く使われるので、数だけで選ぶと白が 3 つ取れて縁が消える。そこで最初の
中心はいちばん多い色、それ以降は「すでに選ばれた色からの距離 × 占める量」が最大の色
とし、あとは普通に収束させる。4 回まわす。数十色を 3 つにまとめるにはそれで足りる。

**それぞれがどれだけ出ているか。** ディスプレイセットはそれを言わない。字幕を下ろす
のは後から来る別のセットである。ユニットの方は言える。止める側のシーケンスがそれで
ある。そこで 1 つずつ手元に留め、それを終わらせるセットが来てから、遅延を埋めて書く。
留めずに出しっぱなしにしても、DVD 自身の規則に従うプレーヤーでは正しく出る。だが
libavcodec の上に建っているもの、つまりほとんどのものにとっては、長さゼロの字幕に
なる。1 セット待つことが、その一方をもう一方に変える。

範囲の両端に新しい仕掛けは不要である。ここに届くのは、どちらにせよディスプレイ
セットだからである。運ばれてきたもの、範囲の頭でもう一度出したもの、範囲の末尾で
面を空けるために書いたものである。
[上記](#ディスクが描く字幕)の手当てがそのままここの手当てであり、
範囲の末尾で面を空けるセットが、最後のユニットの「止め」を埋める役をする。

制限が 1 つあり、それは形式のものである。**ユニットは自分の長さを 2 バイトで言う**
ので、1 つは 65535 バイトまでしかない。文字 1 行はランレングス符号で数キロバイト
なので届かない。全画面の画像は届きうるので、入らなかったものはプレーヤーが受け付け
ないものを書く代わりに、数えて報告する。

#### `.sup`: ディスプレイセットに何も被せない形

3 つ目の行き先であり、Blu-ray の字幕を**まったく変換しない**唯一のものである。
`.sup` とは、ディスプレイセットをコンテナの外に出したときの姿である。届いたままの
セグメントが 1 つずつ、いつデコードしていつ出すかを示す 10 バイトを頭に付けて並ぶ
（[`pgs::Sup`](../../rust/crates/core/src/pgs.rs)）:

```text
"PG"  pts  dts  type  length  [ セグメント ]
 2     4    4    1      2
```

形式はこれで全部である。だから Blu-ray の字幕はバイト単位でそのまま出てくるし、
BDSup2Sub も Subtitle Edit も、ディスクの字幕を扱うものは何も教えなくても読む。
DVD の字幕はカットに入れるときと同じ変換（[上記](#dvd-の字幕を-blu-ray-のものに変換する)）
を通り、ストリームではなく `.sup` に着地する。**DVD の字幕を 4 色に潰さずに
`.mp4` と並べて置ける**のはこの方法である。

ここに届くのは 2 ファイルの側に届くのと同じディスプレイセットであり、カットが運ぶ
のとも同じものである。だから残す範囲の両端の手当ては[上記](#ディスクが描く字幕)の
ままで、ここは何も知らなくてよい。

2 ファイルとの違いが 1 つあり、それは形式のものである。**`.sup` は 1 ストリーム
しか持てない**。`.idx` はディスクが持っていただけの本数を書ける。字幕が 2 本ある
録画は 2 ファイルになり、それぞれがディスクの言う言語を名前に取る
（`cut_title.eng.sup`）。ディスクが言語を言わないとき、あるいは 2 本が同じことを
言っているときは、乗っている番号が代わりに入る。

読み取りについて 2 つ、どちらも半日を費やしたので書いておく。

* **DVD の字幕は、録画のストリーム一覧にそもそも出てこないことがある。** 音声と
  1 本のストリームを共有し、パケットの頭の 1 バイトで区別されるので、libavformat は
  最初の 1 つに出会って初めてストリームを作る。ここで測ったディスクでは 400 MB
  読んだところだった。タイトルを開くのにそこまでプローブするのは割に合わない。
  ディスク自身の索引は最初から知っているので、一覧はそちらから取り、パケットは
  あらかじめ決めた索引ではなく**それが何であるか**で突き合わせる。
* **捨てるのはシークの後。前ではない。** 範囲の手前 8 秒は、映像と音声を
  libavformat の内側で捨てながら読む。それが先読みを安くしている。だが先に捨てて
  しまうとシークがきっぱり拒否される。録画は自分のストリームのどれかを頼りに
  シークするので、捨てたストリームでは辿れない。そして何も読めないコンテキストと、
  字幕なしで静かに開く範囲が残る。

書き込みについても 1 つ。**ストリームはファイルのヘッダが書かれる前に存在して
いなければならない。** 変換したストリームは SmartCut 自身のもので、録画の中に
写す元が無い。これをヘッダが出た後に足したところ、マルチプレクサは初期化していない
ストリームを抱えることになった。その代償はエラーではなく、数フレーム後に、
そのストリームについて警告を出そうとしたマルチプレクサの中でのセグメンテーション違反
である。

### フレームレートを名乗らないディスク

libavformat はプローブしながらフレームレートを割り出すが、そのプローブは
特に指示しなければ最初のプログラムマップで止まる。**VC-1** で書かれたプレス
Blu-ray ではそれが早すぎた。`avg_frame_rate` は未設定のまま返り、フレームレートが
「非数」であれば、そこから導かれる長さはすべて意味をなさなくなる。録画の尺も、
印の位置も、区間が何枚のピクチャを持つかもである。

`scan_all_pmts` はすべてのマップを読むので、これを直せる。常に有効にしていないのは、
SmartCut が読む素材に特有の事情があるからである。日本の放送でこの徹底した読み方を
すると、トランスポートストリームが載せている**2 番目の番組**まで拾ってしまう。同じ
素材の携帯向けの複製が、別の pid に載っているのである。それは頼まれた録画とは別の
録画である。そこで `input::demux` はまずコンテナに問い合わせ、答えが返ってこなかった
ときだけ開き直す（`states_frame_rate`）。`+genpts` で開き直すときと同じ考え方で
ある。

## 何をしていないか

| | |
|---|---|
| **暗号化ディスク** | 対象外。AACS の復号は一切扱わない。暗号を外すツールで複製された市販ディスクは、他のディスクと同じように読める |
| **ディスクとして書き出す** | 未対応。オーサリングであり、別の問題である |
| **複数クリップの結合** | 未対応。クリップごとに 1 行として見せている（上記） |
| **BDMV のタイトル** | `index.bdmv` が並べるのはタイトルで、タイトルはナビゲーションのプログラムである。「T05 Extra 01」がどのプレイリストかは解決していない。行の名前はディスク名とクリップ番号 |
| **EP マップが読めないクリップ** | マップがあればそれを使い（[ディスク自身の索引](#ディスク自身の索引)）、無ければパケット走査が答える |
| **BD 固有のストリーム** | PGS の字幕は TS に運ぶ。ディスプレイセット単位で運び、各範囲の両端を整える（[上記](#ディスクが描く字幕)）。指定があればカットとは別のファイルに書く。VobSub の 2 ファイル（[上記](#blu-ray-の字幕を-dvd-のものとして書く)）か `.sup`（[上記](#sup-ディスプレイセットに何も被せない形)）で、ディスクを MP4 に切って字幕を残す道はこれである。IGS（メニュー）と TextST（テキスト字幕）は落とし、落としたと表示する。理由は[上記](#メニューはストリームではなくそれを知っているのは索引だけである)。音声はすべて運ぶ。LPCM・DTS-HD・TrueHD・E-AC-3 である（[上記](#ディスクが持っている音声)）。VC-1 の映像は読み、一覧に出し、カットもできる。部分 GOP は[自前のエンコーダ](rust-core.ja.md#エンコーダのないコーデック-vc-1)が書く |
| **DVD のサブピクチャ** | TS が運べる種類に変換して中に入れる（既定）か、無加工のまま VobSub の 2 ファイルとして別に書くか、変換して `.sup` として別に書くかである（[上記](#ディスクの字幕を焼き込むか別ファイルにするか)）。そのままの形で中には入れない。TS にそのストリーム種別が無いからである |
| **DVD のアングル** | セルがアングルブロックまたはインターリーブユニットになっているチェーンは出さない（[上記](#タイトルはセルの連なりである)） |
| **DVD として書き出す** | DVD タイトルのカットは TS になる。DVD の形とは、大きさに上限のある VOBU、その先頭ごとのナビゲーションパック、全セルを記述する `.IFO` のことであり、それはオーサリングという別の問題である |
| **暗号化された DVD** | AACS と同じく対象外。CSS の復号は一切扱わない |

## 検証

実素材のディスクと、そこから作った合成素材とで確認している。

**実素材の BDAV。** TMSR6 が書いた BDAV を ImgBurn が UDF 2.60 の ISO にしたもの
（3.4 GB、3 クリップ、1920x1080 MPEG-2 + AAC + ARIB 字幕、部分 TS）。3 件の番組名が
すべて正しく読め、バイト範囲は独立に書いた Python の UDF リーダーと一致し、切り出した
60 秒は 99.2% 無劣化で、放送自身のテーブル（PID 0x1100 / 0x1101 / 0x1102、SIT 0x1F）が
そのまま乗った。**同じクリップをフォルダーに取り出して同じ範囲を切ると、出力は
md5 まで一致した。**

**実素材の BDMV。** 12 話 1 期を MakeMKV でバックアップし、ImgBurn が UDF 2.50 の
ISO にしたもの（33 GB、45 プレイリスト、328 PlayItem、62 クリップ）。ディスク名は
`META` から読め、62 行は重複なしで出て、最初からチェックが入ったのはちょうど 12 話で、
各話は自分のプレイリストが書いた 4 つのチャプターを持つ。バイト範囲は `subfile` 経由で
開いて demux できた。0x1011 の H.264、0x1100 / 0x1101 の TrueHD（AC-3 込み）、
0x1200 / 0x1201 の PGS である。1 話を 10 秒切り出したところ 91.8% がコピーで、
TrueHD 2 本ともそれぞれの PID に乗り、全サンプルがデコードできた。

**UHD ディスクの字幕をカットを越えて運ぶ。** 2160p 本編（HEVC、LPCM 5.1、
0x1200 の PGS）から 60 秒を切り出し、4 つある境界のうち 3 つが字幕の途中に落ちるように
2 範囲でカットした。範囲の中のディスプレイセットは composition 番号もそのままに
44 パケットが向こう側へ出て、ディスクがそこへ送っていないパケットが 11 本書かれた。
2 つ目の範囲が開く瞬間に出ていたセット 5 本（最初のフレームで出し直したもの）と、
2 つの範囲の消去 3 本ずつである。読み戻すと `.m2ts` でも素の `.ts` でも 0x1200 は
`hdmv_pgs_subtitle` と名乗り、デコードして焼き込むと、継ぎ目の次のフレームには
前の範囲の行ではなく新しい範囲の行が出ており、字幕の途中で開く範囲の先頭フレームには
その字幕が出ており、ファイルの終わりに出しっぱなしのものは残っていない。BDAV
フォルダーへ書くと、クリップ索引はこのストリームを coding `0x90` として並べる。実物の
ディスク上のパスで開けば、地図が何も言わない言語が `CLIPINF` から出てくる（`jpn`）。

続けて、ディスクそのものから 10 秒を、半分が再エンコード、半分がコピーになる形で
切り出した。81 GB のクリップを、自前のエントリーポイントマップ経由で開いたものである。
**範囲の中のディスプレイセットは 1 つ残らず順番どおりに出た**。再エンコード区間と
コピー区間の継ぎ目の 66 ミリ秒手前で始まり、継ぎ目の向こうで終わるセットも含めて、
運んだのは 39 パケット、書いたのは 8 パケットである。このセットこそ、ディスプレイ
セットを読みかけているあいだセグメントが自分の終端を越えて読み進める理由であり、
「終端を過ぎたか」をパケットが持つ 2 つの時刻の早いほうで判断する理由でもある。
セットは表示される少し前に**送られる**ので、セットの先頭のパケットは、表示時刻が
いちばん先にあるパケットになる。

**DVD の字幕をイメージから運び出す。** 4.1 GB の `.iso`、タイトルセット 1 つ、
`0x20` に日本語のサブピクチャ。libavformat はこれを 400 MB 読むまで見つけない。
本編から 2 範囲を切り出すと、別ファイルに 11 ユニットが出た。範囲の中でディスクが送った
9 つ、2 つ目の範囲が開く瞬間に出ていて最初のフレームで書き直された 1 つ、そして
1 つ目の範囲を終わらせる停止である。読み戻すと `ffprobe` は 2 ファイルの中に
`dvd_subtitle` を 1 本見つけ、短いカットではユニット 2 つとも読めた。カットに
焼き込むと、継ぎ目の次のフレームにはその瞬間ディスクが出していた行が、
`VTS_02_0.IFO` から取ったディスク自身の色で出ている。外すよう指示すれば、
書かれるのは `.ts` だけになる。

**同じ字幕を変換したもの。** 同じ 2 範囲を `--subtitles pgs` で。9 つの字幕が
ディスプレイセットとして入り、`.ts` では `0x20`、`.m2ts` では他のストリームと同じ
ように `0x1200` に振り直された。`ffprobe` はどちらからも `hdmv_pgs_subtitle` として
読み戻す。素の `.ts` でそうなるということは、マルチプレクサの地図の上に書いた地図が効いて
いるということである。焼き込むと、継ぎ目の次のフレームには別ファイルの 2 つが
出していたのと同じ行が、同じ色で出ている。

**Blu-ray の字幕を 2 ファイルとして書く。** 1080p 本編（H.264、LPCM、`0x1200` の
PGS）から 20 秒の範囲を 2 つ、2 つ目が字幕の途中で開くように取った。別ファイルに出た
ユニットは 11 個。範囲の中でディスクが描いたものが 10 個と、2 つ目の範囲が開く
瞬間に出ていた 1 個を最初のフレームで書き直したものである。**両端に余りは出ない。**
範囲の末尾で面を空けるディスプレイセットが、自前のユニットを足す代わりに最後の
ユニットの「止め」を埋めるからで、1 つ目の範囲の最後の字幕は範囲が終わる瞬間に
止まっている。読み戻すと `ffprobe` は 2 ファイルから 1920x1080 の `dvd_subtitle`
を 1 本見つけ、すべてのユニットをデコードでき、そのどれもが自分の表示時間を持っている。
作り出したパレットは 2 範囲で 6 色、同じ本編の 3 分で 13 色になった。

平らな背景に描いて、同じ字幕をディスク自身のディスプレイセットのまま `.ts` に
運んだものと比べると、両者は**色は完全に一致し、輝度で 39.7 dB 離れている**。
Blu-ray のアンチエイリアスを DVD の 4 色に潰す代償はこれで全部であり、画素は 1 つも
動かず、字幕の時刻も 1 つも変わっていない。`.mp4` を指定すれば同じ 2 ファイルが
同じ場所に出る。あのコンテナでディスクのカットが字幕を保つ方法はこれだけである。

**Blu-ray の字幕を `.sup` として書く。** 同じ 2 範囲を `--subtitles sup` で。出た
85 セグメントは、同じカットの PGS を `.ts` に運んで ffmpeg に `.sup` へ詰め直させた
ものと**バイト単位で一致した**。セグメント種別も中身もすべて同じで、時刻の差は
最大 **90 kHz の 6 チック**、67 µs である。カッター自身の時計を秒の浮動小数で一往復
した分に過ぎない。読み戻すと `ffprobe` は 1920x1080 の `hdmv_pgs_subtitle` として
開き、開始位置はカット内の最初の字幕になる。字幕が `0x1200` と `0x1201` の 2 本
あってどちらも `eng` を名乗るディスクでは、`cut.1201.sup` になった。言語では見分けが
付かないので、乗っている番号が入る。範囲の中に 1 つも無かった方は、空のファイルを
残さずにその旨を表示した。DVD に同じ指定をすると、先にユニットを変換して、
そのディスプレイセットを、`.mp4` と同じ名前の `.sup` に書く。

**メニューを音声と取り違える。** UHD ディスクのクリップ 00004。映像と LPCM 1 本、
そして `0x1400` のメニュー。libavformat はこのメニューを **MP3 音声**と呼ぶ。今この
このクリップを調べると、本物の音声 1 本だけを並べ、`not carried: a menu on pid 0x1400`
と表示する。メニューだけの 3 クリップ、つまりグラフィックスだけで映像が無いものは、
映像が無いという失敗ではなく、メニューであると表示する。

もう一方は数えて確かめた。**8 枚のディスク、748 個のクリップ索引**。うち 29 個の
クリップがメニューを積んでいて、**テキスト字幕を積んだものは 1 つも無い。**
`0x92` はどこにも無かった。これが TextST を運ばずに名前だけ付けて置いていく
もう半分の理由である。運ぶものが無く、運ぶ実装を突き合わせる相手も無い。

**VC-1 で書かれたプレス Blu-ray 2 枚。** その年代のディスクの多くがこのコーデックで
あり、この 2 枚で Advanced Profile の違いはほぼ覆える。1 枚は 1920x1080i 29.97、
インターレースフレーム符号化、non-uniform 量子化、全 GOP がクローズド。もう 1 枚は
1920x1080 プログレッシブ 23.976、uniform 量子化、全 GOP がオープン、skipped ピクチャ
あり、強いフィルムグレイン。どちらも読み、一覧に出し、GOP 途中から GOP 途中まで
10 秒のカットを行った。**308/308 と 246/246 枚、映像の 90% がディスクとバイト単位で
一致**し、両端の部分 GOP は SmartCut 自身のエンコーダが書いた。どちらのコンテナも、
すべてのプログラムマップを読むまでフレームレートを名乗らなかった（[上記](#フレームレートを名乗らないディスク)）。
エンコーダの代償と、正しいと分かる理由は
[Rust コア](rust-core.ja.md#エンコーダのないコーデック-vc-1)にある。

**合成素材。** [`tests/run_disc_tests.sh`](../../tests/run_disc_tests.sh) が、既存の
テスト素材から方言ごとに 1 枚ずつディスクを組み立てる。TS を 192 バイトパケットに
詰め直し、[`tests/disc_index.py`](../../tests/disc_index.py) が索引ファイルを書き、
genisoimage がそれぞれを UDF 1.02 のイメージに包む。そのうえで、4 つの形すべてが
同じ答えを返すこと、そこから切った出力が**バイト単位で同一**であること、そして
テーブルが書き戻されることを確かめる。同一とは、互いにも、生のストリームからの
出力ともである。35 件すべて通っている。

**実素材の DVD-Video。** 2009 年に Sonic Scenarist でマスタリングされた NHK の
ドキュメンタリー（4.1 GB、ISO 9660 の上に UDF 1.02、タイトルセット 1 つが
VOB 4 ファイル、MPEG-2 720x480 + AC-3）。2 つのタイトルと 19 個・18 個の
チャプターが `.IFO` から読め、独立に書いた Python のリーダーと一致した。
バイト範囲は 24,727,552〜4,289,400,832 で、VOB 4 ファイルとちょうど同じだった。
最終セルの手前の不連続を検出して行を分けた。`VOBU_S_PTM` は 0.280633 秒で、
libavformat がコンテナの開始として報告する値とマイクロ秒まで一致した。
2 区間 480 秒のカットは**14,386 フレーム、99.8% がコピー**で、コピーされた
フレームは素材と**md5 単位で、連続して一致**し、映像と音声のずれは 13 ミリ秒
以内だった。同じタイトルを `VIDEO_TS` フォルダーから読み、VOB ファイルの
継ぎ目をまたいで切った場合も 60 秒で 1798 フレームだった。

**合成素材の DVD。** [`tests/run_dvd_tests.sh`](../../tests/run_dvd_tests.sh) が既存の
テスト素材から 2 枚組み立てる。1 枚はふつうの DVD で、タイトルセットのストリームが
2 ファイルに分かれている。もう 1 枚はタイトルが 2 回に分けて多重化されていて、途中で
時計が振り出しに戻る。[`tests/dvd_index.py`](../../tests/dvd_index.py) が
ナビゲーションパックを埋め、`.IFO` のテーブルを書く。そのうえで、行・長さ・
チャプター・トラック・セクタ範囲が書いたとおりに読めること、厄介なほうが 2 つの
時計を持つ 2 行として出ること、そしてカットが**md5 まで同一**であることを確かめる。
フォルダーからでも、イメージからでも、ディスクの被さっていない生のプログラム
ストリームからでもである。23 件すべて通っている。

**音声をコーデックごとに。**
[`tests/run_bd_audio_tests.sh`](../../tests/run_bd_audio_tests.sh)
が 1 本ずつクリップを組み立てる。16 ビットと 24 ビットの LPCM、DTS、TrueHD、
E-AC-3 である。それぞれを `.ts`・`.m2ts`・`.mp4` に切り出し、そのコーデックが
立てている主張を確かめる。ディスクが使っていたストリーム種別が出力にも出てくること、
LPCM を MP4 に入れても**1 サンプルも違わない**こと、LPCM の境界が落ちたフレームは
向こう側が無音になり手前側は残ること、DTS と TrueHD のカットの音声が素材自身の
バイト列の一続きであること（実際に探して見つける）。39 件すべて通っている。
