# ディスクを読む

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](disc.md)

*逆方向——一晩ぶんのカットをディスクとして書き出すほう——は
[ディスクを書く](bdav.ja.md)にあります。*

**ディスクは、フォルダーのままでも `.iso` のままでも開ける。** Blu-ray は規格の
両方、つまり録画形式の BDAV と市販ソフトの形式である BDMV のどちらも読む。DVD-Video
も読む（[後述](#dvd-video)）。一覧に並ぶのは `00001.m2ts` ではなく番組名である。

```
$ smartcut Anime_Test.iso
disc  : Anime_Test.iso
        bdav -- Anime_Test
        3 recording(s)

  1  00:08:30.010  2026年08月17日01時00分-衛星第一-サンプル番組 てすとばんぐみ!にっ!! #07「架空の休息日の過ごし方。」  2 mark(s)
       0x1101  AAC stereo 48kHz
       0x1102  stream type 0x06
  2  00:08:30.010  …
```

市販ディスクには番組名が入っていないので、行の名前はディスク名とクリップ番号になる。
また、入っているものの大半は本編ではないので、本編らしいものには印が付く。

```
$ smartcut AnimeBox_Season1.iso
disc  : AnimeBox_Season1.iso
        bdmv -- Anime Box Season 1
        62 recording(s)

   1  00:00:43.543  Anime Box Season 1 00008  1 mark(s)
       0x1100  AC-3 stereo 48kHz eng
       0x1200  PGS eng
   2  00:00:11.511  Anime Box Season 1 00002  1 mark(s)
   …
*  8  00:11:52.003  Anime Box Season 1 00014  4 mark(s)
       0x1100  TrueHD multi 48kHz eng
       0x1101  TrueHD stereo 48kHz jpn
       0x1200  PGS eng
       0x1201  PGS eng
```

市販ディスクは丸ごと取り込むのではなく、まず訊く。後述の[選択ダイアログ](#選択ダイアログ)を参照。

GUI では、ISO かディスクのフォルダーをウィンドウにドロップすると、その中のどれを
読むのかを確認する画面が出る。ディスクを何枚か入れたフォルダーを落としても同じで、
一晩ぶんのディスクがそのまま 1 つの一覧になる。

## ふたつの方言

**BDAV** は**録画の形式**で、レコーダーが書くのも、オーサリングツールに
「録画のディスク」を作らせたときに出てくるのもこちらである。

```
BDAV/
  info.bdav              プレイリストの一覧と順序
  PLAYLIST/00001.rpls    録画 1 件: どのクリップを、どこからどこまで
  CLIPINF/00001.clpi     そのクリップの索引
  STREAM/00001.m2ts      トランスポートストリームそのもの
```

**BDMV** は市販の映像ソフトの形式である。プレスされたディスクか、その複製がこれに
あたる。構造は同じだが名前が違い、そして分量がまるで違う。メニュー、Java アプリケー
ション、索引一式の予備が `BACKUP/` にもう 1 組。そのどれも録画ではない。

```
BDMV/
  index.bdmv             プレイヤーのメニュー用のタイトル一覧
  PLAYLIST/00009.mpls    ディスクの通し方 1 通り: どのクリップを、どの順で
  CLIPINF/00014.clpi     そのクリップの索引
  STREAM/00014.m2ts      トランスポートストリームそのもの
  META/DL/bdmt_eng.xml   ディスクの名前
  BACKUP/                上のすべての予備
```

違うのは 4 か所だけである。ディレクトリ名、プレイリストの拡張子とマジック、
プレイリスト一覧の出どころ、そしてプレイリストが番組名を持つかどうか。残りはすべて
同じである。
**PlayItem のバイト配置も、チャプターマークのそれも同じ**である。だから
[`disc.rs`](../../rust/crates/core/src/disc.rs) は「どちらの方言を見ているか」を
渡された 1 つのリーダーであって、同じものを 2 回書いた 2 つのリーダーではない。

BDMV にひとつだけ、ここでは読めないものがある。`index.bdmv` が並べているのは
**タイトル**であり、タイトルはプレイリストではなくナビゲーション／Java のプログラムである。
「T05 Extra 01」がどのプレイリストを再生するかを知るにはディスク自身のメニューコードを
走らせるしかなく、それは Blu-ray プレイヤーであってこれではない。したがって
プレイリストはディレクトリから名前順に取っている。これはオーサリングツールが番号を
振った順であり、実際に見たどのディスクでも、人が選ぶとすれば同じ順になる。

ストリームは MPEG-2 TS を 192 バイトパケットで包んだもの（188 バイトのパケットの前に
到着時刻 4 バイトが付く）で、libavformat は何も指定しなくても読める。**したがって
ストリームは最初から問題ではなかった。** 足りなかったのは索引である。`00014.m2ts`
`00015.m2ts` `00016.m2ts` という並びは、どれが本編で、どれがメニュー前に流れる 8 秒の
ロゴなのかを何も語らない。

## ISO をマウントせずに読む

`.iso` は UDF ファイルシステムである。Linux ならマウントできるが、マウントには root と
ループデバイスが要り、編集のあいだじゅうカット編集ツールにマウントを握らせるのは、
落ちたときに宙ぶらりんのマウントを残すということである。Windows なら `.iso` は
ダブルクリックでマウントできるが、それは「プログラムを使う前にユーザーが済ませて
おかなければならない手順」がひとつ増えるということである。

そこでマウントはしない。イメージはその場で読む
（[`udf.rs`](../../rust/crates/core/src/udf.rs)）。答えを出すべき問いは 1 つだけで
ある。

> **各ファイルはイメージの何バイト目から始まり、何バイトあるのか。**

焼かれた `.m2ts` はひと続きのバイト列なので、答えは**バイト範囲**になる。そして
バイト範囲は、libavformat に `subfile` プロトコルでそのまま渡せる:

```
subfile,,start,747520,end,1232594944,,:file:/rec/Anime_Test.iso
```

デマルチプレクサはこれをただのストリームとして読み、まわりにファイルシステムが
あることを最後まで知らない。だからその先——パケット走査、アクセスポイントへのシーク、
コピー——は普通のファイルのときと 1 行も変わらない。

> 内側のパスを `file:` で始めているのは、オプションの並びが**最初のコロンで終わる**
> ためである。そうしないと Windows の `C:\…` が「プロトコル `c`」と読まれる。

### 1 ギガバイトの壁

UDF の割り当て記述子は長さフィールドが 30 ビットしかないので、記述子 1 個で
1 GiB より長い範囲は表せない。つまり 1.2 GB のクリップは記述子 2 個になる。

```
len=1073739776  lbn=77      -> byte 747520
len=158107648   lbn=524364  -> byte 1074487296
```

747520 + 1073739776 = 1074487296。**隙間なく続いている。** 焼き込みは連続した領域に
書くので、断片化しているのは記述子であってファイルではない。
[`Entry::contiguous`](../../rust/crates/core/src/udf.rs) は続いているものを繋いで
1 つの範囲にし、本当に飛んでいる場合は `None` を返す（焼かれたディスクではまず
起きない）。誤った範囲を読むくらいなら、読めないと答えるほうがよい。

### メタデータパーティション

UDF 2.50 以降のイメージには**メタデータパーティション**がある。ファイルエントリを
まとめて置くための仕組みで、ファイル本体は隣の物理パーティションに残る。つまり
論理ブロック番号を「メタデータファイルの中の位置」として解き、そのファイル自身の
エクステントを辿って初めて実際のセクタになる。ImgBurn が書く UDF 2.60 はこれを使い、
genisoimage が書く UDF 1.02 は使わない。両方読める。

**暗号化されたディスクは対象外である。** AACS は復号の問題であり、このプログラムは
その一切を持たない。

## プレイリストは録画について何を言っているか

**BDAV では、人が読むものはプレイリストに住んでいる。** 番組名だけではない。
レコーダーは、録ったチャンネルとその 3 桁の番号、録画を始めた瞬間、そして放送局が
書いた番組内容——番組表に載る 1 文と、その下の出演者やスタッフ——を数百バイト書く。
どれもプレイリスト先頭の自己記述の中の決まった位置にあり、ここではその全部を読む。
その録画のカットを自分のディスクに書くとき、同じことを言えないといけないからだ。
位置と、どのツールがどれを書くのかは[ディスクを書く](bdav.ja.md#プレイリストが言っていること)にある。

`smartcut <disc> --title N` は読めたものを表示する。

```
title : アニメ 第03話「はじめての遠出」ほか
        衛星第一 (161)  2010-02-14 00:30:00
        美術科に入学した主人公が、学校の前のアパートでひとり暮らしを始める。…
```

## 番組名は ARIB のテキストである

**これは BDAV の話である。** `.rpls` は番組名を UTF-8 では持っていない。ARIB
STD-B24 の 8 単位符号で書かれている。これは ISO 2022 の子孫で、漢字・英数・ひらがな・
カタカナの 4 つの図形集合を同時に保持し、シフトとエスケープで切り替える方式である。
文字の大きさや色の制御符号も、同じバイト列に混ざっている。

[`arib.rs`](../../rust/crates/core/src/arib.rs) はこれを**読む**。描画はしない。
大きさも色も落として、文字の並びだけを取り出す。JIS X 0208 から Unicode への表は
自前で持たず、EUC-JP 経由で引いている（EUC-JP は JIS X 0208 の両バイトに最上位ビットを
立てたものなので、同じ表である）。依存は `encoding_rs` ひとつと、自前の表がひとつ——
JIS が最後まで割り当てなかった区であり、UTF-8 の世界のどの符号化も ARIB と同じようには
埋めていない領域である。

2 つだけ気を付けている点がある。

- **JIS の 85 区以降は ARIB 自身の記号であり、名前を与えなければならない。** JIS では
  未定義のこの領域に、ARIB は自前の記号を置いている。それらを埋めている**別の**符号化の
  変換表に通すと、まったく違う文字が出てくる。だから自前で名前を与えないのなら、
  受像機が出すのと同じ `〓` を返すほかない。

  最初は 85 区以降をまるごと `〓` にしていた。番組名が天気記号を持つことはない、という
  理由である。**しかしシーズン番号は持つ。** 第 3 期のシリーズは `Ⅲ` であり、これは
  94 区 3 点——JIS でもなければ ASCII の `III` でもない。番組名は真ん中に `〓` を抱えて
  戻ってきて、同じ文字列がそのままディスクに書かれるものだから、`〓` がディスクに焼かれて
  残った。同じ領域には JIS X 0208 が落とした漢字——`髙` `﨑`——も入っており、日本語の
  名前はこれを普通に使う。そこで今はすべてに名前を与えている。出典は ARIB STD-B62 の
  対応表で、85・86 区が漢字、90 区が交通の記号、91 区が地図の記号、92 区が単位と数字、
  93 区が天気と分数、94 区が数字記号である。何も割り当てられていないセルは今も `〓` で、
  DRCS のダウンロード外字も `〓` である。

  **90 区の 48〜84 セルは、描くのではなく書き下す。** 番組表の角括弧付きの記号——
  `[新]` `[字]` `[終]` `[再]`——である。テレビでは 1 つの囲み文字、それ以外の場所では
  囲みの中の語になる。Unicode にはこれらの文字もあるが、機械にあるフォントの半分は
  それを描けない。そして番組表が言っているのは `[新]` である。

  **書き出すときは、語を元のセルへ戻す。** 録画が 1 セルで持っていたものを 3 文字で
  書くのは、放送が送った名前ではなく番組表が刷る名前を書くことになる。セルなら 2 バイト
  で済むところが 10 バイトになり、テレビは囲み文字を描くはずのところに `[` `新` `]` を
  描く。そこで書き出すときに綴りを照合する——ただし角括弧で語を綴るものだけである。
  37 個のうち 3 個は普通の文字で綴られており（`■` `●` `ほか`）、番組名はそれらを
  それ自体として持ちうる。`…遠出」ほか` で終わる題名は、そうしないと末尾のかな 2 文字を
  記号に飲み込まれてしまう。

  **この罠には反対側の端もある。** `Ⅲ` `①` `㈱` `℡` `㎏` はいずれも 13 区にあり、
  ここも JIS X 0208 は未定義のまま残していて、UTF-8 の世界が手を伸ばす符号化はそこを
  ベンダーの追加文字で埋めている。つまり EUC-JP を通して名前を書き**出す**と、数字記号は
  ARIB が何も置いていない区へ入り、受像機はそこに描くものを持たない。入口で 85 区以降を
  断るのと同じ理由で、出口では 13 区を断り、代わりに ARIB 自身のセルへ書く——エスケープ
  で G0 に指示し、書いたら指示を戻す。これはこの問題が見つかった放送自身がしている
  ことでもある。
- **かなの集合の末尾 8 セルは、かなではなく約物である。** JIS の 4 区・5 区は最後まで
  埋まっておらず、ARIB は余ったセルに `ー` `。` `「` `」` `、` `・` を入れている。
  ここを取りこぼすと、番組名が `#07〓架空の休息日の過ごし方。」` になる。

`.mpls` のほうは名前をまったく持っていない。映画のタイトルはメニュー、つまり Java
アプリケーションの中にあるからである。そこで市販ディスクの行は、`Anime Box Season 1
00014` のように、ディスク名とクリップ番号で名付ける。ディスクが自分を何と呼んでいるか
は `META/DL/bdmt_*.xml` から取る。ただし XML として解析するのではなく、必要な部分を
拾い読みしている。あのファイルは名前空間が十数個宣言された文書だが、必要な要素は
1 つだけである。`<di:name>` を読むためだけに XML パーサを抱え込めば、このプログラム
最大の依存関係になってしまう。

## 一覧に並ぶもの

**クリップ 1 本が 1 行**である。プレイリスト 1 件が 1 行、ではない。

BDAV ではこの 2 つは同じことである——プレイリストが 2 つ以上のクリップを再生している
場合を除いて。それは番組が、レコーダーがストリームを分割する長さを超えたときに起きる。
その場合はクリップごとに 1 行にして `(1/3)` `(2/3)` `(3/3)` と付ける。

BDMV ではまるで同じことではない。市販ディスクは同じクリップを複数のプレイリストから
名指す。そのクリップ専用のプレイリストで 1 回、「全話連続再生」の中で 1 回、メニューの
チャプター一覧が指すもので 1 回。これを書くにあたって使ったディスクでは、
**45 本のプレイリストが合わせて 328 個の PlayItem を名指し、実体は 62 クリップだった。**
PlayItem ごとに 1 行にすれば、同じ話数を 3 回並べることになる。

そこで行の鍵は「プレイリストがそのクリップのどの部分を再生するか」——クリップ番号と
IN/OUT をティック単位で——にし、最初にそれを名指したプレイリストが行を作る。クリップ
だけを鍵にしないのは、レコーダーが 2 番組を 1 本のストリームに書き、半分ずつの
プレイリストを 2 本書くことがあるからで、それは 2 件の録画である。

複数クリップのプレイリストを 1 つのタイムラインに繋ぐのは、別の仕事である（クリップ
ごとに時計が違うので、2 本を繋ぐのは 1 本を切るのとは別の操作になる）。それが
できるようになるまでは、分かれていることをそのまま見せるほうが正直である。ディスクの
どの秒にも手は届くし、分かれていることは一覧が示している。なお、市販ディスクの
「全話連続再生」は*分かれた録画ではない*ので、その行に `(1/15)` は付けない。ディスク
自身がそんな関係を主張していない以上、付ければこちらが関係を捏造したことになる。

### 選択ダイアログ

録画ファイルは 1 件で、訊くことは何もない。市販ディスクはそうではない。あの 62 行は
ロゴ・警告・メニューのループ・8 秒の繋ぎが 50 本と、その中に紛れた 12 話であり、
ディスクはそのすべてを `000NN` と呼んでいる。

そこで索引を並べ、何も開かないうちに一度だけ確認する。ダイアログに出る情報が、長さ・
サイズ・PID で名指したトラックという、索引だけで答えられるものばかりなのはそのため
である。

**5 分**を超えるクリップは最初からチェックが入る。あのディスクではそれがちょうど 12 話で、
残りはチェックボックスひとつの裏に畳まれる。この閾値は、ディスクを取っておく理由に
なるいちばん短いものよりずっと短く、メニューを構成するいちばん長いものよりずっと長い。
どれも 5 分に届かないディスクは「何も入っていないディスク」ではないので、その場合は
いちばん長いものにチェックを入れる。BDAV は全部にチェックが入る。録画のディスクは、
誰かが録ると決めたものが入っているディスクだからである。

### クリップが持っているもの

各行の下に出るトラックは、そのクリップの `.clpi` から読む。十分に安く済むのはこれ
だけだからである。自分を描画するために 30 ギガバイトを demux するダイアログなど、
誰も待ってくれない。実際にカットするときに最終的な根拠になるのは demuxer が読み取った
内容で、ここに出しているのは「ディスクがそう書いている」という情報である。

```
映像  / H.264 1080p 23.976fps / PID 0x1011 / 映像は外せません
音声  / TrueHD multi 48kHz    / eng / PID 0x1100
音声  / TrueHD stereo 48kHz   / jpn / PID 0x1101
字幕  / PGS                   / eng / PID 0x1200
メニュー / IGS                / eng / PID 0x1400 / カットでは持ち出せません
```

方言によって `.clpi` の署名が違い、その後ろは同じである——市販ディスクは `HDMV`、
レコーダーは `M2TS` で始まる。またレコーダーは言語欄を切り詰めるので、BDAV の行は
言語なしの `AAC stereo 48kHz` になる。続いていた 3 バイトを言語として出すよりましである。
放送の私的ストリーム（字幕もそのひとつ）は番号で呼ぶ。私的ストリームの中身はディスクの
索引が言うことではなく、索引ではなく録画そのものを読む編集画面のトラックメニューが
きちんと名前を付ける。

4 種類が並ぶが、外せないものが 1 つ、持ち出せないものが 1 つある。映像はカットの
対象そのものなので外せない。メニュー（IGS）はボタンの状態と飛び先を持っていて、
その飛び先はカットが今ばらしたばかりのタイムラインを指している。一覧に出しているのは
選ばせるためではなく、持ち出せないことを伝えるためである。字幕（PGS）は同じ種類の
ストリームだが仕事が違い、こちらは[運ぶ](#ディスクが描く字幕)。

ディスクに入っている話数はどれも同じトラック構成なので、1 行の答えを同じ構成の全行に
写すボタンを用意してある。同じ問いに 12 回答えさせるのは、答えを 1 回聞くこととは
別物だからである。

**言語もカットについていく。** ブルーレイの番組マップには言語記述子が無い
——言語は `CLIPINF` にしか書かれていない——ので、`.m2ts` だけを渡された
デマルチプレクサには手がかりがない。その結果、一覧では `eng` と `jpn` と
出ているディスクを切ると、区別のつかない音声トラックが 2 本並ぶ出力になって
いた。書き出したトランスポートストリームにも無く、そこから作ったディスクの
クリップ索引にも無い——索引はストリームを読み直して作るからだ。そこで、
ディスク上の録画を開いたときに `disc::carry_disc_languages` が PID で
突き合わせて埋め、カットが書くマップには各トラックの ISO 639 記述子が入る。
ストリーム自身が言語を宣言していた場合はそちらが優先される。放送がそう言って
いるなら、それはどの索引よりも音に近いところで言っている。

### トラックは PID で名指す

選択ダイアログは**何も開かないうちに**答えを出す。一方、ストリーム番号は libavformat
が録画を読んで初めて作られるものである。そこで、答えは PID の並びとして持ち回り、
実際にストリームを開く側、つまりその行を開いたときの編集画面と、書き出すときの
バックエンドで解決する。

PID は 2 本以上のストリームを指すことがある。Blu-ray のロスレス音声は、AC-3 を内側に
畳み込んだ TrueHD として**ひとつの PID に**乗ってきて、libavformat はそれを別々に渡す。

```
stream|index=1|codec_name=truehd|channels=6|id=0x1100
stream|index=2|codec_name=ac3   |channels=6|id=0x1100
```

そのトラックを外すというのは、両方を外すということである。PID で指定していれば
そうなるが、ストリーム番号で指定していたら片方だけを外すことになっていた。

**1 つの PID から書き出すのは 1 本目だけ**なのも同じ理由である。カットは各ストリームを
到着した PID へ書き戻すので、2 本のストリームが 1 つの PID を共有することはできない。
マルチプレクサにそれを頼めば、次のように言って止まる。

```
[mpegts] Duplicate stream id 4352
Error: Invalid argument
```

PID の 1 本目は番組マップが名指したストリームで、その後ろに来るものは demuxer が
そこから切り出した断片である。だから TrueHD を書き出し——TrueHD の素ストリーム単体は
プレイヤーがデコードできるトラックである——内側に畳み込まれていた AC-3 は落とす。
落としたことはトラックメニューとコマンドラインの出力で言う。

```
        not carried: a compatibility stream folded into the track written on pid 0x1100
```

選択ダイアログの答えが効くのは、編集画面が答えを出すまでである。あちらのトラックメニューは
ストリーム番号を編集内容に書き、その瞬間から編集内容がその行を代表する。そうしないと、
編集画面で戻したトラックが、誰も録画を見ないうちに出された答えによって出口でまた
外されてしまう。

### ディスクが持っている音声

放送の録画が持っているのは AAC だけである。ディスクはそれ以外に 5 種類を持ってきて、
そのどれもが書き出しでは別々の問題になる。

| ディスク上 | カットがすること |
|---|---|
| **LPCM**（`pcm_bluray`） | TS へはそのままコピーし、**スマートレンダリングもする**。LPCM にはエンコーダ遅延も窓の重なりも無いので、境界が落ちたフレームは向こう側を無音にして書き直すだけで済み、ほかは何も動かない。MP4・MKV へはビッグエンディアンの PCM として書く（`ipcm`、QuickTime なら `twos` / `in24`）。素材と同じビット幅である。どちらのコンテナにも Blu-ray のフレーミングを入れる箱が無いからである |
| **DTS**・**DTS-HD**・**DTS-HD MA** | どのコンテナへもバイト単位でそのままコピーする |
| **TrueHD** | バイト単位でそのままコピーする。同じ PID に畳み込まれた AC-3 コアは抜く（上記）。MP4 では 2 つの妥協が要り、そう表示する。`mlpa` の箱は規格外であり、トラックはストリーム自身の同期点から始めなければならない（測った素材では頭が 13 ミリ秒ほど遅れる） |
| **E-AC-3** | そのままコピーする |

**ロスレス音声を再エンコードすることはない。** libavformat が持っている DTS と
TrueHD のエンコーダはロッシーなコアだけを書き、ロスレスたらしめている部分を落とす。
境界フレームを「差し替え」たら、それは切り詰めではなくトラックに開いた穴になる。
だから全再エンコードを頼まれても、ダウンミックス——名前を変えただけの再エンコードで
ある——を頼まれても、従いもせず失敗もせず、断ってそう言う。

**LPCM を MP4 に入れても何も失われない。** サンプルは 32 ビット浮動小数点を通るが、
その 24 ビットの仮数は Blu-ray LPCM が運べる値をすべて表せる——そして Blu-ray の
LPCM は 24 ビットより深くならない。MP4 から出てくるのは入れたものと 1 サンプルも
違わない。変わったのは周りの箱だけである。

ストリーム種別はディスク自身のものである。libavformat の TS マルチプレクサは上の
3 つを知らない——LPCM を書けと言われれば「private data」と宣言し、E-AC-3 を書けと
言われれば Blu-ray の `0x84` ではなく ATSC の `0x87` を持ち出す——が、`.ts` として
書いたカットは[録画自身のテーブル](broadcast-ts.ja.md)を保つので、
番号はそこから来る。

### ディスクが描く字幕

放送は字幕を**書く**。ARIB の字幕文は 1 パケットに 1 つの時刻で収まっていて、
カットを越えて運ぶとは 1 パケットを運ぶことである。ディスクは**描く**。運ばれるのは
**ディスプレイセット**——どこに何を置くかという composition、window、パレット、
そしてランレングス圧縮された絵そのもの——で、その一つひとつが自分の時刻を持った
PES パケットである。

```
PCS  WDS  PDS  ODS  END      字幕が出る
PCS  WDS  END                そしてしばらく後、面が消される
```

つまりパケットは字幕と同じように時刻を持ち、同じように運べる。違うのは時刻が
**まとまり単位**に付いていて、まとまりは半分では意味を持たないことである。違いは
それだけで、規則にすると 3 つになる——[`pgs.rs`](../../rust/crates/core/src/pgs.rs)：

1. **ディスプレイセットは丸ごと運ぶか、まったく運ばないか。** 範囲の終わりを
   またぐものは置いていく。意味を与える composition のないまま断片だけが届いても
   仕方がない。
2. **範囲が開く瞬間に出ている字幕は、もう一度出し直す。** それを描いたセットは
   カットの手前の素材と一緒に置いていかれている。そこでカットは各範囲の手前 8 秒を
   読み、単独で成立する最後のディスプレイセットを覚えておいて、範囲の最初のフレームで
   もう一度送る。エポックの先頭だと書き換えて送る——この出力にとっては実際そうだから
   である。
3. **範囲が終わる瞬間に出ている字幕は、下ろす。** 消しに来るはずのセットはカットの
   向こう側の素材にある。消去は、出ている composition から object を取り除いて番号を
   1 つ進めたものであり、ディスクが面を空けるときに送っているものと同じである。

手前 8 秒を読むのは 2 と 3 のためで、どれだけ読めば足りるかはディスクの振る舞いが
決める。あるディスクの本編 30 分を測ると、ディスプレイセットは 1334 個。うち 386 個が
エポックの先頭、561 個が**アクイジションポイント**——途中から再生を始めたプレイヤーの
ために、同じ字幕を丸ごと送り直したもの——、387 個が面の消去である。1 つの字幕が
出ている時間は中央値 2.3 秒、最長は 116 秒。それでも単独で成立するセットの間隔は
2.8 秒を超えない。どれだけ長く出ていようと、このディスクは送り直し続けている。
8 秒はそれを何度も含み、送り直しをまったくしないディスクでも、いちばん長く出ている
字幕以外は拾える。読む費用は 1 範囲あたり 1 秒ほどで、図形ストリームを持つ録画で
しか発生しない。

**どこへ出せるか。** Blu-ray 自身の枠組み（`.m2ts`）へは出せる。libavformat が
プレイヤーの期待する種別を書く。素の `.ts` へも出せる——ただしマルチプレクサは
種別不明の private data として書き、それを読み戻すと何もかもが `bin_data` になる。
運ばれ、宣言され、そして見えない。そこでマルチプレクサの地図の上に書き直す地図が
`0x90` と言い、番組を HDMV として登録する。[ディスクの LPCM](#ディスクが持っている音声)
に必要な訂正と同じもので、同じパスで行う。MP4 へはそもそも出せず、そう言われる。

メニュー（IGS）は同じ種類のストリームで仕事が違う。ボタンには状態と飛び先があり、
どちらもカットが今ばらしたばかりのタイムラインを指している。こちらは置いていくことを
伝えるためだけに一覧に出す。

### メニューはストリームではなく、それを知っているのは索引だけである

Blu-ray が積んでいるもののうち 2 つは、ディスク自身の索引だけが名前を知っていて、
どちらも置いていく（[`disc.rs`](../../rust/crates/core/src/disc.rs)）。

| | |
|---|---|
| **メニュー**（`0x91`、IGS） | インタラクティブグラフィックス。絵と、状態と遷移コマンドを持つボタンである。コマンドはカットの傍らには存在しないプレイリストやタイトルを指しており、composition はカットが今ばらしたばかりのプレイリストの時計で時刻を持っている |
| **テキスト字幕**（`0x92`、TextST） | 書式付きのテキスト。その書体はストリームの中ではなくディスクの `AUXDATA` にあるファイルである。カットに持ち込んでも、描けるものが何も無いテキストになる——そして描こうとするものも無い。libavcodec は `hdmv_text_subtitle` というコーデック ID を持っているだけで、その後ろにデコーダーは無い |

**この PID に何が乗っているかを demuxer に訊けば答えは返ってくる。ただしそれは
当て推量である。** ここで測ったディスクでは、`0x1400` のメニューが **MP3 音声**
として返ってきた——映像も本物の音声も持っているクリップで、である。それを信じた
カットは、メニューを音声と宣言して出力に書き込んでいたことになる。助かったのは、
同じプローブがその推量に添えるサンプリング周波数を見つけられず、周波数の無い
トラックは数行後に外されるからで、しかもそのときの注記は「pid 0x1400 の音声」と
呼んでいた。

そこで索引に答えさせる。索引がこの 2 つのどちらかだと言う PID は、プローブが
入れようとしたどの一覧からも外し、実際に何であるかで名前を付ける。

```text
audio  : pcm_bluray 48000Hz 2ch  jpn  main   [stream 1 pid 0x1100]
        not carried: a menu on pid 0x1400
```

**メニューだけ**のクリップ——ディスクのメニュークリップは実際そうで、グラフィックス
だけで絵が 1 枚も無い——は、何かが欠けた録画として失敗するのではなく、そうと言う。

### マーク

チャプターマークは**信用できるときだけ**読む。マークの並びは節の長さから分かるが、
その中で何がどこに座っているかは方言によって違う。BDMV のマークは 14 バイト——予約 1
バイト、種別、属する PlayItem、そして時刻——で、レコーダーの BDAV のマークはもっと長く、
名前とサムネイル参照を時刻の傍らに伴う。そこで配置は決め打ちにしない。候補をそれぞれ
試し、**全部のマークが、自分が属すると言っているクリップの中に落ちる**ものを採る。
どれも落ちなければマークは出さない。見当違いの場所にあるチャプターは、チャプターが
無いことより悪い。

**マークがどの PlayItem のものか**を読むことが、「全話連続再生」を使えるものにしている。
それが無ければ、どのマークも下に時計のない数字でしかない。5 話目のチャプターは 5 話目
自身のタイムライン上にあり、1 話目のそれとは「どちらも 11 秒あたりから始まる」以上の
共通点がない。どのクリップのことか言えない配置は、クリップを 1 本しか再生しない
プレイリストでだけ信用する。そうしなければ全話のチャプターが 1 話目に積み上がるが、
それなら 1 個も置かないほうがましである。

行のマークをいちばん**短い**プレイリストから取るのも同じ理由である。ディスクは
1 つの話数を、専用のプレイリストでも「全話連続再生」の中でも名指していて、
どの話数のことか知らずに読めるのは前者だけである。

### マークはキーフレームになる

ディスクから開いた録画は、そのチャプターが最初からカット編集画面に並んでいる。
日本のレコーダーのチャプターは CM の境目そのものであることが多く、それは
[CM 検出](../user-guide/cm-detection.ja.md)が数分かけて探しているものを、録画した
機械が正確に書き残したものである。

1 つだけ食い違うのが**時計**である。プレイリストはストリーム自身の 45 kHz で数えて
いるのに対し、編集画面が描くタイムラインはコンテナの開始時刻を原点に取り直してある。
そのため、マークの置き場所は次の式で求める。

```
entry.start + mark - src.start_time
```

`entry.start` はプレイリストの IN 点で、まさにこのためにマークと一緒に持ち回る。
ディスクを読む側は `start_time` を知らない——それはストリームを開いて初めて分かる
——ので、マークは読んだ場所で時刻に直さず、行と一緒に編集画面まで運ばれる。

マークを置くのは**初めて開いたときだけ**で、録画の隣に `.keyframe` があればそちらが
優先される。`.keyframe` は人が出した答えであり、ディスクのマークは誰も答えていない
ときの初期値だからである。素材の範囲外に落ちるマークは、丸め込まずに捨てる（理由は
上と同じ）。GUI を開かずに時刻を確認したいときは、`smartcut <ディスク> --title N` が
そのまま印字する。

## ディスク自身の索引

**ブルーレイはもうそのパスを済ませている。** すべてのストリームの隣、
`CLIPINF/000NN.clpi` に、プレイヤーが再生を始められるピクチャの位置が
——表示時刻と、ファイル中のパケット番号として——書かれている。それは
[パケットを走査するパス][packetscan]が録画を丸ごと 1 回読んで作る一覧と同じものだ。

だから読む。`disc::entry_points` がマップを解釈し、`index::DiscIndex` が
[`IndexSource`] として差し出す。そのための継ぎ目は初めから用意してあった。
ここで計った UHD ディスク——1 クリップ 81 GB、2 時間 34 分——では、タイトルを
開くのに **8 分 45 秒かかっていたものが 1 秒未満**になり、出てきた計画は
セグメント単位で走査版と一致した。

マップは 2 枚の表でできている。**粗い**エントリが時刻の上位とパケット番号の
上位を持ち、残りを埋める**細かい**エントリの先頭を指す。だから 1 点の時刻は
両者を組み合わせて得る。配置は `libbluray` が読んでいるものと同じで、規格の
記述に出てこない点がひとつある。ストリームごとのマップは、自分の細かい表への
4 バイトのオフセットで始まり、粗い表はその後ろから始まる。

**マップが言えないこと**は、GOP が開いているかどうか、そこにぶら下がる先行
ピクチャを捨ててよいかどうかだ。それはビットストリームの中にあり、どんな索引
にもない。だから点は `leading_known: false` で届き、`index::refine_leading` が
境界の落ちうる点だけを測る——各範囲の両端の前後 20 数点ずつ、1 点につきシーク
1 回と短い読み 1 回。範囲の中の全点を測ると（走査版は自分で答えられるので
この関数が走らず、長らく見えていなかった）、あの 1 万 6 千点で 10 分かかった。
つまりディスクの索引が何ももたらさない。

ピクチャの重さも言えない。継ぎ足すぶんは[録画が入ってきたときのレート][splice]
で書くので、誰も数えなかった場合はファイル自身のレートから音の分を引いた値が
代わりに立つ。ブルーレイではそれで大半が説明できる——非圧縮の音は、ピクチャの
次に重いものだからだ。

[`IndexSource`]: ../../rust/crates/core/src/index.rs
[packetscan]: ../../rust/crates/core/src/index.rs
[splice]: rust-core.ja.md#継ぎ目

## 出力先と名前

ディスクの中には書けない。イメージの中にはそもそもフォルダーが無いし、コピーした
ディスクの中はディスクのものである。だから既定の出力は**ディスクの隣**、名前は
**番組名**になる。

```
/rec/Anime_Test.iso
/rec/cut_2026年08月17日01時00分-衛星第一-サンプル番組 ….ts
```

ファイル名にできない文字（`\ / : * ? " < > |`）は全角に置き換える。日本のレコーダーが
同じ問題に対してしていることと同じで、名前は読めるまま残る。

**コンテナは `.ts` になる。** `.m2ts` を求められた libavformat は Blu-ray 自身の形
——192 バイトのフレーミングと、Blu-ray 自身の PID 番号——で書く。しかしどちらも
マルチプレクサが決めることであり、[このプログラムが書き戻す放送のテーブル](broadcast-ts.ja.md)
が示している配置とは違う。そこで、ディスクから来た録画について「入力と同じ」は `.ts`
を意味することにしている。中身は同じストリームである。出力設定画面で M2TS を選べば、
これまでどおり M2TS で出力される（そのときテーブルはマルチプレクサに任されることを、
その場で表示する）。

## 名前が 1 本であること

このプログラムは、録画 1 本を**1 つの文字列**で表すことに統一している。一覧が
持つのも、シーク用インデックスとプロキシのキャッシュキーも、出力を隣に置くときの
基準も、デマルチプレクサに渡すのも、すべてその 1 本である。ディスクの中の録画を
扱えるようにしても、この前提は変えたくなかった。

そこで、イメージの中の録画には**イメージをフォルダーのように綴った名前**を与えて
いる。

```
/rec/Anime_Test.iso/BDAV/STREAM/00001.m2ts
```

これは勝手に作った記法ではない。イメージには本当にその名前のファイルが入っている。
普通と違うのは `/rec/Anime_Test.iso` がフォルダーではなくファイルである点だけで、
[`input.rs`](../../rust/crates/core/src/input.rs) が見ているのはまさにそこである。
パスを遡って**ファイルであるところ**で切ると、3 つの答えが同時に出る。

| | |
|---|---|
| **URL** | `subfile,,start,…,end,…,,:file:/rec/Anime_Test.iso` — libavformat に渡すもの |
| **ファイル** | `/rec/Anime_Test.iso` — OS に問い合わせるもの。キャッシュが大きさと更新時刻で判断できる |
| **範囲** | そのバイト範囲。libavformat を通さず自分で TS を読む処理のため |

3 つ目が要るのは [`si.rs`](../../rust/crates/core/src/si.rs) である。放送自身の
テーブル（PAT・PMT・SDT・EIT・SIT）を読む処理はファイルを直接舐めるので、**イメージの
中の範囲**として開き、なおかつ **192 バイト間隔**でパケットを拾えなければならない。
どちらも入ったので、ディスクから切った出力にも放送のテーブルがそのまま乗る。

## DVD-Video

DVD は Blu-ray と同じ入口から来るが、共通点はそれだけである。だから
[`disc.rs`](../../rust/crates/core/src/disc.rs) ではなく
[`dvd.rs`](../../rust/crates/core/src/dvd.rs) が読む。`disc::read` は両方に訊き、
ディスクを認識したほうが答える。下流に渡るのはこれまでと同じ `Disc`・`Entry`・
`Track` である。

```
$ smartcut documentary-01.iso
disc  : documentary-01.iso
        dvd -- documentary-01
        2 recording(s)

  1  00:59:51.400  documentary-01 1 (1/2)  18 mark(s)
       0x01e0  MPEG-2 720x480 NTSC 4:3
       0x0080  AC-3 2ch 48kHz  ja
  2  00:00:08.342  documentary-01 1 (2/2)  1 mark(s)
```

DVD の性質のうち 3 つが、この読み取りの形を決めている。

### ストリームは 9 本ではなく 1 本である

`VTS_01_1.VOB` から `VTS_01_9.VOB` までは**1 本の** MPEG プログラムストリームで、
ISO 9660 が 1GB より大きいファイルを扱えなかったために分割されているにすぎない。
ディスクはこれを 0 から数える 1 続きのセクタとして指す。つまりセクタ 536,000 から
始まるセルは、**3 本目**のファイルの 400MB 目にある。

断片は隙間なく並んでいる。今回対象にしたディスクではぴったり並んでいた。

| | オフセット | 終端 |
|---|---|---|
| `VTS_01_1.VOB` | 24,727,552 | 1,098,182,656 |
| `VTS_01_2.VOB` | 1,098,182,656 | 2,171,582,464 |
| `VTS_01_3.VOB` | 2,171,582,464 | 3,244,935,168 |
| `VTS_01_4.VOB` | 3,244,935,168 | 4,289,400,832 |

だからイメージの中ならタイトルセット全体が**ひと続きのバイト範囲**であり、
タイトルは Blu-ray のクリップと同じく `subfile` 1 本で開く。フォルダーなら断片は
9 個のファイルなので、libavformat の `concat` プロトコルでつなぎ、その外側に
`subfile` を被せてタイトルの範囲だけを取り出す。どちらの場合も、展開もコピーも
しない。

プロトコルを入れ子にするには一言必要になる。最上位で何が許されていようと、
その**内側**のプロトコルは `file` だけを含むホワイトリストで検査される。
`input::demux` は、このプログラム自身が書いた URL に対してだけ
`protocol_whitelist` を設定し、ただのパスには設定しない。

### タイトルはセルの連なりである

Blu-ray が 1 話に 1 本のストリームを与えるのに対し、DVD が与えるのは 1 本の
ストリームの一区間であり、その位置を語るのは `.IFO` のテーブルだけである。

| テーブル | そこから取るもの |
|---|---|
| `VIDEO_TS.IFO` の `TT_SRPT` | プレーヤーが番号を振る順のタイトル一覧と、それぞれがどのタイトルセットにあるか |
| `VTS_NN_0.IFO` の `VTS_PTT_SRPT` | セット内の各タイトルについて、チャプターである `(チェーン, プログラム)` の組 |
| `VTS_NN_0.IFO` の `VTS_PGCIT` | 各プログラムチェーン——そのセル、長さ、再生するセクタ、各プログラムが始まるセル |
| `VTS_NN_0.IFO` の `VTSI_MAT` | 映像と、セットが宣言している音声・サブピクチャのトラック |

チャプターの位置は、その手前のセルの長さの合計で決まる。つまり、セルが端から端まで
連なっていなければこの計算は意味を持たない。連なっていないチェーンはアングルブロック
か、複数タイトルの断片から組まれたものなので、これらは読まない。セルがたまたま収まって
いる範囲はタイトルではないので、それをタイトルとして差し出すくらいなら、何も出さない
ほうがよい。

タイトルがファイルではなく区間である以上、名前がどの区間かを言う必要がある。

```
/rec/documentary-01.iso/VIDEO_TS/VTS_01_1.VOB@0-2081904
```

このセクタ番号はディスク自身のもので、タイトルセットのストリームの先頭から
数えている。`VTS_01_1.VOB` とだけ書いた名前は、ディスクが持つ 4GB 全部を指して
しまい、どの 1 話も指さない。

### 時計はストリームの側にあり、索引の側にはない

セルの時間は、タイトルの先頭から数えた長さである。プログラムストリームの
タイムスタンプは、オーサリング時の多重化器が始めた場所から始まる——今回の
ディスクなら 0.281 秒である。「12 分のところ」というチャプターは、両者を
つなぐものがなければその時計の上の時刻にはならない。

つなぐのはナビゲーションパックである。VOBU は必ずこれで始まる。プレーヤーが
読んで表示しない 2048 バイトで、`VOBU_S_PTM`——後続の絵を提示する時刻——と
`VOBU_E_PTM`——それが終わる時刻——を持っている。タイトルの先頭セクタのそれを
読むのは 2048 バイトの読み取り 1 回で、エディターがまさに必要とする数値が
そのまま得られる。DVD の `Entry::start` が索引の推測ではなく実測なのはそのため
である。

**そしてこれが、タイトルが複数の時計をまたいでいることを教えてくれる。** DVD は
別々に多重化された断片からタイトルを組んでよく、その継ぎ目でタイムスタンプは
振り出しに戻る。今回のディスクがまさにそれだった。

```
セル 18 の終わり  323,571,480  (3595.24 秒)
セル 19 の始まり       36,010  (   0.40 秒)
```

2 つの時計を繋ぐのは、1 つを切るのとは別の操作である。Blu-ray で複数クリップの
プレイリストがクリップごとに 1 行になるのと同じ理由である。そこで DVD のタイトルも
継ぎ目で分ける。上のディスクは、18 チャプターの 1 時間と、その隣の 8 秒として出る。
1 行のなかで後半が前半に重なることはない。2 つのセルが同じ連なりに属するのは、後の
セルが前のセルの終わったところから始まるときである。前のセルがどこで終わったかは、
索引が指し示すそのセルの最終 VOBU から読み取る。

このディスクの 2 つのタイトルは、19 セルと、その最後を除いた 19 セルである。
合わせて 3 つではなく 2 つなので、行は指しているストリームの区間で重複を除く。

### プログラムストリームはタイムスタンプを省く

プログラムストリームは、すべての絵に提示時刻を載せるわけではない。前後の絵から
表示順が割り出せる場合、多重化器はそれを省く。今回のディスクでは 4 枚に 1 枚が
そうだった。

```
pts=31263  dts=22254  K     pts=N/A    dts=31263
pts=25257  dts=25257        pts=34266  dts=34266
pts=28260  dts=28260        pts=N/A    dts=40272
```

ここの処理はすべて提示時刻を鍵にしているので、時刻のない絵は捨てられていた。
無劣化コピーの出力からフレームが 4 分の 1 も減る、ということが起きる。
libavformat 自身は時刻を割り出せる（`fflags +genpts` がデコード時刻から並べ直す。
これは正確である）が、ファイルを開く前に指定しなければ動かない。そこで
`input::demux` は、プログラムストリームに対してだけこのフラグを指定する。トランス
ポートストリームはすべての絵に時刻を打っているので、このフラグを付けても何も変わら
ないが、それでも、すべての録画が通る経路に余計なフラグを置くことになるからである。
（開き直す理由はもう 1 つあり、それも同じ考え方による。[下記](#フレームレートを名乗らないディスク)。）

プログラムストリームがもう 1 つ持っていないのが、**自分の長さ**である。libavformat
はファイルの両端のタイムスタンプから長さを割り出すが、末尾に不連続を含む 4GB の DVD
では、1 時間のタイトルに対して 8.3 秒と答えてきた。全パケットを読む走査のほうが正しい
答えを持っているので、そちらを `index::Index::end` として報告するようにした。ただし
コンテナ自身の答えのほうが長ければ、そちらを採る。長さを正しく知っているコンテナは、
その答えをそのまま保てる。

### コンテナのシークテーブルは、末尾まで届くだけでなく録画全体を覆っていなければならない

`--index auto` はパケット走査の前にコンテナのシークテーブルを尋ねる。テーブルを
読むのはただで、4 GB を歩くのはただではないからだ。ところがプログラムストリームには
そんなテーブルが無い。libavformat がプログラムストリームに対して返すのは、最初の
数フレームへ辿り着くまでの probe がたまたま索引した分だけである。12 分半のタイトルで
**8 エントリ、先頭 4 秒ぶん**だった。

これを額面どおり受け取ると、索引が無いより悪い。4 秒より後のどこで切ってもコピー元に
できるエントリーポイントが見つからず、タイトルを丸ごと再エンコードすることになる。
`--scenes` は録画中の境界をすべて同じ絵に引き寄せる。

そこで、ただで済む問いをテーブルに投げる。**そのテーブルは録画を覆っているか**。
probe が止まったところで止まっているテーブルは断り、代わりに走査が答える。同じカット
が 98.2% をコピーするようになり、シーン一覧は 1 つの繰り返しではなく 249 件になった。

**末尾まで届いているか**だけを問うのでは足りない。1999 年の DVD がそれを見せた。
libavformat はプログラムストリームの長さを、ファイルの末尾へシークしてそこにあるもの
を読んで測る。そしてその 1 パケットも他と同じように索引する。1 時間半のタイトルに対して
残されたテーブルは、**先頭 5 秒に 10 エントリ、そして 5110.9 秒のうち 5110.6 秒に
1 エントリ**だった。末尾には届いている。その間には何も無く、それで通ってしまった。
結果として壊れたのはカットではなく編集画面である。フィルムストリップはエントリー
ポイントの上にセルを描くので、その 1 時間半のどこを開いても描く材料は 2 つしかなく、
キーフレーム送りには送る先が無かった。

そこで穴についても問う。ただし測る相手はテーブル自身の間隔ではなく録画の長さである。
本物のテーブルの間隔は 3 倍どころではなく散らばる——エンコーダは絵が変わったところ
にエントリを置くからだ——のに対し、ここで捕まえたいのは間隔が不揃いなテーブルでは
なく空のテーブルである。**録画の 10 分の 1 より広い穴**が空いているものは、コンテナが
保っていたテーブルではない。

代わりに答えた走査は、4 GB のタイトル全体を **3.2 秒**で読み切った。これがこの順序が
正しいもう半分の理由である。DVD ではテーブルは元々たいして節約しておらず、そのくせ
すべてを台無しにしていた。

`examples/indexdiag.rs` は 3 つの供給元それぞれに別々に尋ね、各々が何と答えるかを
表示する。断るべきテーブルが通ってしまっていることは、こうして見つかる。早い段階の
供給元が誤った答えを返しても、どこも派手には壊れないからだ——録画は開くし、編集画面は
渡されたエントリーポイントで描かれる。

### DVD の音声は、DVD 以外が名乗らないストリームに入った LPCM である

DVD のリニア PCM は、その枠組みを DVD だけが説明するプライベートストリームに乗って
いる。ストリーム種別「何かのプライベートデータ」——多重化器が手を伸ばすのはこれである
——で書き出すと、どの読み手もそのトラックを `bin_data` と呼び、無音を再生した。

そこで **Blu-ray の LPCM** として出すようにした。トランスポートストリームがまさに
これらのサンプルのために持っている形である。多重化器が正しく名乗る `.m2ts` と
ディスクは、それだけで直る。素の `.ts` には
[PMT の書き直し](broadcast-ts.ja.md#録画自身の表を書き戻す)が要り、
そもそも放送でなかった録画には PMT のパスが無かった。今はそれも通る。多重化器自身が
書いたものを土台に、この 1 点だけ直して、他には何も足さずに組み直す。

### DVD の字幕は傍らに置くか、変換して中に入れる

DVD も Blu-ray と同じように字幕を描く——表示コマンドの付いたランレングス圧縮された
絵である——が、似ているのはそこまでである。Blu-ray のグラフィックスには TS の
ストリーム種別 `0x90` があり、[カットの中を運べる](#ディスクが描く字幕)。**DVD の
ものには無い。** `.ts` に書き込むと種別不明の private data になり、読み戻すと
どれも `bin_data` になる。運ばれ、宣言され、そして見えない。訂正に使える番号が
存在しない。

そこでカットの傍らに書く。世の中がすでに読める形——**VobSub** の 2 ファイルである
（[`vobsub.rs`](../../rust/crates/core/src/vobsub.rs)）:

```text
cut_title.ts     カット
cut_title.idx    字幕が何で、どれがいつ出るか
cut_title.sub    字幕の絵そのもの、無加工
```

再エンコードは一切しない。`.sub` にはディスク自身のユニットが、届いたときの
プログラムストリームの枠組みのまま、1 セクターに 1 つずつ入る。`.idx` は時刻と
ファイル位置のテキストである。プレイヤーはカットを開けば名前でこの 2 つを見つける。

**パレットはストリームの中に無い。** ユニットは「色 4」としか言わず、色 4 が何色かは
言わない。DVD は 16 色を索引の側、それが属するセルの連なりの傍らに置いている。
そこでカットはディスクに戻ってタイトルが切り出されたチェーンのパレットを読み、
DVD が書いている studio range の輝度と 2 つの色差から変換して、`.idx` の先頭に
書く。これが無いと字幕は偶然にしか読めない。

**残す範囲の両端は繕う。** Blu-ray のグラフィックスと同じで、しかももっと単純である
——ユニットは自分の時間割を持っているからだ。範囲が開く瞬間に出ていたものは最初の
フレームでもう一度書き、終わる瞬間に出ているものは「止めろ」とだけ言う 10 バイトの
ユニットで下ろす。ディスク自身が面を空けるときに送っているものと同じである。後半は
省けない。ここで測ったディスクのユニットは、**1 つとして自分では止まらない**。
どの字幕も次のユニットが来るまで出続けるので、途中で終わったカットは出しっぱなしの
まま、下ろしに来るものが無い状態になる。

**あるいは変換して、1 ファイルにまとめる。** もう一つの答えは、DVD のユニットから
絵を取り出して、TS が運べる種類の字幕——Blu-ray のもの——として書き直すことである。
そうすれば字幕はカットの中にあり、開いた読み手はどれもそれを見つける。
`--subtitles pgs`、あるいは DVD を切るときに出力設定が 1 行で訊く質問である。

再サンプルはせず、画素は 1 つも失わない。**2 つの形式は字幕を同じ形で持っている**
——画素ごとのインデックス、そのランレングス符号、そして色の表である。変わるのは
ランの綴り方（一方に 4 通り、他方にも別の 4 通りある）と、色の書き方だけである。
DVD は赤・緑・青とどれだけ不透明かを言い、Blu-ray は輝度・2 つの色差と
どれだけ不透明かを言う。絵を取り出すのは libavcodec 自身のデコーダで（ディスクの
索引から取ったパレットを渡す。これだけはデコーダに分かりようがない）、書き直すのは
[`pgs.rs`](../../rust/crates/core/src/pgs.rs) である。

画素の他に要るのは時間割で、そこが 2 つの形式の食い違うところである。DVD の
ユニットは自分がいつ出るかを言い、ときにいつ消えるかも言う。Blu-ray の
ディスプレイセットは両方を言われないと分からない。そこでここでは 1 つずつ持つ
——新しいものが出れば前のものを置き換え、消える時刻を言っていたものはその時刻に
下ろし、範囲が終わる時点で出ているものはそこで下ろす。[上記](#ディスクが描く字幕)で
範囲の両端を繕ったのと同じことを、反対側からやっている。

読み取りについて 2 つ、どちらも半日を費やしたので書いておく。

* **DVD の字幕は、録画のストリーム一覧にそもそも出てこないことがある。** 音声と
  1 本のストリームを共有し、パケットの頭の 1 バイトで区別されるので、libavformat は
  最初の 1 つに出会って初めてストリームを作る——ここで測ったディスクでは 400 MB
  読んだところだった。タイトルを開くのにそこまでプローブするのは割に合わない。
  ディスク自身の索引は最初から知っているので、一覧はそちらから取り、パケットは
  あらかじめ決めた索引ではなく**それが何であるか**で突き合わせる。
* **捨てるのはシークの後。前ではない。** 範囲の手前 8 秒は、映像と音声を
  libavformat の内側で捨てながら読む。それが先読みを安くしている。だが先に捨てて
  しまうとシークがきっぱり拒否される——録画は自分のストリームのどれかを頼りに
  シークするので、捨てたストリームでは辿れない——そして何も読めないコンテキストと、
  字幕なしで静かに開く範囲が残る。

書き込みについても 1 つ。**ストリームはファイルのヘッダーが書かれる前に存在して
いなければならない。** 変換したストリームはこのプログラム自身のもので——録画の中に
写す元が無い——ヘッダーが出た後に足したところ、多重化器は初期化していない
ストリームを抱えることになった。その代償はエラーではなく、数フレーム後に、
そのストリームについて警告を出そうとした多重化器の中でのセグメンテーション違反
である。

### フレームレートを名乗らないディスク

libavformat はプローブしながらフレームレートを割り出すが、そのプローブは
特に指示しなければ最初のプログラムマップで止まる。**VC-1** で書かれたプレス
Blu-ray ではそれが早すぎた。`avg_frame_rate` は未設定のまま返り、フレームレートが
「非数」であれば、そこから導かれる長さはすべて意味をなさなくなる——録画の尺も、
印の位置も、区間が何枚のピクチャを持つかも。

`scan_all_pmts` はすべてのマップを読むので、これを直せる。常に有効にしていないのは、
このプログラムが読む素材に特有の事情があるからである。日本の放送でこの徹底した読み方を
すると、トランスポートストリームが載せている**2 番目の番組**まで拾ってしまう。同じ
素材の携帯向けの複製が、別の pid に載っているのである。それは頼まれた録画とは別の
録画である。そこで `input::demux` はまずコンテナに問い合わせ、答えが返ってこなかった
ときだけ開き直す（`states_frame_rate`）。`+genpts` で開き直すときと同じ考え方で
ある。

## 何をしていないか

| | |
|---|---|
| **暗号化ディスク** | 対象外。AACS の復号は一切扱わない。暗号を外すツールで複製された市販ディスクは、他のディスクと同じように読める |
| **ディスクとして書き出す** | 未対応。オーサリングであり、別の問題である |
| **複数クリップの結合** | 未対応。クリップごとに 1 行として見せている（上記） |
| **BDMV のタイトル** | `index.bdmv` が並べるのはタイトルで、タイトルはナビゲーションのプログラムである。「T05 Extra 01」がどのプレイリストかは解決していない。行の名前はディスク名とクリップ番号 |
| **EP マップが読めないクリップ** | マップがあればそれを使い（[ディスク自身の索引](#ディスク自身の索引)）、無ければパケット走査が答える |
| **BD 固有のストリーム** | PGS の字幕は TS に運ぶ。ディスプレイセット単位で運び、各範囲の両端を繕う——[上記](#ディスクが描く字幕)。IGS（メニュー）と TextST（テキスト字幕）は落とし、落としたと表示する。理由は[上記](#メニューはストリームではなくそれを知っているのは索引だけである)。音声はすべて運ぶ——LPCM・DTS-HD・TrueHD・E-AC-3、[上記](#ディスクが持っている音声)。VC-1 の映像は読み、一覧に出し、カットもできる。部分 GOP は[自前のエンコーダ](rust-core.ja.md#エンコーダのないコーデック-vc-1)が書く |
| **DVD のサブピクチャ** | 無加工のまま VobSub の 2 ファイルとして傍らに書くか、TS が運べる種類に変換して中に入れるか——[上記](#dvd-の字幕は傍らに置くか変換して中に入れる)。そのままの形で中には入れない。TS にそのストリーム種別が無いからである |
| **DVD のアングル** | セルがアングルブロックまたはインターリーブユニットになっているチェーンは出さない（[上記](#タイトルはセルの連なりである)） |
| **DVD として書き出す** | DVD タイトルのカットは TS になる。DVD の形とは、大きさに上限のある VOBU、その先頭ごとのナビゲーションパック、全セルを記述する `.IFO` のことであり、それはオーサリングという別の問題である |
| **暗号化された DVD** | AACS と同じく対象外。CSS の復号は一切扱わない |

## 検証

実素材のディスクと、そこから作った合成素材とで確認している。

**実素材の BDAV** — TMSR6 が書いた BDAV を ImgBurn が UDF 2.60 の ISO にしたもの
（3.4 GB、3 クリップ、1920x1080 MPEG-2 + AAC + ARIB 字幕、部分 TS）。3 件の番組名が
すべて正しく読め、バイト範囲は独立に書いた Python の UDF リーダーと一致し、切り出した
60 秒は 99.2% 無劣化で、放送自身のテーブル（PID 0x1100 / 0x1101 / 0x1102、SIT 0x1F）が
そのまま乗った。**同じクリップをフォルダーに取り出して同じ範囲を切ると、出力は
md5 まで一致した。**

**実素材の BDMV** — 12 話 1 期を MakeMKV でバックアップし、ImgBurn が UDF 2.50 の
ISO にしたもの（33 GB、45 プレイリスト、328 PlayItem、62 クリップ）。ディスク名は
`META` から読め、62 行は重複なしで出て、最初からチェックが入ったのはちょうど 12 話で、
各話は自分のプレイリストが書いた 4 つのチャプターを持ち、バイト範囲は `subfile` 経由で
開いて demux できた——0x1011 の H.264、0x1100 / 0x1101 の TrueHD（AC-3 込み）、
0x1200 / 0x1201 の PGS。1 話を 10 秒切り出したところ 91.8% がコピーで、
TrueHD 2 本ともそれぞれの PID に乗り、全サンプルがデコードできた。

**UHD ディスクの字幕をカットを越えて運ぶ** — 2160p 本編（HEVC、LPCM 5.1、
0x1200 の PGS）から 60 秒を切り出し、4 つある境界のうち 3 つが字幕の途中に落ちるように
2 範囲でカットした。範囲の中のディスプレイセットは composition 番号もそのままに
44 パケットが向こう側へ出て、ディスクがそこへ送っていないパケットが 11 本書かれた
——2 つ目の範囲が開く瞬間に出ていたセット 5 本（最初のフレームで出し直したもの）と、
2 つの範囲の消去 3 本ずつである。読み戻すと `.m2ts` でも素の `.ts` でも 0x1200 は
`hdmv_pgs_subtitle` と名乗り、デコードして焼き込むと、継ぎ目の次のフレームには
前の範囲の行ではなく新しい範囲の行が出ており、字幕の途中で開く範囲の先頭フレームには
その字幕が出ており、ファイルの終わりに出しっぱなしのものは残っていない。BDAV
フォルダーへ書くと、クリップ索引はこのストリームを coding `0x90` として並べる。実物の
ディスク上のパスで開けば、地図が何も言わない言語が `CLIPINF` から出てくる（`jpn`）。

続けて、ディスクそのもの——81 GB のクリップを自前のエントリーポイントマップ経由で
開いたもの——から 10 秒を、半分が再エンコード、半分がコピーになる形で切り出した。
**範囲の中のディスプレイセットは 1 つ残らず順番どおりに出た**。再エンコード区間と
コピー区間の継ぎ目の 66 ミリ秒手前で始まり、継ぎ目の向こうで終わるセットも含めて、
運んだのは 39 パケット、書いたのは 8 パケットである。このセットこそ、ディスプレイ
セットを読みかけているあいだセグメントが自分の終端を越えて読み進める理由であり、
「終端を過ぎたか」をパケットが持つ 2 つの時刻の早いほうで判断する理由でもある——
セットは表示される少し前に**送られる**ので、セットの先頭のパケットは、表示時刻が
いちばん先にあるパケットになる。

**DVD の字幕をイメージから運び出す** — 4.1 GB の `.iso`、タイトルセット 1 つ、
`0x20` に日本語のサブピクチャ。libavformat はこれを 400 MB 読むまで見つけない。
本編から 2 範囲を切り出すと、傍らに 11 ユニットが出た。範囲の中でディスクが送った
9 つ、2 つ目の範囲が開く瞬間に出ていて最初のフレームで書き直された 1 つ、そして
1 つ目の範囲を終わらせる停止である。読み戻すと `ffprobe` は 2 ファイルの中に
`dvd_subtitle` を 1 本見つけ、短いカットではユニット 2 つとも読めた。カットに
焼き込むと、継ぎ目の次のフレームにはその瞬間ディスクが出していた行が、
`VTS_02_0.IFO` から取ったディスク自身の色で出ている。外すよう指示すれば、
書かれるのは `.ts` だけになる。

**同じ字幕を変換したもの** — 同じ 2 範囲を `--subtitles pgs` で。9 つの字幕が
ディスプレイセットとして入り、`.ts` では `0x20`、`.m2ts` では他のストリームと同じ
ように `0x1200` に振り直された。`ffprobe` はどちらからも `hdmv_pgs_subtitle` として
読み戻す——素の `.ts` でそうなるということは、多重化器の地図の上に書いた地図が
効いているということである。焼き込むと、継ぎ目の次のフレームには傍らの 2 ファイルが
出していたのと同じ行が、同じ色で出ている。

**メニューを音声と取り違える** — UHD ディスクのクリップ 00004。映像と LPCM 1 本、
そして `0x1400` のメニュー。libavformat はこのメニューを **MP3 音声**と呼ぶ。今この
クリップを訊くと、本物の音声 1 本だけを並べ、`not carried: a menu on pid 0x1400`
と言う。メニューだけの 3 クリップ——グラフィックスだけで絵が無い——は、映像が
無いという失敗ではなく、メニューであると言う。

もう一方は数えて確かめた。**8 枚のディスク、748 個のクリップ索引**。うち 29 個の
クリップがメニューを積んでいて、**テキスト字幕を積んだものは 1 つも無い**——
`0x92` はどこにも無かった。これが TextST を運ばずに名前だけ付けて置いていく
もう半分の理由である。運ぶものが無く、運ぶ実装を突き合わせる相手も無い。

**VC-1 で書かれたプレス Blu-ray 2 枚** — その年代のディスクの多くがこのコーデックで
あり、この 2 枚で Advanced Profile の違いはほぼ覆える。1 枚は 1920x1080i 29.97、
インタレースフレーム符号化、non-uniform 量子化、全 GOP がクローズド。もう 1 枚は
1920x1080 プログレッシブ 23.976、uniform 量子化、全 GOP がオープン、skipped ピクチャ
あり、強いフィルムグレイン。どちらも読み、一覧に出し、GOP 途中から GOP 途中まで
10 秒のカットを行った。**308/308 と 246/246 枚、映像の 90% がディスクとバイト単位で
一致**し、両端の部分 GOP は SmartCut 自身のエンコーダが書いた。どちらのコンテナも、
すべてのプログラムマップを読むまでフレームレートを名乗らなかった（[上記](#フレームレートを名乗らないディスク)）。
エンコーダの代償と、正しいと分かる理由は
[Rust コア](rust-core.ja.md#エンコーダのないコーデック-vc-1)にある。

**合成素材** — [`tests/run_disc_tests.sh`](../../tests/run_disc_tests.sh) が、既存の
テスト素材から方言ごとに 1 枚ずつディスクを組み立てる。TS を 192 バイトパケットに
詰め直し、[`tests/disc_index.py`](../../tests/disc_index.py) が索引ファイルを書き、
genisoimage がそれぞれを UDF 1.02 のイメージに包む。そのうえで、4 つの形すべてが
同じ答えを返すこと、そこから切った出力が**バイト単位で同一**であること——互いにも、
生のストリームからの出力とも——、テーブルが書き戻されることを確かめる。
35 件すべて通っている。

**実素材の DVD-Video** — 2009 年に Sonic Scenarist でマスタリングされた NHK の
ドキュメンタリー（4.1 GB、ISO 9660 の上に UDF 1.02、タイトルセット 1 つが
VOB 4 ファイル、MPEG-2 720x480 + AC-3）。2 つのタイトルと 19 個・18 個の
チャプターが `.IFO` から読め、独立に書いた Python のリーダーと一致した。
バイト範囲は 24,727,552〜4,289,400,832 で、VOB 4 ファイルとちょうど同じだった。
最終セルの手前の不連続を検出して行を分けた。`VOBU_S_PTM` は 0.280633 秒で、
libavformat がコンテナの開始として報告する値とマイクロ秒まで一致した。
2 区間 480 秒のカットは**14,386 フレーム、99.8% がコピー**で、コピーされた
フレームは素材と**md5 単位で、連続して一致**し、映像と音声のずれは 13 ミリ秒
以内だった。同じタイトルを `VIDEO_TS` フォルダーから読み、VOB ファイルの
継ぎ目をまたいで切った場合も 60 秒で 1798 フレームだった。

**合成素材の DVD** — [`tests/run_dvd_tests.sh`](../../tests/run_dvd_tests.sh) が既存の
テスト素材から 2 枚組み立てる。1 枚はふつうの DVD で、タイトルセットのストリームが
2 ファイルに分かれている。もう 1 枚はタイトルが 2 回に分けて多重化されていて、途中で
時計が振り出しに戻る。[`tests/dvd_index.py`](../../tests/dvd_index.py) が
ナビゲーションパックを埋め、`.IFO` のテーブルを書く。そのうえで、行・長さ・
チャプター・トラック・セクタ範囲が書いたとおりに読めること、厄介なほうが 2 つの
時計を持つ 2 行として出ること、そしてカットが——フォルダーからでも、イメージ
からでも、ディスクの被さっていない生のプログラムストリームからでも——
**md5 まで同一**であることを確かめる。23 件すべて通っている。

**音声をコーデックごとに** — [`tests/run_bd_audio_tests.sh`](../../tests/run_bd_audio_tests.sh)
が 1 本ずつクリップを組み立てる。16 ビットと 24 ビットの LPCM、DTS、TrueHD、
E-AC-3 である。それぞれを `.ts`・`.m2ts`・`.mp4` に切り出し、そのコーデックが
立てている主張を確かめる。ディスクが使っていたストリーム種別が出力にも出てくること、
LPCM を MP4 に入れても**1 サンプルも違わない**こと、LPCM の境界が落ちたフレームは
向こう側が無音になり手前側は残ること、DTS と TrueHD のカットの音声が素材自身の
バイト列の一続きであること（実際に探して見つける）。39 件すべて通っている。
