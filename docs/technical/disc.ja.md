# ディスクを読む

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](disc.md)

*逆方向、つまりその日のカットをディスクとして書き出す側は
[ディスクを書く](bdav.ja.md)にある。*

**ディスクは、フォルダーのままでも `.iso` のままでも開ける。** Blu-ray は
録画形式の BDAV と市販ソフトの形式である BDMV の両方を読む。DVD-Video も読む
（[後述](#dvd-video)）。一覧に並ぶのは `00001.m2ts` ではなく番組名である。

```
$ smartcut Anime_Test.iso
disc  : Anime_Test.iso
        bdav -- Anime_Test
        3 recording(s)

  1  00:08:30.010  2026年08月17日01時00分-衛星第一-サンプル番組 てすとばんぐみ!にっ!! #07「架空の休息日の過ごし方。」  2 mark(s)
       0x1101  AAC stereo 48kHz
       0x1102  stream type 0x06
  2  00:08:30.010  …
```

市販ディスクには番組名が入っていないので、行の名前はディスク名とクリップ番号になる。
また、入っているものの大半は本編ではないので、本編らしいものには印が付く。

```
$ smartcut AnimeBox_Season1.iso
disc  : AnimeBox_Season1.iso
        bdmv -- Anime Box Season 1
        62 recording(s)

   1  00:00:43.543  Anime Box Season 1 00008  1 mark(s)
       0x1100  AC-3 stereo 48kHz eng
       0x1200  PGS eng
   2  00:00:11.511  Anime Box Season 1 00002  1 mark(s)
   …
*  8  00:11:52.003  Anime Box Season 1 00014  4 mark(s)
       0x1100  TrueHD multi 48kHz eng
       0x1101  TrueHD stereo 48kHz jpn
       0x1200  PGS eng
       0x1201  PGS eng
```

市販ディスクは丸ごと取り込まず、まずどれを読むかを確認する。
後述の[選択ダイアログ](#選択ダイアログ)を参照。

GUI では、ISO かディスクのフォルダーをウィンドウにドロップすると、その中のどれを
読むのかを確認する画面が出る。ディスクを何枚か入れたフォルダーをドロップしても
同じで、その日に取り込んだディスク全部が 1 つの一覧に並ぶ。

## ふたつの方言

**BDAV** は録画用の形式である。レコーダーが書くディスクも、オーサリングツールで
「録画のディスク」として作ったディスクも、この形式になる。

```
BDAV/
  info.bdav              プレイリストの一覧と順序
  PLAYLIST/00001.rpls    録画 1 件: どのクリップを、どこからどこまで
  CLIPINF/00001.clpi     そのクリップの索引
  STREAM/00001.m2ts      トランスポートストリームそのもの
```

**BDMV** は市販の映像ソフトの形式で、プレスされたディスクとその複製がこれに
あたる。構造は BDAV と同じだが、名前が違い、分量もまるで違う。メニューと Java
アプリケーションが入り、索引一式の予備が `BACKUP/` にもう 1 組ある。そのどれも
録画ではない。

```
BDMV/
  index.bdmv             プレーヤーのメニュー用のタイトル一覧
  PLAYLIST/00009.mpls    ディスクの通し方 1 通り: どのクリップを、どの順で
  CLIPINF/00014.clpi     そのクリップの索引
  STREAM/00014.m2ts      トランスポートストリームそのもの
  META/DL/bdmt_eng.xml   ディスクの名前
  BACKUP/                上のすべての予備
```

両者で違うのは、ディレクトリ名、プレイリストの拡張子とマジック、プレイリスト一覧の
出どころ、プレイリストに番組名が入るかどうかの 4 か所だけで、残りはすべて
同じである。PlayItem のバイト配置も、チャプターマークの配置も変わらない。そのため
[`disc.rs`](../../rust/crates/core/src/disc.rs) は、どちらの方言かを引数で受け取る
1 つのリーダーになっていて、同じ処理を 2 つ書き分けてはいない。

BDMV には 1 つだけ、ここでは読めないものがある。`index.bdmv` に並んでいるのは
タイトルであり、タイトルはプレイリストではなくナビゲーションや Java のプログラムを
指している。「T05 Extra 01」がどのプレイリストを再生するかは、ディスク自身の
メニューコードを実行しなければ分からない。それをするのは Blu-ray プレーヤーの仕事で
あって、SmartCut の仕事ではない。そこでプレイリストはディレクトリから名前順に
取っている。オーサリングツールが番号を振った順であり、実際に見たどのディスクでも、
人が選ぶ順と同じになっていた。

ストリームは MPEG-2 TS を 192 バイトパケットで包んだもの（188 バイトのパケットの前に
到着時刻 4 バイトが付く）で、libavformat は何も指定しなくても読める。つまり
ストリームそのものは最初から問題ではなく、足りなかったのは索引である。`00014.m2ts`
`00015.m2ts` `00016.m2ts` という並びからは、どれが本編で、どれがメニュー前に流れる
8 秒のロゴなのかが分からない。

## ISO をマウントせずに読む

`.iso` は UDF ファイルシステムである。Linux ならマウントできるが、マウントには root
権限とループデバイスが必要になる。しかも編集のあいだずっとカット編集ツールが
マウントを保持することになり、途中で落ちればマウントが宙に浮いたまま残る。Windows
なら `.iso` はダブルクリックでマウントできるが、それでは SmartCut を使う前に
利用者が済ませておく手順が 1 つ増える。

そこでマウントはせず、イメージをその場で読む
（[`udf.rs`](../../rust/crates/core/src/udf.rs)）。必要なのは次の 1 点だけである。

> **各ファイルはイメージの何バイト目から始まり、何バイトあるのか。**

焼かれた `.m2ts` はひと続きのバイト列なので、結果はバイト範囲になる。バイト範囲は
libavformat に `subfile` プロトコルでそのまま渡せる:

```
subfile,,start,747520,end,1232594944,,:file:/rec/Anime_Test.iso
```

デマルチプレクサはこれをただのストリームとして読むので、外側にファイルシステムが
あることは関知しない。その先のパケット走査・アクセスポイントへのシーク・コピーは、
普通のファイルを読むときと 1 行も変わらない。

> 内側のパスを `file:` で始めているのは、オプションの並びが最初のコロンで終わる
> ためである。そうしないと Windows の `C:\…` が「プロトコル `c`」と解釈される。

### 1 ギガバイトの壁

UDF の割り当て記述子は長さフィールドが 30 ビットしかないので、記述子 1 個では
1 GiB より長い範囲を表せない。1.2 GB のクリップは記述子 2 個に分かれる。

```
len=1073739776  lbn=77      -> byte 747520
len=158107648   lbn=524364  -> byte 1074487296
```

747520 + 1073739776 = 1074487296 で、隙間なく続いている。焼き込みは連続した領域に
書くので、断片化しているのは記述子であってファイルではない。
[`Entry::contiguous`](../../rust/crates/core/src/udf.rs) は続いている記述子を繋いで
1 つの範囲にし、本当に飛んでいる場合は `None` を返す（焼かれたディスクではまず
起きない）。誤った範囲を読むより、読めないと報告するほうがよい。

### メタデータパーティション

UDF 2.50 以降のイメージにはメタデータパーティションがある。ファイルエントリを
まとめて置くための仕組みで、ファイル本体は同じイメージの物理パーティションに残る。
論理ブロック番号はまずメタデータファイルの中の位置として解釈し、そのファイル自身の
エクステントを辿って初めて実際のセクタになる。ImgBurn が書く UDF 2.60 はこれを使い、
genisoimage が書く UDF 1.02 は使わない。両方読める。

**暗号化されたディスクは対象外である。** AACS は復号の問題であり、SmartCut には
復号の機能が一切無い。

ただし、暗号化されていることは表示する。レコーダーはストリームだけを暗号化し、索引は
平文のまま残すので、この種のディスクは一覧までは完璧に出て、どの行も開けない。
libavformat が返すのは `Invalid data found when processing input` で、バイト列に
ついては正しいが、理由は分からない。理由は `BDAV` と同じ階層にある `AACS`
ディレクトリにある。選択画面ではチェックを付ける前にこれを表示し、開くのに失敗した
ときはデマルチプレクサのメッセージの代わりに表示する。ディレクトリを見るのは失敗した
後か説明するときだけで、開くのを拒む根拠には使わない。ストリームをその場で復号した
イメージはディレクトリを残したまま開けるし、ストリームを別の場所へ移すツールは
ディレクトリも一緒に移すからである。

## プレイリストは録画について何を言っているか

**BDAV では、人が読む情報はプレイリストに入っている。** 番組名だけではない。
レコーダーは、録ったチャンネルとその 3 桁の番号、録画を始めた日時、そして放送局が
書いた番組内容を数百バイト分書き込む。番組表に載る 1 文と、その下に続く出演者や
スタッフである。どれもプレイリスト先頭の自己記述の中の決まった位置にあり、
SmartCut はその全部を読む。その録画のカットを自分のディスクに書くときに、同じ情報を
書き込む必要があるからである。位置と、どのツールがどの項目を書くのかは
[ディスクを書く](bdav.ja.md#プレイリストに書かれていること)にある。

`smartcut <disc> --title N` を実行すると、読めた情報が表示される。

```
title : アニメ 第03話「はじめての遠出」ほか
        衛星第一 (161)  2010-02-14 00:30:00
        美術科に入学した主人公が、学校の前のアパートでひとり暮らしを始める。…
```

## 番組名は ARIB のテキストである

**これは BDAV の話である。** `.rpls` の番組名は UTF-8 ではなく、ARIB STD-B24 の
8 単位符号で書かれている。ISO 2022 の系譜に属する方式で、漢字・英数・ひらがな・
カタカナの 4 つの図形集合を同時に保持し、シフトとエスケープで切り替える。文字の
大きさや色の制御符号も、同じバイト列に混ざっている。

[`arib.rs`](../../rust/crates/core/src/arib.rs) はこれを読むだけで、描画はしない。
大きさも色も落として、文字の並びだけを取り出す。JIS X 0208 から Unicode への表は
自前で持たず、EUC-JP 経由で引いている（EUC-JP は JIS X 0208 の両バイトに
最上位ビットを立てたものなので、表としては同じである）。依存は `encoding_rs`
1 つと、自前の表が 1 つである。自前の表が受け持つのは JIS が最後まで割り当てなかった
区で、UTF-8 系のどの符号化も ARIB と同じようには埋めていない領域である。

気を付けている点は 2 つある。

- JIS の 85 区以降は ARIB 独自の記号なので、自前で文字を割り当てる必要がある。JIS
  では未定義のこの領域に、ARIB は独自の記号を置いている。この領域を埋めている別の
  符号化の変換表に通すと、まったく違う文字が出てくる。自前で割り当てないのなら、
  受像機と同じく `〓` を返すしかない。

  最初は 85 区以降をまるごと `〓` にしていた。番組名に天気記号は入らないと
  考えたからである。ところがシーズン番号は入る。第 3 期のシリーズは `Ⅲ` で、これは
  94 区 3 点にあり、JIS にも無ければ ASCII の `III` でもない。番組名は真ん中に `〓`
  を含んだまま読み出され、同じ文字列がそのままディスクに書かれるので、`〓` が
  ディスクに焼かれて残った。同じ領域には JIS X 0208 に入らなかった漢字、`髙` や `﨑`
  もあり、日本語の人名では普通に使われる。そこで今はすべてのセルに文字を
  割り当てている。出典は ARIB STD-B62 の対応表で、85・86 区が漢字、90 区が交通の
  記号、91 区が地図の記号、92 区が単位と数字、93 区が天気と分数、94 区が
  数字記号である。何も割り当てられていないセルは今も `〓` で、DRCS の
  ダウンロード外字もここでは `〓` にする。番組名は文字列であり、放送局がドットで
  送ってきた字は文字列にならないからである。そのドットを受け取って描くのは字幕側で、
  [放送局が「画像で送ってくる文字」](broadcast-ts.ja.md#放送局が画像で送ってくる文字)
  にある。

  90 区の 48〜84 セルは、囲み文字として描くのではなく語に開く。番組表の角括弧付きの
  記号、`[新]` `[字]` `[終]` `[再]` である。テレビでは 1 つの囲み文字として描かれ、
  それ以外の場所では角括弧で囲んだ語として書かれる。Unicode にも囲み文字はあるが、
  環境にあるフォントの半分は描けない。しかも番組表に載っているのは `[新]` の
  形である。

  書き出すときは、語を元のセルへ戻す。録画が 1 セルで持っていたものを 3 文字で
  書けば、放送が送った名前ではなく番組表に印刷される名前を書くことになる。セルなら
  2 バイトで済むところが 10 バイトになり、テレビは囲み文字を描くはずの場所に `[`
  `新` `]` を描く。そこで書き出すときに綴りを照合する。ただし照合するのは角括弧で
  語を綴るものだけである。37 個のうち 3 個は普通の文字で綴られていて（`■` `●`
  `ほか`）、番組名にはそれらが文字として入りうる。`…遠出」ほか` で終わる題名は、こう
  限定しないと末尾のかな 2 文字が記号に置き換わってしまう。

  同じ問題が反対側にもある。`Ⅲ` `①` `㈱` `℡` `㎏` はいずれも 13 区にあり、ここも
  JIS X 0208 では未定義のまま残っていて、UTF-8 系の環境が使う符号化はそこを
  ベンダーの追加文字で埋めている。したがって EUC-JP を通して名前を書き出すと、
  数字記号は ARIB が何も置いていない区へ入り、受像機はそこに描く文字を持たない。
  入口で 85 区以降を除外するのと同じ理由で、出口では 13 区を除外し、代わりに ARIB
  自身のセルへ書く。エスケープで G0 に指示し、書いたら指示を戻す。この問題が
  見つかった放送局自身も同じ書き方をしている。
- かなの集合の末尾 8 セルは、かなではなく約物である。JIS の 4 区・5 区は最後まで
  埋まっておらず、ARIB は余ったセルに `ー` `。` `「` `」` `、` `・` を入れている。
  ここを取りこぼすと、番組名が `#07〓架空の休息日の過ごし方。」` になる。

### ただし 4K レコーダーは UTF-8 で書く

**4K レコーダーは番組名を UTF-8 で書く。** 放送が独自の文字として送っている記号
（`🆞`・`🈔`）も、Unicode の文字に直したうえで入っている。これを ARIB として読むと
`ＮＨＫ　ＢＳ` が `わぜぎわぜえわぜかゃわぜあわぜこ` になり、そのディスクの行が
全部でたらめな名前になる。

どちらの符号化かは、まずファイルのバージョンで判別する。4K 録画のプレイリストと
クリップ索引はバージョン 2.00 で、マジックが `PLST0200`・`M2TS0200` になる。
オーサリングツールは `0100`、HD のレコーダーは `0110` である。ただし `info.bdav` は
2.00 のディスクでも `BDAV0100` のままなので、バージョンだけでは決められず、
バイト列も見る。

バイト列から分かることには限りがある。ARIB のテキストは `0E`・`0F`・`1B` で
文字集合を切り替えるが、UTF-8 のテキストにこれらのバイトは現れない。`89`・`8A` の
単一シフトも同様で、これで始まる正しい UTF-8 の並びは無い。ところが漢字だけで
書かれた名前はシフトを一度も使わない。復号が漢字集合から始まるからである。そういう
名前は `0x80` 未満のバイトの並びなので UTF-8 としても妥当で、UTF-8 として読めば
2 バイトずつがラテン文字のでたらめな綴りになる。そこで、2.00 のファイルは UTF-8
として読み、2.00 でないファイルは ARIB では書けない文字がバイト列に
入っているときだけ UTF-8 として読む。これが `disc::recorded_text` である。

`.mpls` には名前がまったく入っていない。映画のタイトルはメニュー、つまり Java
アプリケーションの中にあるからである。そこで市販ディスクの行は、`Anime Box Season 1
00014` のように、ディスク名とクリップ番号で名付ける。ディスク名は
`META/DL/bdmt_*.xml` から取る。ただし XML として解析するのではなく、必要な部分を
拾い読みしている。このファイルは名前空間が十数個宣言された文書だが、必要な要素は
1 つだけである。`<di:name>` を読むためだけに XML パーサを依存に加えると、SmartCut
最大の依存関係になってしまう。

## 文字スーパーと、もう一つの字幕

放送が送っているテキストは字幕だけではない。字幕とは別に**文字スーパー**がある。
地震、開票速報、迷子の知らせなど、放送局がそのとき画面に出ている映像の上に重ねて
出す行で、専用のストリームに字幕と同じ ARIB の文字で載っている。さらに 4K 放送の
字幕はまったく別の形式で書かれている。TTML、つまり字幕 1 枚につき XML 文書 1 つで、
文字列と、それを置く領域がピクセル単位で入っている。

libav はこの 3 つのうち 1 つだけに名前を付け、残り 2 つをひとまとめにする。HD
放送の字幕は `arib_caption` として返ってくるが、文字スーパーと 4K の字幕はどちらも
`bin_data`、つまり素性の無いバイト列として返ってくる。そのまま読んだ結果、4K
ディスクの字幕は「文字スーパー」として扱われ、捨てられていた。1 行に間違いが 2 つ
あったことになる。

見分ける根拠は録画自身の map にある。ARIB はストリームを 1 バイトの component tag で
指し、0x30〜0x37 が字幕、0x38〜0x3F が文字スーパーである。その隣にデータ符号化方式
記述子があり、テキストが ARIB STD-B24 であることを示す。4K 録画にはこの記述子も
このテキストも無い。そこで map は開くたびに読み（`si::stream_tags`）、tag と記述子の
両方で 3 つを見分ける。規則の全体は `lib::text_stream` にある。map が読めなかった
ときは libav が付けた名前をそのまま使う。

3 つとも `.ts` へ運び、3 つともプレビューに出せる。それ以外の目的で読むのは字幕だけ
である。切れ目を探すのも（[`caption::resets`]）、ディスクの字幕を描き換えるのも、
番組の字幕が対象であって、放送局の文字スーパーは対象にしない。

### 4K の字幕は、時刻が文書の中にある

TTML のストリームには、ほかのどのストリームとも違う点が 2 つある。

**パケットに載っているのは時刻ではなくカウンタである。** レコーダーは 1・2・3 と
番号を打ち、最初の文書の presentation time が `1`、次が `2` になる。文字を出す時刻は
`begin="00:02:21.667"` のように、文書の中に文字列で入っている。

その時刻は、ファイルの先頭ではなく、クリップが提示を始める位置から数えてある。
どこから始まるかはディスクの管理情報に書かれていて、プレイリストの `IN_time` と同じ
値になる。これを読むのが `disc::clip_presentation_start` である。提示開始が 0.5 秒
違う 2 本のクリップで測ったところ、どちらも最初の字幕がちょうどその 5 秒後、タイトル
バックに切り替わるフレームに乗った。ファイルの先頭から数えたとすれば、2 本は
それぞれ 1.2 秒と 1.7 秒ずれる。

そのためカットでは、このパケットをほかのストリームのようには動かせない。代わりに、
文書の中の時刻を書き換えて書き戻す（`cut::take_ttml`）。どの区間にも入らない字幕は
運ばない。区間の先頭をまたぐ字幕は区間の先頭から出し、区間の末尾を越える字幕は区間の
末尾で消す。`HH:MM:SS.mmm` は幅が固定なので文書の長さは変わらない。レコーダーが
文書の前に書く 12 バイトには文書の長さが入っているので、長さが変わらないことには
意味がある。

書き換えた時刻は、カットの最初のピクチャから数えたものになる。プレイリストの無い
ファイルはそこから始まるからである。

## 一覧に並ぶもの

一覧は**クリップ 1 本につき 1 行**で、プレイリスト 1 件につき 1 行ではない。

BDAV ではこの 2 つはほぼ同じである。違いが出るのは、プレイリストが 2 つ以上の
クリップを再生している場合だけで、番組がレコーダーのストリーム分割長を超えたときに
起きる。その場合はクリップごとに 1 行にし、`(1/3)` `(2/3)` `(3/3)` と付ける。

BDMV では話がまるで違う。市販ディスクは同じクリップを複数のプレイリストから指す。
そのクリップ専用のプレイリストで 1 回、「全話連続再生」の中で 1 回、メニューの
チャプター一覧が指すプレイリストで 1 回、といった具合である。この部分を書くときに
使ったディスクでは、45 本のプレイリストが合わせて 328 個の PlayItem を指していて、
実体は 62 クリップだった。PlayItem ごとに 1 行にすれば、同じ話数が 3 回並ぶ。

そこで行の鍵は「プレイリストがそのクリップのどの部分を再生するか」、つまりクリップ
番号と IN/OUT のティックにし、その組み合わせを最初に指したプレイリストが行を作る。
クリップだけを鍵にしないのは、レコーダーが 2 番組を 1 本のストリームに書いて、
半分ずつを指すプレイリストを 2 本作ることがあるからで、その場合は 2 件の録画として
扱うべきである。

複数クリップのプレイリストを 1 つのタイムラインに繋ぐのは別の仕事になる。
クリップごとに時計が違うので、2 本を繋ぐのは 1 本を切るのとは別の操作だからである。
それができるようになるまでは、分かれているものを分かれたまま見せるほうが正確である。
ディスクのどの秒にも手は届くし、分かれていることは一覧を見れば分かる。なお、
市販ディスクの「全話連続再生」は分割された録画ではないので、その行に `(1/15)` は
付けない。ディスク自身がそういう関係を示していない以上、付ければこちらが関係を
捏造したことになる。

### 選択ダイアログ

録画ファイルは 1 件なので、確認することは何もない。市販ディスクはそうではない。
先ほどの 62 行は、ロゴ・警告・メニューのループ・8 秒の繋ぎが 50 本と、その中に
紛れた 12 話であり、ディスク上ではそのすべてが `000NN` という名前になっている。

そこで索引を並べ、何も開かないうちに一度だけ確認してもらう。ダイアログに出る情報が
長さ・サイズ・PID で示したトラックという、索引だけで分かるものばかりなのはその
ためである。

長さが 5 分を超えるクリップには最初からチェックが入る。先ほどのディスクではそれが
ちょうど 12 話で、残りはチェックボックス 1 つの裏に畳まれる。この閾値は、ディスクを
取っておく理由になる最短の本編よりずっと短く、メニューを構成する最長のクリップより
ずっと長い。どれも 5 分に届かないディスクでも何も入っていないわけではないので、
その場合はいちばん長いクリップにチェックを入れる。BDAV は全部にチェックが入る。
録画のディスクには、誰かが録ると決めたものしか入っていないからである。

### クリップが持っているもの

各行の下に出るトラックは、そのクリップの `.clpi` から読む。十分に軽く済む方法は
これしかないからである。自分を描画するために 30 ギガバイトを demux するダイアログを
待ってくれる人はいない。実際にカットするときの最終的な根拠は demuxer が読み取った
内容で、ここに出しているのはディスクの索引に書かれている情報である。

```
映像  / H.264 1080p 23.976fps / PID 0x1011 / 映像は外せません
音声  / TrueHD multi 48kHz    / eng / PID 0x1100
音声  / TrueHD stereo 48kHz   / jpn / PID 0x1101
字幕  / PGS                   / eng / PID 0x1200
メニュー / IGS                / eng / PID 0x1400 / カットでは持ち出せません
```

`.clpi` の署名は方言によって違うが、その後ろは同じである。市販ディスクは `HDMV`、
レコーダーは `M2TS` で始まる。またレコーダーは言語欄を切り詰めるので、BDAV の行は
言語なしの `AAC stereo 48kHz` になる。続いていた 3 バイトを言語として出すよりは
よい。放送の私的ストリーム（字幕もその 1 つ）は番号で呼ぶ。私的ストリームの中身は
ディスクの索引には書かれていないので、索引ではなく録画そのものを読む編集画面の
トラックメニューで、正しい名前が付く。

4 種類が並ぶが、外せないものが 1 つ、持ち出せないものが 1 つある。映像はカットの
対象そのものなので外せない。メニュー（IGS）はボタンの状態と飛び先を持っていて、
その飛び先はカットでばらしたタイムラインを指している。一覧に出しているのは選ばせる
ためではなく、持ち出せないことを伝えるためである。字幕（PGS）は同じ種類の
ストリームだが役割が違い、こちらは[運ぶ](#ディスクが描く字幕)。

ディスクに入っている話数はどれも同じトラック構成なので、1 行の選択を同じ構成の
全行に写すボタンを用意してある。同じ選択を 12 回させるのと 1 回で済ませるのとでは
手間が違う。

**言語もカットについていく。** Blu-ray の番組マップに言語記述子は無い。言語は
`CLIPINF` にしか書かれていないので、`.m2ts` だけを渡されたデマルチプレクサには
手がかりが無い。その結果、一覧では `eng` と `jpn` と出ているディスクを切ると、
区別のつかない音声トラックが 2 本並ぶ出力になっていた。書き出したトランスポート
ストリームにも言語は無く、索引はストリームを読み直して作るので、そこから作った
ディスクのクリップ索引にも無い。そこで、ディスク上の録画を開いたときに
`disc::carry_disc_languages` が PID で突き合わせて言語を埋め、カットが書くマップには
各トラックの ISO 639 記述子が入るようにした。ストリーム自身が言語を宣言していた
場合はそちらが優先される。放送側の宣言は、どの索引よりも音声に近い場所にあるから
である。

### トラックは PID で示す

選択ダイアログでの選択は、何も開かないうちに確定する。一方、ストリーム番号は
libavformat が録画を読んで初めて付くものである。そこで選択結果は PID の並びとして
持ち回り、実際にストリームを開く側、つまりその行を開いたときの編集画面と、書き出す
ときのバックエンドで解決する。

1 つの PID が 2 本以上のストリームを指すこともある。Blu-ray のロスレス音声は、
AC-3 を内側に畳み込んだ TrueHD として 1 つの PID に乗っていて、libavformat はそれを
別々のストリームとして渡す。

```
stream|index=1|codec_name=truehd|channels=6|id=0x1100
stream|index=2|codec_name=ac3   |channels=6|id=0x1100
```

そのトラックを外すとは、この両方を外すことである。PID で指定していればそうなるが、
ストリーム番号で指定していたときは片方しか外れなかった。

**1 つの PID から書き出すのは 1 本目だけ**なのも同じ理由による。カットは
各ストリームを到着した PID へ書き戻すので、2 本のストリームが 1 つの PID を
共有することはできない。マルチプレクサにそう指示すると、次のように表示して止まる。

```
[mpegts] Duplicate stream id 4352
Error: Invalid argument
```

PID の 1 本目は番組マップに載っているストリームで、その後ろに来るのは demuxer が
そこから切り出した断片である。そこで TrueHD を書き出し、内側に畳み込まれていた
AC-3 は落とす。TrueHD の素ストリーム単体は、プレーヤーがそのままデコードできる
トラックである。落としたことはトラックメニューとコマンドラインの出力に表示される。

```
        not carried: a compatibility stream folded into the track written on pid 0x1100
```

選択ダイアログでの選択が有効なのは、編集画面で選び直すまでである。編集画面の
トラックメニューはストリーム番号を編集内容に書き込み、それ以降はその編集内容がその
行の設定になる。そうしないと、編集画面で戻したトラックが、録画を開く前に決めた選択に
よって出口でまた外されてしまう。

### ディスクが持っている音声

放送の録画に入っている音声は AAC だけだが、フレーミングは 2 種類ある。HD 録画は
ADTS の MPEG-2 AAC で、ストリーム種別は `0x0F`。4K 録画は LATM の MPEG-4 AAC で、
種別は `0x11` である。一覧の行にはそのどちらかが表示される。どちらであるかによって、
カットの境界のフレームの書き方が変わる。詳しくは
[もう一つのフレーミング](audio.ja.md#もう一つのフレーミング-latm4k-録画)にある。
4K レコーダーは標本周波数の欄に `15` を書く。索引が表せるレートのどれにも当たらない
ので、行にはレートを出さない。実際のレートはフレームに入っているので、録画を開けば
トラックの行に 48 kHz と表示される。

ディスクにはそれ以外に 5 種類の音声が入ってくることがあり、書き出しではそれぞれ
別の問題になる。

| ディスク上 | カットがすること |
|---|---|
| **LPCM**（`pcm_bluray`） | TS へはそのままコピーし、スマートレンダリングもする。LPCM にはエンコーダ遅延も窓の重なりも無いので、境界にかかったフレームは範囲外の側を無音にして書き直すだけで済み、ほかは何も動かない。MP4・MKV へはビッグエンディアンの PCM として書く（`ipcm`、QuickTime なら `twos` / `in24`）。ビット幅は素材と同じである。どちらのコンテナにも Blu-ray のフレーミングを入れる箱が無いからである |
| **DTS**・**DTS-HD**・**DTS-HD MA** | どのコンテナへもバイト単位でそのままコピーする |
| **TrueHD** | バイト単位でそのままコピーする。同じ PID に畳み込まれた AC-3 コアは抜く（上記）。MP4 では妥協が 2 つ必要になり、その旨を表示する。`mlpa` の箱は規格外であり、トラックはストリーム自身の同期点から始めなければならない（測った素材では先頭が 13 ミリ秒ほど遅れる） |
| **E-AC-3** | そのままコピーする |

**ロスレス音声は再エンコードしない。** libavformat が持っている DTS と TrueHD の
エンコーダはロッシーなコアだけを書き、ロスレスにしている部分を落とす。
境界フレームをそれで差し替えれば、切り詰めではなくトラックに開いた穴になる。そのため
全再エンコードを指定されてもダウンミックスを指定されても、実行も失敗もせず、
受け付けないことをその旨と一緒に表示する。ダウンミックスは名前が違うだけで
再エンコードと同じである。

LPCM を MP4 に入れても何も失われない。サンプルは 32 ビット浮動小数点を通るが、
その 24 ビットの仮数は Blu-ray LPCM が運べる値をすべて表せるし、Blu-ray の LPCM は
24 ビットより深くならない。MP4 から出てくるのは入れたものと 1 サンプルも違わず、
変わるのは周りの箱だけである。

ストリーム種別はディスク自身の値を使う。libavformat の TS マルチプレクサはこの
3 つを扱えず、LPCM を書けば「private data」と宣言し、E-AC-3 を書けば Blu-ray の
`0x84` ではなく ATSC の `0x87` を使う。ただし `.ts` として書いたカットは
[録画自身のテーブル](broadcast-ts.ja.md)を保つので、番号はそちらから来る。

### ディスクが描く字幕

放送の字幕は文字である。ARIB の字幕文は 1 パケットに 1 つの時刻で収まっていて、
カットを越えて運ぶには 1 パケットを運べばよい。ディスクの字幕は画像である。運ぶ
単位は**ディスプレイセット**で、どこに何を置くかという composition、window、
パレット、そしてランレングス圧縮された画像そのものから成り、その一つひとつが自分の
時刻を持った PES パケットになっている。

```
PCS  WDS  PDS  ODS  END      字幕が出る
PCS  WDS  END                そしてしばらく後、面が消される
```

つまりパケットは字幕と同じように時刻を持ち、同じように運べる。違うのは時刻が
まとまり単位に付いていて、まとまりが半分では意味を持たないことである。違いはそれ
だけで、規則にすると 3 つになる（[`pgs.rs`](../../rust/crates/core/src/pgs.rs)）。

1. ディスプレイセットは丸ごと運ぶか、まったく運ばないかのどちらかにする。範囲の
   終わりをまたぐものは置いていく。意味を与える composition の無い断片だけが届いても
   役に立たないからである。
2. 範囲が開く瞬間に出ている字幕は、もう一度出し直す。それを描いたセットは、カットの
   手前の素材と一緒に置き去りになっている。そこでカットは各範囲の手前 8 秒を読み、
   単独で成立する最後のディスプレイセットを覚えておいて、範囲の最初のフレームで
   もう一度送る。送るときはエポックの先頭に書き換える。この出力にとっては実際に
   先頭だからである。
3. 範囲が終わる瞬間に出ている字幕は消す。消しに来るはずのセットはカットの向こう側の
   素材にある。消去は、出ている composition から object を取り除いて番号を 1 つ
   進めたもので、ディスクが面を空けるときに送っているものと同じである。

手前 8 秒を読むのは 2 と 3 のためで、どれだけ読めば足りるかはディスクの振る舞いで
決まる。あるディスクの本編 30 分を測ると、ディスプレイセットは 1334 個あった。うち
386 個がエポックの先頭、561 個がアクイジションポイント、387 個が面の消去である。
アクイジションポイントは、途中から再生を始めたプレーヤーのために同じ字幕を丸ごと
送り直したものである。1 つの字幕が出ている時間は中央値 2.3 秒、最長は 116 秒だが、
それでも単独で成立するセットの間隔は 2.8 秒を超えない。どれだけ長く出ている
字幕でも、このディスクは送り直し続けている。8 秒あればそれを何度も含むし、
送り直しをまったくしないディスクでも、いちばん長く出ている字幕以外は拾える。
読むのにかかる時間は 1 範囲あたり 1 秒ほどで、図形ストリームを持つ録画でしか
発生しない。

出力先について。Blu-ray 自身の枠組み（`.m2ts`）へは出せる。libavformat が
プレーヤーの期待する種別を書く。素の `.ts` へも出せる。ただしマルチプレクサは
種別不明の private data として書くので、それを読み戻すと何もかもが `bin_data`
になる。運ばれて宣言もされているのに見えない。そこで、マルチプレクサの書いたマップの
上から書き直すマップで種別を `0x90` にし、番組を HDMV として登録する。
[ディスクの LPCM](#ディスクが持っている音声)に必要な訂正と同じもので、同じ経路で
行う。MP4 へはそもそも出せず、その旨が表示される。そのうえで、もう 1 つの選択肢、
つまりカットの中ではなく
[別ファイルに書く](#ディスクの字幕を焼き込むか別ファイルにするか)ことを提示する。

メニュー（IGS）は同じ種類のストリームで役割が違う。ボタンには状態と飛び先があり、
どちらもカットでばらしたタイムラインを指している。こちらは置いていくことを伝える
ためだけに一覧に出す。

編集画面のプレビューにも出せる。運ぶのとは別の用途で、いま画面に何が出ているのかを
確認するためのものである（`subs.rs`）。こちらは libavcodec で復号できる。PGS も
DVD のサブピクチャも、返ってくるのは 1 ピクセル 1 バイトの索引と色の表で、
[`vobsub::drawn_from`](../../rust/crates/core/src/vobsub.rs) が両方を 1 つの形に
まとめている。それを字幕自身の矩形に切り詰めた PNG にして、ウィンドウが画面の
同じ場所に重ねる。DVD のパレットはストリームに無いので、ここでもディスクの管理情報
から読む（[下記](#ディスクの字幕を焼き込むか別ファイルにするか)）。放送の文字字幕を
読む仕組みは
[放送 TS](broadcast-ts.ja.md#字幕を読んでプレビューの上に出す) にある。

### メニューはストリームではなく、それを知っているのは索引だけである

Blu-ray に載っているもののうち 2 つは、ディスク自身の索引にしか正体が
書かれておらず、どちらも置いていく
（[`disc.rs`](../../rust/crates/core/src/disc.rs)）。

| | |
|---|---|
| **メニュー**（`0x91`、IGS） | インタラクティブグラフィックス。画像と、状態と遷移コマンドを持つボタンである。コマンドはカットには存在しないプレイリストやタイトルを指しており、composition の時刻はカットでばらしたプレイリストの時計で数えてある |
| **テキスト字幕**（`0x92`、TextST） | 書式付きのテキスト。書体はストリームの中ではなく、ディスクの `AUXDATA` にあるファイルで指定される。カットに持ち込んでも、描くための書体が無いテキストになる。描こうとするソフトも無い。libavcodec は `hdmv_text_subtitle` というコーデック ID を持っているだけで、デコーダは無い |

この PID に何が乗っているかは demuxer に問い合わせれば分かるが、その結果は
当て推量である。ここで測ったディスクでは、`0x1400` のメニューが MP3 音声として
返ってきた。映像も本物の音声も持っているクリップでそうなった。それを信じていた
カットは、メニューを音声と宣言して出力に書き込んでいたことになる。実害が
無かったのは、同じプローブがその推量に添えるサンプリング周波数を見つけられず、
周波数の無いトラックは数行後に外されていたからである。しかもそのときの注記は
「pid 0x1400 の音声」と表示していた。

そこで索引を根拠にする。索引がこの 2 つのどちらかだと示す PID は、プローブが
入れようとしたどの一覧からも外し、実際に何であるかで名前を付ける。

```text
audio  : pcm_bluray 48000Hz 2ch  jpn  main   [stream 1 pid 0x1100]
        not carried: a menu on pid 0x1400
```

メニューだけのクリップは、何かが欠けた録画として失敗させるのではなく、メニューで
あると表示する。ディスクのメニュークリップは実際にそういうもので、グラフィックス
だけで映像が 1 枚も無い。

### マーク

チャプターマークは**信用できるときだけ**読む。マークの並びは節の長さから分かるが、
その中の各項目の位置は方言によって違う。BDMV のマークは 14 バイトで、予約 1 バイト・
種別・属する PlayItem・時刻が入る。レコーダーの BDAV のマークはもっと長く、時刻と
一緒に名前とサムネイル参照を持つ。そこで配置は決め打ちにせず、候補をそれぞれ試して、
全部のマークが自分の属するクリップの中に収まる配置を採る。どの候補でも収まらなければ
マークは出さない。見当違いの場所にあるチャプターは、チャプターが無いより悪い。

マークがどの PlayItem のものかを読めるからこそ、「全話連続再生」のプレイリストが
使える。それが読めなければ、どのマークも基準となる時計の無い数字でしかない。5 話目の
チャプターは 5 話目自身のタイムライン上にあり、1 話目のチャプターとは「どちらも
11 秒あたりから始まる」以上の共通点が無い。どのクリップのものかが分からない配置は、
クリップを 1 本しか再生しないプレイリストでだけ信用する。そうしないと全話の
チャプターが 1 話目に積み上がるが、それなら 1 個も置かないほうがよい。

行のマークをいちばん短いプレイリストから取るのも同じ理由による。ディスクは 1 つの
話数を専用のプレイリストでも「全話連続再生」の中でも指しているが、どの話数のものかを
知らなくても読めるのは前者だけである。

### マークはキーフレームになる

ディスクから開いた録画は、そのチャプターが最初からカット編集画面に並んでいる。
日本のレコーダーのチャプターは CM の境目そのものであることが多く、
[CM 検出](../user-guide/cm-detection.ja.md)が数分かけて探しているものを、録画した
機器が正確に書き残したものといえる。

1 つだけ食い違うのが**時計**である。プレイリストはストリーム自身の 45 kHz で数えて
いるのに対し、編集画面が描くタイムラインはコンテナの開始時刻を原点に取り直してある。
そのため、マークの位置は次の式で求める。

```
entry.start + mark - src.start_time
```

`entry.start` はプレイリストの IN 点で、この計算のためにマークと一緒に持ち回る。
`start_time` はストリームを開いて初めて分かる値なので、ディスクを読む段階では
分からない。そのためマークは読んだ場所で時刻に直さず、行と一緒に編集画面まで運ぶ。

マークを置くのは初めて開いたときだけで、録画と同じ名前の `.keyframe` があれば
そちらが優先される。`.keyframe` は人が決めた編集内容であり、ディスクのマークは
まだ誰も決めていないときの初期値だからである。素材の範囲外に落ちるマークは、丸め
込まずに捨てる（理由は上と同じ）。GUI を開かずに時刻を確認したいときは、
`smartcut <ディスク> --title N` でそのまま印字できる。

## ディスク自身の索引

**Blu-ray には索引が最初から入っている。** すべてのストリームに対応する
`CLIPINF/000NN.clpi` に、プレーヤーが再生を始められるピクチャの位置が、表示時刻と
ファイル中のパケット番号として書かれている。これは
[パケットを走査する処理][packetscan]が録画を丸ごと 1 回読んで作る一覧と同じもので
ある。

そこでこれを読む。`disc::entry_points` がマップを解釈し、`index::DiscIndex` が
[`IndexSource`] として提供する。そのための接続点は初めから用意してあった。
ここで計った UHD ディスク、1 クリップ 81 GB・2 時間 34 分では、タイトルを開くのに
8 分 45 秒かかっていたものが 1 秒未満になり、出てきた計画はセグメント単位で走査版と
一致した。

マップは 2 枚の表でできている。粗いエントリが時刻の上位とパケット番号の上位を持ち、
残りを埋める細かいエントリの先頭を指す。したがって 1 点の時刻は両者を組み合わせて
得る。配置は `libbluray` が読んでいるものと同じで、規格の記述に出てこない点が 1 つ
ある。ストリームごとのマップは、自分の細かい表への 4 バイトのオフセットで始まり、
粗い表はその後ろから始まる。

ただし粗いエントリの上位が正しいとは限らない。細かいエントリが持つパケット番号は
17 ビットで、131,072 パケットごとに一周する。録画にすると 20 秒ほどで、
一周するたびに粗いエントリが 1 つ書かれる。ここで測ったレコーダーのディスクのうち
1 クリップでは、そのうち 9 つが一周分古い上位を書いていた。細かいエントリと組むと、
マップが 25 MB 引き返したように読める。後ろの区間の時刻を持つ 9 点が、前の区間の中に
入り込む。同じ 4 枚の残り 19 クリップは正常で、測ったプレスディスクも
全部正常である。エントリーポイントはファイルの中の位置であり、ファイルは一方向にしか
進まない。そこで位置が戻るときは、戻らなくなるまで 17 ビットの周を足す。
20 クリップのうち 19 はこれまでと 1 バイトも変わらない。

古い上位を持つ粗いエントリは、両方のフィールドが古い。そのため時刻も同じように
繰り上げる。細かいエントリが持つ時刻は 11 ビットで、2^20 チックごとに一周する。11.65
秒で、粗いエントリの刻み 2 つ分にあたる。粗いエントリが進んでいないと、
時刻はまるまる一周分早く読める。直し方は位置と同じだが、1 つだけ違いがある。時刻が
単調に増えるのは 1 つの区間の中だけである。何度かに分けて書かれたクリップは
区間ごとに時計を持ち、それが振り出しに戻るのはマップのずれではない。ここの
ディスクには、前の区間が終わる 7 秒前から始まる区間がある。そこで基準は継ぎ目ごとに
捨て、時計が戻るマップは読んだままにする。ピクチャと突き合わせて確認したところ、
測った 4 クリップのうち 3 つは、3,592 点から 3,615 点の全部が、書いてある
時刻にそこにあるピクチャを指していた。直す前も後も同じである。

4 つ目のクリップのマップは、ストリームとは別のものを記述していた。1 つの区間、
クリップの 1 割にあたる 357 点が、指しているピクチャより 6 秒ほど早い時刻を書いて
いて、位置もどのピクチャにも当たらない。同じクリップの残り 5 区間は正確である。
ビットのずれが 1 つも無いので、ここまでの直しはどれも効かない。レコーダーは、
実際には書かなかった区間のマップを書いたことになる。カットにできるのは、その旨を
表示することだけである。エントリーポイントの時刻に届いてピクチャが無かったとき、
代わりに始められる最初のピクチャがどれだけ先かを表示する。8 秒ずれた読みを、
シークの余裕不足と取り違えないためである。

マップから分からないのは、GOP が開いているかどうか、そこにぶら下がる先行ピクチャを
捨ててよいかどうかである。それはビットストリームの中にあり、どんな索引にも無い。
そのため点は `leading_known: false` で届き、`index::refine_leading` が境界の落ちうる
点だけを測る。各範囲の両端の前後 24 点ずつで、どの点もマップが示すバイト位置から
読む。範囲の中の全点を測ると（走査版は自分で判定できるのでこの関数が走らず、長らく
気づかなかった）、先ほどの 1 万 6 千点で 10 分かかった。それではディスクの管理情報を
読む意味が無い。

**1 つの点を測るのは 1 回だけである。** 測った点には印（`AccessPoint::measured`）を
付けるので、録画を開いている間は次の編集で測り直さない。0.8.1 までは編集の
たびに測り直しており、しかもファイルを二分探索するタイムスタンプのシークを使って
いた。UHD のタイトルでは計画 1 回に 30 秒かかり、その間カット編集が止まっていた。
測っている間は開いている録画をロックしたままで、画面の描画もすべてその録画を通して
読むからである。いまは録画の複製で測り、元の録画のロックはすぐに解放する。
タイムスタンプのシークに戻るのは、バイト位置からの読みが外れたときだけである。

ピクチャの大きさも分からない。継ぎ足す分は[録画が入ってきたときのレート][splice]で
書くので、誰も数えていない場合はファイル自身のレートから音声の分を引いた値を代わりに
使う。Blu-ray ではそれで大半が説明できる。非圧縮の音声は、ピクチャの次に大きいから
である。

[`IndexSource`]: ../../rust/crates/core/src/index.rs
[packetscan]: ../../rust/crates/core/src/index.rs
[splice]: rust-core.ja.md#継ぎ目

## 出力先と名前

ディスクの中には書けない。イメージの中にはそもそも書き込めるフォルダーが無いし、
コピーしたディスクの中身はディスクのものである。そこで既定の出力先は**ディスクと
同じ場所**、名前は番組名になる。

```
/rec/Anime_Test.iso
/rec/cut_2026年08月17日01時00分-衛星第一-サンプル番組 ….ts
```

ファイル名にできない文字（`\ / : * ? " < > |`）は全角に置き換える。日本の
レコーダーが同じ問題に対してしているのと同じ方法で、名前は読めるまま残る。

**コンテナは `.ts` になる。** `.m2ts` を指定された libavformat は、Blu-ray 自身の
形、つまり 192 バイトのフレーミングと Blu-ray 自身の PID 番号で書く。しかしどちらも
マルチプレクサが決める値であり、
[SmartCut が書き戻す放送のテーブル](broadcast-ts.ja.md)
が示す配置とは違う。そこで、ディスクから来た録画については「入力と同じ」を `.ts` の
意味にしている。中身は同じストリームである。出力設定画面で M2TS を選べば、これまで
どおり M2TS で出力される（その場合はテーブルがマルチプレクサ任せになることを、
その場で表示する）。

## 名前が 1 本であること

SmartCut は、録画 1 本を**1 つの文字列**で表すことに統一している。一覧が持つ
名前も、シーク用インデックスとプロキシのキャッシュキーも、出力を同じ場所へ置くときの
基準も、デマルチプレクサに渡す名前も、すべてその 1 本である。ディスクの中の録画を
扱えるようにしても、この前提は変えたくなかった。

そこで、イメージの中の録画には、イメージをフォルダーのように綴った名前を与えて
いる。

```
/rec/Anime_Test.iso/BDAV/STREAM/00001.m2ts
```

これは勝手に作った記法ではなく、イメージには本当にその名前のファイルが入っている。
普通と違うのは `/rec/Anime_Test.iso` がフォルダーではなくファイルである点だけで、
[`input.rs`](../../rust/crates/core/src/input.rs) が見ているのはまさにそこである。
パスを遡ってファイルであるところで切ると、3 つの情報が同時に得られる。

| | |
|---|---|
| **URL** | `subfile,,start,…,end,…,,:file:/rec/Anime_Test.iso`。libavformat に渡すもの |
| **ファイル** | `/rec/Anime_Test.iso`。OS に問い合わせるもの。キャッシュが大きさと更新時刻で判断できる |
| **範囲** | そのバイト範囲。libavformat を通さず自分で TS を読む処理のため |

3 つ目が必要なのは [`si.rs`](../../rust/crates/core/src/si.rs) である。放送自身の
テーブル（PAT・PMT・SDT・EIT・SIT）を読む処理はファイルを直接読むので、イメージの
中の範囲として開き、なおかつ 192 バイト間隔でパケットを拾えなければならない。
どちらも実装したので、ディスクから切った出力にも放送のテーブルがそのまま乗る。

### 時計が途中で戻るクリップ

レコーダーは録画を止めては再開する。止めるたびに、次に書く区間は新しいシーケンスと
して自分の時計を持ち、それが 1 本の `.m2ts` に全部入る。ここで測った BD-RE は
1 クリップに 5 本、6 本、7 本のシーケンスを持っていた。プレイリストにはそのとおり
書いてある。シーケンス 1 本につきプレイアイテム 1 つで、IN と OUT がどのシーケンスの
時計の上にあるかも書いてある。

このファイルを丸ごと読むと、何の警告も無いまま読めていなかった。エントリーポイント
マップは 3,598 点あり、バイト位置は最後まで増え続けるのに、時刻は 2 回戻る。
4 点目で 7.1 秒から 1.1 秒へ、最終点でもう一度戻り、時刻が位置を指さなくなる。
libavformat はこのファイルの長さを測るのを諦めるので、`--keep` はすべて「長さ 0 の
録画より後ろから始まっている」として受け付けられなかった。ストリームが壊れている
わけではなく、先頭から読めば最後までデコードできる。

**そこで、読みながら時計をつなぎ直す。**
[`restamp.rs`](../../rust/crates/core/src/restamp.rs) がそれで、つなぎ方の全部が
ここにある。各区間をファイルに入っている順に 1 本の時間軸へ並べ、その差分を区間の
中の全タイムスタンプに足す。提示時刻は PES ヘッダの決まった 5 バイト、プログラム
クロック参照はアダプテーションフィールドの決まった 6 バイトなので、何も動かないし
長さも変わらない。クリップ自身のエントリーポイントマップは元の位置を指したまま
だし、シークインデックスも同じバイトを指す。デマルチプレクサが読むのは、端から端まで
1 本の時計で走るストリームになる。

状態も持たない。あるバイトがどの区間に属するかは位置だけで決まるので、補正値は
パケットの位置から求まる。これでシークが成立する。libavformat はどこへ飛んでもよく、
着いたパケットは先頭から読んだときと同じだけ補正される。

区間をどこへ置くかは、2 つの手がかりを突き合わせて決める。どちらも単独では
足りないからである。シーケンス表にはその区間が提示する範囲が書いてあるが、それは
プレイアイテムが再生する範囲であって、ファイルに入っている範囲ではない。測った
クリップでは 892.94 秒と書いてあり、ピクチャは 894.5 秒まで続いていた。レコーダーは
グループの末尾まで書いて、その内側で編集する。エントリーポイントマップにはピクチャの
位置が入っているが、プレーヤーが再生を始められる位置しか無い。両端でグループ 1 つ分
足りない。ただしマップからは速度、つまりこの区間の 1 秒が何バイトかが出る。最後の
エントリーポイントから区間の終わりまでのバイト数をその速度で換算すれば、どれだけ
続くかが出る。どちらの手がかりも捨てず、区間を広く見積もった方を採る。そうすれば
プレイアイテムが再生する範囲が外に出ることはない。先頭の区間は動かさないので、
先頭から読んだクリップはこれまでと同じ時刻で読める。

どちらの手がかりも、再生される範囲の外側までは届かない。プレイアイテムの IN は
ピクチャだが、その瞬間の音声は 1、2 フレーム手前から始まっていて、ファイルには
それが入っている。ピクチャを起点に置き場所を決めると、その音声は前の区間の終わりより
後ろに落ちる。そこはもう出力の時間軸に書き終えた場所なので、カットはそれを落とす。
その瞬間自体は前の区間が埋めているので、落ちるのは 2 度目の記述であって穴ではない。
カットの最後に出る注記は今そう表示する。以前は録画が壊れていると表示していた。

どちらの読みも上限でも下限でもない。2 つとも区間を狭く見積もるので、置いた結果と
して区間どうしが重なることがある。ここで測ったクリップでは、ある区間が 1 つ前の
区間の末尾 0.46 秒に食い込んで始まる。そのバイト範囲では、1 つの時刻が 2 つの区間を
指す。したがって、あるパケットがどちらの区間のものかは、時計ではなく位置で決める。
`restamp::Seam` が両方を持つのはそのためである。時刻は計画が切る場所を表す。範囲は
時刻の範囲だからである。バイトはレコーダーが実際に書いた境目を表す。

行はクリップ全体になり、名前はもとのままである。

```
/rec/Recording.iso/BDAV/STREAM/00001.m2ts
```

SmartCut のデマルチプレクサは文字列 1 本からしか開かないので、実際に渡すのは
この名前を `restamp:` の URL で包んで補正表を持たせたものである。
[`input.rs`](../../rust/crates/core/src/input.rs) は自前の libavformat i/o
コンテキストを通して読み、ソースパケット単位で読み出し経路に補正をかける。
`subfile` と `concat` がそのまま効くのはそのためである。

継ぎ目はカットとして計画する。区間の先頭のピクチャは、レコーダーが止まる前の
ピクチャを参照しているが、そのピクチャは書かれていない。そのままコピーすると、
デコーダは次に画面を作り直すピクチャまで壊れた映像を出す。レコーダーのストリームでは
それが 1 分後ということもある。そこで `plan::plan_on` は計画の前に、残す範囲を
継ぎ目で切る。セグメントが占めるのは書いたフィールド数であって元の時刻ではないので、
出力の時間軸は詰まる。測った録画では、全体のカットが 5 範囲でコピー 99.7% だった。

そのカットが狙った場所に落ちるには 4 つの条件が必要で、この録画を通しで切るまで
どれも合っていなかった。

- 継ぎ目はカットを指示する側の時計に乗せる。`input::joins` が返すのは
  デマルチプレクサ自身の時計で、トランスポートストリームはゼロから始まらない。
  直さないと継ぎ目は毎回その秒数だけ後ろの区間の中に置かれる。あるクリップでは
  1.1 秒、別のクリップでは 5.0 秒だった。手前の範囲は次の録画のピクチャを要求し、
  コピーは本物の継ぎ目をまたいで走っていた。
- デコーダには区間を 1 つしか見せない。向こう側も渡すと、libavcodec は手前の分を
  捨てる。継ぎ目の後の区間は IDR で始まり、その IDR には並べ替え待ちのピクチャを
  出さない指示が付いている。手前の区間の最後の 1 秒は、完成して順番を
  待っていただけのピクチャごと消える。そこで `cut::reencode_segment` は継ぎ目の
  バイトで供給を止め、そこでデコーダを空にする。待たされていたピクチャはそれで
  返ってくる。
- 向こう側は継ぎ目ではなく最初のエントリーポイントから始める。間にあるのはその区間の
  先行ピクチャで、ファイルの中にそれを解く材料は無い。普通の先頭として計画すると、
  存在しないピクチャの再エンコードを指示することになってカットが止まる
  （`segment …: no pictures decoded`）。`plan::past_the_seam` が範囲の先頭を
  エントリーポイントへ動かす。プレーヤーが再生を始める位置も同じである。一緒に
  録れていた音声もそこで捨てる。0.3 秒ほどである。ピクチャより先まで音声を残すと、
  範囲の残り全部がずれるからである。
- 読み出しは正しい区間の中から始める。継ぎ目の向こうの時刻へは、時刻として
  シークできない。libavformat はバイト位置で時刻を読みながら探すが、継ぎ目を
  またぐと時刻がバイトと一緒に増えなくなる。継ぎ目の直後から始まるコピーは、1 つ前の
  区間の最後のエントリーポイントを先に拾う。ファイルでは手前にあって時刻では後ろに
  ある点である。それをシークの行き過ぎと判定して止まっていた。着地が継ぎ目より
  手前になるときは、`cut::seek_into` が継ぎ目のバイトへシークする。

つなぐのは、プレイリストがクリップ全体を説明しているときだけである。つまり、
クリップが持つシーケンスの全部を、ファイルに入っている順に、プレイアイテム
1 つずつで指している場合である。それ以外はこれまでどおり、プレイアイテムごとに
1 行にし、再生するパケットの範囲で指す。DVD のタイトルをセクタで指すのと同じである。

```
/rec/Recording.iso/BDAV/STREAM/00001.m2ts@8960-4605951
```

シーケンスが 1 本のクリップは丸ごと指す。これまでのディスクは全部それだし、
SmartCut が書くディスクもそうである。シーケンス表が表として読めないクリップも
丸ごと指す。シーケンスはクリップの先頭から始まり、前のものより後ろに並び、全部が
ファイルの中に収まっていなければならない。

実測では、レコーダーが焼いた BD-RE 4 枚で、106 行に並んでいた 20 番組が 20 行に
なった。長さは索引のとおり 44:19 から 47:57 で、放送の長さである 44:41 と 45:10 に
合う。参照ディスク 4 枚、プレス Blu-ray、DVD は以前とまったく同じに並ぶ。

カットも 20 本すべて通した。書き出せたのは 17 本から 19 本になった。20 本目は
[次の節](#区間のマップが別の何かを指している)で扱う。どちらでも書き出せたタイトルで
比べると、出力の映像の最大の穴は 0.751 秒から 0.083 秒に縮む。継ぎ目 1 つで失う
ピクチャは 3 枚であって、1 秒分ではない。出力の時間軸に置けなかったピクチャ 68 枚も
0 枚になる。音声の穴は残る。同じタイトルで 0.38 秒と 0.84 秒で、これは新旧どちらも
同じである。録画そのものにある穴だからである。トランスポートストリームはある瞬間の
音声をピクチャの 1 秒ほど後ろに載せるので、レコーダーが書き終えた時点でその 1 秒は
書かれていない。

継ぎ目で失うピクチャが 3 枚で済まないこともある。ここで測った 1 か所は 22 枚
だった。コピーをどこから始められるかは、その入口にぶら下がる先行ピクチャで決まる。
それを測る（`index::refine_leading`）のは、呼び出し側が指定した範囲の境目のまわり
だけである。継ぎ目は計画の側があとから作る境目なので、そこで範囲が始まる点は一度も
測られない。ピクチャを読んでいない索引では、どの点も安全と見なされる。レコーダーの
ストリームではそうでないことが多い。このクリップを走査すると、5,444 点のうち
5,440 点が「参照されている先行ピクチャを持つ開いた GOP」である。そこからコピーを
始めると、デコーダは復帰するまで何も出さない。1 本丸ごとで測ると、4 つの継ぎ目のうち
2 つは 0 枚、3 つ目が 0.067 秒、4 つ目が 0.734 秒だった。パケットは書かれている。
映像が画面に出ないだけである。

継ぎ目でも測った結果に従うのが素直な方法だが、採っていない。この素材では負担が
大きいからである。コピーを再開できるのは約 18 秒先で、継ぎ目 4 つなら 72 秒の
再エンコードになる。ほかは 99.7% がコピーのタイトルでそうなる。`--clean-joins` が
既定オフで提供されているのと同じ判断なので、ここに書き留めておく。

### 区間のマップが別の何かを指している

20 本目はここで止まっていた。上の 4 つとは別の不具合で、継ぎ目はレコーダーが
記録したとおりの場所にあり、エントリの側が間違っている。1 本のクリップの 6 区間の
うち 4 番目だけが、指している位置のピクチャより 6 秒早い時刻を書いていて、しかも
先頭 2 点はさらに 11.65 秒早い。これは細かいエントリが持つ 11 ビットの一周分である。
区間の長さも同じだけ狂っていて、ピクチャ 289 秒分に対して 316 秒と書いてある。
同じクリップの他の区間も、同じディスクの他の 7 クリップの 3,592〜3,615 点も、
すべてストリームと 1/1000 秒の精度で合っている。

どの区間が信用できるかはマップのどこにも書いていないので、全部の区間を 1 つずつ
確認する。シーク 1 回と短い読み取り 1 回で済む確認で、**その区間の先頭バイトにある
最初のピクチャが、先頭のエントリの指すピクチャと一致するか**を見る。一致しなければ
その区間のエントリは捨て、ストリームを読んで作り直す。読むのはその区間だけ
（数百 MB）で、クリップ全体ではない。そして手前の継ぎ目を、その区間が実際に持って
いる最後のピクチャまで引き戻す。これが `index::mend_stretches` である。

確認するのは継ぎ目を持つクリップ、つまりレコーダーが焼いたクリップだけで、しかも
ストリームから作っていない索引に対してだけである。走査した索引は自分が読んだものと
食い違いようがない。20 本のうち発動するのは 1 本の 1 区間で、残り 19 本はコピー
秒数まで以前と同じ計画になる。直った 1 本はコピー 99.8% で書き出せる。隣の
タイトルと同じ値である。

普通の録画には何も起きない。それも測った。放送 TS 3 本、参照 Blu-ray 2 枚、
DVD 2 タイトルのカットは、バイト単位で以前と同一である。

## DVD-Video

DVD は Blu-ray と同じ入口から入ってくるが、共通点はそれだけである。そのため
[`disc.rs`](../../rust/crates/core/src/disc.rs) ではなく
[`dvd.rs`](../../rust/crates/core/src/dvd.rs) が読む。`disc::read` は両方を試し、
ディスクを認識したほうの結果を使う。下流に渡るのはこれまでと同じ `Disc`・`Entry`・
`Track` である。

```
$ smartcut documentary-01.iso
disc  : documentary-01.iso
        dvd -- documentary-01
        2 recording(s)

  1  00:59:51.400  documentary-01 1 (1/2)  18 mark(s)
       0x01e0  MPEG-2 720x480 NTSC 4:3
       0x0080  AC-3 2ch 48kHz  ja
  2  00:00:08.342  documentary-01 1 (2/2)  1 mark(s)
```

DVD の性質のうち 3 つが、この読み取りの形を決めている。

### ストリームは 9 本ではなく 1 本である

`VTS_01_1.VOB` から `VTS_01_9.VOB` までは 1 本の MPEG プログラムストリームで、
ISO 9660 が 1 GB より大きいファイルを扱えなかったために分割されているにすぎない。
ディスクはこれを 0 から数える 1 続きのセクタとして指す。つまりセクタ 536,000 から
始まるセルは、3 本目のファイルの 400 MB 目にある。

断片は隙間なく並ぶ。今回対象にしたディスクでもぴったり並んでいた。

| | オフセット | 終端 |
|---|---|---|
| `VTS_01_1.VOB` | 24,727,552 | 1,098,182,656 |
| `VTS_01_2.VOB` | 1,098,182,656 | 2,171,582,464 |
| `VTS_01_3.VOB` | 2,171,582,464 | 3,244,935,168 |
| `VTS_01_4.VOB` | 3,244,935,168 | 4,289,400,832 |

したがってイメージの中ではタイトルセット全体がひと続きのバイト範囲になり、
タイトルは Blu-ray のクリップと同じく `subfile` 1 本で開く。フォルダーなら断片は
9 個のファイルなので、libavformat の `concat` プロトコルでつなぎ、その外側に
`subfile` を被せてタイトルの範囲だけを取り出す。どちらの場合も、展開もコピーも
しない。

プロトコルを入れ子にするには指定が 1 つ必要になる。最上位で何が許されていようと、
その内側のプロトコルは `file` だけを含むホワイトリストで検査される。
`input::demux` は、開くすべての録画に `protocol_whitelist` を `file,subfile,concat`
として設定する。ただのパスも例外ではない。0.8.3 からそうしている。`.ts` を名乗る
プレイリストを渡されると、libavformat はそこに書かれた先を取りに行くからである。

### タイトルはセルの連なりである

Blu-ray では 1 話に 1 本のストリームが対応するのに対し、DVD では 1 本のストリームの
一区間が 1 話に対応し、その位置は `.IFO` のテーブルにしか書かれていない。

| テーブル | そこから取るもの |
|---|---|
| `VIDEO_TS.IFO` の `TT_SRPT` | プレーヤーが番号を振る順のタイトル一覧と、それぞれがどのタイトルセットにあるか |
| `VTS_NN_0.IFO` の `VTS_PTT_SRPT` | セット内の各タイトルについて、チャプターである `(チェーン, プログラム)` の組 |
| `VTS_NN_0.IFO` の `VTS_PGCIT` | 各プログラムチェーン。そのセル、長さ、再生するセクタ、各プログラムが始まるセル |
| `VTS_NN_0.IFO` の `VTSI_MAT` | 映像と、セットが宣言している音声・サブピクチャのトラック |

チャプターの位置は、その手前のセルの長さの合計で決まる。したがって、セルが端から
端まで連なっていなければこの計算は成り立たない。連なっていないチェーンはアングル
ブロックか、複数タイトルの断片から組まれたものなので、これらは読まない。セルが
たまたま収まっている範囲はタイトルではないので、それをタイトルとして出すくらいなら
何も出さないほうがよい。

タイトルがファイルではなく区間である以上、名前でどの区間かを示す必要がある。

```
/rec/documentary-01.iso/VIDEO_TS/VTS_01_1.VOB@0-2081904
```

このセクタ番号はディスク自身のもので、タイトルセットのストリームの先頭から
数えている。`VTS_01_1.VOB` とだけ書いた名前では、ディスクにある 4 GB 全部を指して
しまい、どの 1 話も指せない。

### 時計はストリームの側にあり、索引の側にはない

セルの時間は、タイトルの先頭から数えた長さである。一方、プログラムストリームの
タイムスタンプは、オーサリング時のマルチプレクサが始めた値から始まる。今回の
ディスクなら 0.281 秒である。「12 分のところ」というチャプターは、両者をつなぐ
ものが無ければストリームの時計の上の時刻にならない。

両者をつなぐのがナビゲーションパックである。VOBU は必ずこれで始まる。プレーヤーが
読んで表示しない 2048 バイトで、`VOBU_S_PTM`（後続のピクチャを提示する時刻）と
`VOBU_E_PTM`（それが終わる時刻）を持っている。タイトルの先頭セクタのものを読むのは
2048 バイトの読み取り 1 回で済み、編集画面がまさに必要とする数値がそのまま得られる。
DVD の `Entry::start` が索引からの推測ではなく実測値なのはそのためである。

**タイトルが複数の時計をまたいでいることも、これで分かる。** DVD は別々に多重化
された断片からタイトルを組んでよく、その継ぎ目でタイムスタンプは振り出しに戻る。
今回のディスクがまさにそうだった。

```
セル 18 の終わり  323,571,480  (3595.24 秒)
セル 19 の始まり       36,010  (   0.40 秒)
```

2 つの時計を繋ぐのは、1 つを切るのとは別の操作である。Blu-ray で複数クリップの
プレイリストがクリップごとに 1 行になるのと同じ理由で、DVD のタイトルも継ぎ目で
分ける。上のディスクは、18 チャプターの 1 時間と、それに続く 8 秒の 2 行として出る。
1 行のなかで後半が前半に重なることはない。2 つのセルが同じ連なりに属するのは、後の
セルが前のセルの終わった位置から始まるときである。前のセルがどこで終わったかは、
索引が指すそのセルの最終 VOBU から読み取る。

このディスクの 2 つのタイトルは、19 セルと、その最後を除いた 19 セルである。
合わせて 3 つではなく 2 つなので、行は指しているストリームの区間で重複を除く。

### プログラムストリームはタイムスタンプを省く

プログラムストリームは、すべてのピクチャに提示時刻を載せるわけではない。前後の
ピクチャから表示順が割り出せる場合、マルチプレクサはそれを省く。今回のディスクでは
4 枚に 1 枚がそうだった。

```
pts=31263  dts=22254  K     pts=N/A    dts=31263
pts=25257  dts=25257        pts=34266  dts=34266
pts=28260  dts=28260        pts=N/A    dts=40272
```

SmartCut の処理はすべて提示時刻を鍵にしているので、時刻の無いピクチャは捨てられて
いた。その結果、無劣化コピーの出力からフレームが 4 分の 1 も減っていた。
libavformat 自身は時刻を割り出せる（`fflags +genpts` がデコード時刻から並べ直す。
これは正確である）が、ファイルを開く前に指定しなければ動かない。そこで
`input::demux` は、プログラムストリームに対してだけこのフラグを指定する。トランス
ポートストリームはすべてのピクチャに時刻を打っているので、このフラグを付けても何も
変わらないが、すべての録画が通る経路に余計なフラグを置きたくないからである。
（開き直す理由はもう 1 つあり、それも同じ考え方による。
[下記](#フレームレートを名乗らないディスク)。）

プログラムストリームには自分の長さも入っていない。libavformat はファイルの両端の
タイムスタンプから長さを割り出すが、末尾に不連続を含む 4 GB の DVD では、1 時間の
タイトルに対して 8.3 秒という値を返してきた。全パケットを読む走査のほうが正しい値を
持っているので、そちらを `index::Index::end` として報告するようにした。ただし
コンテナ自身の値のほうが長ければ、そちらを採る。長さを正しく持っているコンテナは、
その値をそのまま保てる。

### コンテナのシークテーブルは、末尾まで届くだけでなく録画全体を覆っていなければならない

`--index auto` はパケット走査の前にコンテナのシークテーブルを調べる。テーブルを
読むのは一瞬で済み、4 GB を読み通すのはそうではないからである。ところがプログラム
ストリームにはそういうテーブルが無い。libavformat がプログラムストリームに対して
返すのは、最初の数フレームへ辿り着くまでの probe がたまたま索引した分だけである。
12 分半のタイトルで 8 エントリ、先頭 4 秒分だった。

これを額面どおり受け取ると、索引が無いより悪い。4 秒より後のどこで切ってもコピー元に
できるエントリーポイントが見つからず、タイトルを丸ごと再エンコードすることになる。
`--scenes` も録画中の境界をすべて同じフレームに引き寄せてしまう。

そこで、負担のかからない確認をテーブルに対して行う。そのテーブルは録画を覆って
いるか、という確認である。probe が止まった位置で終わっているテーブルは採用せず、
代わりに走査の結果を使う。これで同じカットが 98.2% をコピーするようになり、シーン
一覧は 1 つの繰り返しではなく 249 件になった。

末尾まで届いているかだけを確認するのでは足りない。1999 年の DVD でそれが分かった。
libavformat はプログラムストリームの長さを、ファイルの末尾へ
シークしてそこにあるものを読んで測る。そしてその 1 パケットも他と同じように
索引する。1 時間半のタイトルに対して残ったテーブルは、先頭 5 秒に 10 エントリ、
そして 5110.9 秒のうち 5110.6 秒に 1 エントリだった。末尾には届いている。その間には
何も無いのに、確認を通ってしまった。結果として壊れたのはカットではなく
編集画面である。フィルムストリップはエントリーポイントの上にセルを描くので、その
1 時間半のどこを開いても描く材料は 2 つしかなく、キーフレーム送りには送る先が
無かった。

そこで穴の有無も確認する。ただし比べる相手はテーブル自身の間隔ではなく録画の
長さである。本物のテーブルの間隔は 3 倍どころではなく散らばる。エンコーダが映像の
変わったところにエントリを置くからである。ここで捕まえたいのは、間隔が不揃いな
テーブルではなく空のテーブルである。**録画の 10 分の 1 より広い穴**が
空いているものは、コンテナが保持していたテーブルではない。

代わりに使った走査は、4 GB のタイトル全体を 3.2 秒で読み切った。これがこの順序が
正しいもう半分の理由である。DVD ではテーブルは元々たいして時間を節約しておらず、
そのくせすべてを台無しにしていた。

`examples/indexdiag.rs` は 3 つの供給元それぞれを別々に調べ、各々が何を返すかを
表示する。除外すべきテーブルが通ってしまっていることは、こうして見つかる。早い段階の
供給元が誤った結果を返しても、どこも派手には壊れないからである。録画は開くし、編集
画面は渡されたエントリーポイントで描かれる。

### DVD の音声は、DVD 以外が名乗らないストリームに入った LPCM である

DVD のリニア PCM は、DVD の規格でしか定義されていないプライベートストリームに
乗っている。マルチプレクサが選ぶストリーム種別は「何かのプライベートデータ」で、
これで書き出すと、どの読み取り側もそのトラックを `bin_data` と判定し、無音を
再生した。

そこで **Blu-ray の LPCM** として出すようにした。トランスポートストリームが
まさにこの種のサンプルのために持っている形である。マルチプレクサが正しい種別を書く
`.m2ts` とディスクは、それだけで直る。素の `.ts` には
[PMT の書き直し](broadcast-ts.ja.md#録画自身の表を書き戻す)が必要だが、そもそも
放送でなかった録画には PMT を書き直す経路が無かった。今はそれも通る。マルチプレクサ
自身が書いたものを土台に、この 1 点だけ直して、他には何も足さずに組み直す。

### ディスクの字幕を焼き込むか、別ファイルにするか

DVD の字幕も Blu-ray と同じく画像で、表示コマンドの付いたランレングス圧縮の画像で
ある。似ているのはそこまでである。Blu-ray のグラフィックスには TS のストリーム種別
`0x90` があり、[カットの中に入れて運べる](#ディスクが描く字幕)が、DVD のものには
無い。`.ts` に書き込むと種別不明の private data になり、読み戻すとどれも `bin_data`
になる。運ばれて宣言もされているのに見えない。訂正に使える番号が存在しない。

そこで行き先を 3 つ用意し、`--subtitles` で選ぶ。ディスクを切るときに出力設定が
1 行で確認する内容も同じである:

| | |
|---|---|
| `pgs`（既定） | カットの中へ、TS が運べる種類として。Blu-ray のものは無加工で通し、DVD のものは[変換する](#dvd-の字幕を-blu-ray-のものに変換する) |
| `beside` | カットとは別のファイルへ、`.idx` と `.sub` の 2 ファイルとして。DVD のものは無加工で置き、Blu-ray のものは[ディスプレイセットから読み戻す](#blu-ray-の字幕を-dvd-のものとして書く) |
| `sup` | カットとは別のファイルへ、`.sup` として。コンテナの外に出したディスプレイセットそのもの。Blu-ray のものはバイト単位でそのまま、DVD のものはカットに入れるときと同じ変換を通す（[下記](#sup-ディスプレイセットに何も被せない形)） |

既定が「中」なのは、1 ファイルで完結するからである。字幕が中に入ったカットは、
どこで開いても字幕が付いてくる。別ファイルが必要になるのは字幕ツール、古いセット
トップボックス、そして MP4 である。MP4 は何を指定されても別ファイルにしか置けない。

2 ファイルの形式は、既存のソフトで広く読める VobSub である
（[`vobsub.rs`](../../rust/crates/core/src/vobsub.rs)）:

```text
cut_title.ts     カット
cut_title.idx    字幕が何で、どれがいつ出るか
cut_title.sub    字幕の画像そのもの、無加工
```

再エンコードは一切しない。`.sub` にはディスク自身のユニットが、届いたときの
プログラムストリームの枠組みのまま、1 セクターに 1 つずつ入る。`.idx` は時刻と
ファイル位置を書いたテキストである。プレーヤーはカットを開けば名前でこの 2 つを
見つける。

**パレットはストリームの中に無い。** ユニットには「色 4」としか書かれておらず、
色 4 が何色かは書かれていない。DVD は 16 色を索引の側に、それが属するセルの連なりと
一緒に置いている。そこでカットはディスクに戻り、タイトルを切り出したチェーンの
パレットを読み、DVD が書いている studio range の輝度と 2 つの色差から変換して、
`.idx` の先頭に書く。これが無いと字幕は偶然にしか正しく表示されない。

残す範囲の両端は整える。Blu-ray のグラフィックスと同じだが、ユニットが自分の
時間割を持っているぶん、もっと単純である。範囲が開く瞬間に出ていたものは最初の
フレームでもう一度書き、終わる瞬間に出ているものは停止だけを指示する 10 バイトの
ユニットで消す。ディスク自身が面を空けるときに送っているものと同じである。後者は
省けない。ここで測ったディスクのユニットは、1 つとして自分では止まらない。どの
字幕も次のユニットが来るまで出続けるので、途中で終わったカットでは出しっぱなしの
まま、消しに来るものが無い状態になる。

範囲の頭で書き直すユニットに停止の指示があれば、停止までの時間を範囲の最初の
フレームから数え直す。停止はユニットが表示された時点から数える。0.8.3 までは
ユニットをそのまま書いていたので、範囲が始まる前に出ていた時間のぶんだけ字幕が
長く残っていた。

#### DVD の字幕を Blu-ray のものに変換する

これが既定である。カットは 1 ファイルで完結すべきだからである。DVD のユニットから
画像を取り出して、TS が運べる種類の字幕、つまり Blu-ray の形式として書き直す。
そうすれば字幕はカットの中にあり、開いた読み取り側はどれもそれを見つける。運べるのは
TS だけなので、MP4 を指定された場合はその旨を表示して、代わりに 2 ファイルを別途
書き出す。

再サンプルはせず、画素は 1 つも失わない。**2 つの形式は字幕を同じ形で持っている。**
画素ごとのインデックス、そのランレングス符号、そして色の表である。変わるのは
ランの綴り方（一方に 4 通り、他方にも別の 4 通りある）と、色の書き方だけである。
DVD は赤・緑・青と不透明度で書き、Blu-ray は輝度・2 つの色差と不透明度で書く。
画像を取り出すのは libavcodec 自身のデコーダで（ディスクの索引から取ったパレットを
渡す。これだけはデコーダには分からない）、書き直すのは
[`pgs.rs`](../../rust/crates/core/src/pgs.rs) である。

画素の他に必要なのは時間割で、そこが 2 つの形式の食い違うところである。DVD の
ユニットは、いつ出るかを自分で持ち、いつ消えるかも持っていることがある。Blu-ray の
ディスプレイセットは、どちらも外から指示されないと決まらない。そこでここでは
1 つずつ保持する。新しいものが出れば前のものを置き換え、消える時刻を
持っていたものはその時刻に消し、範囲が終わる時点で出ているものはそこで消す。
[上記](#ディスクが描く字幕)で範囲の両端を整えたのと同じことを、反対側から
やっている。

表示するものを持たないユニットもある。停止だけのユニットや、全面が透明な画像の
ユニットで、ディスクはこれを使って字幕を消す。libavcodec はこうしたユニットに
対して何もデコードしない。0.8.3 まではそれを読み飛ばしていたので、消えるはずの
字幕が次の字幕まで残っていた。いまはそのユニットが表示される時刻に面を空ける。

#### Blu-ray の字幕を DVD のものとして書く

同じ変換を逆向きに行う。理由も逆で、字幕ツールや、ディスプレイセットを扱えない
プレーヤーや、MP4 が読めるのは別ファイルの 2 つだからである。Blu-ray に
`--subtitles beside` を指定すると、ディスプレイセットを 1 つずつデコードし
（[`pgs::read`](../../rust/crates/core/src/pgs.rs)）、その画像を DVD の
ユニットとして書き直す（[`vobsub::unit`](../../rust/crates/core/src/vobsub.rs)）。

途中で 3 つのものを作り出す必要がある。DVD の形式にはあって、Blu-ray の形式では
2 ファイルに必要な場所に無いものである。

**16 色のパレット。** DVD のパレットはディスクの管理情報にある。Blu-ray のパレットは
ディスプレイセットごとに入っていて、毎回違い、多いときは 256 色ある。そこで字幕を
処理するたびに 16 色を組み立てる。各字幕の色を `.idx` の番号の下に書き留め、すでに
書いた色に十分近い色はその色に寄せる。字幕の 4 色はそれが描かれた色の平均であり、
同じ白い文字でも 1 行ごとに平均が一段ずれる。来たとおりに書き留めていたら、1 本の
映画の白だけでパレットを使い切る。16 色が埋まったあとは、いちばん近い色が 17 色目の
代わりになる。

字幕あたり 4 色。DVD のユニットは 1 画素 2 ビットで、16 色のうち 4 つ、背景・
パターン・エンファシス 2 つを指定する。これはまさに字幕を構成する要素、すなわち
「何も無い」と文字と縁とその間のぼかしである。Blu-ray のアンチエイリアスされた
文字はそれが 30 段階で届くので、実際に描かれている色を、各色が画像のどれだけを
占めるかで重み付けして 3 つにまとめる。使用量の多い順に 3 つ取るのではない。文字の
内側の階調は縁より多く使われるので、数だけで選ぶと白が 3 つ取れて縁が消える。そこで
最初の中心はいちばん多い色、それ以降は「すでに選ばれた色からの距離 × 占める量」が
最大の色とし、あとは普通に収束させる。4 回まわす。数十色を 3 つにまとめるにはそれで
足りる。

それぞれの表示時間。ディスプレイセットには表示時間が無く、字幕を消すのは後から来る
別のセットである。ユニットの方には書ける。止める側のシーケンスがそれである。そこで
1 つずつ手元に留め、それを終わらせるセットが来てから、時間を埋めて書く。留めずに
出しっぱなしにしても、DVD 自身の規則に従うプレーヤーでは正しく出る。だが
libavcodec の上に作られたソフト、つまりほとんどのソフトでは、長さゼロの字幕になる。
1 セット待つだけで、この違いが無くなる。

範囲の両端に新しい仕掛けは不要である。ここに届くのは、どちらにせよディスプレイ
セットだからである。運ばれてきたもの、範囲の先頭でもう一度出したもの、範囲の末尾で
面を空けるために書いたものである。[上記](#ディスクが描く字幕)の手当てがそのまま
ここの手当てになり、範囲の末尾で面を空けるセットが、最後のユニットの停止時刻を
埋める役をする。

形式上の制限が 1 つある。ユニットは自分の長さを 2 バイトで持つので、1 つは
65535 バイトまでしか書けない。文字 1 行はランレングス符号で数キロバイトなので
届かない。全画面の画像は届きうるので、入らなかったものはプレーヤーが受け付けない
ものを書く代わりに、数えて報告する。

#### `.sup`: ディスプレイセットに何も被せない形

3 つ目の行き先であり、Blu-ray の字幕を**まったく変換しない**唯一のものである。
`.sup` とは、ディスプレイセットをコンテナの外に出したときの形である。届いたままの
セグメントが 1 つずつ、いつデコードしていつ出すかを示す 10 バイトを先頭に付けて並ぶ
（[`pgs::Sup`](../../rust/crates/core/src/pgs.rs)）:

```text
"PG"  pts  dts  type  length  [ セグメント ]
 2     4    4    1      2
```

形式はこれで全部である。そのため Blu-ray の字幕はバイト単位でそのまま出てくるし、
BDSup2Sub も Subtitle Edit も、ディスクの字幕を扱うソフトなら何も設定しなくても
読める。DVD の字幕はカットに入れるときと同じ変換
（[上記](#dvd-の字幕を-blu-ray-のものに変換する)）を通り、ストリームではなく `.sup`
に書かれる。DVD の字幕を 4 色に潰さずに `.mp4` と並べて置けるのはこの
方法だけである。

ここに届くのは 2 ファイルの側に届くのと同じディスプレイセットであり、カットが運ぶ
のとも同じものである。したがって残す範囲の両端の手当ては
[上記](#ディスクが描く字幕)のままで、ここでは何も考慮しなくてよい。

2 ファイルとの違いが 1 つあり、それは形式上のものである。`.sup` は 1 ストリーム
しか持てない。`.idx` はディスクにあっただけの本数を書ける。字幕が 2 本ある録画は
2 ファイルになり、それぞれがディスクに書かれた言語を名前に取る
（`cut_title.eng.sup`）。ディスクに言語が無いとき、あるいは 2 本が同じ言語のときは、
乗っている番号が代わりに入る。

読み取りについて 2 つ、どちらも半日を費やしたので書いておく。

* DVD の字幕は、録画のストリーム一覧にそもそも出てこないことがある。音声と 1 本の
  ストリームを共有し、パケットの先頭の 1 バイトで区別されるので、libavformat は
  最初の 1 つに出会って初めてストリームを作る。ここで測ったディスクでは 400 MB
  読んだところだった。タイトルを開くのにそこまでプローブするのは割に合わない。
  ディスク自身の索引には最初から書かれているので、一覧はそちらから取り、
  パケットはあらかじめ決めた索引ではなく、それが何であるかで突き合わせる。
* 捨てるのはシークの後であって、前ではない。範囲の手前 8 秒は、映像と音声を
  libavformat の内側で捨てながら読む。それで先読みが軽くなる。だが先に捨てて
  しまうとシークが拒否される。録画は自分のストリームのどれかを頼りにシークするので、
  捨てたストリームでは辿れない。そして何も読めないコンテキストと、字幕なしで警告も
  なく開く範囲が残る。

書き込みについても 1 つ。**ストリームはファイルのヘッダが書かれる前に存在して
いなければならない。** 変換したストリームは SmartCut 自身が作るもので、録画の中に
写す元が無い。これをヘッダが出た後に足したところ、マルチプレクサは初期化していない
ストリームを抱えることになった。その結果はエラーではなく、数フレーム後に、その
ストリームについて警告を出そうとしたマルチプレクサの中でのセグメンテーション違反
だった。

### フレームレートを名乗らないディスク

libavformat はプローブしながらフレームレートを割り出すが、そのプローブは特に
指示しなければ最初のプログラムマップで止まる。VC-1 で書かれたプレス Blu-ray では
それでは早すぎた。`avg_frame_rate` は未設定のまま返り、フレームレートが「非数」で
あれば、そこから導かれる長さはすべて意味をなさなくなる。録画の長さも、マークの
位置も、区間が何枚のピクチャを持つかもである。

`scan_all_pmts` はすべてのマップを読むので、これで直せる。常に有効にしていないのは、
SmartCut が読む素材に特有の事情があるからである。日本の放送でこの徹底した読み方を
すると、トランスポートストリームに載っている 2 番目の番組まで拾ってしまう。同じ
素材の携帯向けの複製が別の pid に載っているためで、それは指定された録画とは別の
録画である。そこで `input::demux` はまずコンテナから読み、フレームレートが得られ
なかったときだけ開き直す（`states_frame_rate`）。`+genpts` で開き直すときと同じ
考え方である。

## 何をしていないか

| | |
|---|---|
| **暗号化ディスク** | 対象外。AACS の復号は一切扱わない。暗号を外すツールで複製された市販ディスクは、他のディスクと同じように読める |
| **ディスクとして書き出す** | 未対応。オーサリングであり、別の問題である |
| **複数クリップの結合** | 未対応。クリップごとに 1 行として見せている（上記） |
| **BDMV のタイトル** | `index.bdmv` に並ぶのはタイトルで、タイトルはナビゲーションのプログラムである。「T05 Extra 01」がどのプレイリストかは解決していない。行の名前はディスク名とクリップ番号になる |
| **EP マップが読めないクリップ** | マップがあればそれを使い（[ディスク自身の索引](#ディスク自身の索引)）、無ければパケット走査で作る |
| **BD 固有のストリーム** | PGS の字幕は TS に運ぶ。ディスプレイセット単位で運び、各範囲の両端を整える（[上記](#ディスクが描く字幕)）。指定があればカットとは別のファイルに書く。VobSub の 2 ファイル（[上記](#blu-ray-の字幕を-dvd-のものとして書く)）か `.sup`（[上記](#sup-ディスプレイセットに何も被せない形)）で、ディスクを MP4 に切って字幕を残す方法はこれである。IGS（メニュー）と TextST（テキスト字幕）は落とし、落としたことを表示する。理由は[上記](#メニューはストリームではなくそれを知っているのは索引だけである)。音声はすべて運ぶ。LPCM・DTS-HD・TrueHD・E-AC-3 である（[上記](#ディスクが持っている音声)）。VC-1 の映像は読み、一覧に出し、カットもできる。部分 GOP は[自前のエンコーダ](rust-core.ja.md#エンコーダのないコーデック-vc-1)が書く |
| **DVD のサブピクチャ** | TS が運べる種類に変換して中に入れる（既定）か、無加工のまま VobSub の 2 ファイルとして別に書くか、変換して `.sup` として別に書くかのいずれかである（[上記](#ディスクの字幕を焼き込むか別ファイルにするか)）。そのままの形で中には入れない。TS にそのストリーム種別が無いからである |
| **DVD のアングル** | セルがアングルブロックまたはインターリーブユニットになっているチェーンは出さない（[上記](#タイトルはセルの連なりである)） |
| **DVD として書き出す** | DVD タイトルのカットは TS になる。DVD の形式とは、大きさに上限のある VOBU、その先頭ごとのナビゲーションパック、全セルを記述する `.IFO` のことであり、それはオーサリングという別の問題である |
| **暗号化された DVD** | AACS と同じく対象外。CSS の復号は一切扱わない |

## 検証

実素材のディスクと、そこから作った合成素材とで確認している。

**実素材の BDAV。** TMSR6 が書いた BDAV を ImgBurn で UDF 2.60 の ISO にしたもの
（3.4 GB、3 クリップ、1920x1080 MPEG-2 + AAC + ARIB 字幕、部分 TS）。3 件の
番組名がすべて正しく読め、バイト範囲は独立に書いた Python の UDF リーダーと一致し、
切り出した 60 秒は 99.2% 無劣化で、放送自身のテーブル（PID 0x1100 / 0x1101 /
0x1102、SIT 0x1F）がそのまま乗った。同じクリップをフォルダーに取り出して同じ範囲を
切ると、出力は md5 まで一致した。

**実素材の BDMV。** 12 話 1 期を MakeMKV でバックアップし、ImgBurn で UDF 2.50 の
ISO にしたもの（33 GB、45 プレイリスト、328 PlayItem、62 クリップ）。ディスク名は
`META` から読め、62 行は重複なしで出て、最初からチェックが入ったのはちょうど
12 話で、各話は自分のプレイリストが書いた 4 つのチャプターを持つ。バイト範囲は
`subfile` 経由で開いて demux できた。0x1011 の H.264、0x1100 / 0x1101 の
TrueHD（AC-3 込み）、0x1200 / 0x1201 の PGS である。1 話を 10 秒切り出したところ
91.8% がコピーで、TrueHD 2 本ともそれぞれの PID に乗り、全サンプルがデコードできた。

**UHD ディスクの字幕をカットを越えて運ぶ。** 2160p 本編（HEVC、LPCM 5.1、0x1200 の
PGS）から 60 秒を切り出し、4 つある境界のうち 3 つが字幕の途中に落ちるように
2 範囲でカットした。範囲の中のディスプレイセットは composition 番号もそのままに
44 パケットが出力側へ出て、ディスクがそこへ送っていないパケットが 11 本書かれた。
2 つ目の範囲が開く瞬間に出ていたセット 5 本（最初のフレームで出し直したもの）と、
2 つの範囲の消去 3 本ずつである。読み戻すと `.m2ts` でも素の `.ts` でも 0x1200 は
`hdmv_pgs_subtitle` として認識され、デコードして焼き込むと、継ぎ目の次のフレームには
前の範囲の行ではなく新しい範囲の行が出ており、字幕の途中で開く範囲の
先頭フレームにはその字幕が出ており、ファイルの終わりに出しっぱなしのものは
残っていない。BDAV フォルダーへ書くと、クリップ索引はこのストリームを coding `0x90`
として並べる。実物のディスク上のパスで開けば、マップには無い言語が `CLIPINF` から
得られる（`jpn`）。

続けて、ディスクそのものから 10 秒を、半分が再エンコード、半分がコピーになる形で
切り出した。81 GB のクリップを、自前のエントリーポイントマップ経由で
開いたものである。範囲の中のディスプレイセットは 1 つ残らず順番どおりに出た。
再エンコード区間とコピー区間の継ぎ目の 66 ミリ秒手前で始まり、継ぎ目の向こうで終わる
セットも含めて、運んだのは 39 パケット、書いたのは 8 パケットである。この
セットこそ、ディスプレイセットを読みかけているあいだセグメントが自分の終端を越えて
読み進める理由であり、「終端を過ぎたか」をパケットが持つ 2 つの時刻の早いほうで
判断する理由でもある。セットは表示される少し前に送られるので、セットの先頭の
パケットは、表示時刻がいちばん先にあるパケットになる。

**DVD の字幕をイメージから運び出す。** 4.1 GB の `.iso` で、タイトルセット 1 つ、
`0x20` に日本語のサブピクチャが入っている。libavformat は 400 MB 読むまでこれを
見つけない。本編から 2 範囲を切り出すと、別ファイルに 11 ユニットが出た。範囲の中で
ディスクが送った 9 つ、2 つ目の範囲が開く瞬間に出ていて最初のフレームで書き直された
1 つ、そして 1 つ目の範囲を終わらせる停止である。読み戻すと `ffprobe` は
2 ファイルの中に `dvd_subtitle` を 1 本見つけ、短いカットではユニット 2 つとも
読めた。カットに焼き込むと、継ぎ目の次のフレームにはその瞬間ディスクが出していた
行が、`VTS_02_0.IFO` から取ったディスク自身の色で出ている。外すよう指定すれば、
書かれるのは `.ts` だけになる。

**同じ字幕を変換したもの。** 同じ 2 範囲を `--subtitles pgs` で切った。9 つの字幕が
ディスプレイセットとして入り、`.ts` では `0x20`、`.m2ts` では他のストリームと同じ
ように `0x1200` に振り直された。`ffprobe` はどちらからも `hdmv_pgs_subtitle` として
読み戻す。素の `.ts` でそうなるということは、マルチプレクサのマップの上から書いた
マップが効いているということである。焼き込むと、継ぎ目の次のフレームには別ファイルの
2 つが出していたのと同じ行が、同じ色で出ている。

**Blu-ray の字幕を 2 ファイルとして書く。** 1080p 本編（H.264、LPCM、`0x1200` の
PGS）から 20 秒の範囲を 2 つ、2 つ目が字幕の途中で開くように取った。別ファイルに出た
ユニットは 11 個で、範囲の中でディスクが描いたものが 10 個と、2 つ目の範囲が開く
瞬間に出ていた 1 個を最初のフレームで書き直したものである。両端に余分なユニットは
出ない。範囲の末尾で面を空けるディスプレイセットが、自前のユニットを足す代わりに
最後のユニットの停止時刻を埋めるからで、1 つ目の範囲の最後の字幕は範囲が終わる
瞬間に止まっている。読み戻すと `ffprobe` は 2 ファイルから 1920x1080 の
`dvd_subtitle` を 1 本見つけ、すべてのユニットをデコードでき、そのどれもが自分の
表示時間を持っている。作り出したパレットは 2 範囲で 6 色、同じ本編の 3 分で 13 色に
なった。

平らな背景に描いて、同じ字幕をディスク自身のディスプレイセットのまま `.ts` に
運んだものと比べると、色は完全に一致し、輝度は 39.7 dB 離れていた。Blu-ray の
アンチエイリアスを DVD の 4 色に潰すことで失われるのはこれだけで、画素は 1 つも
動かず、字幕の時刻も 1 つも変わっていない。`.mp4` を指定すれば同じ 2 ファイルが同じ
場所に出る。このコンテナでディスクのカットが字幕を保つ方法はこれだけである。

**Blu-ray の字幕を `.sup` として書く。** 同じ 2 範囲を `--subtitles sup` で切った。
出た 85 セグメントは、同じカットの PGS を `.ts` に運んで ffmpeg に `.sup` へ詰め直さ
せたものとバイト単位で一致した。セグメント種別も中身もすべて同じで、時刻の差は最大
90 kHz の 6 チック、67 µs である。カッター自身の時計を秒の浮動小数で一往復した分に
過ぎない。読み戻すと `ffprobe` は 1920x1080 の `hdmv_pgs_subtitle` として開き、
開始位置はカット内の最初の字幕になる。字幕が `0x1200` と `0x1201` の 2 本あって
どちらも `eng` と書かれたディスクでは、`cut.1201.sup` になった。言語では見分けが
付かないので、乗っている番号が入る。範囲の中に 1 つも無かった方は、空のファイルを
残さずにその旨を表示した。DVD に同じ指定をすると、先にユニットを変換して、その
ディスプレイセットを `.mp4` と同じ名前の `.sup` に書く。

**メニューを音声と取り違える。** UHD ディスクのクリップ 00004 には、映像と LPCM
1 本、そして `0x1400` のメニューが入っている。libavformat はこのメニューを MP3 音声
と判定する。今このクリップを調べると、本物の音声 1 本だけを並べ、
`not carried: a menu on pid 0x1400` と表示する。メニューだけの 3 クリップ、つまり
グラフィックスだけで映像が無いものは、映像が無いという失敗ではなく、メニューであると
表示する。

もう一方は数えて確かめた。8 枚のディスク、748 個のクリップ索引のうち、29 個の
クリップにメニューが入っていて、テキスト字幕が入ったものは 1 つも無かった。`0x92` は
どこにも無かった。これが TextST を運ばずに名前だけ付けて置いていくもう半分の理由で
ある。運ぶものが無く、運ぶ実装を突き合わせる相手も無い。

**VC-1 で書かれたプレス Blu-ray 2 枚。** その年代のディスクの多くがこの
コーデックであり、この 2 枚で Advanced Profile の違いはほぼ網羅できる。1 枚は
1920x1080i 29.97、インターレースフレーム符号化、non-uniform 量子化、全 GOP が
クローズド。もう 1 枚は 1920x1080 プログレッシブ 23.976、uniform 量子化、全 GOP が
オープン、skipped ピクチャあり、強いフィルムグレインである。どちらも読み、一覧に
出し、GOP 途中から GOP 途中まで 10 秒のカットを行った。308/308 と 246/246 枚、映像の
90% がディスクとバイト単位で一致し、両端の部分 GOP は SmartCut 自身のエンコーダが
書いた。どちらのコンテナも、すべてのプログラムマップを読むまでフレームレートが
得られなかった（[上記](#フレームレートを名乗らないディスク)）。エンコーダの欠点と、
正しいと分かる理由は
[Rust コア](rust-core.ja.md#エンコーダのないコーデック-vc-1)にある。

**合成素材。** [`tests/run_disc_tests.sh`](../../tests/run_disc_tests.sh) が、既存の
テスト素材から方言ごとに 1 枚ずつディスクを組み立てる。TS を 192 バイトパケットに
詰め直し、[`tests/disc_index.py`](../../tests/disc_index.py) が索引ファイルを書き、
genisoimage がそれぞれを UDF 1.02 のイメージに包む。そのうえで、4 つの形すべてが
同じ結果を返すこと、そこから切った出力がバイト単位で同一であること、そしてテーブルが
書き戻されることを確かめる。同一とは、互いにも、生のストリームからの出力ともである。
35 件すべて通っている。

**実素材の DVD-Video。** 2009 年に Sonic Scenarist でマスタリングされた NHK の
ドキュメンタリー（4.1 GB、ISO 9660 の上に UDF 1.02、タイトルセット 1 つが
VOB 4 ファイル、MPEG-2 720x480 + AC-3）。2 つのタイトルと 19 個・18 個の
チャプターが `.IFO` から読め、独立に書いた Python のリーダーと一致した。
バイト範囲は 24,727,552〜4,289,400,832 で、VOB 4 ファイルとちょうど同じだった。
最終セルの手前の不連続を検出して行を分けた。`VOBU_S_PTM` は 0.280633 秒で、
libavformat がコンテナの開始として報告する値とマイクロ秒まで一致した。
2 区間 480 秒のカットは 14,386 フレーム、99.8% がコピーで、コピーされたフレームは
素材と md5 単位で連続して一致し、映像と音声のずれは 13 ミリ秒以内だった。同じ
タイトルを `VIDEO_TS` フォルダーから読み、VOB ファイルの継ぎ目をまたいで切った場合も
60 秒で 1798 フレームだった。

**合成素材の DVD。** [`tests/run_dvd_tests.sh`](../../tests/run_dvd_tests.sh) が
既存のテスト素材から 2 枚組み立てる。1 枚はふつうの DVD で、タイトルセットの
ストリームが 2 ファイルに分かれている。もう 1 枚はタイトルが 2 回に分けて
多重化されていて、途中で時計が振り出しに戻る。
[`tests/dvd_index.py`](../../tests/dvd_index.py) がナビゲーションパックを埋め、
`.IFO` のテーブルを書く。そのうえで、行・長さ・チャプター・トラック・セクタ範囲が
書いたとおりに読めること、厄介なほうが 2 つの時計を持つ 2 行として出ること、そして
カットが md5 まで同一であることを確かめる。フォルダーからでも、イメージからでも、
ディスクの形をしていない生のプログラムストリームからでも同一である。23 件すべて
通っている。

**音声をコーデックごとに。**
[`tests/run_bd_audio_tests.sh`](../../tests/run_bd_audio_tests.sh)
が 1 本ずつクリップを組み立てる。16 ビットと 24 ビットの LPCM、DTS、TrueHD、E-AC-3
である。それぞれを `.ts`・`.m2ts`・`.mp4` に切り出し、そのコーデックについて本文で
述べたことを確かめる。ディスクが使っていたストリーム種別が出力にも出てくること、LPCM
を MP4 に入れても 1 サンプルも違わないこと、LPCM の境界にかかったフレームは範囲外の
側が無音になり手前側は残ること、DTS と TrueHD のカットの音声が素材自身のバイト列の
一続きであること（実際に探して見つける）。39 件すべて通っている。
