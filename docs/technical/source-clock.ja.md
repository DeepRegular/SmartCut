# 元の時計と、可変レートの範囲の終わり

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](source-clock.md)

タイムスタンプの時計と公称のフレームレートは、別々の役割を持つ。
継ぎ目を再エンコードするエンコーダには、従来どおり公称のレートと画質の設定を渡す。
一方、出力のタイムラインには、元の録画の表示時刻をそのまま表せる細かさが必要になる。
この文書は、その細かさをいつ変えるかと、変えたときに範囲の終わりをどう扱うかを
説明する。

## 時計を細かくする条件

`Grid::of` が出力の時刻の格子を細かくするのは、次の 3 つをすべて満たす
素材だけである。

| 条件 | 対象外になる例 |
|---|---|
| TS ではない | 放送の `.ts`、`.m2ts` |
| プログレッシブである | インターレースの録画 |
| 可変レートと判定された | 一定レートの録画（CFR） |

CFR の録画は、フレーム間隔が元の時計の整数倍でなくても、公称の格子と
タイムスケールのまま書く。たとえば Matroska の 29.97 fps は、時計がミリ秒なので
タイムスタンプの間隔が 33 ms と 34 ms の交互になる。これは丸めの結果で、
表示間隔が本当に揺れているわけではない。この録画を MP4 に書くと、
間隔は 1001/30000 秒ちょうどになる。入力のミリ秒の丸めは持ち込まない。

すでに条件を満たしている格子は、約分もせずにそのまま返す。

`on_clock` は、フィールドの格子と元の時計の 1 刻みを両方とも表せる細分を選ぶ。
出力のタイムベースを約分するのは、新しく合わせ直した格子だけである。
計算はすべて桁あふれを検査し、MP4 の 32 ビットの間隔とタイムスケールの上限に収める。
収まる細分が見つからなければ、従来の格子のまま書く。
したがって、どんな時計とファイル長でも刻みが正確になるわけではない。

細かくした時計は、MPEG-TS と MPEG-PS の 90 kHz より細かいことがある。
1 単位しか離れていない 2 つのデコード時刻は、出力では同じ刻みに丸まってしまう。
B ピクチャの階層が深い録画を `.ts` や `.m2ts` に切ると、マルチプレクサが
"Invalid argument" で受け付けなかった。この 2 つのマルチプレクサに書くときは、
`Writer::dts_gap` が隣り合うデコード時刻を出力の 1 刻み以上あける。
ほかの格子とほかのコンテナでは、従来どおり 1 単位あければよい。

### 可変レートの判定

`varies` は表示間隔を 2 通りに数え、どちらかが当てはまれば可変レートとする。

| 数えるもの | 基準 |
|---|---|
| 長すぎる間隔（保持） | 平均と典型値（正の間隔の中央値）の小さいほうの 1.75 倍を超える |
| 短すぎる間隔 | 平均の半分に満たない |

保持のほうで中央値も使うのは、平均だけでは見逃す録画があるからである。
40/40/80 ms の繰り返しは平均すると約 53 ms になる。80 ms の間隔はその 1.75 倍
（約 93 ms）に届かないので、保持と見なされず、一定レートと誤判定していた。
中央値の 40 ms と比べれば、80 ms は保持として数えられる。

短い間隔は平均とだけ比べる。一定レートの録画を切るときの格子は平均から作るので、
それより詰まったフレームがあるかを確かめれば足りる。中央値と比べると、
速い間隔が大半を占める録画で 1 つも数えられない。画面録画を Matroska に
入れ直した素材で、毎秒 30 フレームで動いたあと 10 秒止まるものが一定レートと
判定され、195 フレームのうち 150 フレームしか書かれなかった。

ミリ秒に丸めた NTSC と 2:3 のケイデンスは、どちらの判定でも可変レートにならない。

### B ピクチャを含む素材は全体を走査することがある

次の素材では、カットの前にファイル全体のパケットを走査する。

- 可変レートとまだ判定されていない
- プログレッシブで、B ピクチャを含む
- 平均のレートが、宣言されたレートより 1% を超えて低い

FFmpeg から読めるコンテナの索引には、デコード時刻しか入っていない。
B ピクチャがあると、そこから表示間隔は分からない。
そこで `ContainerIndex` はこの素材の索引を作らず、既定の `--index auto` は
パケットの走査に切り替える。

大きなファイルは、開くまでの時間がはっきり延びる。シークテーブルだけで済まず、
ファイル全体を読むからである。ただし読むのはパケットだけで、映像はデコードしない。
通常の CFR の録画は、従来どおりシークテーブルだけで開ける。

`--index container` を指定した場合は、索引を作れない理由を表示する。
シーク用インデックスのバージョンは 20 に上げた。以前に保存した判定結果は使われない。
19 は開発中のビルドだけが書いた番号で、公開した版には無い。

## 継ぎ目は範囲の終わりではない

1 つの残す範囲の中にある継ぎ目では、次のセグメントが実測のフレームから再開する。
ここで前のセグメントを公称のフレーム長まで伸ばすと、継ぎ目より後のフレームが
すべてずれる。範囲の中の継ぎ目と範囲の終わりは、`SegmentCtx::last` で区別する。

範囲の終わりでは、変更前と同じく、通常のフレームの符号化上の長さを表示時間の
下限にする。
レビューで使った再現素材では、37.996 秒にフレームがあり、OUT が 38 秒にある。
時計を細かくしても、このフレームを 4 ms で消えるフレームにしてはならない。
23.976 fps の通常のフレームなら、表示時間は約 41.708 ms である。

`coded_length_unbounded` に当たる録画は、従来どおり時刻で保持の長さを決める。
長く保持されたフレームの中に範囲が丸ごと入る場合も同じである。

### 最後のフレームは書き出しを待たせる

時計を細かくした場合、最後に表示するフレームは書き出しキューに残しておく。
書き出すのは、それより後に表示するフレームが届いたときか、
最後の保持時間が決まったときである。

デコーダの並べ替えの深さだけでは、待たせる長さが足りない。
コピーした H.264 の P ピクチャのあとに B ピクチャが 3 枚続いても、
`has_b_frames` は 2 のことがある。この P ピクチャを早く書き出すと、
最後の保持時間を後から直せない。40/40/80 ms の選択範囲では、出力が
約 27 ms 短くなった。

キューの上限は、継ぎ目のバッファと同じ 256 MiB である。上限を超えたら、
従来どおり `emit_one()` でフレームを書き出し、カットを続ける。
書き出したパケットはもう変更できないので、その場合は最後の保持時間が
短くなることがある。

時計を細かくしない素材では、キューの動作は変わらない。

### 最後の範囲を止まったフレームで終えない

`.mkv`・`.webm`・`.mp4`・`.mov` では、可変レートの録画の最後の範囲が
止まったフレームのまま延びることは無くなった。Matroska はどれかのブロックが
表示される最も遅い時刻をファイルの長さとし、MP4 のエディットリストも
いちばん遅く終わるフレームまで続く。終わりの少し前のフレームに平均 1 フレーム分の
長さが付いていると、出力は範囲の終わりを越えていた。

そこで各フレームの長さは、次に表示するフレームまでに抑える。次のフレームが
キューで待っていても、すでに書き出してあっても同じである。最後のフレームは
範囲の終わりまで表示する。終わりまで保持されるフレームは、従来どおり
終わりまで続く。

## 検証を再現する

プロジェクトの FFmpeg 7.1 SDK で CLI をビルドしてから、次を実行する。

```sh
bash tests/run_source_clock_tests.sh
# 実行ファイルとツールを明示する場合
python3 tests/source_clock_tests.py --cut rust/target/release/smartcut \
  --ffmpeg ffmpeg --ffprobe ffprobe --work-dir /tmp
bash tests/run_vfr_tests.sh
```

### 95 件のスイートの中身

入力は AVC・HEVC・AV1・VP9 で生成する。レビューで使った 90 秒・720p の
コマンドも、変えずにそのまま入れてある。MP4 と MKV のそれぞれで、
次の切り方を試す。

- 範囲 1 つと複数
- コピーだけのカット、1 フレームだけのカット
- 長い保持
- CFR の対照

ミリ秒時計の CFR の対照は MP4 にも書き出す。間隔と平均レートが公称どおりであることを
確かめる。Matroska の 29.97 fps の VP9 もここに含む。

確かめる項目は次のとおり。

| 項目 | 内容 |
|---|---|
| フレーム数 | デコードしたフレームの数 |
| 表示時刻 | すべての PTS |
| デコード順 | MP4 は DTS が狭義単調増加であること |
| 終端 | ムービーの終端と、映像トラックの終端 |
| コピーしたフレーム | 圧縮データと、デコードした画素の両方 |

AVC と HEVC は、VCL のバイトを、繰り返し入るパラメータセットの NAL と分けて比べる。
Matroska は DTS を持たない。ミリ秒の時計で推定した DTS が等しくなる場合は
記録だけして、逆行した場合は失敗にする。

### 実行のたびに残るもの

実行するたびに新しいディレクトリを作り、コマンド・ハッシュ・結果をすべて書き出す。
`--fixtures <前回のディレクトリ>/fixtures` を渡すと、前回とまったく同じ入力で
試せる。

FFmpeg 7.1 で生成した、B ピクチャを含む VFR の MP4 は、エディットリストのせいで
最後のフレームが見えなくなることがある。そのため参照用のデコードだけは
`ignore_editlist=1` を付けて、生成したパケットをすべて読む。
出力は常に通常どおり分離し、厳格にデコードして読む。終端の時刻は別に確かめる。

### このスイートで確かめないもの

対象は時刻とコピーだけである。次のものは確かめない。

- AV1 の MP4 での sample description の適合（[MP4 に書く AV1 の構成情報](av1-mp4.ja.md)）
- SAR の受け渡し
- M2TS の到着時刻
- GUI の再生
- ハードウェアのプレーヤー

### 直していない既知の挙動

レビューの検査は、既定の索引の作り方で行う。PTS が重複する合成素材に
`--index scan` を強制すると、以前からある保持の不具合が出る。
794 フレームのはずが 796 フレームになり、範囲の終わりに約 4 ms の半端が残る。
v0.8.39 でも同じで、この変更では直していない。
