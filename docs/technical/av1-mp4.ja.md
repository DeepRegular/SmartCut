# MP4 に書く AV1 の構成情報

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](av1-mp4.md)

AV1 の継ぎ目を再エンコードすると、エンコーダが録画とは違う Sequence Header OBU を
書くことがある。継ぎ目を問題なくデコードできても、それだけでは足りない。
MP4 の `av1C` は 1 つしか書けないので、それを参照するすべてのサンプルと
内容が合っている必要がある。この文書は、その食い違いをどう見つけ、どう合わせ、
合わせられないときにどうするかを説明する。

## 検査する範囲

この検査が働くのは、出力のマルチプレクサが `mp4` のときだけである。
Sequence Header は FFmpeg の `extract_extradata` フィルターで取り出す。
比べるのは、`av1C` に写される次の欄だけである。

| 欄 | 内容 |
|---|---|
| profile | プロファイル |
| level・tier | 最初のオペレーティングポイントのもの |
| ビット深度 | 8・10・12 ビット |
| monochrome | モノクロかどうか |
| 色差のサブサンプリング | 4:2:0・4:2:2・4:4:4 |
| 色差のサンプル位置 | chroma sample position |

取り出したパケットに Sequence Header が複数あれば、すべてを比べる。
バイト列が違っても、これらの欄が一致していれば同じ `av1C` で表せる。

トラックの構成情報には、実際に最初に書いたシーケンスを使う。
そのシーケンスが入力の extradata にしか無い場合は、最初の出力パケットに付ける。
これで、選択範囲を丸ごと再エンコードしたときの問題も直る。
録画と違う構成で再エンコードしても、やり直しは必要ない。

## level だけが違うときは書き換える

コピーするフレームを含むカットでは、継ぎ目のエンコーダが録画より低い level を
書くことがある。合わせる先は、出力で有効になっている欄である。
最初のフレームを再エンコードする場合は、録画のシーケンスか、確定した `av1C` の
欄に合わせる。

違うのが level だけで、合わせる先の level がエンコーダの level より上なら、
`seq_level_idx[0]` を書き換える。書き換えるのは、継ぎ目の Sequence Header と、
取り出したパケットの構成情報の 2 か所である。

| ヘッダの種類 | tier の扱い |
|---|---|
| 通常のヘッダ | index が 7 より大きいときだけ tier のビットがある |
| reduced still picture | tier は常に 0 とみなされる |

ほかの構文はそのまま残す。末尾の 1 ビットとゼロの詰め物は作り直し、
必要なら OBU のサイズも更新する。コピーするパケットは読むだけで、変更しない。
選択範囲をすべて再エンコードする場合は、エンコーダが実際に書いた構成をそのまま使う。

### 上げてよい level

index 31 には level による制約が無い。31 以外に合わせる場合は、
次の条件をすべて満たすときだけ書き換える。

- エンコーダの index と合わせる先の index が、どちらも定義済みである
- 合わせる先のほうが高い
- tier を含め、`av1C` のほかの欄が一致している

Annex A.3 の表の上限は、index が上がると同じか大きくなる。
最小圧縮率の許容値（MinCompBasis × レート ÷ MaxDisplayRate）も同様で、
3.1 では 2 ÷ 31,950,720、4.0 では 4 ÷ 70,778,880 になる。
したがって、定義済みでより高い index なら、どれを書いてもよい
（[AV1 仕様 Annex A.3](https://aomediacodec.github.io/av1-spec/av1-spec.pdf#page=651)）。

ただし decoder model の情報を明示している録画は、31 以外への書き換えを行わない。
バッファの条件を別に確かめる必要があるからである。

次の場合は書き換えず、後述のやり直しに回す。

- 合わせる先の level のほうが低く、31 でもない
- ビット深度・色差・プロファイルが違う
- コピーするシーケンスどうしが一致していない

## 継ぎ目のエンコーダと level

SVT-AV1 で録画の形式を書ける場合は、継ぎ目を SVT-AV1 で書く。
SVT-AV1 は level をフレームから決める。

SVT-AV1 は 4:4:4・4:2:2・12 ビットを扱えないので、これらは rav1e で書く。
rav1e は指定しないと index 31 を書く。録画の level が 31 以外なら、31 からは
上げられないので、カットは必ずやり直しになる。

そこで rav1e には、録画の最初のオペレーティングポイントの level を
`level=X.Y` で渡す。渡すのは、その level が定義済みで、tier が main の場合だけ
である。
指定すれば rav1e はその index をそのまま書き、符号化したフレームは変わらない。

フレームがその level を超えていると、rav1e は指定を受け付けない。
録画が level を実際より低く書いている場合に起きる。そのときは level を指定せずに
開き直す。この指定はコンテナを問わないので、Matroska と WebM の継ぎ目にも
録画の level が書かれるようになった。

## 合わせられないときは丸ごと再エンコードする

FFmpeg 7.1 の MOV/MP4 マルチプレクサは、`stsd` のエントリを 1 つしか書かない。
`NEW_EXTRADATA` のサイドデータで構成は更新できるが、変わったサンプルに
2 つ目のエントリを割り当てることはできない。

MP4 への書き出し中に欄を合わせられなかった場合は、書きかけの出力を閉じる。
そのうえで、映像の範囲をすべて再エンコードしてやり直す。
音声と字幕の扱いは元の設定のままである。

ログには、最初に表示したコピーの割合が破棄した計画のものであることと、
やり直しでは映像を 1 フレームもコピーしないことが出る。
やり直しは 1 回だけで、そこでも構成が変わればエラーになる。

やり直すと書き出しが 1 回増え、エンコード時間と世代劣化も増える。
MP4 に複数の sample description を書く方法は実装していない。
解析結果と GUI に出る計画は最初の見積もりのままで、やり直すと進捗が
最初からになることがある。

元の時計・VFR・SAR の変更は、それぞれ別の PR で入った。

### Matroska と WebM は対象外

Matroska と WebM は従来どおりで、この検査もやり直しも通らない。
Matroska の中で AV1 のシーケンスが変わったときに、拒否するか、警告するか、
オプションにするか、丸ごと再エンコードするかは方針の問題で、
この変更では決めていない。

## 検証を再現する

```bash
cd rust && cargo build --release --locked -p smartcut-cli && cd ..
bash tests/run_av1_mp4_tests.sh
# または: bash tests/ci.sh av1_mp4
```

必要なものは Python 3.11 以上と、libaom-av1・librav1e・libsvtav1 を有効にした
FFmpeg と ffprobe である。

スイートは MP4 への書き出し 18 件と、Matroska の対照 3 件からなる。

| ケース | 求める結果 |
|---|---|
| rav1e の level 31、有限の Level 4.0 | コピーと再エンコードが混在し、コピーしたキーパケットと画素がそのまま |
| 色差のサンプル位置が colocated の入力 | 映像全体のやり直しがちょうど 1 回 |
| Matroska の対照 | 構成のやり直しが増えていない |

MP4 の出力では次を確かめる。

- 厳格なデコードが通ること
- フレーム数、表示 PTS、DTS、映像の長さ
- `av1C` が、独立した CBS の `trace_headers` で読んだ内容と一致すること
- 宣言したコピー区間の中で、パケットと画素が録画と同じであること

Matroska の対照は、やり直しが増えていないことを確かめるだけである。
Matroska の Sequence Header の適合までは保証しない。

`--cut`・`--ffmpeg`・`--ffprobe`・`--work-dir`・`--fixtures` で、パスを明示したり、
同じ入力で 2 回の実行を比べたりできる。コマンド・ハッシュ・結果・出力のログは、
表示される作業ディレクトリの下に残る。素材とビルドしたバイナリはコミットしない。
