# 放送録画ワークフローとの互換

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](broadcast-ts.md)

日本の放送録画を前提にしたツール（DGIndex など）は、フレームを 1 枚も読む前に
PID・PMT・サービス番号・記述子を読む。そこが録画と違っていると、ファイルが開かない
か、音声トラックが見つからない。

このページでは、切ったあとの `.ts` を「元の録画と同じ形」に保つために SmartCut が
何をしているかを扱う。

## 出力の TS は録画のレイアウトを引き継ぐ

ソースと並べると、初期の出力は次のようになっていた。

| | PMT PID | 映像 PID | 音声 PID | 音声の記述子 |
|---|---|---|---|---|
| ソース（BS フジ） | 0x100 | 0x1100 | 0x1101 | `0x52` `0x0a` |
| 出力（当初） | 0x1000 | 0x100 | 0x101 | **なし** |
| 出力（現在） | 0x100 | 0x1100 | 0x1101 | `0x0a` |

**PID は映像ストリームの PID から導く。** 「ファイル内で最小の PID」からではない。
放送録画は字幕やデータ放送も*ストリーム*として持っており、その PID はマルチプレクサが
受け付ける範囲（0x0020〜0x1FFA）より下にある。最初の実装はそれを拾ってしまい、
`mpegts_start_pid` に 18 を渡し、0 バイトの出力を作った。

`0x52`（component_tag）だけは書かれない。ffmpeg のマルチプレクサが書かないからである。

### いまはストリームごとに元の PID へ戻す

「映像の PID から採番する」方式で到達できるのは、上の表までである。マルチプレクサは
`AVStream.id` を**そのストリームを書く PID** として読む。16 以上の値は
`mpegts_start_pid` からの採番ではなくそのまま使われるので、各ストリームに録画での
PID を渡せば、音声も字幕も元の位置に戻る。

旧方式で音声が一致していたのは偶然である。0x1100 に 1 を足すとたまたま 0x1101 に
なるからである。PID が散らばっている録画（0x100f / 0x104f / 0x120f）ではまったく
一致しなかった。

記述子は別の話で、マルチプレクサはそもそもそれを書かない。記述子は次に述べるパスで
復元する。

## 録画自身の表を書き戻す

> 0.6.5 以降、`.ts` は指定が無ければこの形で書く。`.m2ts` は後述の部分 TS に
> なる。ディスクのストリームとはそういうものだからである。その下にある仕組みは
> 両方の形式に共通である。

放送は自分自身についても語っている。これはどのサービスか、放送局の名前は何か、
いま何を放送していて次は何か、いまは何時か。PAT・PMT・SDT・EIT・TOT がそれである。
**録画機のライブラリ表示も、プレーヤーのチャンネル表示も、下流のツールも、実際に
読んでいるのはこれである。**

そしてこれらは多重化を生き延びない。libavformat は自分の知っていること、つまり
ストリームの情報だけから PAT・PMT・SDT を書く。字幕はマルチプレクサがそのコーデックを
知っているので ARIB の記述子つきで出てくるが、それ以外は書かれない。音声の
component tag も、コピー制御記述子も、文字スーパーのストリームの素性もである。
EIT と TOT にいたっては、単に失われるよりたちの悪いことが起きる。PID 0x12 を
コピーするよう指示すると、マルチプレクサはそれを無名の private ストリームとして受け入れ、
**自分の選んだ PID に置く**。そこは誰も見に来ない場所である。

そこで、書き終えたファイルを 1 パス走査して書き戻す。

- **PMT を録画自身の記述子で作り直す**
- **SDT を録画自身のセクションで置き換える。** これにより、サービス名が ARIB の
  文字符号のまま届く。SmartCut は 1 バイトも解釈する必要がない
- **EIT present/following と TOT を、本来の PID に注入する**
- 連続性カウンタをすべて振り直す

注入したセクションをどこに置くかは、出力側の時計で決める。残す区間ごとに、その区間の
最初のピクチャが来る**ソース上のバイト位置**で読んだスナップショットを使う。その
バイト位置はアクセスポイント索引が知っているので、数ギガバイトのファイルでも安く
済む。したがって番組の境界をまたぐカットは、両方の番組を記述する。TOT の時刻は出力の
進行に合わせて進める。スナップショットのままにすると、ファイル全体で同じ秒を
名乗ってしまう。

書き直すマップに引き継がない記述子が 5 つある。

2 つはカットに存在しないスクランブルについてのものだ。限定受信記述子（0x09）と、
ARIB 版のアクセス制御記述子（0xF6）。どちらもスクランブル方式と ECM の PID を
書いている。日本の放送は番組ループと字幕のそばに 1 組ずつ積んでくる。出力は
スクランブルされておらず ECM ストリームも無いので、残したまま焼いたディスクは、
ディスクに無い PID の ECM を、何もスクランブルされていないファイルの中で
名乗っていた。

残り 3 つは、その放送が送られた条件だ。0xC1 は何回コピーしてよいか、0xDE は
そもそも蓄積してよいか、0xC8 は受信中のサービスの映像をデコーダがどう扱うか。
**どれもファイルについてのものではない。** カットの元は、もうスクランブルが
解かれ、もうディスクに載っている録画だ。放送ではなくなったものの map に放送の
条件を書き戻すのは、その録画が録られる前に終わっていた状況を記述することになる。

オーサリングツールのディスクは 5 つとも落とし、番組ループを空にしている。map に
残るのは各ストリームの stream identifier、字幕のそばのデータ符号化方式記述子、
そして音声の言語だ。レコーダーは map では後ろ 3 つを残し、自分の記述子を 1 つ足す。
ただしレコーダーは「いま受信しているもの」を記述しており、こちらはそうではない。

**同じ 3 つはイベントの側からも落とす。** 録画はコピー制御を 2 か所で述べている。
map と、イベント自身の記述子ループだ。後者は下の SIT が引き継ぐ場所である。参照
ディスクはどちらも、どちらの場所にも持っていない。イベントは放送のイベントのまま
である。番組名も放送日時も番組内容も来たとおりに運ぶ。落ちるのは条件のほうで、
2 か所からまとめて落とすか、どちらからも落とさないかのどちらかしかない。

NIT は 1 つのことだけのために読む。引き継ぎはしない。**その録画がリモコンの
どのボタンだったか**だ。TS 情報記述子（0xCD）にしか書かれておらず、これが無いと
地上波の 3 桁チャンネル番号は組み立てられない。[ディスクを書く](bdav.ja.md#チャンネル番号)
を参照。

## 録画の中で PMT は固定ではない

上の表はファイルの先頭側から読む。PAT・PMT・SDT は数百ミリ秒ごとに繰り返される
ので、数メガバイトもあれば何十回分にもなるからだ。**しかしそれは「最初の 1 部が
正しい」ということではない。**

放送局は番組が始まるときに字幕ストリームを PMT に加える。第 2 音声も一緒である。
そして番組が終われば外す。数秒早く始まる録画、つまりすべての録画は、そのどちらも
載っていない PMT で始まる。最初に届いた PMT を採ってそれ以上確かめないと、字幕
パケットは正しい PID に全部あるのに、PMT がそれを記載していないカットが書かれる。
プレーヤーからも見つからないし、ディスクの管理情報を書くために SmartCut 自身が
読み直したときも見つからず、ストリーム種別を推測で埋めることになる。

実測では、32 局から 1 本ずつ採った標本のうち **4 局がこれに当たり**、無作為に
選んだ 400 本のうち **95 本が最初の PMT より後で PMT を差し替えていた**。しかも
遅れて現れるストリームは、すべて字幕か第 2 音声だった。まさにカットが運ぶものである。
差し替えの位置は局によってまちまちで、最初の 1 秒以内のものもあれば、8 MB を
少し過ぎたところ（従来の読み取り窓の終端）のものもある。

そこで PMT は**対象を指定して**要求するようにした。`si::read_service` は呼び出し側が
これから運ぶ PID を受け取り、手元の PMT がそのすべてを記載するまで読み進める。
より多くを記載する後続の PMT が来れば前のものと置き換え、最初のパスで足りな
かったときだけ窓を一度だけ 64 MB まで広げる。PMT を差し替える局は録画の始めの
ほうでそうするし、最初の 1 分でストリームを名乗らない録画は結局名乗らない。
特に探すものが無い呼び出し側は従来どおり最初の PMT で答えられ、余分な読み取りは
発生しない。

## ファイルは、それが録画ではないサービスまで記述している

多重の中から 1 サービスだけを録るレコーダーは、そのサービスのパケットとそのサービスの
PMT を残す。そして SDT と EIT は多重のもの**そのまま**残る。つまり 1 局を 1 時間
録っただけのファイルが、5 つのサービスについて「名前は何か」「今なにをやっているか」
「次はなにか」を語っている。そのうちどれがこの録画なのかは、どこにも書かれていない。

`si::programme` は最初に見つけた記述を読んでいた。衛星の多重ではそれが録画中の
サービスである保証はまるでない。アニメ専門局の録画が、放送していないはずの舞台中継の
名前と、出ていない時刻を返してきた。そしてそこから作ったディスクは、レコーダーの
一覧にその名前で並んだ。

コーパスから無作為に採った 60 本での実測：**レコーダー自身が付けたファイル名と一致
したのは 24 本**、サービス名がチャンネルと一致したのは 31 本。下記の読み方では
**60 本中 60 本**が、両方とも一致した。

どのサービスなのかは、実はもう一段手前の表に書いてある。PAT は多重が運んでいた
全サービスと、それぞれの PMT の PID を並べていて、レコーダーはそのうち 1 つの PMT
だけを残した。つまり **PMT がファイルの中にあるサービスが、この録画のサービス**である。
それで決まらないとき、つまり PAT が残っていないときや、全部の PMT が残っている
ときは、従来どおり最初の記述を読む。この判定が `si::recorded_service` で、見つかった
サービス番号で EIT を絞り、同じ 1 セクションに複数サービスが入る SDT も絞る。

## 他のツールが多重化したファイルは、チャンネル名を ARIB で書いていない

テーブルの中の名前は、すべて ARIB STD-B24 のテキストとして読んでいた。SmartCut が
受け取る録画が、どれも日本の放送だったからである。`ffmpeg` を通ったファイルはそうでは
ない。多重化したツールは自分で SDT を書き、そこに世界の他の放送が使う符号、つまり
DVB EN 300 468 の文字テーブルを入れる。それを ARIB の符号表で読むと、`Service01` は
漢字 5 文字になる。名前の先頭では英数の集合が呼び出されていないので、バイトは 2 つずつ
JIS として読まれる。日本語の入った名前のほうは、誰も打っていない文字列になる。

`ffmpeg -i rec.ts -c copy -f mpegts out.ts` が書くのはまさにそれである。事業者名は
`FFmpeg`、サービス名は `Service01`、ネットワークは 0xFF01。そのファイルを切って
ディスクに載せると、チャンネル欄に漢字 5 文字が並ぶ。1 時間前まで、同じ録画は正しい
局名で並んでいた。

どちらの流儀で書かれた欄なのかは、`text::decode` が 3 段階で決める。

**選択バイト。** DVB は既定のテーブル以外で書いたテキストの前に 0x20 未満のバイトを
置き、そのバイトがテーブルを指す。0x10 から 0x15、つまり中国語 2 つ、韓国語、UTF-16、
そして `ffmpeg` が非 ASCII の名前に使う UTF-8 は、ARIB が何も割り当てていない符号
である。だからこの範囲で始まる欄は、録画が何であれ DVB として読む。残りは ARIB の
制御符号と衝突する。0x07 はベル、0x09 から 0x0B は字幕のカーソル移動である。これらを
選択バイトとして読むのは、次の段階で DVB だと分かっているときだけにする。

**ネットワーク。** SDT も EIT も、どのネットワークから来たかをセクションに書いている。
日本は衛星が 4・6・7、地上が 0x7880 から 0x7FE8。それ以外は他国のネットワークか、
多重化ツールが勝手に付けた番号であり、そこに載るテキストは DVB のものとして読む。
0 は「何も書いていない」であって、ARIB のままにする。部分 TS もこちらに落ちる。
ネットワークを名乗る表が入っていないからである。

**バイトそのもの。** 日本の録画のテーブルをツールが書き直した場合、ネットワーク番号は
残り、文字符号だけが変わる。これを救うのが 3 つ目の判定である。欄全体が UTF-8 として
妥当で、ASCII 以外の文字を含み、**かつ** 0x80 から 0x9F のバイトを含むなら UTF-8 と
みなす。両方が必要である。ARIB の図形バイトの短い並びが、偶然 UTF-8 として妥当になることは
ある。しかし 0x80 から 0x9F は C1 の制御符号であり、後ろにパラメータを従える。
チャンネル名に入るものではない。

コーパス 2,979 本、名前と説明の欄 13,788 個で実測した。**最初の 2 段階が別扱いに
回す先頭バイトを持つ欄は 0 個。** 9,331 個は 0x0E、つまりカタカナへのロッキングシフト
で始まり、3,281 個は 0x1B のエスケープで始まる。**3 つ目が UTF-8 と誤認した欄も
0 個。** コーパスのネットワーク番号はすべて日本のものだった。放送の録画の読み方は、
1 欄も変わっていない。

ここで決めているのは、名前を**どう読むか**だけである。テーブル自体は届いたバイトの
まま出力へ写す。プレーヤーは録画を読むのと同じように読む。SmartCut が書く
ディスクには、名前を ARIB の符号に戻して入れる。レコーダーが描くのはそれだからである。

DVB の既定テーブルは ISO 6937 である。下半分は ASCII で、アクセントは付く文字の前に
書く。`0xC2 0x65` は `é` になる。これも解釈する。専用の 1 文字がある組み合わせは
結合文字ではなくその 1 文字にする。名前は比較され、並べ替えられ、ファイル名になる
からである。ただし UTF-8 を先に試す。自分で名前を書く多重化ツールは OS から渡された
ものをそのまま書くのであって、それを名乗る選択バイトまで書くものは、テキストを書く
ものより少ない。

## 書き戻す説明は、実際に書いたものに合わせて削る

同じ理屈をもう一歩先まで適用する必要がある。放送はデータ放送を「送っているストリーム」
として記述しているが、それを置けない形で書いたカットはそれを運ばない。番組の記述を
そのまま丸ごとコピーすると、**出力はファイルに存在しないものへのエントリポイントを
宣言する**ことになる。BS フジの録画では、データ放送（component tag 0x40）を指す
データコンテンツ記述子が、データ放送の入っていないファイルに残っていた。

この文からは、その後 2 つ抜けた。文字スーパーは今は運ぶので、それを指す記述子は残る。
[文字スーパーと、もう一つの字幕](disc.ja.md#文字スーパーともう一つの字幕)に詳しい。
データ放送も `.ts` なら運ぶようになったので、同じデータコンテンツ記述子はまた本当の
ことになり、残る。[データ放送を運ぶ](#データ放送を運ぶ)を参照。
判断のもとは「実際に書いたストリームの一覧」であって種類の一覧ではないので、運ぶように
なったストリームは、ここを書き換えなくても削られなくなる。

ARIB はストリームを PID ではなく 1 バイトの component tag で指す。そのやり方で
他のストリームを指す記述子は 3 つあり（component 0x50、audio component 0xC4、
data content 0xC7）、3 つともタグを本体の 3 番目に置く。**録画のマップが記述して
いて、出力が運んでいない**タグを指す記述子は削除し、長さと CRC を付け直して
セクションを閉じ直す。

この規則は両方の条件が必要である。SmartCut が読んだどのマップにも現れない
タグはそのまま残す。放送局自身のテーブルが食い違っていることは、ここで決着を
つける問題ではないからである。

ダウンミックスしたトラックは「運んでいない」に数える。畳んだトラックは、その audio
component 記述子が名乗るチャンネル構成をもう持たないので、マップから外れるのと同じ
理由で番組の記述からも外れる。

**削るのは、いま放送中の番組の記述だけである。** present/following は 2 つの
セクションとして来るが、このファイルについて語っているのは最初の 1 つだけである。
2 つ目は「そのあと放送で何が来たか」の記録であり、そのストリームがこのファイルに
入ることは最初からありえない。それをこのファイルの内容と照合しても意味は無く、
そこに書かれた唯一正しい情報を捨てるだけになる。

## データ放送を運ぶ

> 0.6.6 から、断られない限り `.ts` はこれも運ぶ。ほかの形式は運べない。

d ボタンの向こうにあるのは小さなアプリケーションである。地域の天気、番組自身のページ、
道路の状況。送り方は**カルーセル**で、番組が続くあいだモジュールの一式を繰り返し送る。
途中から受信した機器でも数秒で全部そろう、という仕組みである。コーパスから無作為に
40 本を見たところ、**30 本がデータ放送を積んでいた**。すべて stream type 0x0D、
component tag は 0x40 以上である。占有率は小さくない。タイトル画面だけを送る局で
0.9%、地デジ各局で 10〜14%、ページ数の多い BS の局で 22% だった。

**これは多重化を通り抜けられない。** カルーセルは PES ではなくセクションで送られ、
libavformat の demuxer は自分が読むテーブル以外のセクションを渡さない。ストリームの
一覧には出る（`Unknown: none ([13][0][0][0] / 0x000D)`）が、中身は一切出てこない。
`-copy_unknown` を付けてコピーさせると、ffmpeg は自分のマップにエントリだけ書き、
その後ろに**パケットを 1 つも書かない**。データ放送を名乗っていて持っていないファイル
ができる。

そこで、パケットを録画からバイトとして取り出し、書き上がったファイルにバイトとして
入れる。やるのは、すでに表を書き戻しているあのパスである。あのパスはカットを 1 パケット
ずつ読み、それぞれが何秒の位置かを知っている。だから録画を横で読み、送られていた位置へ
配り直せばよい。中身には時刻が無い。セクションは時刻を持たない。だから継ぎ合わせるもの
は何も無く、置いて、連続性カウンタを振り直すだけで、あとは届いたままである。

あとは、どこへ置くかと、どう名乗るかである。

- **断られない限り運ぶ。** カットは録画を短くしたものであり、d ボタンの向こう側も
  録画に入っていたからである。捨てるなら `--no-data-broadcast`。GUI では環境設定の
  「出力設定」に同じ問いをチェックボックスで置いてある。既定は**オン**である。
  削除して得られるのはファイルサイズの削減である。
- **置けるのは、放送自身の表を持つ素の `.ts` だけ**である。カルーセルを書くのは表の
  パスなので、`--tables muxer` には書く場所が無い。Blu-ray の形式には置き場が無い
  （レコーダーが BD へダビングするときにデータ放送を落とすのと同じ理由である）。MP4 は
  そもそも TS ではない。そこへは何も言わずに入れない。`--data-broadcast` と明示的に
  指定したときだけ、入れられない旨を表示する。
- **マップは録画の書き方のまま名乗る。** 録画自身のエントリと、そのデータコンポーネント
  記述子である。番組の記述からも、それを指す記述子が削られなくなる。

出てきたものが使えるかどうかは 3 つで決まる。3 つとも `tests/run_broadcast_tests.sh`
が実物の録画で検査している。

- **モジュールが欠けていないこと。** 受信機はブロックを集めてモジュールに戻すので、
  1 つでも足りなければそのページは描けない。カルーセルは 3〜6.5 秒で一周する（BS の
  ある局、22 モジュールでの実測）。通常の長さの区間なら一周分が丸ごと入る。カット点が
  するのはモジュールの途中での中断で、ブロックを取り逃した受信機は次の周回を待つ。
  受信が切れたときに現にやっていることである。
- **中身が録画のものと同一であること。** ブロック単位で比べる。ここでは何も書き換えない。
- **カウンタが飛ばないこと。** 区間と区間のあいだは書かれていないので連続性カウンタは
  振り直す。飛びは、受信機にとっては取り逃したパケットである。

地デジ（カルーセル 7 PID）と BS（9 PID）の録画で実測した。モジュールはすべて完全、
すべて録画と同一、どの PID にもカウンタの飛びは無かった。

残らないものが 1 つある。番組連動型のデータ放送は、ストリームに合わせて時刻を取る。
そのストリームから一部を抜いた以上、合わせようがない。ページは開くが、特定の瞬間に
切り替わるはずだったページには、その瞬間がもう無い。

## 部分 TS として書く（`--tables partial`、および `.m2ts`）

放送録画のカットは、規格の言葉でいえば**部分トランスポートストリーム**である。
DVB は EN 300 468 Annex C で、ARIB は TR-B15 でこれを規定している。Blu-ray
レコーダーが書くのもこれであり、TMPGEnc MPEG Smart Renderer もこれを書く。

部分 TS は、生の多重を記述するテーブルを一切持たない。NIT・SDT・EIT・TDT・TOT の
代わりに **SIT が 1 枚**あり（PID 0x001F、テーブル 0x7F）、すべてがそこに入る。

| 場所 | 内容 |
|---|---|
| 伝送ループ | `partial_transport_stream_descriptor`（このファイル自身の実測ピークレート）と `network_identification_descriptor`（JPN と BS/CS/TB。元のネットワーク ID から読む） |
| サービスループ | `partial_transport_stream_time_descriptor`（番組が放送された時刻と長さ）、`service_descriptor`（サービス名。録画の SDT から）、および**現在のイベントが持っていた記述子すべて**（番組名・詳細・ジャンル・コンポーネント。録画の EIT から） |

**バイト列は録画自身のものである。** サービス名も番組名も ARIB の文字符号のまま
運ばれ、SmartCut はその中身を一切解釈しない。ここで書くのはその周りの枠だけで
ある。

コピーできない数値が 1 つだけある。ピークレートである。録画は部分 TS ではなかった
ので、自分を部分 TS として記述しておらず、その数値を誰も書き残していない。そこで
出力を 1 パスで測る。窓は 1 秒である。これより短い窓で測ると、大きなピクチャ 1 枚が
ファイルの持続しないバーストとして読まれてしまい、どの機器も用意する必要のない
レートをテーブルが名乗ることになる。

次に来た番組は入れない。present/following は 2 つのセクションとして来るが、この
ファイルについて語っているのは最初の 1 つだけである。SIT はこのファイルが*何で
あるか*を述べるものである。

SIT は残す区間ごとに作り、バージョンは内容が変わったときにだけ進める。番組の境界を
またぐカットでは、それぞれの番組がそれぞれの範囲で名乗られる。内容が変わっていない
のにバージョンだけ変えるのは、すでに持っているテーブルを読み直せとプレーヤーに
言うことになる。

セクションの上限は 4096 バイトで、実際の録画の拡張イベント記述子はそれだけで
1 キロバイトに達していた。入りきらない分は末尾から記述子単位で丸ごと落とす。
時刻とサービス名を先に書いているのはそのためである。

**1 秒に 1 枚、その 1 秒に 1 パケットずつ散らして送る。** 参照ディスクをセクション
開始どうしで測ると、レコーダーの実機は 998 ミリ秒ごと、オーサリングツールは
800 ミリ秒ごとだった。以前は libavformat がサービス記述を書くスロットに相乗り
していて、500 ミリ秒になっていた。どちらより頻繁で、誰が選んだわけでもない値で
ある。いまは 1 セクションのパケットをその間隔に散らす。これも実機の形だ。実機の
PID には 200 ミリ秒ごとに何かが乗っていて、1000 ミリ秒に 5 パケットまとめて、では
ない。バッファが一度に場所を空けなければならない塊にもならない。そうやって書いた
カットの実測は、セクションが 1001 ミリ秒ごと、パケットが 200 ミリ秒ごとである。

最初の map より前には 1 パケットも出さない。ストリームはテーブルが何についてのもの
かで始まるのであって、テーブルの説明で始まるのではない。参照ディスクはどちらも
そうなっていて、libavformat はサービス記述を先に書いていた。

## どちらで書くかは拡張子が決める

書いているものが何かによって、正しい答えが変わるからである。

`.m2ts` は Blu-ray のクリップである。そこでの部分 TS は好みではなく、形式そのもの
である。`--bdav` でディスクに載せる場合も、単体で書く場合も、`.m2ts` は部分 TS に
なる。フレーミングを選ぶ判定と同じ判定である。

それ以外は人が開くファイルである。そして**日本の録画まわりのソフトが実際に読んで
いるのは SDT と EIT である**。TVTest も EDCB も ffmpeg も読む。SIT を読むものは
無い。部分 TS に `ffprobe` をかけてもサービス名は返ってこない。TMSR の出力でも
同じである。TvtPlay で再生しても、TVTest には番組名も放送局名も時刻も出ない。
TVTest が見る PID が空だからである。そこで `.ts` は放送のテーブルのまま書く。

0.6.5 までは両方とも部分 TS が既定だった。「録画とは何か」に対する規格の答えが
それだから、という理由である。下流にその問いを立てるものは無く、番組情報を誰も
読めないカットができるだけだった。

`--tables` はどちらの向きにも上書きできる。`--tables broadcast` は PMT を作り直し、
SDT を録画自身のものに置き換え、EIT present/following と TOT を本来の PID に注入
する。TOT の時刻は各区間が開始したソース時刻から進むので、カットのたびに飛ぶ。
放送自身の実時刻を保つとはそういうことである。

`--tables muxer`（旧 `--no-tables`）は、マルチプレクサが書いた PAT・PMT・SDT をそのまま
残す。録画ではなく素のストリームが欲しいツールのため、そして下流のツールが食い違う
ときに「どちらの記述を読んでいたのか」を切り分けるためのものである。どれが使われて
いるかは `--analyze` の出力行に出る。

## PID は録画のまま、クロックは映像に乗る

部分 TS は PID の割り当てを規定していない。TMSR は 0x1100 番台に振り直すが、
**SmartCut は録画自身の PID を保つ。** マップも映像も音声も字幕も、すべて元の PID に
戻る。

1 つだけ引き継げないものがある。**日本の放送はクロックを専用の PID で送っている**
（BS フジは 0x0100、地上波は 0x01FF）。libavformat の mpegts マルチプレクサにはそうさせる
手段が無いので、PCR は映像のアダプテーションフィールドに乗る。

PMT はそのとおりに記述しており、ファイルは自己整合している。MPEG-2 としても ARIB
としても合法であり、PMT から PCR_PID を読むものは影響を受けない。専用 PID を合成する
こと自体はできるが、そうすると映像側にクロックの写しが二重に存在することになる。
しかも、挿入したパケットが実際に置かれる位置と、そのパケットが名乗る時刻との差
（24 Mbit/s で約 63 マイクロ秒）は、MPEG が PCR に許す誤差の範囲外である。規格の
字面だけを満たす作り物のクロックより、正しい位置に置かれた映像上のクロックのほうが
よい。

## 再エンコードした先頭が「59.94 fps」と名乗っていた

DGIndex → AviSynth（MPEG2Dec）でフレームレートが合わない、という報告から表面化した。
**無劣化点以外で切れば先頭は再エンコード区間になり、そのシーケンスヘッダを書くのは
SmartCut である。** それがソースと食い違っていた。

```
ソース   frame_rate_code=4 (30000/1001)
出力     frame_rate_code=7 (60000/1001)   <- 再エンコードした先頭だけ
```

**インデックス作成ツールは、最初に出会ったシーケンスヘッダをファイル全体のものとして
信用する。** そのため 29.97 の録画が 59.94 として下流に渡っていた。

原因は出力タイムラインの単位だった。フィールド単位のタイムベース（1 ティック＝
1 フィールド）をそのままエンコーダへ渡していて、**MPEG-2 のフレームレートコードは
タイムベースから導かれる**ので、2 倍になった。`framerate` を別途設定しても効かない。
mpeg12enc はタイムベースしか見ないからである。

エンコーダには**ピクチャ単位のタイムベース**を渡し、渡すピクチャに番号を振り、その
番号がタイムライン上のどこに落ちて何フィールドを占めるかを別に管理することで修正
した。出力側のフィールド単位タイムラインは変えていない。

これはフレームハッシュ照合では見つからない種類の問題なので、
`tests/run_ts_layout_tests.sh` に「再エンコードした先頭のシーケンスヘッダがソースと
一致するか」の検査を追加した。

## 再エンコードした先頭は 104.857 Mbit/s とも名乗っていた

同じヘッダの 2 つ先の欄で、上の検査はそこを見ていなかった。このファイルを渡された
スマートレンダラーは **「ビットレート（サポートしていません）」** と言って受け付けない。

```
録画本体   bit_rate=50000 (20.000 Mbit/s)  vbv=597   x484
先頭       bit_rate=262143 (104.857 Mbit/s)  vbv=252   x1
```

262143 は 18 ビットすべて 1 で、ヘッダが「分からない」と言う値である。libavcodec は
MPEG-2 シーケンスヘッダのレートとバッファを**レート制御**から書く。`rc_max_rate` と
`rc_buffer_size` で、どちらも設定していなかった。何も渡さなければこの値を書く。
`bit_rate` はヘッダに届かない。あれはエンコーダが*使う*量であって、*名乗る*量では
ない。

そこで録画自身の 2 つの数値をシーケンスヘッダから読み戻し
（[`bitstream::mpeg2_rate`](../../rust/crates/core/src/bitstream.rs)）、レート制御に
渡す。エンコーダが書くヘッダは、周りのコピーされたピクチャと同じ値を名乗るようになる。
読む側の費用は無い。ヘッダはバイト列の中にあり、TS ならエントリーポイントごとに
書き直されている。ただし読む場所が `signalling_of` で、ここは HDR でなければ早期に
return していた。つまり普通の放送はすべて素通りしていた。

libavcodec に渡す前に答えておくことが 2 つある。渡した上限を超える目標値は拒否され、
実測平均の 1.2 倍は録画自身の上限を普通に超える。そこで目標値は上限まで下げる。
両隣のコピーされたピクチャに許されていた上限でもあるので妥当である。もう 1 つ、その目標値で
1 フレームが入らないバッファも拒否される。自分のフレームが入らないバッファを名乗って
いる録画は起こり得ないことを記述しているので、そこは深追いせず、数値をそのままにする。

検査はレートとバッファも比べるようにした。**SmartCut が放送から作ったカットは、
残した区間の先頭ごとに、ずっとこのヘッダを積んでいた。**退行ではなく最初からあった
もので、見つかったのは、プレーヤーが何も言わずに拒否するところを、2 つ目のヘッダを
読むツールが明示的に指摘してくれたからである。

## 字幕を読んで、プレビューの上に出す

カットに関するかぎり、ARIB 字幕は**運ぶもの**であって読むものではない。バイト列を
そのまま出力へ移し、範囲の両端を整えればよい。ところが編集画面には別の問いがある。
**いまこの瞬間、画面には何が出ているのか。** 継ぎ目が台詞の途中に落ちていないかは、
映像だけを見ても分からない。

その字幕を復号できるものは、SmartCut が同梱する FFmpeg には無い。Debian の
FFmpeg 7.1 に ARIB 字幕のデコーダは入っていないし、`libaribcaption` を積んだ
ビルドを前提にすることもできない。そこで**自分で読む**（`caption.rs` の `Layout`）。
文字そのものの復号は、番組名を読むのに使っている `arib.rs` がすでにできる。
足りないのは**どこに置くか**である。

字幕の文（statement）はレイアウトの宣言から始まる。放送はこう送ってくる:

```
CS  SWF(7)  SDF(620;480)  SDP(170;30)  SHS(4)  SVS(24)  SSM(36;36)
APS(5,0)  [≫カローラは]  APS(6,0)
```

- `SWF` は画面の形式。**7 は 960 x 540 の字幕プレーン**である。これは規格を引くまでも
  なく録画自身から読める。表示領域 620 x 480 を (170, 30) に置くと、左右に 170 ずつ、
  上下に 30 ずつで、960 x 540 にちょうど収まる。
- `SSM` が文字の大きさ（36 x 36）、`SHS` と `SVS` が文字のまわりに空ける幅（4 と 24）。
  足したものが**文字フィールド**で、この放送では 40 x 60。表示領域 620 x 480 には
  15 桁 x 8 行が入る。
- `APS(行, 桁)` が書き始める位置で、**行が先**、どちらも表示領域の左上から 0 で
  数える。上の例は下から 3 行目である。8 行のうち行 5・6・7 に置かれるのが普通の
  字幕で、これは画面の下に出る字幕そのものである。
  数える単位は**そのとき有効な文字の大きさ**のフィールドになる。`MSZ` で書いている
  局が桁 25 を送れば 58 + 25 x 20 で、右端にそろえた 1 行になる。全角のまま数えると
  1058 で、960 ドットのプレーンの外である。`SSZ` なら行も半分で、こちらは下へはみ
  出す。実放送 5 局で試して 3 局がこれに当たった。プレーンの外の行は描かれないので、
  返事や相づちが丸ごと消えていた。
- `SDF` は表示領域の大きさ。ここで使うのは**右端**である。文字が右端に入らなければ、
  次の行の左端へ送る。受信機がそうするので、放送局もそれを見込んで書いている。
  1 つの文に 2 人分の台詞を入れ、位置を変えずに色だけ変えて続ける局があり、後ろの
  台詞はプレーンの外へ出ていた。行末がちょうど右端に乗る局もあるため、端に乗る文字
  は収まったものとして扱う。
- `ACPS(x; y)` は行を置くもう一つのやり方で、多くの局はこちらを使う。行と桁ではなく
  **プレーンのドットそのもの**で位置を指定する。指すのは文字フィールドの**左下**で、
  540 ドットのプレーンの 509 は「一番下の行」であって「下からはみ出した行」ではない。
  しかも大きさの指定（フィールドの高さが決まる）は ACPS の前に来ることも後に来ることも
  あるので、下端のまま持っておき、文字を描く段になって上端に直す。読み飛ばしていたため、
  これらの局の字幕はすべて左上に出ていた。
- 色は `RDF`〜`WHF` の 8 色と、`COL` の番号指定。ここで追うのは前景色だけで、
  背景はプレビュー側が半透明の黒い箱を敷く。放送局が指定する背景色は 128 色の
  カラーマップの中にあり、プレビューに必要なのは「文字が読めること」だからである。
- 文が `CS` だけで終わっていれば、それは**字幕を下ろす合図**である。同じ形が CM の
  切れ目の手がかりにもなっている（[CM 検出](cm-detection.ja.md)）。
- `TIME` は文が自分で時間を計るためのもの。`TIME(0x20, n)` は 0.1 秒単位で n だけ待ち、
  その後ろの `CS` は「いま消す」ではなく「待ったあとに消す」を意味する。つまり
  `CS … 本文 … TIME(2.0) CS` は 2 秒間出る 1 行である。ただの消去として読むと直前の
  本文まで消えてしまい、この書き方をする局の字幕は**まったく出なかった**。そこで 1 つの
  文からは**ページの並び**（`caption::Page`）が返る。それぞれに出る時刻が付き、
  文に書かれていれば下ろす時刻も付く。

半角も扱う。英数字と半角カタカナの集合は 1 文字が半フィールド、`MSZ`（中サイズ）は
全角文字を半フィールドに描く。1 行 15 文字では足りない字幕は、これで書かれる。

### 放送局が「画像で送ってくる文字」

字幕の中身には、どの集合にも符号が無いものがある。文が次の行へ続くことを示す矢印、
話者名を囲む二重括弧、ドイツ語の行に出る `ü` である。ARIB の答えは**ドットを送る**
ことだ。文は本文の隣のデータユニット（`data_unit_parameter` は 1 バイト集合が 0x30、
2 バイト集合が 0x31）にグリフのパターンを載せ、終端バイトの前に `0x20` を置く
エスケープでダウンロード集合を指示し、そこに入れた区点を書く。

綴る材料が無いので `〓` を返していた。グリフを持たない受信機が出すものである。
**これは珍しい話ではない。** ここにある 32 局から 1 局 2 本ずつ、62 本を読んだ。
字幕があるのは 51 本、読めた文は 27,829。そのうち 971 文（3.5%）に `〓` が出て
おり、**その全部**がダウンロード集合の区点だった（名前の付かない普通の区点では
ない）。グリフを送ってくるのは、字幕を出す 26 局のうち 15 局。（ただしその区点が
全部グリフだったわけではない。マクロで指示し直されたひらがなも混じっている。
次の節である。マクロを実行しない読み取り側には、その 2 つが区別できない。）

そこでドットを run に付けて返し（`caption::Glyph`。1 ドット 1 ビット、階調は潰す）、
ウィンドウ側がフォントのグリフと同じ文字セルの中に描く。標本の 43 種類は、文字セル
そのものである 36 x 36 で送られ、わずかに 18 x 36 がある。これは `MSZ` で書かれた行に
放送局が送る大きさである。どちらもセルの中に描くので、その大きさで送られていない
グリフは**拒否するのではなく伸縮する**。

外から見るとバグに見える性質が 2 つある。

- **同じ区点が行ごとに定義し直される。** ある局は区点を 1 つ、DRCS-1 の先頭の
  0x4121 しか使わず、使う文のたびに中身を入れ替える。この行では矢印、次の行では
  括弧。最初のパターンを覚えて使い回す読み取り側は、番組の残りをすべて矢印で描く
  ことになる。
- **パターンが同じ文に入っていない区点も書かれる。** そこでパターンは（書式と同じ
  理由で、同じ
  `Layout` に）覚えておく。一度も定義されていない区点はやはり `〓` になる。時間軸を
  掃けば普通に起きることで、ウィンドウはその瞬間の前後だけを読むから、区点を定義した
  文が手前にあることがある。

### 話者名の前に付く 2 バイト

字幕が集合を切り替えるのは `SS3`、つまり `0x1D` と 1 バイトである。そこにあるのは
**カタカナではない**。字幕の初期状態は 4 枠のうち 3 枠までは番組名と同じだが、
4 枠目だけが違う。**マクロ集合**で、そのセルはエスケープシーケンスそのものである。
`1D 60` は漢字・英数・ひらがな・マクロを 4 枠に指示して 1 枠目と 3 枠目を呼び出し、
`1D 61` は英数の代わりにカタカナを入れた同じもの。放送局はこれを短縮形として使い、
話者名を出す行は 6 バイトのあいだに 3 回も集合を切り替える:

```
1D 60  0E  MSZ  (    1D 61  0E  ヨ ハ ネ ス    1D 60  0E  )
```

これを文字として読むと、切り替えのたびにカタカナが 1 つ紛れ込む。さらに悪いことに
指示されるはずの集合が指示されないので、後続の本文は違う集合で読まれる。この行は
放送が `（ヨハネス）` と言っているところを `ム(メhOM9ム)` として返っていた。
そして `1D 60` は、G2 に入れたダウンロード外字を**ひらがなに戻す**ときにも使われる。
つまりこの局では、外字より後ろのかなが軒並み外字として読まれ、セルごとに `〓` に
なっていた。上の節の修正だけを見ていると、外字のせいに見える `〓` である。

規格の先頭にある 3 つのマクロは実行する。知らないセル、つまりモザイク集合やデータ
放送のダウンロード集合を指示する残り 13 個は、当て推量ではなく**何もしないものとして
実行する**。集合はそのまま、文字も書かない。初期状態は名前で指定するようにした
（`arib::Start`）。SmartCut が読む 2 種類の文字列は、初期状態を共有しない。

両方を直してから同じ 62 本を読み直すと、**`〓` は 1 つも出ない**。字幕を運ぶ 51 本の
27,829 文の中でダウンロードされたグリフを 1,213 個描き、名前の付かないセルは残らな
かった（`capdiag <file> stats`）。これはバイト列が持っている文の全部である。テーブルを
無視して字幕パケットを直接探す読み取り側と同じ数で、そこに追いつくには次の節が必要
だった。

### 先頭のテーブルに載っていない字幕

レコーダーは番組より先に録画を始め、放送局は番組が始まってから字幕ストリームを
announce する。だからファイル先頭の PMT には映像と音声しか載っておらず、数秒後に
字幕 PID を含む PMT へ差し替わる。libavformat はファイルの先頭を調べて **5 MB で
打ち切る**。放送なら 2.5 秒ほどである。そのため、そういう録画では 2 枚目の PMT を
見ない。字幕ストリームは一覧に出ず、編集画面に字幕トラックは出てこないし、CM 検出は字幕の
印を読めないし、カットも運ぶべきものを特定できない。

同じ 300 本（32 局から 2 本ずつ）のうち字幕を運ぶのは 279 本で、そのうち **7 本が
遅れて announce** されていた。位置は 8.4〜8.8 MB で、探索が止まるすぐ先である
（最初の字幕パケットはさらに先、10〜12 MB）。残り 20 本はファイルのどこにも字幕が無い。
テーブルではなくバイト列を直接見た答えである。

そこで、**字幕ストリームが 1 本も出てこなかった TS だけ**、32 MB の探索でもう一度
開く（`input.rs` の `captions_may_come_later`）。この 32 MB は読む量ではなく上限で、
解析はいくら上限を上げても 5 秒分、放送なら 10 MB ほどで止まる。実測で、本当に字幕が
無い録画で約 0.3 秒、最初から字幕が載っていた 10 本に 9 本ではゼロ。必要なところで
だけ訊く。このモジュールの他の 2 つの開き直しと同じ作法である。

出てくるのは「文字列と、それをどこに置くか」である。放送局が描いた字については、
そのドットも付く。**描くのはウィンドウ側**で、持っているフォントで縁取り付きに描く。
だから拡大しても輪郭がぼやけないし、ここにある描画コードは、どのフォントにも無い字の
ドットをほどく分だけである。フォントが指定のフィールドより広く描く字は、
その中に詰める。ARIB を知らないフォントは、半フィールドを指定されようが全角の括弧を
全角の幅で描くので、話者名の頭の括弧が隣の名前の下に潜っていた。

読む範囲も全部ではない。プレビューは時間軸を掃くものなので、**その瞬間の前後だけ**を
読んで持っておく（`subs.rs`。手前 30 秒・先へ 30 秒）。手前を読むのは、いま出ている
字幕を出したのは**前の**文だからである。再生中に窓の端を越えるのは 1 分に 1 回で、
その中の移動はただの検索になる。ディスクの字幕も同じ仕組みで読む
（[ディスクが描く字幕](disc.ja.md#ディスクが描く字幕)）。

## 音声だけを `.aac` として取り出す

DGIndex → x264 → mux というワークフローでは、音声は**素の ADTS ファイル**として
マルチプレクサに渡る。その `.aac` を作る段が弱点になっていた例がある。DGIndex が出力した
`.aac` が `FF F8 04 22` で始まっていた。同期語は正しいが、続く内容が
「Main プロファイル / 88.2 kHz / 0 チャンネル」を宣言しており、そんなものは存在
しえない。L-SMASH は最初のフレームから AudioSpecificConfig を組み立てるので、何も
読まないうちに諦める（`failed to find the matched importer`）。

コピーされたフレームはソースと 1 バイトも違わない。

```
ソース                ff f8 4c a0  MPEG-2、CRC 付き、profile=LC、48000Hz、2ch
コピーしたフレーム    ff f8 ...    構造上、録画自身のバイト列
ここで書いたフレーム  ff f9 ...    MPEG-2、CRC なし
```

決め手は、**コピーではなく書き出したフレームでだけ壊れる**という点だった。コピーの
場合は放送自身のバイト列がそのまま通るので ADTS は `ff f8` のまま、つまり日本の放送
AAC が常に取る形のままである。同じフレームを ffmpeg の ADTS 書き出しに渡すと
`ff f1`（MPEG-4、CRC なし）が**ハードコードで**書かれる。ヘッダ長が 9 バイトから
7 バイトに変わるので、ARIB を前提に 9 バイト目を見に行くツールは設定を読み違える。
そして `04 22`（Main / 88.2 kHz / 0ch）は、まさに「読めなかった」ときの既定値である。
この 2 ビットは ffmpeg 側からは変えられない。

そこで ffmpeg 側では書かないことにした。`adts.rs` がヘッダをこちらで組み立て、
SmartCut が書くフレームは録画が名乗るバージョンを名乗る。放送は MPEG-2 AAC であり、
継ぎ目も MPEG-2 AAC である。[音声](audio.ja.md#mpeg-2-aac-で書き出す--aac)を参照。

録画と形が違うまま残っているのは CRC である。ここで書くフレームは
`protection_absent` を立てているので、ヘッダが 9 バイトではなく 7 バイトになる。
これはフレームごとのフィールドなので、CRC を持つフレームの中に混在しても合法だが、
録画が持っていたはずのバイト列とは一致しない。`--aac mpeg2|mpeg4` でバージョンを
上書きできる。ただしフレームをコピーしているあいだは、録画と食い違う要求は、2 種類の
AAC が混在するストリームを作るのではなく拒否する。

そうしたフレームが何個あるかはモードによる。既定の `smart` では境界がまたがる
フレームだけ、2 区間のカットで 5606 個中 4 個であり、CM カットのように継ぎ目が無音
なら 0 個である。`reencode` では全部、`copy` では 0 個である。

`write_audio_es()`（CLI では `--audio-es`）は、**書き終えた出力を読み直して**音声を
ADTS として書き出す。そのため、動画の隣に置かれるファイルは、必ずその動画に入って
いる音声そのものになる。L-SMASH の `muxer` を通ることも確認済みである
（`Track 1: MPEG-4 Audio`、48 kHz ステレオ、尺も一致）。

このサイドカー出力自体は、GUI からは外してある。回避策が必要だった原因、つまり
MPEG-2 のストリームの中で継ぎ目だけが MPEG-4 を名乗るという問題は、いまは発生源で
直っているからである。音声の*モード*は出力設定画面にあり、チャンネル数やビット
レートと並んでいる（[音声](audio.ja.md#出力設定画面での音声設定)）。既定はエンジン
自身の既定、つまりスマートレンダリングである。

## L-SMASH に渡すなら素のストリームで

出力を L-SMASH の `muxer` に渡すと `[importer: Error]: failed to find the matched
importer.` で止まる、という報告があったので確認した。**ソースの `.ts` を渡しても同じ
エラーになる。** `muxer` が読むのは素のストリームだけであり（Annex-B の
H.264/H.265、ADTS AAC、AC-3 など）、トランスポートストリームは最初から対象外である。
出力の AAC には何の問題も無い。

確認した内容は次のとおり。

| 渡したもの | 結果 |
|---|---|
| 出力の `.ts` をそのまま | `failed to find the matched importer` |
| **ソースの `.ts` をそのまま** | **同じエラー** |
| 出力から取り出した `.aac`（ffmpeg） | `Track 1: MPEG-4 Audio` — 通る |
| 出力から取り出した `.aac`（PID の PES を素朴に連結） | 通る |
| ソースから取り出した `.aac` | 通る |

出力の PMT はソースと同じ stream_type `0x0F`（ADTS AAC）を持ち、先頭バイトは
`ff f8` の同期語である。PID をそのままダンプする素朴な方法でも取り出せる。

```bash
ffmpeg -i cut_xxx.ts -map 0:a:0 -c copy cut_xxx.aac   # これを muxer に渡す
```

なお **L-SMASH は MPEG-2 映像を扱えない**（`remuxer` は `no support to remux this
stream` と言う）ので、この素材を L-SMASH だけで MP4 にすることはそもそもできない。
想定されているワークフローには映像を H.264 に変換する別の段があり、音声だけを引き
継ぐ形になっている。
