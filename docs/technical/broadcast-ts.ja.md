# 放送録画ワークフローとの互換

[← ドキュメント](../README.ja.md) ・ [← SmartCut](../../README.ja.md) ・ [English](broadcast-ts.md)

日本の放送録画を前提にしたツール（DGIndex など）は、フレームを 1 枚も読む前に
PID・PMT・サービス番号・記述子を読む。そこが録画と違っていると、ファイルが開かない
か、音声トラックが見つからない。

このページでは、切ったあとの `.ts` を「元の録画と同じ形」に保つために SmartCut が
何をしているかを扱う。

## 出力の TS は録画のレイアウトを引き継ぐ

ソースと並べると、初期の出力は次のようになっていた。

| | PMT PID | 映像 PID | 音声 PID | 音声の記述子 |
|---|---|---|---|---|
| ソース（BS フジ） | 0x100 | 0x1100 | 0x1101 | `0x52` `0x0a` |
| 出力（当初） | 0x1000 | 0x100 | 0x101 | **なし** |
| 出力（現在） | 0x100 | 0x1100 | 0x1101 | `0x0a` |

**PID は映像ストリームの PID から導く。** 「ファイル内で最小の PID」からではない。
放送録画は字幕やデータ放送も*ストリーム*として持っており、その PID は多重化器が
受け付ける範囲（0x0020〜0x1FFA）より下にある。最初の実装はそれを拾ってしまい、
`mpegts_start_pid` に 18 を渡し、0 バイトの出力を作った。

`0x52`（component_tag）だけは書かれない。ffmpeg の多重化器が書かないからである。

### いまはストリームごとに元の PID へ戻す

上の表は「映像の PID から採番する」でたどり着ける限界である。多重化器は
`AVStream.id` を**そのストリームを書く PID** として読む。16 以上の値は
`mpegts_start_pid` からの採番ではなくそのまま使われるので、各ストリームに録画での
PID を渡せば、音声も字幕も元の位置に戻る。

旧方式で音声が一致していたのは偶然である。0x1100 に 1 を足すとたまたま 0x1101 に
なるからである。PID が散らばっている録画（0x100f / 0x104f / 0x120f）ではまったく
一致しなかった。

記述子は別の話で、多重化器はそもそもそれを書かない。記述子は次に述べるパスで
復元する。

## 録画自身の表を書き戻す

> 0.3.1 以降、既定の出力は後述の部分 TS である。この節が説明するのは
> `--tables broadcast` の動作であり、その下にある仕組みは両方の形式に共通である。

放送は自分自身についても語っている。これはどのサービスか、放送局の名前は何か、
いま何を放送していて次は何か、いまは何時か。PAT・PMT・SDT・EIT・TOT がそれである。
**録画機のライブラリ表示も、プレイヤーのチャンネル表示も、下流のツールも、実際に
読んでいるのはこれである。**

そしてこれらは多重化を生き延びない。libavformat は自分の知っていること、つまり
ストリームの情報だけから PAT・PMT・SDT を書く。字幕は多重化器がそのコーデックを
知っているので ARIB の記述子つきで出てくるが、それ以外は書かれない。音声の
component tag も、コピー制御記述子も、文字スーパーのストリームの素性もである。
EIT と TOT は失われるよりたちが悪い。PID 0x12 をコピーするよう指示すると、
多重化器はそれを無名の private ストリームとして受け入れ、**自分の選んだ PID に
置く**。そこは誰も見に来ない場所である。

そこで、書き終えたファイルを 1 パスなめて書き戻す。

- **PMT を録画自身の記述子で作り直す**
- **SDT を録画自身のセクションで置き換える。** これにより、サービス名が ARIB の
  文字符号のまま届く。このプログラムは 1 バイトも解釈する必要がない
- **EIT present/following と TOT を、本来の PID に注入する**
- 連続性カウンタをすべて振り直す

注入したセクションをどこに置くかは、出力側の時計で決める。残す区間ごとに、その区間の
最初のピクチャが来る**ソース上のバイト位置**で読んだスナップショットを使う。その
バイト位置はアクセスポイント索引が知っているので、数ギガバイトのファイルでも安く
済む。したがって番組の境界をまたぐカットは、両方の番組を記述する。TOT の時刻は出力の
進行に合わせて進める。スナップショットのままにすると、ファイル全体で同じ秒を
名乗ってしまう。

限定受信記述子（0x09）だけは引き継がない。出力はスクランブルされておらず ECM
ストリームも無いので、書き戻すのは存在しないファイルを記述することになる。

## 書き戻す説明は、実際に書いたものに合わせて削る

同じ理屈をもう一歩先まで適用する必要がある。放送はデータ放送と文字スーパーを
「送っているストリーム」として記述しているが、カットした出力はそのどちらも運ばない。
番組の記述をそのまま丸ごとコピーすると、**出力はファイルに存在しないものへの
エントリポイントを宣言する**ことになる。BS フジの録画では、データ放送
（component tag 0x40）を指すデータコンテンツ記述子が、データ放送の入っていない
ファイルに残っていた。

ARIB はストリームを PID ではなく 1 バイトの component tag で指す。そのやり方で
他のストリームを指す記述子は 3 つあり（component 0x50、audio component 0xC4、
data content 0xC7）、3 つともタグを本体の 3 番目に置く。**録画のマップが記述して
いて、出力が運んでいない**タグを指す記述子は削除し、長さと CRC を付け直して
セクションを閉じ直す。

この規則は両方の条件が必要である。このプログラムが読んだどのマップにも現れない
タグはそのまま残す。放送局自身のテーブルが食い違っていることは、ここで決着を
つける問題ではないからである。

ダウンミックスしたトラックは「運んでいない」に数える。畳んだトラックは、その audio
component 記述子が名乗るチャンネル構成をもう持たないので、マップから外れるのと同じ
理由で番組の記述からも外れる。

**削るのはいま放送中の番組の記述だけである。** present/following は 2 つの
セクションとして来るが、このファイルについて語っているのは最初の 1 つだけである。
2 つ目は「そのあと放送で何が来たか」の記録であり、そのストリームがこのファイルに
入ることは最初からありえない。そのタグをこのファイルの内容と照合するのは、誰も
していない問いに答えることであり、そこに書かれた唯一正しい情報を捨てることになる。

## 部分 TS として書く（既定）

放送録画のカットは、規格の言葉でいえば**部分トランスポートストリーム**である。
DVB は EN 300 468 Annex C で、ARIB は TR-B15 でこれを規定している。ブルーレイ
レコーダーが書くのもこれであり、TMPGEnc MPEG Smart Renderer もこれを書く。

部分 TS は、生の多重を記述するテーブルを一切持たない。NIT・SDT・EIT・TDT・TOT の
代わりに **SIT が 1 枚**あり（PID 0x001F、テーブル 0x7F）、すべてがそこに入る。

| 場所 | 内容 |
|---|---|
| 伝送ループ | `partial_transport_stream_descriptor`（このファイル自身の実測ピークレート）と `network_identification_descriptor`（JPN と BS/CS/TB。元のネットワーク ID から読む） |
| サービスループ | `partial_transport_stream_time_descriptor`（番組が放送された時刻と長さ）、`service_descriptor`（サービス名。録画の SDT から）、および**現在のイベントが持っていた記述子すべて**（番組名・詳細・ジャンル・コンポーネント。録画の EIT から） |

**バイト列は録画自身のものである。** サービス名も番組名も ARIB の文字符号のまま
運ばれ、このプログラムはその中身を一切解釈しない。ここで書くのはその周りの枠だけで
ある。

コピーできない数値が 1 つだけある。ピークレートである。録画は部分 TS ではなかった
ので、自分を部分 TS として記述しておらず、その数値を誰も書き残していない。そこで
出力を 1 パスで測る。窓は 1 秒である。これより短い窓で測ると、大きなピクチャ 1 枚が
ファイルの持続しないバーストとして読まれてしまい、どの機器も用意する必要のない
レートをテーブルが名乗ることになる。

次に来た番組は入れない。present/following は 2 つのセクションとして来るが、この
ファイルについて語っているのは最初の 1 つだけである。SIT はこのファイルが*何で
あるか*を述べるものである。

SIT は残す区間ごとに作り、バージョンは内容が変わったときにだけ進める。番組の境界を
またぐカットでは、それぞれの番組がそれぞれの範囲で名乗られる。内容が変わっていない
のにバージョンだけ変えるのは、すでに持っているテーブルを読み直せとプレイヤーに
言うことになる。

セクションの上限は 4096 バイトで、実際の録画の拡張イベント記述子はそれだけで
1 キロバイトに達していた。入りきらないぶんは末尾から記述子単位で丸ごと落とす。
時刻とサービス名を先に書いているのはそのためである。

## 放送のテーブルのまま書く（`--tables broadcast`）

部分 TS は規格の答えだが、**日本の録画まわりのソフトが実際に読んでいるのは SDT と
EIT である**。TVTest も EDCB も ffmpeg も読む。SIT を読むものは無い。部分 TS に
`ffprobe` をかけてもサービス名は返ってこない。TMSR の出力でも同じである。

そこで従来の形も残してある。`--tables broadcast` は PMT を作り直し、SDT を録画自身の
ものに置き換え、EIT present/following と TOT を本来の PID に注入する。TOT の時刻は
各区間が開始したソース時刻から進むので、カットのたびに飛ぶ。放送自身の実時刻を保つ
とはそういうことである。

`--tables muxer`（旧 `--no-tables`）は、多重化器が書いた PAT・PMT・SDT をそのまま
残す。録画ではなく素のストリームが欲しいツールのため、そして下流のツールが食い違う
ときに「どちらの記述を読んでいたのか」を切り分けるためのものである。どれが使われて
いるかは `--analyze` の出力行に出る。

## PID は録画のまま、クロックは映像に乗る

部分 TS は PID の割り当てを規定していない。TMSR は 0x1100 番台に振り直すが、
**SmartCut は録画自身の PID を保つ。** マップも映像も音声も字幕も、すべて元の PID に
戻る。

1 つだけ引き継げないものがある。**日本の放送はクロックを専用の PID で送っている**
（BS フジは 0x0100、地上波は 0x01FF）。libavformat の mpegts 多重化器にはそうさせる
手段が無いので、PCR は映像のアダプテーションフィールドに乗る。

PMT はそのとおりに記述しており、ファイルは自己整合している。MPEG-2 として合法であり
ARIB としても合法で、PMT から PCR_PID を読むものは影響を受けない。専用 PID を合成する
ことはできるが、そうすると映像がクロックの 2 つ目の写しを持つことになる。しかも挿入
したパケットが実際に置かれる位置と、そのパケットが名乗る時刻との差（24 Mbit/s で
約 63 マイクロ秒）は、MPEG が PCR に許す誤差の範囲外である。規格の字面を満たす
でっち上げのクロックより、正しく置かれた映像上のクロックのほうがよい。

## 再エンコードした先頭が「59.94fps」と名乗っていた

DGIndex → AviSynth（MPEG2Dec）でフレームレートが合わない、という報告から表面化した。
**無劣化点以外で切れば先頭は再エンコード区間になり、そのシーケンスヘッダを書くのは
SmartCut である。** それがソースと食い違っていた。

```
ソース   frame_rate_code=4 (30000/1001)
出力     frame_rate_code=7 (60000/1001)   <- 再エンコードした先頭だけ
```

**インデックス作成ツールは、最初に出会ったシーケンスヘッダをファイル全体のものとして
信用する。** そのため 29.97 の録画が 59.94 として下流に渡っていた。

原因は出力タイムラインの単位だった。フィールド単位のタイムベース（1 ティック＝
1 フィールド）をそのままエンコーダへ渡していて、**MPEG-2 のフレームレートコードは
タイムベースから導かれる**ので、2 倍になった。`framerate` を別途設定しても効かない。
mpeg12enc はタイムベースしか見ないからである。

エンコーダには**ピクチャ単位のタイムベース**を渡し、渡すピクチャに番号を振り、その
番号がタイムライン上のどこに落ちて何フィールドを占めるかを別に管理することで修正
した。出力側のフィールド単位タイムラインは変えていない。

これはフレームハッシュ照合では見つからない種類の問題なので、
`tests/run_ts_layout_tests.sh` に「再エンコードした先頭のシーケンスヘッダがソースと
一致するか」の検査を追加した。

## 音声だけを `.aac` として取り出す

DGIndex → x264 → mux というワークフローでは、音声は**素の ADTS ファイル**として
多重化器に渡る。その `.aac` を作る段が弱点になっていた例がある。DGIndex が出力した
`.aac` が `FF F8 04 22` で始まっていた。同期語は正しいが、続く内容が
「Main プロファイル / 88.2kHz / 0 チャンネル」を宣言しており、そんなものは存在
しえない。L-SMASH は最初のフレームから AudioSpecificConfig を組み立てるので、何も
読まないうちに諦める（`failed to find the matched importer`）。

コピーされたフレームはソースと 1 バイトも違わない。

```
ソース                ff f8 4c a0  MPEG-2、CRC 付き、profile=LC、48000Hz、2ch
コピーしたフレーム    ff f8 ...    構造上、録画自身のバイト列
ここで書いたフレーム  ff f9 ...    MPEG-2、CRC なし
```

決め手は、**コピーではなく書き出したフレームでだけ壊れる**という点だった。コピーの
場合は放送自身のバイト列がそのまま通るので ADTS は `ff f8` のまま、つまり日本の放送
AAC が常に取る形のままである。同じフレームを ffmpeg の ADTS 書き出しに渡すと
`ff f1`（MPEG-4、CRC なし）が**ハードコードで**書かれる。ヘッダ長が 9 バイトから
7 バイトに変わるので、ARIB を前提に 9 バイト目を見に行くツールは設定を読み違える。
そして `04 22`（Main / 88.2kHz / 0ch）は、まさに「読めなかった」ときの既定値である。
この 2 ビットは ffmpeg 側からは変えられない。

そこで ffmpeg 側では書かないことにした。`adts.rs` がヘッダをこちらで組み立て、
SmartCut が書くフレームは録画が名乗るバージョンを名乗る。放送は MPEG-2 AAC であり、
継ぎ目も MPEG-2 AAC である。[音声](audio.ja.md#mpeg-2-aac-で書き出す--aac)を参照。

録画と形が違うまま残っているのは CRC である。ここで書くフレームは
`protection_absent` を立てているので、ヘッダが 9 バイトではなく 7 バイトになる。
これはフレームごとのフィールドなので、CRC を持つフレームの中に混在しても合法だが、
録画が持っていたはずのバイト列とは一致しない。`--aac mpeg2|mpeg4` でバージョンを
上書きできる。ただしフレームをコピーしているあいだは、録画と食い違う要求は、2 種類の
AAC が混在するストリームを作るのではなく拒否する。

そうしたフレームが何個あるかはモードによる。既定の `smart` では境界がまたがる
フレームだけ、2 区間のカットで 5606 個中 4 個であり、CM カットのように継ぎ目が無音
なら 0 個である。`reencode` では全部、`copy` では 0 個である。

`write_audio_es()`（CLI では `--audio-es`）は、**書き終えた出力を読み直して**音声を
ADTS として書き出す。動画の隣に置かれるものは、構造上、その動画の中に入っている音声
そのものである。L-SMASH の `muxer` を通ることも確認済みである（`Track 1: MPEG-4
Audio`、48kHz ステレオ、尺も一致）。

サイドカーそのものは GUI からは外してある。この回避策を必要にしていた事情、つまり
MPEG-2 のストリームの中で継ぎ目だけが MPEG-4 を名乗るという問題は、いまは発生源で
対処されている。音声の*モード*は出力設定画面にあり、チャンネル数とビットレートと
一緒に置かれている（[音声](audio.ja.md#出力設定画面での音声設定)）。既定はエンジン
自身の既定、つまりスマートレンダリングである。

## L-SMASH に渡すなら素のストリームで

出力を L-SMASH の `muxer` に渡すと `[importer: Error]: failed to find the matched
importer.` で止まる、という報告があったので確認した。**ソースの `.ts` を渡しても同じ
エラーになる。** `muxer` が読むのは素のストリームだけであり（Annex-B の
H.264/H.265、ADTS AAC、AC-3 など）、トランスポートストリームは最初から対象外である。
出力の AAC には何の問題も無い。

確認した内容は次のとおり。

| 渡したもの | 結果 |
|---|---|
| 出力の `.ts` をそのまま | `failed to find the matched importer` |
| **ソースの `.ts` をそのまま** | **同じエラー** |
| 出力から取り出した `.aac`（ffmpeg） | `Track 1: MPEG-4 Audio` — 通る |
| 出力から取り出した `.aac`（PID の PES を素朴に連結） | 通る |
| ソースから取り出した `.aac` | 通る |

出力の PMT はソースと同じ stream_type `0x0F`（ADTS AAC）を持ち、先頭バイトは
`ff f8` の同期語である。PID をそのままダンプする素朴な方法でも取り出せる。

```bash
ffmpeg -i cut_xxx.ts -map 0:a:0 -c copy cut_xxx.aac   # これを muxer に渡す
```

なお **L-SMASH は MPEG-2 映像を扱えない**（`remuxer` は `no support to remux this
stream` と言う）ので、この素材を L-SMASH だけで MP4 にすることはそもそもできない。
想定されているワークフローには映像を H.264 に変換する別の段があり、音声だけを引き
継ぐ形になっている。
