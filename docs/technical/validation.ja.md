# 検証結果と既知の制限

## 検証結果

`tests/run_tests.sh` は出力を復号してソースのフレームハッシュと突き合わせ、
フレーム数・整列・ビット単位で一致したフレーム数を検査する。

| ケース | 無劣化コピー率 |
|---|---|
| H.264 単一区間 | 180/222（81.1%） |
| H.264 複数区間 | 300/336（89.3%） |
| H.264 中抜き（末尾まで） | **540/540（100%）** |
| H.264 アクセスポイントちょうど | **180/180（100%）** |
| H.264 区間が GOP より短い | 0/21 — 全編再エンコードにフォールバック |
| HEVC | 300/342（87.7%） |
| H.264 29.97 fps | 300/342（87.7%） |
| H.264 オープン GOP（leading picture が参照される） | 0/342 — 開始点として拒否。これが正しい動作 |
| **MPEG-2 TS オープン GOP** | **328/342（95.9%）** |
| MPEG-2 TS 複数区間 | 296/299（99.0%） |
| MPEG-2 TS 末尾まで | 447/449（99.6%） |
| Matroska 出力 | 180/222（81.1%） |

13 ケースすべてでフレーム数と整列が一致している。

## 実素材での検証

合成素材では見えない問題があるので、実際の放送録画に対しても検証している。
`tests/verify_real.py <src> <out> <ranges>` が、フレーム数・整列・ビット一致率・
タイムライン・インターレース・音声と映像の尺の差をまとめて検査する。

| 素材 | 結果 |
|---|---|
| 地上波 NHK E テレ（MPEG-2 1440x1080i、真の 29.97） | **899/899、98.2% 無劣化、タイムライン一致、インターレース保持、A/V 2.0 ms** |
| BS11（MPEG-2 1920x1080i） | **899/899、98.2% 無劣化、上と同じ** |
| AT-X（MPEG-2 1440x1080、**2:3 プルダウン**） | **719/719、99.9% 無劣化、2:3 パターン保持、A/V 2.0 ms** |
| **VC-1** のプレス Blu-ray（1920x1080i アニメ）、GOP 途中〜GOP 途中 10 秒 | **308/308、映像の 90% がバイト一致**、部分 GOP は 48dB で書き直し |
| **VC-1** のプレス Blu-ray（1920x1080p 実写・強いグレイン）、同 10 秒 | **246/246、90% がバイト一致**、45dB で書き直し、グレインも残存 |
| YouTube の H.264 720p（29.24 fps） | 878 フレーム、A/V 2.6 ms |
| VP9 + Opus（webm→mp4） | コピーのみの計画になる場合は通る |

**VC-1 のカットだけは、検査の方法を変えざるをえない。** `verify_real.py` は 2 つの
ファイルをフレーム番号で突き合わせるが、Blu-ray から切り出した断片はそのフレーム
番号を持たない。GOP の途中から始まるため、デコーダは復号できないピクチャを捨て、
そこから先はその枚数だけずれてしまうからである。

そこで [`tests/run_vc1_tests.sh`](../../tests/run_vc1_tests.sh) はバイト列で確認
する。カットの長い一続きが、録画の中に**そのまま**現れることを見るのである。これ
なら整列は要らない。加えて、自分で書いたピクチャについては、一般的なプレイヤーが
使っているデコーダに通し、置き換えた元のピクチャからどれだけ離れているかを測る。
この 2 つが両方とも必要である。わずかに壊れたビットストリームでも復号自体はできて
しまうし、変換の正規化を間違えたストリームは、明るさだけが違う絵として何の警告も
なく復号されるからである。エンコーダとその代償は
[Rust コア](rust-core.ja.md#エンコーダのないコーデック-vc-1)にある。

この検証の過程で、実際の TS が持ち込む厄介事はひととおり出てきた。

- **`start_time` が 29288 秒**（PCR が実時刻に基づいているため）
- **すべてのアクセスポイントがオープン GOP**（776 個中 776 個。leading picture は
  捨ててよいもの）
- **フレーム欠落**（668 MB の録画に 28 個。受信のドロップアウトによる）
- **複数ストリームの共存**（ARIB 字幕、データ放送など）

### 音声を何フレーム再エンコードしたか

`tests/run_aac_tests.sh` は、映像に適用しているのと同じ基準を音声に当てる。出力の
ADTS を 1 フレームずつ辿り、録画自身のバイト列と比較する。素材は日本テレビの録画、
2 区間・境界 4 か所である。

| モード | コンテナ | そのままのフレーム | 再エンコード | ADTS |
|---|---|---|---|---|
| `copy` | TS | **5606/5606（100%）** | 0 | すべて MPEG-2 LC |
| `smart` | TS | **5602/5606（99.929%）** | **4** | すべて MPEG-2 LC |
| `smart` | MP4 | 5602/5606（ペイロード） | 4 | — |
| `reencode` | TS | 0/5607 | 5607 | すべて MPEG-2 LC |
| `smart --aac mpeg4` | TS | 5602/5606 | 4 | **すべて MPEG-2**（下記参照） |
| `reencode --aac mpeg4` | TS | 0/5607 | 5607 | すべて MPEG-4 |
| `smart`、**CM ブロックを 1 つ切り落とし**、境界 4 か所すべて無音 | TS | **1392/1392（100%）** | **0** | すべて MPEG-2 LC |

最後の行が通常のカットの姿であり、そこでは出力が **`copy` とバイト単位で一致する**。

フレームをコピーしているかぎり、録画が持っていない種別の AAC を要求されても応じ
られない。応じれば 2 種類の AAC が混在するストリームになるからである。要求は注記
つきで拒否し、録画自身の種別に従う。全編再エンコードなら何もコピーしないので要求に
応じる。それが `reencode --aac mpeg4` の行である。

MP4 は ADTS のフレーミングを捨ててペイロードだけを保持するので、そちらではペイロード
を比較する。ペイロードが同じなら音も同じである。

### 実素材で見つかったバグ: 再エンコード部でインターレースが失われる

再エンコードされた部分 GOP だけが `interlaced_frame=0` で出力され、コピー部分と
櫛の状態が食い違っていた。原因は `AV_CODEC_FLAG_INTERLACED_DCT` と `INTERLACED_ME`、
およびフィールド順をエンコーダに渡していなかったことである。放送素材ではカット点
ごとに画質が変わることになるので致命的である。修正済み。

### 2:3 プルダウン対応（フィールド単位のタイムライン）

アニメの多くは 24 fps のフィルム素材を、`repeat_first_field` によって 29.97 の
ストリームに載せている。したがって復号されたピクチャは**0.0334 秒と 0.0500 秒の
間隔が交互に来る**。ピクチャ単位で見れば、このストリームは CFR ではない。

手持ちのライブラリで測ったところ、**40 本中 13 本（32%）**がプルダウンだった。

| 局 | プルダウン率 |
|---|---|
| AT-X | 8/14（57%） |
| ディズニーチャンネル | 2/2（100%） |
| BS アニマックス | 3/10（30%） |
| BS11 / BS-TBS / BS 日テレ / NHK / キッズ / テレ朝ch2 | 0% |

無視できる頻度ではないので対応している。要点は**出力タイムラインの単位をフレーム
からフィールドへ落とす**ことである。プルダウンは 2 フィールドと 3 フィールドの
繰り返しなので、フィールド格子の上なら整数で表現できる。出力のタイムベースは
`1/(2 × fps の分子)`（29.97 なら 1/60000）となり、1 フィールドがちょうど
`fps の分母` ティックになる。

副作用として、DTS の作り方も変える必要があった。各ピクチャの継続時間を復号順に
足していく方式は、フィールド長が変動すると表示時刻を追い越してしまい、多重化器に
`pts < dts` で拒否される。表示順の位置から DTS を導く正しい構成に置き換えた。

### planner の位相問題（解決済み）

以前は区間の境界を理想格子 `round(t*fps)/fps` に吸着させていた。これが実際の
ストリームのフレーム位相とずれ（テスト素材で 0.010 秒）、区間の端で 1 フレームを
落としていた。

**吸着をやめたら直った。** 現在、セグメントの長さは planner の計算ではなく
**実際に書き出されたピクチャから測る**ので、格子に合わせる対象がそもそも無い。
各セグメントは自分の最初のピクチャを基準に配置され、次のセグメントは前のセグメントが
実際に占めた長さのあとから始まる。これで位相もプルダウンも自動的に追従する。

### 検証側にもバグがあった

いずれも実素材でのみ表面化した。

- **正解データをフレーム番号で切り出していた。** 実際の録画はフレームを落とすので
  「フレーム番号 = 時刻 × fps」が成り立たず、比較対象が 27 フレームずれていた。
  見かけ上は「一致率 0%」になる。PTS を基準に切り出すよう修正した。
- **時刻の原点が違っていた。** カットは*表示*タイムライン（フォーマットの
  `start_time`、プレイヤーが 00:00 と表示する位置）を基準にしているが、ffmpeg の
  復号出力は*映像ストリームの* `start_time` を基準にしている。放送録画では音声が
  先に始まるので、両者は 0.346 秒ずれる。補正を追加した。

## 既知の制限

- **壊れた録画で失われるのは、傷んだ箇所の絵であって切り出しではない。** 放送には
  穴が開く（受信の乱れ、アンテナが一瞬衛星を見失う）。そこから三つのことが起きる。
  libavcodec は傷んだ箇所のパケットを受け取らない。そのパケットが運んでいた絵の
  表示位置が抜けるので、DTS が越えなければならない間隔が広がる。そして傷の周辺で
  タイムスタンプが進まなくなり、音声フレームが同じ時刻を主張する。以前はこの三つの
  どれもが切り出し全体を止めていた——他は何ともない録画なのに。いまは復号できない
  パケットを捨て、出力タイムラインに置き場のない絵を落とし、直前より後ろに来ない
  音声フレームを落とす。それぞれ数えて、終わりに一度だけ報告する。コピーされる
  部分はどれにも影響されない。32 局 82 本で測ったところ、三つすべてを踏むほど
  傷んでいたのは 1 本だった。
- **最初のフレームが 13 ミリ秒早い**（Python 実装のみ）。生エレメンタリストリームは
  タイムスタンプを一切持たない（全パケットが `N/A`）ので、ffmpeg が `-r` と POC から
  合成する。その過程で最初の `has_b_frames` 個のパケットが PTS 無しで出てくる。
  これを許容するのは MP4 多重化器だけで（`-avoid_negative_ts make_zero`）、Matroska と
  MPEG-TS は拒否する。MKV 出力を MP4 経由で再多重化しているのはそのためである。
  2 フレーム目以降の間隔は完全に均一である。libav 実装ではパケットごとに PTS/DTS を
  自分で割り当てるので、この問題は起きない。
- **leading picture が参照ピクチャであるような H.264/HEVC のオープン GOP は、コピー
  開始点として使えない**（[難所 3](algorithm.ja.md#3-leading-picture--オープン-gop-問題の核心)）。
  これは方式に内在する制限である。回避するには leading picture をビットストリームに
  残したままエディットリストで隠す必要があり、エレメンタリストリーム連結方式では
  表現できない。IDR が規則的に入る素材では問題にならず、放送の H.264 はほぼそれに
  あたる。
- **IDR でないエントリーポイントに継いだコピーは、絵を 1 枚だけ逆順に返すことが
  ある**（[難所 10](algorithm.ja.md#10-継ぎ目の両側のピクチャオーダーカウントは互いのものではない)）。
  復号そのものは間違っていない——リカバリーポイント以降の絵は録画自身と突き合わせて
  確認済みである——が、継ぎ目の両側を並べるカウントは別々のエンコーダが書いたもの
  なので、出ていく場面の絵が入ってくる場面の絵より後に返ることがある。見つかった
  ディスクでは 12 箇所の切り出しで 5 枚。`--clean-joins` で IDR まで進めば 2 枚に
  なり、残る 2 枚は 2 秒以内に IDR が無い継ぎ目である。既定で無効なのは正確さを
  失うからで、置き換わる区間は同じ絵のコピー（ビット単位で一致）に対して 51dB に
  なる。並べ替えの無い素材（MPEG-2、VC-1）には関係しない。
- **Python 版の leading picture 参照判定はファイル内の 1 か所を標本にして**全体に
  適用している（エンコーダが途中で方針を変えないという仮定）。Rust 実装では demux
  しながら `nal_ref_idc` を直接読めるので、この仮定は不要である。
- **H.264 / HEVC のプルダウン（SEI の `pic_struct`）は検出しない。** 日本の放送
  H.264 は CFR なので実害は観測されていないが、MPEG-2 と違って検出していない。
- **Python リファレンス実装は依然として理想格子へ吸着する**ので、位相問題も残って
  いる（`tests/run_tests.sh` の `mpeg2 ts multi` は xfail）。テストオラクルとしては
  機能しているが、Rust 実装のほうが先へ進んでいる。
- **対応コーデックは H.264 / HEVC / MPEG-2 / MPEG-4 Part 2 / VC-1。** VP9 と AV1 は
  エレメンタリストリームを連結する形式を持たないので、別の設計が必要になる。
- **Dolby Vision はコピーには耐えるが再エンコードには耐えない。** 毎ピクチャの RPU は
  ピクチャと一緒にコピーされるので、範囲の両端が録画自身のエントリポイントに落ちる
  カットは RPU を 1 本残らず持って出ていく。継ぎ目で書き直されたピクチャには無い。
  libavcodec が libx265 を設定できるのは、自分が書けるプロファイルに限られるからだ。
  カットはそのことを述べ、録画がストリームレベルで名乗っている Dolby Vision も出力
  から外す。ピクチャが裏付けられないことを名乗り続けるものを残さないためである。
  計測に使ったのは profile 4 の録画で、libavcodec はこれを門前払いする。GOP が 4.2 秒
  あるので、エントリポイントを外した範囲は長く再エンコードされる。
  [Rust コア](rust-core.ja.md#dolby-vision-もピクチャの中にあり書き戻せない)を参照。
- **後方互換の形で書かれた HLG の伝達関数を保てるのは HEVC だけ。** シーケンス
  ヘッダが `bt2020-10` と書き、その隣の SEI が HLG だと言う——この両方を継ぎ目の
  向こうでも再現するには libx265 に `atc-sei` を指示する必要があり、libx264 には
  相当するものが無い。この書き方で HLG を名乗る H.264 の録画は、ここでは計測して
  いない。
- **VC-1 の部分 GOP は SmartCut 自身のエンコーダが書き、書くのはイントラピクチャ
  だけである**（[Rust コア](rust-core.ja.md#エンコーダのないコーデック-vc-1)）。
  libavcodec に VC-1 のエンコーダが無いので、代わりに使えるものが無い。ピクチャは
  置き換える予測ピクチャよりビットを食う（それでもディスク自身の I ピクチャよりは
  小さい）。またフォーマットのうち 2 つ、すなわちパンスキャンのウィンドウと、
  ピクチャ端で量子化を変える指定（`DQUANT=2`）については、間違って書くくらいならと、
  名指しで断るようにしている。フィールドピクチャは読めるが、書くときはインタレース
  フレームにする。

- **映像トラックは 1 本のみ。** Python リファレンス実装では音声も 1 本のみ。Rust
  エンジンは録画が持つ音声トラックをすべて読んですべて書き出し、`.ts` 出力時には
  2 種類の字幕をどちらも引き継ぐ——放送が送る ARIB 字幕と、ディスクが描く PGS
  （[音声](audio.ja.md#音声多重放送)、
  [放送録画ワークフローとの互換](broadcast-ts.ja.md)、
  [ディスクが描く字幕](disc.ja.md#ディスクが描く字幕)を参照）。DVD の字幕は
  TS に運べるストリーム種別が無いので、カットの傍らに VobSub の 2 ファイルとして
  書くか、Blu-ray の種類に変換して中に入れる
  （[同上](disc.ja.md#dvd-の字幕は傍らに置くか変換して中に入れる)）。**Blu-ray の
  メニュー（IGS）とテキスト字幕（TextST）は運ばない。** ただし黙って捨てるのでは
  なく、置いていくものとして名前を出す。メニューのボタンはカットには無いディスク
  構造を指しており、TextST の書体はストリームではなくディスク側にある
  （[同上](disc.ja.md#メニューはストリームではなくそれを知っているのは索引だけである)）。
- **`reencode` 以外のモードでは、音声の境界は依然としてフレーム単位に丸められる。**
  `smart` が取り除くのは「切った側の音が継ぎ目に残ること」であって、区間がフレームの
  整数倍になること自体は変わらない。1 つの瞬間に 2 つのフレームを置けるコンテナが
  無いかぎり、継ぎ目では最大 10.7 ミリ秒の無音が増えるか、最大 10.7 ミリ秒の音が
  失われる。
- **ここで書き出すフレームは ADTS の CRC を持たない**（`protection_absent = 1`）。
  これはフレームごとのフィールドなので、CRC を持つフレームの中に混在しても合法だが、
  録画のフレームとバイト単位で同じ形ではない。
- **`smart` は AAC までで止まる。** 差し替えるフレームは、録画のフレームが覆っていた
  のと同じサンプル範囲を覆わなければならず、それが可能かどうかはエンコーダの遅延が
  フレームの整数倍かどうかで決まる。AAC の遅延は 1024、ちょうど 1 フレームなので、
  出力パケットが同じ格子に乗る。AC-3 は 256 で、出力パケットが常に格子から 256
  サンプルずれる。MP2 のエンコーダはそもそも planar float を受け付けない。どちらも
  実行前に検出して明示し、コピーに切り替える。つまりそうした素材では、既定の動作は
  `copy` と完全に同じになる。
- **`--aac` が届くのは SmartCut が書くフレームだけである。** コピーされたフレームは
  自分の ADTS ヘッダを保つので、**素材を一方の種別からもう一方へ変換することはでき
  ない**。ペイロードが他方のバージョンに無いツールを使っている可能性があり、ビットだけ
  書き換えるのは嘘になるからである。録画と食い違う要求は、混在ストリームを作るのでは
  なく注記つきで拒否する。ただし全編再エンコードのときは何もコピーしないので要求に
  応じる。
