# 放送録画ワークフローとの互換

[← ドキュメント一覧](README.ja.md) ・ [← SmartCut](../README.ja.md) ・ [English](broadcast-ts.md)

## 出力の TS は録画のレイアウトを引き継ぐ

DGIndex のような**放送録画を前提にした道具は、フレームを 1 枚も読む前に
PID・PMT・サービス番号・記述子を読む**。そこが録画と違えば、開けないか、
音声トラックを見つけられない。素材と初期の出力を並べるとこうだった:

| | PMT PID | 映像 PID | 音声 PID | 音声の記述子 |
|---|---|---|---|---|
| 素材（BS フジ） | 0x100 | 0x1100 | 0x1101 | `0x52` `0x0a` |
| 出力（当初） | 0x1000 | 0x100 | 0x101 | **なし** |
| 出力（現在） | 0x100 | 0x1100 | 0x1101 | `0x0a` |

**PID は映像ストリームのものを起点にする。** 「ファイル中の最小 PID」では
ない——放送録画は字幕やデータ放送も*ストリーム*として持っていて、その PID は
多重化器が受け付ける範囲（0x0020〜0x1FFA）より下にある。最初はそれを拾って
`mpegts_start_pid` に 18 を渡し、出力が 0 バイトになった。

`0x52`（component_tag）だけは ffmpeg の多重化器が書かないので付かない。

### いまはストリームごとに元の PID へ戻す

上の表は「映像の PID を起点に連番」までの話である。多重化器は
`AVStream.id` を **書き出す PID そのもの** として読む——16 以上なら
`mpegts_start_pid` からの連番ではなくその値を使う——ので、各ストリームに
録画で乗っていた PID を渡せば、音声も字幕も**同じ PID に戻る**。連番だと
音声が 0x1101 ではなく 0x1100+1 になるだけで一致していたのは偶然で、
PID が飛び飛びの録画（0x100f / 0x104f / 0x120f）では一致しなかった。

記述子のほうは多重化器では埋まらないので、下記の 1 パスで書き戻す。

## 録画自身の表を書き戻す

> 0.3.1 から、既定の出力は下記「部分TS として書く」である。この節が説明
> しているのは `--tables broadcast` の中身で、仕組み自体は両方の土台になる。

放送は自分についても語っている。どのサービスか、局名は何か、いま何の番組で
次は何か、いま何時か——PAT・PMT・SDT・EIT・TOT がそれで、**録画ソフトの
ライブラリ表示も、プレイヤーのチャンネル表示も、下流の道具も、実際に読むのは
そこ**である。

多重化を通ると全部消える。libavformat は自分の PAT・PMT・SDT を
「ストリームがこうある」という情報だけから書く。字幕が ARIB の記述子つきで
出るのは多重化器がそのコーデックを知っているからで、それ以外——音声の
component_tag、コピー制御記述子、文字スーパーの素性——は**書かれない**。
EIT と TOT は消えるより悪い: PID 0x12 をコピーしろと言えば受け付けるが、
匿名の private stream として**多重化器が選んだ PID に置く**ので、そこを
見に行くものは何もない。

なので後から入れ直す。書き終えた TS を 1 パスなめて:

- **PMT を組み直す**（録画自身の記述子つきで）
- **SDT を録画のものに差し替える**——こうするとサービス名が ARIB の文字
  符号のまま届く。こちらが 1 バイトも解釈しなくていい
- **EIT p/f と TOT を、本来の PID の上に差し込む**
- 連続性カウンタを振り直す

差し込む位置は出力自身の PCR で決める。区間ごとに、その区間が開く
**素材のバイト位置**（アクセスポイント索引が知っている）から読んだ
スナップショットを使うので、番組をまたぐカットは両方の番組を名乗る。
TOT の時刻は出力の経過に合わせて進める——スナップショットのまま置くと、
ファイル中ずっと同じ秒を名乗ることになる。

条件付きアクセス記述子（0x09）だけは持ち越さない。出力はスクランブルされて
おらず ECM ストリームも無いので、書き戻せば「無い物」の説明になる。

## 書き戻す説明は、実際に書いたものに合わせて削る

同じ理屈が、もう一段先にも要る。放送はデータ放送も文字スーパーも送っている
ストリームとして説明していて、カットはそれらを運ばない。番組情報をそのまま
写すと、**出力が「無いコンポーネントへの入口」を名乗る**——BS フジの録画で
言えば、データ放送（コンポーネントタグ 0x40）への入口を指す data_content
記述子が、データ放送の入っていないファイルに残る。

ARIB はストリームを PID ではなく 1 バイトのコンポーネントタグで指す。そう
やって他のストリームを指す記述子は 3 つ——component（0x50）、
audio_component（0xC4）、data_content（0xC7）——で、どれもタグは本体の
3 バイト目にある。**録画の PMT が説明していて、出力が運んでいない**タグを
名乗る記述子は落とし、節を締め直す（長さと CRC を計算し直す）。落とすのは
その 2 つが揃ったときだけで、録画の PMT にそもそも無いタグは触らない——
放送側のテーブル同士の食い違いは、ここで決める話ではないからである。

ダウンミックスした音声も「運んでいない」に数える。折り畳んだ音声は
audio_component 記述子が名乗るチャンネル構成をもう持っていないので、PMT で
記述子を落とすのと同じ理由で、番組情報の側からも落とす。

**削るのは「現在」の番組だけ。** present/following は 2 つの節で届き、この
ファイルについて語っているのは前者だけである。後者は「次に何が放送されたか」
の覚え書きで、その番組のストリームは初めからここに入らない。こちらのタグを
このファイルに照らして削るのは、誰も訊いていない問いに答えることであり、
唯一の正しい情報を捨てることになる。

## 部分TS として書く（既定）

放送録画を切り出したものは、規格の上では**部分TS（partial transport stream）**
である。DVB は EN 300 468 Annex C で、ARIB は TR-B15 でそれを定めていて、
BD/DVD レコーダも TMPGEnc MPEG Smart Renderer も**そう書く**。

部分TS は生の多重を説明する表を持たない。NIT・SDT・EIT・TDT・TOT の代わりに
**SIT（Selection Information Table、PID 0x001F、table_id 0x7F）が 1 枚**あり、
そこに全部が入る。SmartCut が書くのは:

| どこに | 何を |
|---|---|
| 伝送情報ループ | `partial_transport_stream_descriptor`（このファイルの実測ピークレート）、`network_identification_descriptor`（JPN と BS/CS/TB、original_network_id から引く） |
| サービスループ | `partial_transport_stream_time_descriptor`（放送の開始時刻と長さ）、`service_descriptor`（局名、録画の SDT から）、そして**現在番組の記述子ぜんぶ**（番組名・詳細・ジャンル・コンポーネント、録画の EIT から） |

**バイトは録画のものをそのまま運ぶ。** 局名も番組名も ARIB の文字符号のまま
移すので、こちらが 1 バイトも解釈しなくていい。書き起こすのは枠だけである。

ピークレートだけは録画から写せない——録画は自分を部分TS だと名乗って
いなかったので、その数字はどこにも書いていない。なので**出力を 1 パス測る**。
窓は 1 秒。これより短く測ると大きな絵 1 枚が「ファイルが出しもしない瞬間値」
として出てしまい、どの機器も用意する必要のないレートを名乗ることになる。

「次の番組」は SIT に入らない。present/following のうちこのファイルを
説明しているのは前者だけで、SIT は**このファイルが何であるか**を言う表だから
である。

区間ごとに SIT を作り、内容が変わったときだけ version を上げる。番組を
またぐカットは、それぞれの区間で自分の番組を名乗る。何も変わっていないのに
version が動く表は、「読み直せ」と言っているのと同じである。

節には天井（4096 バイト）がある。実在の録画で拡張形式イベント記述子だけで
1 キロバイトに達したので、入り切らないぶんは**記述子まるごと、後ろから**
落とす。時刻と局名が先頭にあるのはそのためである。

## 放送のテーブルのまま書く（`--tables broadcast`）

部分TS が規格の答えだが、**日本の録画まわりの道具が実際に読むのは SDT と
EIT** である。TVTest もEDCB も ffmpeg も SIT は読まない——`ffprobe` に
部分TS を掛けると局名は出てこない。TMSR の出力でも同じことが起きる。

なので旧来の書き方も残してある。`--tables broadcast` は PMT を組み直し、
SDT を録画のものに差し替え、EIT p/f と TOT を本来の PID に差し込む。
TOT の時刻は区間ごとに素材の実時刻から進むので、カット点で時刻が飛ぶ——
放送の壁時計をそのまま保つということである。

`--tables muxer`（旧 `--no-tables`）は muxer 自身の PAT・PMT・SDT をそのまま
残す。録画ではなく素のストリームが欲しいツールのためであり、下流と話が
合わないときに「どちらの説明を読んでいたのか」を切り分けるためでもある。

どれになるかは `--analyze` の行が言う。

## PID は素材のまま。PCR だけは映像に乗る

部分TS 規格は PID の配置を規定していない。TMSR は 0x1100 番台へ振り直すが、
SmartCut は**素材の PID をそのまま使う**——PMT も映像も音声も字幕も、
録画で乗っていた PID に戻る。

ひとつ引き継がないものがある。**日本の放送は PCR を専用 PID で送る**
（BS フジなら 0x0100、地デジなら 0x01FF）が、libavformat の mpegts 多重化器に
PCR PID を指定する手立ては無く、PCR は映像の PID に乗る。PMT はそれを正しく
申告するので、ファイルとして矛盾は無い——MPEG-2 としても ARIB としても
合法で、PCR_PID を PMT から読む機器は何も困らない。専用 PID を合成する道は
あるが、それは映像の adaptation field と PCR が二重になるうえ、挿入位置と
値のずれ（24 Mbps で 1 パケット≒63 µs）が MPEG の PCR 精度規定を外れる。
捏造したデータで規格を満たすより、正しく置かれた PCR を映像に乗せておく
ほうがよい。

## 再エンコードした先頭が「59.94fps」と名乗っていた

DGIndex → AviSynth（MPEG2Dec）でフレームレートが合わない、という報告から
出てきた不具合。**無劣化点から外れたところで切ると先頭が再エンコード区間に
なり、そのシーケンスヘッダを書くのはこちら**だ。そこが素材と食い違っていた:

```
素材   frame_rate_code=4 (30000/1001)
出力   frame_rate_code=7 (60000/1001)   ← 再エンコードした先頭だけ
```

**索引を作る道具は最初に出会ったシーケンスヘッダを全編ぶんとして信じる**ので、
29.97 の録画が 59.94 として下流に渡っていた。

原因は出力タイムラインの単位。フィールド単位（1 目盛 = 1 フィールド）の
time_base をエンコーダにもそのまま渡していて、**MPEG-2 のフレームレート符号は
time_base から逆算される**ため倍になった。`framerate` を別に立てても
mpeg12enc は time_base しか見ないので効かない。エンコーダには**ピクチャ単位の
time_base** を渡し、渡す絵には通し番号を振って、**その番号がタイムライン上の
どこに何フィールド分置かれるかは別に覚えておく**形にして解決。出力側の
フィールド単位のタイムラインはそのまま。

フレームハッシュの比較では出ない種類なので、`tests/run_ts_layout_tests.sh` に
「再エンコードした先頭のシーケンスヘッダが素材と一致するか」を足した。

## 音声だけを `.aac` で出せる

DGIndex → x264 → mux という流れでは、音声は**素の ADTS ファイル**として
mux 器に渡ることになる。その `.aac` を作る工程が弱い環に化けた例があって、
**DGIndex が出した `.aac` の先頭が `FF F8 04 22`**——同期語は正しいのに、
そのあとが「Main プロファイル / 88.2kHz / チャンネル数 0」という、およそ
成り立たない申告になっていた。L-SMASH はその 1 フレーム目から
AudioSpecificConfig を組むので、読む前に匙を投げる
（`failed to find the matched importer`）。

コピーしたフレームは素材と 1 バイトも違わない:

```
素材              ff f8 4c a0  MPEG-2 CRCあり profile=LC rate=48000 ch=2
コピーしたフレーム ff f8 ...    定義上、録画そのもののバイト列
ここで書くフレーム ff f9 ...    MPEG-2・CRC なし
```

**壊れるのはコピーではなく「書いた」フレームのときだけ**、というのが
決め手だった。コピーなら放送そのもののバイト列が通るので ADTS は
`ff f8`（MPEG-2・CRC あり）——日本の放送 AAC は必ずこの形。同じフレームを
ffmpeg の ADTS 書き出しに渡すと `ff f1`（MPEG-4・CRC なし）を**決め打ちで**
書く。ヘッダ長が 9 バイトから 7 バイトに変わるので、ARIB 前提で 9 バイトを
見に行く道具は設定を読み損ねる——`04 22`（Main / 88.2kHz / 0ch）という
「読めなかったときの既定値」がそれだ。ffmpeg 側にこの 2 ビットを変える術は
ない。

だから ffmpeg 側には書かせていない。ADTS ヘッダは `adts.rs` が自分で組み立て、
ここで書くフレームは録画と同じ版を名乗る——放送なら MPEG-2 AAC で、継ぎ目も
MPEG-2 AAC になる（[Rust コアの実装](rust-core.ja.md#音声のスマートレンダリング--audio-mode-smart)）。
録画と同じ形になっていないのは CRC だけで、ここで書くフレームは
`protection_absent` を立てるためヘッダが 9 バイトではなく 7 バイトになる。
フレームごとのフィールドなので CRC ありのフレームの中に混ざっていても
規格上は正しいが、録画が持っていたであろうバイト列そのものではない。
版は `--aac mpeg2|mpeg4` で明示できる。コピーしながら録画と違う版を要求されたら、
2 種類の AAC が混ざったストリームを作らずに理由を出して断る。

そのフレームが何個あるかはモード次第で、既定の `smart` なら境界がまたがる
フレームだけ——5606 フレーム中 4 個、CM カットのように継ぎ目が無音なら 0 個。
`reencode` なら全部、`copy` なら 1 個も無い。

`write_audio_es()`（CLI では `--audio-es`）は**書き終えた出力を読み直して**
音声だけを ADTS で書き出す。隣に置かれるのは定義上その動画の中にある音声
そのもので、L-SMASH の `muxer` に通ることを確認済み（`Track 1: MPEG-4 Audio`、
48kHz ステレオ、尺も一致）。

サイドカーそのものは**窓からは外した**。GUI には出していないし、回避策が
要った理由——MPEG-2 のストリームの中で継ぎ目だけが MPEG-4 を名乗ること——は、
出るところで断ってあるため。音声の*モード*のほうは、チャンネル数・ビット
レートと一緒に出力設定画面にある（[GUI](gui.ja.md#出力設定画面の音声まわり)）。
既定はエンジンと同じくスマートレンダリング。

## L-SMASH に渡すなら素のストリームで

出力を L-SMASH の `muxer` に渡すと
`[importer: Error]: failed to find the matched importer.` で止まる、という
報告があったので確かめた。**素材の `.ts` をそのまま渡しても同じエラーが出る**
——`muxer` が読むのは**素のストリーム**（Annex-B の H.264/H.265、ADTS の AAC、
AC-3 など）だけで、トランスポートストリームは端から対象外だからだ。
出力の AAC が悪いわけではない。

確認したこと:

| 渡したもの | 結果 |
|---|---|
| 出力 `.ts` をそのまま | `failed to find the matched importer` |
| **素材 `.ts` をそのまま** | **同じエラー** |
| 出力から取り出した `.aac`（ffmpeg） | `Track 1: MPEG-4 Audio` — 通る |
| 出力から取り出した `.aac`（PID の PES を素朴に連結） | 通る |
| 素材から取り出した `.aac` | 通る |

出力の PMT も素材と同じ stream_type `0x0F`（ADTS AAC）で、先頭バイトも
`ff f8` の同期語。取り出しは素朴な PID ダンプでも成立する。

```bash
ffmpeg -i cut_xxx.ts -map 0:a:0 -c copy cut_xxx.aac   # これを muxer に渡す
```

なお **L-SMASH は MPEG-2 映像を扱わない**（`remuxer` は
`no support to remux this stream` と言う）ので、この素材を L-SMASH だけで
MP4 にすることはそもそもできない。映像を H.264 に変換する工程が別にあり、
音声だけ持っていく——という使い方が前提になる。
